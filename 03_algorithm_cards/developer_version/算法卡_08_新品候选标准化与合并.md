# 算法卡_08_新品候选标准化与合并

更新时间：2026-08-18

业务原始依据：`01_source_docs/business_algorithm_docs/算法08_新品候选标准化与合并_业务原文.md`

业务解读依据：`03_algorithm_cards/business_readable/算法08_新品候选标准化与合并_业务解读版.md`

开发交付定位：本卡是算法 08 的 V1 开发版算法卡，用于数据开发建设新品候选注册、标准化、合并、拆分、属性血缘、范围结果和算法 09 输入快照。算法 08 不做风险门禁、不做最终推荐排序、不修改上游候选事实。

## 1. 算法目标

算法 08 将算法 06、07 产生的具象新品候选，与算法 02-05 的范围、主体、规格、价格和成本证据对齐，生成稳定可复算的标准候选和范围候选结果。

本算法做：

```text
1. 锁定算法 02-07 正式版本和商品主数据快照。
2. 保存算法 06、07 候选来源快照。
3. 校验候选是否有范围、主体、小分类、属性、规格、价格和证据。
4. 将候选属性映射为标准属性代码和属性血缘。
5. 标准化规格、单位、候选名称和展示名。
6. 生成 candidate_family_id（候选家族 ID）、candidate_direction_id（候选方向 ID）、standard_candidate_id（标准候选 ID）、candidate_scope_result_id（范围候选结果 ID）。
7. 对同一标准候选做精确合并，并保存合并审计。
8. 对规格不同、属性冲突、分类冲突、版本冲突等候选做拆分或异常记录。
9. 输出算法 09 可读取的范围候选结果和候选快照字段。
```

本算法不做：

```text
1. 不重新计算会员画像、门店等级、消费者贡献、SKU 表现、价格带、购物篮规则或外部趋势。
2. 不用名称相似度合并候选。
3. 不用采购人工选择改变候选身份、属性、合并关系或状态。
4. 不从商品名自由猜没有来源的属性。
5. 不把普通热词直接写入候选名称。
6. 不判断当前货盘重复、历史失败、法规风险、毛利风险或同质化风险。
7. 不输出 PASS（通过）、REJECT（拒绝）等门禁结果。
8. 不输出 P0/P1/P2 推荐优先级。
```

## 2. 开发执行流程

算法 08 是离线或准离线计算，不在采购前端查询时实时重算。

### 2.1 运行类型和正式发布口径

算法 08 必须区分正式月度运行和外部信号预览运行。

| 运行类型 | 英文取值 | 触发方式 | 是否进入算法 09 正式门禁 | 结果写法 |
|---|---|---|---|---|
| 月度正式运行 | `FORMAL_MONTHLY` | 算法 02-07 同一正式周期版本冻结后运行 | 是，仅限 `algorithm_09_readiness`（算法 09 就绪状态）为可进入状态的范围候选 | 写正式表正式分区 |
| 外部信号预览 | `EXTERNAL_SIGNAL_PREVIEW` | 算法 07 日采集、周预警或临时外部趋势检查 | 否 | 写预览分区或预览表，不覆盖正式结果 |
| 回溯重算 | `BACKFILL_RECALC` | 上游版本、规则资产或数据修正后重跑历史周期 | 视重算目标决定 | 新运行批次写入，不静默覆盖旧批次 |

正式月度运行必须满足：

```text
算法 02、03、04、05、06、07 的正式周期一致；
候选注册版本、候选属性字典版本、商品命名规则版本、特殊必填规则版本和单位换算版本已锁定；
data_cutoff_at（数据截止时间）之后的数据不得进入本次正式结果；
8 张正式输出表全部写入成功后，才允许发布本次 candidate_registry_run_id（候选注册运行 ID）。
```

算法 07 的日采集、周预警或外部趋势预览可以进入来源快照、观察池或异常诊断，但不能直接进入算法 09 正式门禁，也不能被算法 10 当作正式推荐候选。

任一上游正式版本或规则资产版本变化时，算法 08 必须生成新的 `candidate_registry_run_id`（候选注册运行 ID）。旧结果保留，用于追溯当时为什么合并、拆分、异常或进入 09。

### 2.2 执行步骤

运行顺序：

```text
1. 生成 candidate_registry_run_id（候选注册运行 ID），锁定 formal_period（正式周期）、data_cutoff_at（数据截止时间）和 02-07 上游版本。
2. 读取算法 06、07 候选，生成 new_product_candidate_source_snapshot（新品候选来源快照表）。
3. 关联算法 02、03、04、05 的范围、画像、主体、规格、价格和成本证据。
4. 校验候选最低结构条件：范围、主体、小分类、属性来源、明确规格、价格结果。
5. 构造标准属性 payload（候选标准属性载荷），并写入 new_product_candidate_attribute_lineage（新品候选属性血缘表）。
6. 执行分类保持、主体保持、单位换算、规格标准化和名称模板生成。
7. 生成家族、方向、标准候选、范围候选，以及用于对账的载荷校验码。
8. 按标准身份精确合并 06、07 来源，并写入 merge audit（新品候选合并审计表）。
9. 对无法注册的来源写入 registration exception（新品候选注册异常表）。
10. 写入 8 张正式结果表。
11. 算法 09 读取 mart_new_product_candidate_scope（新品范围候选结果表）中已就绪候选，不在查询时让前端实时触发 08。
```

发布要求：

```text
同一 candidate_registry_run_id（候选注册运行 ID）下 8 张正式表必须原子发布。
任一关键表写入失败时，run_status（运行状态）= FAILED（失败），正式读取视图继续指向上一已发布版本。
PARTIAL_SUCCESS（部分成功）只允许用于来源部分缺失但正式候选、异常和对账表均完整落库的场景。
```

采购前端输入的是筛选条件：

```text
城市/城市群、门店等级、消费者画像、小分类、候选来源、候选状态、09 就绪状态。
```

这些条件只用于读取已计算结果，不是采购手工输入候选商品、规格、成本或合并规则。

## 3. 正式输出表

算法 08 正式交付 8 张表。开发可以有过程表，但下游正式读取只使用以下 8 张。

| 表名 | 中文表名 | 一行代表什么 | 下游用途 |
|---|---|---|---|
| `new_product_candidate_registry_run` | 新品候选注册运行批次表 | 一次算法 08 正式运行 | 版本追溯、调度和对账 |
| `new_product_candidate_source_snapshot` | 新品候选来源快照表 | 一条上游候选来源记录 | 保存 06/07 原始候选和异常来源 |
| `new_product_candidate_attribute_lineage` | 新品候选属性血缘表 | 一个候选的一个属性来源 | 证明候选名称和身份属性来源 |
| `mart_new_product_candidate_direction` | 新品候选方向注册表 | 一个候选方向 | 方向聚合展示和标准候选归属 |
| `new_product_standard_candidate_registry` | 标准新品候选注册表 | 一个与范围无关的标准候选商品实体 | 生成稳定 `standard_candidate_id` |
| `mart_new_product_candidate_scope` | 新品范围候选结果表 | 一个标准候选在一个范围和价格方案下的结果 | 算法 09 的直接输入 |
| `new_product_candidate_merge_audit` | 新品候选合并审计表 | 一次来源合并结果 | 证明精确合并和输入顺序不变 |
| `new_product_candidate_registration_exception` | 新品候选注册异常表 | 一条不能进入正式候选的异常 | 上游修正、重跑和审计 |

### 4.4 上游输入准入条件

算法 08 只读取上游正式结果，不重新计算上游算法。开发实现时按以下准入条件读取来源和范围。

| 上游 | 准入条件 | 不满足时处理 |
|---|---|---|
| 算法 02 门店品类等级 | `final_level` 非空，`scope_version` 非空，结果状态不是数据不完整或不可计算 | 写入注册异常，不生成范围候选 |
| 算法 03 消费者画像贡献 | `final_profile` 非空，消费者贡献结果 ID 和版本非空 | 写入注册异常，不生成范围候选 |
| 算法 04 锚点 SKU 表现 | 主体商品、锚点商品、小分类、商品形态、锚点证据 ID 非空；正式候选优先读取 `is_formal_anchor = 1` | 主体缺失写 `SUBJECT_LINEAGE_CONFLICT` 或来源缺失异常 |
| 算法 05 候选价格可行性 | 同一候选范围只能命中一条有效价格结果；必须有明确规格值、规格单位、计量类型 | 缺价格结果时保留标准候选，`algorithm_09_readiness = NOT_READY_MISSING_PRICE_RESULT`（算法 09 就绪状态 = 缺价格结果）；多条有效结果写 `MULTIPLE_ACTIVE_PRICE_RESULTS`（多条有效价格结果） |
| 算法 06 购物篮候选 | 允许 `FORMAL_NEW_PRODUCT`、`SEASONAL_NEW_PRODUCT`、`LOCAL_PILOT_NEW_PRODUCT`、`EXPLORATORY_NEW_PRODUCT` 进入来源快照和候选注册判断 | 不可转新品、属性不完整、原始共现等状态只保留来源快照或异常，不进入正式标准候选 |
| 算法 07 外部候选 | 允许 `PENDING_ALGORITHM_08_GATE` 和 `EXPLORATORY_PENDING_ALGORITHM_08_GATE` 进入来源快照和候选注册判断 | `RAW_EXTERNAL_SIGNAL`、`CATEGORY_MAPPING_GAP`、`EXTERNAL_TREND_NOT_LOCALLY_MATCHED`、`SOURCE_ADMISSION_STOP` 等只保留证据或异常，不注册标准候选 |

`PENDING_ALGORITHM_08_GATE` 是算法 07 已有字段命名，在算法 08 内按“等待标准化注册”理解，不表示算法 08 执行风险门禁。正式风险门禁仍由算法 09 负责。

算法 05 正式候选价格可行性表必须输出 `price_feasibility_result_id`（价格可行性结果 ID）。如需兼容历史试算表，可按算法 05 正式唯一键派生稳定 ID，并在合并审计中记录派生口径：

```text
price_feasibility_result_id
= "PF_" + HEX(SHA256(canonical_price_result_key))
```

派生键至少包含：

| 中文字段名 | 英文字段名 | 说明 |
|---|---|---|
| 价格带版本 | `price_band_model_version` | 算法 05 本次价格带模型版本 |
| 价格周期开始日期 | `price_period_start` | 算法 05 价格结果对应周期开始 |
| 价格周期结束日期 | `price_period_end` | 算法 05 价格结果对应周期结束 |
| 范围版本 | `scope_version` | 门店和范围口径版本 |
| 范围编码 | `scope_id` | 算法 05 价格结果适用范围；进入 08 范围候选时映射为 `target_city_group_id` |
| 门店等级 | `final_level` | 算法 02 门店等级 |
| 消费者画像 | `final_profile` | 算法 03 目标消费者画像 |
| 品类编码 | `category_code` | 算法 05 价格结果适用品类；品类颗粒度为小类时进入 08 范围候选映射为 `leaf_category_id` |
| 可比商品组 ID | `comparable_product_group_id` | 算法 05 可比价格组 |
| 规格段 ID | `specification_segment_id` | 算法 05 规格段 |
| 候选商品 ID | `candidate_product_id` | 算法 05 候选商品记录 ID |
| 候选规格版本 | `candidate_spec_version` | 算法 05 候选规格版本 |
| 候选成本版本 | `candidate_cost_version` | 算法 05 候选成本估算版本 |

字段为空时必须以显式 `null` 进入规范化载荷，不能删除空字段。这样做是为了区分“这个字段本来就没有值”和“这个字段没有被纳入本次计算”，避免两个实际不同的候选被生成成同一个 ID。

### 4.5 V1 规则资产生成边界

V1 已确认接受系统自动生成或标准导入候选属性字典、商品命名规则和特殊必填属性规则初版。属性别名、外文词和同义词统一收敛到 `dim_candidate_attribute_dictionary.term_alias`，不单独建设同义词表。单位换算由算法 08 固化为版本化配置。

V1 规则资产必须由版本化导入或生成任务产出，并落成正式规则表或固化配置。每条规则必须保留版本、生效时间、规则来源、复核状态和规则状态；业务不需要从零手工提供完整规则表。

| 规则资产 | V1 自动生成来源 | 开发必须保留 | 人工复核范围 |
|---|---|---|---|
| 候选属性字典 | 商品基础表、算法 04 主体和形态、算法 06 结构化属性、算法 07 外部属性映射、合规词规则 | 标准属性代码、属性维度、词语别名、适用品类、是否允许入名、是否风险词、复核状态、版本 | 高频词、入名词、风险词 |
| 商品命名规则 | B3 标准规则、同小分类现有商品名称规律、算法 06/07 候选属性 | 推荐命名结构、名称必填字段、查重字段、异常拦截规则、规则状态、版本 | 重点小分类命名结构 |
| 特殊必填属性规则 | B3 特殊物种必填规则、业务/商品/质量复核 | 商品关键词、必填属性列表、缺失处理动作、规则状态、版本 | 特殊商品和重点小分类 |
| 单位换算配置 | 商品基础规格、算法 05 规格、算法 06/07 候选规格 | 来源单位、标准单位、换算系数、计量类型、未识别处理方式、版本 | 重点小分类常见规格 |

规则资产不能在 SQL 里临时硬编码。规则变更必须有新版本、生效时间和重跑批次。

#### 4.5.1 自动生成任务的开发步骤

开发需要先建设一个规则资产导入或生成任务，保证 `dim_candidate_attribute_dictionary`、`dim_product_naming_rule`、`dim_special_product_required_attribute_rule` 和 `unit_conversion_version` 均有当前有效版本，再运行候选注册任务。

```text
输入：dim_sku（商品基础表）、算法 04 主体和形态、算法 06 购物篮候选属性、算法 07 外部属性映射、算法 05 候选规格。
输出：候选属性字典、商品命名规则、特殊必填属性规则、单位换算配置。
要求：每次生成必须写版本号、生效时间、规则来源、复核状态和规则状态。
```

生成步骤：

| 步骤 | 开发要做什么 | 生成结果 | 异常处理 |
|---|---|---|---|
| 1. 锁定生成批次 | 生成 `rule_generation_run_id`（规则生成运行 ID），锁定商品主数据版本、算法 04/05/06/07 版本和数据截止时间 | 本次规则资产版本号 | 版本缺失时不得发布正式规则 |
| 2. 抽取候选词 | 从商品名称、SPU 名称、小分类、规格单位、算法 06 属性、算法 07 外部词中抽取原始词 | 原始词池 | 只保留来源和词频，不直接进入正式候选名称 |
| 3. 标准化原始词 | 做大小写、全半角、空格、符号、单位别名和多语种归一；外文词优先读取算法 07 映射结果 | 标准化词 | 无法归一时写 `UNMAPPED` |
| 4. 归属属性维度 | 按“上游结构化字段优先，商品名模式辅助”的顺序判断主体、主材料、口味、工艺、功能、商品形态、规格、包装、风险词 | `attribute_dimension`（属性维度） | 无稳定来源时写 `REVIEW_REQUIRED`，不能直接入名 |
| 5. 生成或读取标准属性代码 | 按小分类、属性维度、标准词生成稳定 `canonical_attribute_code`，或读取已导入字典 | `dim_candidate_attribute_dictionary` 初版 | 同义词、外文词、大小写差异和全半角差异必须映射到同一标准属性代码 |
| 6. 归并属性别名 | 把原始词、外部词、别名和翻译词写入 `term_alias` | 候选属性字典别名记录 | 低置信度或高风险词写 `REVIEW_REQUIRED`；复核拒绝写 `REJECTED` |
| 7. 生成单位换算配置 | 从商品基础规格、算法 05 规格、算法 06/07 候选规格中归并单位 | 单位换算配置初版 | 计数单位不得强行换算成重量；未知单位按规则输出未知或阻断注册 |
| 8. 读取商品命名规则 | 按分类匹配 `dim_product_naming_rule`，读取命名结构、必填字段和查重字段 | `naming_rule_version` | 命名规则缺失或未生效时写 `NAME_TEMPLATE_NOT_AVAILABLE` |
| 9. 执行特殊必填校验 | 按 `dim_special_product_required_attribute_rule` 检查特殊商品关键词和必填属性 | `special_rule_version` | 命中缺失且动作为 `DO_NOT_CREATE_FORMAL_CANDIDATE` 时不生成正式候选 |
| 10. 标记人工复核范围 | 高频词、会进入候选名称的词、风险词、重点小分类规则标记为待复核 | `review_status`（复核状态） | 未复核但非风险、非入名、非高频的词可按合同写 `AUTO_APPROVED` |
| 11. 发布规则版本 | 只有 `rule_status = ACTIVE` 的规则进入算法 08 正式运行 | 规则资产正式版本 | 版本发布后如规则变化，必须生成新版本并重跑 08 |

#### 4.5.2 属性维度自动判断规则

属性维度必须按来源优先级判断，不能只靠商品名或大模型常识。

| 属性维度 | 优先来源 | V1 自动判断规则 | 默认是否入候选身份 | 默认是否入候选名称 |
|---|---|---|---|---|
| 主体商品 | 算法 04 锚点主体、商品基础表 SPU/商品名称 | 08 只能继承 04 或商品基础表主体，不允许被 06 关联商品或 07 外部热词替换 | 是 | 是 |
| 商品形态 | 商品基础表、算法 04、算法 06/07 结构化属性 | 如丝、片、块、丸、蛋、袋装菜等，必须能追溯到商品基础或上游结构化字段 | 是 | 视模板决定 |
| 主材料 | 商品基础表、算法 04 主体、算法 06/07 结构化属性 | 与主体一致或构成主体的核心材料；不从无证据热词直接猜 | 条件参与 | 视模板决定 |
| 辅料/配方 | 算法 06 购物篮可转属性、算法 07 外部结构化属性 | 例如青椒、圆葱等；必须通过小分类保持校验 | 条件参与 | 视模板决定 |
| 口味 | 算法 06/07 结构化属性、商品基础同类命名规律 | 如黑椒、蒜香、麻辣；泛场景词不算口味 | 条件参与 | 视模板决定 |
| 工艺/加工方式 | 算法 06/07 结构化属性、商品基础同类命名规律 | 如 HPP、烟熏、即食、腌制；涉及功能或法规风险时标记风险词 | 条件参与 | 视模板决定 |
| 功能属性 | 算法 07 外部属性映射、质量/业务复核 | 如 Omega-3、低钠、高蛋白；V1 必须标记复核状态和风险词标记 | 条件参与 | 需复核后才可入名 |
| 规格/包装 | 算法 05 明确规格、商品基础表规格单位 | 规格由 05 给出，08 只做单位标准化；包装只在商品命名规则允许时参与身份 | 规格是；包装条件参与 | 规格展示；包装视规则决定 |
| 营销词/场景词 | 商品名和外部文本 | 健康、新鲜、方便、早餐、露营等默认只作解释或观察，不进入身份 | 否 | 否 |
| 风险词 | 算法 07 风险线索、法规/质量词表 | 涉及标签、食安、功能声称的词必须标记 `is_risk_term = 1` | 否，除非复核通过且规则允许 | 需复核后才可入名 |

V1 默认置信度处理：

```text
内部结构化字段或已确认规则命中：review_status = AUTO_APPROVED 或 APPROVED，is_active = 1。
自动映射置信度 >= 0.90 且非风险、非入名高频词：review_status = AUTO_APPROVED。
自动映射置信度 >= 0.70 且 < 0.90：review_status = REVIEW_REQUIRED。
自动映射置信度 < 0.70 且无法可靠映射标准属性：不生成正式属性代码，写 ATTRIBUTE_CODE_MISSING 或保留来源证据。
无法可靠映射内部小分类：保留算法 07 的 mapping_status = CATEGORY_MAPPING_GAP，只保留来源证据或写注册异常，不生成可用属性。
风险词、会进入候选名称的词、高频外部词：即使命中高置信，也要进入人工复核清单。
```

算法 07 `external_attribute_mapping.mapping_status = MAPPED`（已映射）的外部词，进入算法 08 规则资产时可写入 `dim_candidate_attribute_dictionary.term_alias`，并按 `review_status` 和 `is_active` 控制是否可用。算法 07 的 `CATEGORY_MAPPING_GAP`（小分类映射缺口）不得写成可用属性。

#### 4.5.3 商品命名规则使用规则

候选名称不是直接拼商品名，也不是直接使用外部热词。开发按 `dim_product_naming_rule` 的推荐命名结构和必填字段生成候选名称：

```text
候选商品名称 = 当前小分类允许入名的属性词元 + 主体商品 + 商品形态
候选展示名称 = 候选商品名称 + 建议规格
```

默认词元顺序：

```text
功能属性 -> 工艺/加工方式 -> 辅料/配方 -> 口味 -> 主体商品 -> 商品形态
```

如果同一小分类现有商品名称已经能稳定识别出不同顺序，可以按小分类生成专属命名结构，但必须写入或更新 `dim_product_naming_rule.recommended_name_structure`，并通过 `naming_rule_version` 追溯。

商品命名规则必须遵守：

```text
规格不放进 candidate_product_name，只放进 recommended_spec 和 candidate_display_name；
营销词、场景词、未映射词、未通过复核的风险词不得进入正式候选名称；
商品命名规则缺失时写 NAME_TEMPLATE_NOT_AVAILABLE，不生成正式候选名称；
命名规则被业务修改后必须发布新 naming_rule_version，并重跑 08。
```

#### 4.5.4 候选词抽取最低规则

开发不能只把整段商品名当作一个属性，也不能只靠大模型拆词。V1 按以下最低规则抽取候选词：

| 抽取对象 | 来源 | 处理规则 | 结果去向 |
|---|---|---|---|
| 上游结构化属性 | 算法 06、算法 07 | 如果上游已经给出属性维度和属性值，08 直接进入属性字典生成，不重新猜维度 | `dim_candidate_attribute_dictionary` |
| 主体商品词 | 算法 04、商品基础表 SPU/商品名称 | 主体优先继承算法 04；商品名只作为辅助校验，不替换 04 主体 | 属性字典中的主体商品属性 |
| 小分类词 | 商品基础表小分类 | 小分类只用于适用范围和分类保持校验，不直接当作新品属性 | 商品命名规则和特殊必填属性规则 |
| 规格和单位 | 商品基础规格、算法 05、算法 06/07 候选规格 | 识别数字 + 单位，例如 200g、12枚、400g/袋；数值进规格字段，单位进单位换算配置 | `unit_conversion_version` |
| 口味/工艺/功能/包装词 | 商品基础同小分类名称规律、算法 06/07 属性 | 先按已知属性词匹配；无法稳定归维度时写 `REVIEW_REQUIRED`，不能入名 | 候选属性字典和属性别名记录 |
| 外部词和多语种词 | 算法 07 外部属性映射 | 先读取算法 07 标准化词和映射置信度；无法映射标准属性时写 `UNMAPPED`；无法映射内部小分类时保留 `CATEGORY_MAPPING_GAP` | 候选属性字典、观察池或注册异常 |
| 泛营销词和场景词 | 商品名、外部标题、社媒或报告文本 | 健康、新鲜、方便、早餐、露营等默认不进候选身份和候选名称 | 仅解释或观察，不进正式身份 |
| 风险词 | 算法 07 风险线索、法规/质量词表 | 涉及功能声称、标签、食安、法规风险的词必须标记 `is_risk_term = 1` | 人工复核清单和 09 风险线索 |

同一个小分类、同一个属性维度、同一个标准化词，必须生成同一个 `canonical_attribute_code`（标准属性编码）。同义词、翻译词、大小写差异和全半角差异不能生成多个标准属性编码。

## 5. 正式粒度和对象 ID

### 5.1 四级对象

| 对象 | 英文字段 | 业务含义 | 是否可作为开发商品 |
|---|---|---|---|
| 候选家族 | `candidate_family_id` | 同一小分类 + 主体 + 商品形态的一组候选方向 | 不可以 |
| 候选方向 | `candidate_direction_id` | 已有创新属性但未绑定明确规格和范围价格的方向 | 不可以 |
| 标准候选 | `standard_candidate_id` | 具体商品实体，例如青椒黑椒牛柳丝 200g | 可以进入范围计算 |
| 范围候选 | `candidate_scope_result_id` | 标准候选在具体城市、门店等级、画像、小分类和价格方案下的结果 | 算法 09 直接读取 |

### 5.2 范围候选唯一键

| 中文字段名 | 英文字段名 | 说明 |
|---|---|---|
| 候选注册版本 | `candidate_registry_version` | 算法 08 候选注册版本 |
| 正式周期开始日期 | `formal_period_start` | 本次正式结果周期开始 |
| 正式周期结束日期 | `formal_period_end` | 本次正式结果周期结束 |
| 城市/城市群 ID | `target_city_group_id` | 候选适用城市或城市群 |
| 门店等级 | `final_level` | 候选适用门店等级 |
| 消费者画像 | `final_profile` | 候选适用目标画像 |
| 小分类 ID | `leaf_category_id` | 候选所在最末级小分类 |
| 标准候选 ID | `standard_candidate_id` | 与范围无关的标准候选商品实体 |
| 价格可行性结果 ID | `price_feasibility_result_id` | 缺算法 05 价格结果时使用 `PRICE_RESULT_MISSING` 占位 |

同一唯一键只能存在一条有效范围候选结果。

### 5.3 ID 生成原则

算法 08 的 ID 不使用自增 ID 或随机 ID。候选家族、候选方向、标准候选和范围候选结果均按“规范化 JSON + SHA-256”生成稳定 ID；来源、方向、候选和异常的校验码字段用于重跑对账和快照校验。

规范化规则：

```text
字段名排序稳定；
数组排序稳定；
空值和缺失值表达固定，字段为空时写 null，不能直接删除字段；
规格数值先转 decimal string；
不使用二进制浮点直接参与校验码生成；
版本字段进入对应 payload（载荷字段集合）；
展示名称不作为身份判断依据。
```

## 6. 核心计算规则

### 6.1 候选最低结构条件

候选进入正式标准候选前必须满足：

```text
目标城市/城市群存在；
门店等级存在；
消费者画像存在；
叶子小分类存在；
主体商品来自算法 04 或经过上游正式规则确认；
至少一条算法 06 或 07 新品属性来源存在；
进入候选名称的属性都有标准属性代码和证据 ID；
算法 05 明确规格值、规格单位和计量类型存在；
小分类保持校验通过；
候选名称模板可生成具体商品名。
```

### 6.2 价格和成本处理

价格和成本不进入 `standard_candidate_id`（标准候选 ID）。

它们进入：

```text
candidate_scope_result_id（范围候选结果 ID）
mart_new_product_candidate_scope（新品范围候选结果表）
算法 09 候选输入快照
```

如果算法 05 缺少范围价格结果：

```text
standard_candidate_id（标准候选 ID）可以生成；
可以生成诊断用 candidate_scope_result_id（范围候选结果 ID）；
price_feasibility_result_id（价格可行性结果 ID）显式写 NULL；
candidate_scope_result_id（范围候选结果 ID）载荷中使用 PRICE_RESULT_MISSING（价格结果缺失）占位；
candidate_scope_result_id（范围候选结果 ID）不进入 09 正式门禁输入；
algorithm_09_readiness（算法 09 就绪状态）= NOT_READY_MISSING_PRICE_RESULT（缺价格结果）。
```

### 6.3 合并规则

正式合并方法只允许：

```text
EXACT_CANONICAL_IDENTITY
```

合并条件：

```text
standard_candidate_id（标准候选 ID）完全一致；
leaf_category_id（小分类 ID）完全一致；
规范化属性 payload（属性载荷字段集合）完全一致；
计量类型、规格值、规格单位完全一致；
candidate_identity_schema_version（候选身份结构版本）一致。
```

合并后：

```text
保留所有来源快照；
属性来源 ID 去重并集；
内部证据 ID 去重并集；
外部证据 ID 去重并集；
source_composition_status 根据来源集合生成。
```

### 6.4 必须拆分或异常的场景

| 场景 | 处理 |
|---|---|
| 同方向不同规格 | 拆成不同 `standard_candidate_id`（标准候选 ID） |
| 主体商品不同 | 不合并，必要时写 `SUBJECT_LINEAGE_CONFLICT` |
| 小分类冲突 | 不合并，写 `LEAF_CATEGORY_LINEAGE_CONFLICT` |
| 属性互斥 | 不合并，写 `MUTUALLY_EXCLUSIVE_ATTRIBUTES` |
| 属性无标准代码 | 写 `ATTRIBUTE_CODE_MISSING` |
| 商品命名规则缺失 | 写 `NAME_TEMPLATE_NOT_AVAILABLE` |
| 多条有效价格结果 | 写 `MULTIPLE_ACTIVE_PRICE_RESULTS` |
| 来源载荷变化但版本未变 | 写 `SOURCE_PAYLOAD_CHANGED_WITHOUT_VERSION` |

### 6.5 名称生成规则

正式名称必须来自商品命名规则和标准属性代码。

允许：

```text
青椒黑椒牛柳丝 200g
Omega-3 鲜鸡蛋 12枚
```

不允许：

```text
健康新鲜鸡蛋
快手场景菜
全部小分类商品
```

### 6.6 标准候选属性结构

算法 08 的身份判断必须基于结构化属性，不允许用商品名称 `LIKE`、文本相似度或大模型自由解释做身份判断。

每个来源候选转换为以下标准结构：

| 中文字段 | 英文字段 | 是否参与身份 | 来源 |
|---|---|---|---|
| 小分类 ID | `leaf_category_id` | 是 | `dim_sku.category_level3_code`、算法 04 小分类、算法 07 `internal_leaf_category_code` 经本算法映射 |
| 主体商品代码 | `product_subject_code` | 是 | 算法 04 锚点主体，06/07 不得替换 |
| 主材料代码列表 | `main_ingredient_codes_json` | 条件参与 | 属性字典和商品命名规则 |
| 辅料/配方代码列表 | `secondary_ingredient_codes_json` | 条件参与 | 算法 06/07 属性血缘 |
| 功能属性代码列表 | `function_attribute_codes_json` | 条件参与 | 算法 07 属性映射和风险复核 |
| 口味代码列表 | `flavor_codes_json` | 条件参与 | 算法 04/06/07 属性血缘 |
| 工艺代码列表 | `processing_method_codes_json` | 条件参与 | 算法 06/07 属性血缘 |
| 商品形态代码 | `product_form_code` | 是 | 算法 04 或商品基础表 |
| 烹饪方式代码列表 | `cooking_method_codes_json` | 条件参与 | 商品命名规则允许时 |
| 包装类型代码 | `package_type_code` | 条件参与 | 算法 05/商品基础表/候选规格 |
| 储存方式代码 | `storage_method_code` | 条件参与 | 商品基础表或属性字典 |
| 季节标记 | `seasonal_status` | 不参与 `standard_candidate_id` | `dim_product_status`/本算法 |
| 标准规格值 | `canonical_spec_value` | 是 | 算法 05 + 单位换算 |
| 标准规格单位 | `canonical_spec_unit` | 是 | 算法 08 单位换算配置 |
| 计量类型 | `measurement_type` | 是 | 算法 05 + 单位换算 |

数组字段必须按标准属性代码升序排序并去重，输入顺序不得影响 ID。

以下字段默认不进入候选身份：

```text
品牌；
供应商；
建议售价；
成本；
毛利率；
促销方式；
竞品渠道；
普通消费场景泛词；
健康、新鲜、便利等没有标准定义的泛营销词；
社媒热度或情绪分；
商品图片。
```

包装属性只有在当前小分类身份模板明确允许，且有正式属性证据时，才进入候选身份。

### 6.7 主体、小分类和名称约束

主体商品必须优先来自算法 04 锚点和商品基础表。

```text
product_subject_code = 算法 04 锚点主体代码
```

算法 06 的关联商品和算法 07 的外部热词只能提供允许的创新属性，不能替换主体。

名称字段固定为三类：

| 中文字段 | 英文字段 | 生成规则 |
|---|---|---|
| 候选商品名称 | `candidate_product_name` | 不含规格的具体商品名，由商品命名规则和入名属性生成 |
| 建议规格 | `recommended_spec` | 算法 05 `mart_candidate_product_price_feasibility.recommended_spec` 产出；08 只透传并用于展示名 |
| 候选展示名称 | `candidate_display_name` | `candidate_product_name + 空格 + recommended_spec`，其中 `recommended_spec` 来自算法 05 |

每个进入候选名称的词元必须满足：

```text
标准属性代码存在；
属性维度被当前商品命名规则允许；
证据 ID 存在；
展示词来自标准属性字典；
不与其他词元互斥；
风险词已进入复核或已通过复核。
```

如果被删除的是候选唯一新品属性，候选不得注册为标准候选，只能写异常或保留方向。

### 6.8 规格和单位标准化

算法 08 使用算法 05 的明确规格，不从规格段、均值、中位数或众数中自行生成规格。

单位换算规则：

| 计量类型 | 标准单位 | 处理 |
|---|---|---|
| 重量 | `g` | `kg`、公斤、千克、克统一换算为 g |
| 体积 | `ml` | `L`、升、毫升统一换算为 ml |
| 计数 | 按业务展示单位 | 枚、个、盒、袋、份、只等保留展示单位，同时标准化数值 |
| 长度 | `mm` | 仅小分类规则允许时使用 |
| 未知 | `UNKNOWN` | 按 `unknown_handling_method` 输出未知或阻断注册 |

转换公式：

```text
canonical_spec_value = source_spec_value * conversion_factor
```

数值必须使用定点十进制字符串参与校验码生成，不能使用二进制浮点。

如果算法 05 推荐规格和算法 06/07 声明规格冲突：

```text
exception_code = UPSTREAM_SPEC_LINEAGE_CONFLICT
```

算法 08 不自行选择其中一个。

### 6.9 ID 和校验码生成规则

四级 ID 都使用“规范化 JSON + SHA-256”生成。这样同一个标准候选在不同批次重跑时仍能得到同一个 ID；如果规格、主体、小分类或关键属性变化，ID 会跟着变化，避免把两个不同候选误合并。

规范化规则：

```text
对象键按字典序排列；
业务无序数组按标准代码升序排列；
数值转为定点十进制字符串；
空数组保留为 []；
空值保留为 null，不能因为字段为空就删除字段；
展示名称、证据数量、抓取时间不进入 standard_candidate_id；
价格、成本和毛利不进入 standard_candidate_id，只进入 candidate_scope_result_id 和候选快照校验码。
```

ID 生成公式：

| ID 或校验码 | 英文字段 | 业务含义 | 载荷最小组成 | 公式 |
|---|---|---|---|---|
| 候选家族 ID | `candidate_family_id` | 判断是否属于同一商品家族，例如同一小分类、主体和形态 | 小分类 + 主体商品 + 商品形态 + 身份结构版本 | `"FAM_" + HEX(SHA256(canonical_family_payload))` |
| 候选方向 ID | `candidate_direction_id` | 判断是否属于同一新品方向，例如同一主体下的同一创新属性组合 | 家族载荷 + 身份属性代码集合 | `"DIR_" + HEX(SHA256(canonical_direction_payload))` |
| 标准候选 ID | `standard_candidate_id` | 判断是否是同一个具体候选商品实体，例如青椒黑椒牛柳丝 200g | 方向载荷 + 计量类型 + 标准规格值 + 标准规格单位 | `"CAND_" + HEX(SHA256(canonical_candidate_payload))` |
| 范围候选结果 ID | `candidate_scope_result_id` | 判断是否是同一候选在同一城市、门店等级、画像和价格方案下的结果 | 正式周期 + 城市/城市群 + 门店等级 + 消费者画像 + 小分类 + 标准候选 ID + 价格可行性结果 ID + 候选注册版本 | `"CS_" + HEX(SHA256(canonical_scope_payload))` |
| 候选快照校验码 | `candidate_payload_hash` | 给算法 09 对账用；同一范围候选的规格、价格、成本、状态或证据变化时，这个值必须变化 | 09 读取所需的候选、规格、价格、成本、状态和证据快照 | `HEX(SHA256(canonical_gate_payload))` |

同一输入快照、同一版本和同一规范化规则重复运行，必须得到相同 ID、相同校验码和相同行数。

### 6.10 商品状态和计划上架窗口映射

算法 08 不从名称或销量曲线猜商品的季节状态。商品状态只从 `dim_product_status` 读取；能匹配到内部商品编码或上游来源商品编码时，按 `product_status_version + region_code + sku_id` 取当前有效记录。

| `dim_product_status.product_status_code` | `seasonality_status` | `seasonal_status` | 计划上架日期写法 | 08 处理 |
|---|---|---|---|---|
| `S` 且 `season_start_date`、`season_end_date` 均非空 | `SEASONAL` | `S` | 分别读取 `season_start_date`、`season_end_date` | 可作为季节候选继续判断 |
| `S` 但开始或结束日期缺失 | `SEASON_WINDOW_INCOMPLETE` | `S` | 缺失字段写 `NULL` | 写 `SEASON_WINDOW_INCOMPLETE`；不因该原因单独阻断 09，09 按季节窗口不完整处理 |
| `A` | `YEAR_ROUND` | `NON_SEASONAL` | `NULL` | 按全年品处理 |
| `O`、`D`、`B` | `NON_SEASONAL_OTHER_STATUS` | `NON_SEASONAL` | `NULL` | 透传商品状态；淘汰、试卖、备选的正式风险判断交给算法 09 |
| 未命中商品状态记录 | `UNKNOWN` | `UNKNOWN` | `NULL` | 保留候选，不得自行猜状态；后续由 09 按状态未知处理 |

`product_status_code = D` 的商品不得在 08 被改写成常规新品候选；08 只保留状态事实和来源，是否拦截由算法 09 风险门禁统一判断。

### 6.11 算法 09 就绪队列规则

算法 08 只把以下范围候选作为算法 09 正式输入：

```text
algorithm_09_readiness（算法 09 就绪状态）= READY_FOR_ALGORITHM_09（可进入算法 09）
或
algorithm_09_readiness（算法 09 就绪状态）= READY_WITH_ESTIMATED_COST（估算成本可进入算法 09）
```

以下状态不得进入算法 09 正式门禁：

```text
NOT_READY_MISSING_PRICE_RESULT（缺价格结果）
REGISTRATION_EXCEPTION（注册异常）
```

`S` 商品缺计划上架开始或结束日期时，08 不得仅因该原因把 `algorithm_09_readiness` 写成 `REGISTRATION_EXCEPTION`。如果候选身份、规格、价格结果和其他注册条件均满足，`algorithm_09_readiness` 仍按价格成本状态写 `READY_FOR_ALGORITHM_09` 或 `READY_WITH_ESTIMATED_COST`；同时在范围候选中写 `seasonality_status = SEASON_WINDOW_INCOMPLETE`、`seasonal_status = S`，缺失的 `season_start` 或 `season_end` 写 `NULL`。这些候选进入 09 后，由 09 按季节窗口不完整处理，不得在 08 提前做历史失败或最终门禁判断。

### 7.1 缺失、不适用和降级处理

算法 08 不删除来源记录，缺失和不适用必须显式写状态。

| 场景 | 处理表 | 状态或字段写法 | 是否进入算法 09 |
|---|---|---|---|
| 06/07 来源可读但候选不能注册 | `new_product_candidate_source_snapshot`、`new_product_candidate_registration_exception` | 保留来源快照，写具体 `exception_code` | 否 |
| 属性没有标准代码 | `new_product_candidate_registration_exception` | `exception_code = ATTRIBUTE_CODE_MISSING` | 否 |
| 属性字典、商品命名规则、特殊必填规则或单位配置版本缺失 | `new_product_candidate_registration_exception` | 对应版本字段为空，写 `ATTRIBUTE_DICT_VERSION_MISSING`、`NAME_TEMPLATE_NOT_AVAILABLE`、`CATEGORY_RULE_NOT_AVAILABLE` 或规则缺失异常 | 否 |
| 只有方向，没有明确规格 | `mart_new_product_candidate_direction`、异常表 | 方向可注册；标准候选不创建；`exception_code = EXACT_SPEC_MISSING` | 否 |
| 标准候选身份成立，但缺算法 05 价格结果 | `new_product_standard_candidate_registry`、`mart_new_product_candidate_scope` | `price_evidence_status = PRICE_RESULT_MISSING`，`algorithm_09_readiness = NOT_READY_MISSING_PRICE_RESULT` | 否 |
| 成本是估算成本但算法 05 已给出可行性结果 | `mart_new_product_candidate_scope` | `algorithm_09_readiness = READY_WITH_ESTIMATED_COST` | 是，由 09 继续判断补证条件 |
| 算法 07 无可展示图片 | `mart_new_product_candidate_scope` | `primary_image_id = NULL`，`image_match_validation_status = IMAGE_NOT_AVAILABLE`，`copyright_or_authorization_status = NOT_AVAILABLE` | 不阻断 |
| 算法 07 有法规、标签、食安或功能声称线索 | `mart_new_product_candidate_scope` | 透传 `risk_handoff_ids` 和外部证据 ID；08 不做风险结论 | 由 09 门禁判断 |
| 商品状态缺失 | `mart_new_product_candidate_scope` | `product_status_code = NULL`，`seasonality_status = UNKNOWN`，`seasonal_status = UNKNOWN` | 不阻断非季节候选；不得猜状态 |
| `S` 商品缺计划上架日期 | `mart_new_product_candidate_scope` | `product_status_code = S`，`seasonality_status = SEASON_WINDOW_INCOMPLETE`，`seasonal_status = S`，缺失日期写 `NULL` | 是，前提是其他注册、规格和价格条件满足；09 按季节窗口不完整处理 |
| 外部预览信号未进入月度正式 07 版本 | 来源快照预览分区或预览表 | `run_type = EXTERNAL_SIGNAL_PREVIEW` | 否 |

金额、概率、数量和规格字段缺失时不能填 0。`0` 只能表示真实计算结果为 0；来源缺失必须写 `NULL` 加状态字段。

```text
06 和 07 指向同一标准候选时，只生成一条标准候选并保留两类证据。
```

### 10.8 缺失和降级验收


### 10.9 算法 09 接口验收

`mart_new_product_candidate_scope` 中 `algorithm_09_readiness` 为以下状态的记录，必须完整映射到算法 09 候选快照：

```text
READY_FOR_ALGORITHM_09（可进入算法 09）
READY_WITH_ESTIMATED_COST（估算成本可进入算法 09）
```

以下状态必须被算法 09、10、Agent 和查询服务过滤出正式推荐链路：

```text
NOT_READY_MISSING_PRICE_RESULT（缺价格结果）
REGISTRATION_EXCEPTION（注册异常）
```

过滤不是删除。记录仍保存在算法 08 表中，用于补数据、异常诊断和重跑。

`SEASON_WINDOW_INCOMPLETE` 是季节窗口完整性状态，不是算法 09 就绪状态。`S` 商品缺计划上架开始或结束日期时，如果其他核心条件满足，仍必须随 `READY_FOR_ALGORITHM_09` 或 `READY_WITH_ESTIMATED_COST` 完整映射给算法 09；09 后续不得把该候选直接当正式季节开发需求发布。

| `primary_image_source_run_id` | `mart_new_product_candidate_scope` | 主图来自哪次算法 07 运行 |
| `image_match_validation_status` | `mart_new_product_candidate_scope` | 图片是否与候选匹配 |
| `copyright_or_authorization_status` | `mart_new_product_candidate_scope` | 图片是否可展示 |
| `candidate_payload_hash` | `mart_new_product_candidate_scope` | 算法 09 快照内容校验码，防止 09 在不知情的情况下读取到已变化的价格、成本、状态或证据 |

## 12. 待评审红线

以下问题会影响算法 08 是否能按 V1 正式交付，需进入项目评审：

| 优先级 | 确认方 | 红线问题 | 不确认时处理 |
|---|---|---|---|
| P1 | 算法/数据开发 | 算法 05 候选价格可行性结果字段是否冻结 | 缺价格结果的候选写 `NOT_READY_MISSING_PRICE_RESULT`，不进入 09 正式门禁输入 |
| P1 | 数据开发/算法开发 | 候选属性字典、商品命名规则、特殊必填规则和单位换算配置是否已落表或固化版本并写入版本字段 | 未落表或缺版本时写注册异常，不进入正式候选名称；业务/商品/质量只复核高频词、入名词、风险词和重点小分类规则，不从零手工提供完整规则表 |
| P1 | 算法/数据开发 | 算法 06、07 候选输出字段是否冻结 | 字段缺失进入异常表，不删除来源快照 |
| P1 | 数据开发/商品 | `dim_product_status` 是否按 SAP POP 来源落表，`S` 商品计划上架开始/结束日期是否齐全 | 缺失时写 `SEASON_WINDOW_INCOMPLETE` 或 `UNKNOWN`，不得猜状态 |
| P2 | 产品/后端/Agent | 未准备好进入 09 的候选是否由 09、10、Agent 和查询服务统一过滤 | 不得作为正式推荐候选进入算法 10 或采购优先级结果 |

## 13. 不能做的事

```text
不能用名称相似度合并候选。
不能让采购人工指定候选、属性或合并关系。
不能从商品名自由猜没有来源的属性。
不能把外部热词直接写进候选名称。
不能把规格不同的候选合并为一个 standard_candidate_id（标准候选 ID）。
不能把不同范围的价格、画像和证据平均。
不能在算法 08 排除当前货盘或历史失败相似商品。
不能在算法 08 替代算法 09 做风险门禁。
不能在算法 08 替代算法 10 做优先级排序。
```
