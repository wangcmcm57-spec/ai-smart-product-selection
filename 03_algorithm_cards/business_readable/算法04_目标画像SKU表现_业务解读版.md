# 算法04_目标画像 SKU 表现_业务解读版

更新时间：2026-08-03

业务原始依据：`算法卡_04_目标画像SKU表现_业务提供最新原始版_20260731.md`

## 1. 先用一句话理解

这个算法要判断：

```text
在某个城市算法区域、某个品类、某个门店等级群和某个消费者画像里，
哪些现有 SKU 是真实卖得好、目标画像更偏好、自然动销健康、毛利为正、证据可靠的锚点商品。
```

这里的“锚点商品”不是新品。

它是已经在卖的商品，用来告诉后续算法：

```text
从哪些现有商品开始做购物篮关联、属性组合和新品方向推导。
```

例子：

```text
算法 04 找到现有锚点：黑椒牛柳丝 200g
后续购物篮发现关联：圆葱、青椒
后续新品候选才可能生成：圆葱黑椒牛柳丝 200g
```

算法 04 只证明“黑椒牛柳丝 200g”是现有高表现锚点，不直接证明“圆葱黑椒牛柳丝 200g”一定值得开发。

## 2. 最终会输出什么

算法 04 正式输出 4 类结果表，V1 额外补 1 张前置复购表。

| 表 | 一行代表什么 | 用途 |
|---|---|---|
| `mart_sku_repurchase_7d_pre19` | 一个周期 + 一个范围 + 一个门店群 + 一个消费者画像 + 一个 SKU 的 7 天 19 点前复购结果 | 先补齐 SKU 维度复购，供算法 04 读取 |
| `mart_target_profile_sku_performance` | 一个周期 + 一个范围 + 一个品类 + 一个门店群 + 一个消费者画像 + 一个 SKU 的表现 | 算法 04 的核心明细结果 |
| `mart_target_profile_product_performance` | 一个标准商品的汇总表现 | V1 使用商品基础表现有 SPU 汇总；SPU 缺失时按 `SKU_ONLY` |
| `mart_target_profile_anchor_summary` | 一个门店群消费者画像下的锚点汇总 | 给后续购物篮、新品候选和机会评分读取 |
| `mart_target_profile_sku_performance_params` | 一个模型版本下的参数、权重、断点和口径 | 用于复算、验收和追溯 |

一条 SKU 表现明细可以理解为：

```text
2026-04-01 到 2026-06-30，
上海，调理牛肉，A/B 级门店群，
目标画像 = 上班族晚高峰型-小家庭-中频-价格非敏感，
SKU = 黑椒牛柳丝 200g，
目标画像贡献、偏好、复购、自然动销、毛利、稳定性和锚点状态分别是什么。
```

后续算法读取的不是一句“好/不好”，而是一组可解释证据：

```text
是否正式锚点
是否当前可订可售
是否历史锚点
目标画像贡献和偏好
19:30 前自然动销
商品毛利
复购证据
门店稳定性
时间稳定性
商品属性
风险状态
```

## 3. 它在 AI 选品链路中的位置

```text
算法 01：会员画像
        ↓
算法 02：门店品类等级
        ↓
算法 03：门店群消费者画像贡献
        ↓
算法 04：目标画像现有高表现锚点商品识别
        ↓
算法 06：购物篮关联
        ↓
算法 09：新品候选方向生成
        ↓
算法 10：新品机会评分
        ↓
AI 商品机会推荐表
```

算法 04 读取算法 01、02、03 的正式结果，不重新贴会员画像，不重新给门店评级，也不重新判断主力消费者类型。

实际运行流程是：

```text
第一步：离线批量计算现有 SKU 表现
每月固定运行，使用最近 3 个完整自然月。
按城市算法区域 + 品类 + 门店群 + 消费者画像 + SKU 计算表现。
这一步不需要候选新品，也不是采购前端查询时实时计算。

第二步：沉淀锚点结果
写入 SKU 表现、标准商品表现、锚点汇总和参数表。
这些结果给后续购物篮、价格带、竞品趋势、新品候选和推荐优先级读取。

第三步：前端查询读取结果
采购选择城市、消费者画像、品类、门店群等查询条件；
系统读取已经计算好的锚点 SKU 和解释字段；
算法 04 不在前端查询时生成新品候选。
```

```text
mart_sku_repurchase_7d_pre19
```

## 5. 数据周期和范围怎么理解

正式评估周期：

```text
最近 3 个数据完整自然月
```

例如 2026 年 7 月运行：

```text
performance_start_date = 2026-04-01
performance_end_date   = 2026-06-30
```

算法 04 的正式范围沿用算法 02、03：

```text
城市算法区域
品类颗粒度
品类编码
门店群类型
门店品类等级
目标消费者画像
```

禁止因为样本不足自动扩大到其他城市、大区或其他品类。

## 6. 核心业务对象怎么定义

算法 04 比较的是“同一小范围内的现有 SKU”。

比较池必须同时相同：

```text
同一数据周期
同一城市算法区域
同一品类颗粒度和品类
同一门店群
同一消费者画像
```

大类、中类、小类分别计算，不能平均下级结果。

消费者类型直接读取算法 01 的 `final_profile`。捡漏型就是 `捡漏型`，不再拼家庭规模、频次和价格态度。

## 7. 先过滤和对账什么

先过滤无效交易：

```text
退货、取消、冲销、测试交易
非正向销售
门店、商品、会员、日期无法关联的记录
```

同一小票里同一个 SKU 出现多行时，先在小票内合并，再计算小票数、购买人数和复购，避免同一张小票被误当作多次购买。

关联后必须对账：

```text
关联前目标画像销售额
= 关联后各 SKU 销售额合计

关联前商品行数
= 关联后商品行数合计
```

对不上时不能发布正式锚点结论。

## 8. 两个时间点不能混用

算法 04 有两个重要时间点：

| 时间点 | 用途 |
|---|---|
| 19:00 前 | 7 天复购的第二次购买判断 |
| 19:30 前 | 自然动销、非促销售罄率 |

复购用 19:00 前。

自然动销用 19:30 前。

不能为了开发方便统一成同一个时间点。

## 9. SKU 基础表现怎么算

先计算每个目标画像下 SKU 的基础表现：

```text
目标画像 SKU 销售额
目标画像 SKU 标准销售量
目标画像购买会员数
目标画像小票数
SKU 在门店群中的销售占比
目标画像购买渗透率
目标画像 7 天 19 点前复购率
```

这些指标回答：

```text
这个目标画像是不是真的在买这个 SKU？
买的人多不多？
买完以后有没有复购？
```

## 10. 近 7 天 19 点前复购怎么算

复购口径：

```text
首次购买时间不限
第二次购买发生在首次购买后的第 1 到第 7 个自然日
第二次购买时间必须在 19:00 前
同一天多张小票不算复购
```

正式评分不能只拿一个复购率，还必须保存：

```text
复购会员数
可观察首购会员数
原始复购率
Jeffreys 95% 下界
```

如果只有 1 人买、1 人复购，页面可以展示原始复购率 100%，但正式评分要用 Jeffreys 下界，避免小样本被误判成强锚点。

## 11. 有效在售、订购和铺货怎么看

当前在售看门店商品每日可订可售表：

```text
是否可售 = 1
是否可订 = 1
```

有效在售 SKU 日还需要有实际进货或实际收货条件。

订购率不进入综合得分，它是独立解释维度。

原因是：

```text
低订购率但表现好，可能说明这个 SKU 有扩店机会。
如果把订购率直接扣进综合分，反而会把这种机会压下去。
```

## 12. 计量单位和标准销售量

不同商品不能直接把“件”和“千克”混在一起比较。

V1 计量识别：

```text
千克、kg、公斤、g、克 -> 重量
件、份、盒、包、袋、瓶、个、只 -> 普通计件数量
枚 -> 蛋类或枚数型数量
L、ml、毫升、升 -> 体积
无法识别 -> UNKNOWN
```

称重商品使用标准重量。

计件商品使用标准数量。

体积商品和蛋类枚数商品也单独保留计量类型。数量、到货量和售罄率只在同一计量类型里比较，不能把 kg、件、枚、L 混在一起算一个数量排名。

算法 04 统一使用小票里的 `weight` 作为销售标准量：

```text
sales_standard_qty = weight
```

本算法不在正文展开字段排查过程。开发只需要按 Doris 字段字典读取 `weight`，再用商品基础表的单位、规格或单位重量解释计量类型。

无法识别时：

```text
measurement_mapping_status = UNKNOWN
```

销售额、会员渗透率、偏好、复购和毛利仍可计算。只有当 `weight` 缺失、`weight <= 0` 或计量类型无法识别时，依赖标准销售量的售罄率、销售深度和目标画像成本才需要标记异常。

## 13. 目标画像相对偏好怎么算

目标画像偏好不是只看目标画像买了多少，而是要和参考人群比较。

核心逻辑：

```text
目标画像购买渗透率
/
参考画像购买渗透率
```

如果目标画像渗透率高于参考人群，说明这个 SKU 更像是目标画像偏好的商品。

小样本和 0 购买不能直接算，要用 Jeffreys 平滑，避免出现无穷大、100% 假强偏好。

如果比较范围里只有一个消费者画像：

```text
preference_reference_status = SINGLE_PROFILE
偏好维度不参与 CRITIC
其他维度照常计算
```

## 14. 小样本和统计证据怎么处理

业务原文不设置人工最小人数门槛。

也就是说，不因为“只有几个人买”就直接删除 SKU。

但正式评分要用统计证据校正：

```text
页面展示原始值
正式评分使用 Jeffreys 95% 下界或校正值
```

这样可以保留真实小样本，同时防止小样本把综合分抬得过高。

## 15. 19:30 前自然动销怎么算

自然动销只看非促销 SKU 日的 19:30 前表现。

第一期没有促销活动表，所以 V1 用折扣字段做代理：

```text
19:30 前 discount_amt = 0
-> 作为非促销/无折扣代理窗口

19:30 前 discount_amt > 0
-> 不进入自然动销窗口
```

自然动销主要看：

```text
19:30 前售罄率
非促销 19:30 前售罄率
19:30 前每有效在售门店日标准销售量
目标画像 19:30 前吸收贡献
```

其中 `19:30 前售罄率` 看全部有效 SKU 日，`非促销 19:30 前售罄率` 只看 19:30 前没有折扣代理的有效 SKU 日，两者不能混成一个指标。

如果出现：

```text
19:30 前销售量 / 实际收货量 > 1.10
```

说明售罄率分子分母可能异常，不能截断成 100% 继续评分，开发版会标记 `SELL_THROUGH_DATA_ERROR`。

如果整个周期没有自然销售窗口：

```text
natural_sales_status = NO_NATURAL_SALES_WINDOW
不能成为正式成熟锚点
```

## 16. 19:30 后折扣阶梯怎么用

19:30 后折扣阶梯只用于解释，不进入综合得分。

业务原文要求按实际半小时折扣档输出：

```text
19:30-20:00 销售量 / 增量售罄率 / 实际折扣率
20:00-20:30 销售量 / 增量售罄率 / 实际折扣率
20:30-21:00 销售量 / 增量售罄率 / 实际折扣率
```

它解释的是：

```text
这个 SKU 是 19:30 前自然卖掉的，
还是主要靠晚间折扣清掉的。
```

## 17. 商品毛利怎么算

业务原文给的核心公式是：

```text
目标画像 SKU 毛利额
= 目标画像 SKU 销售额 - 目标画像 SKU 成本金额
```

商品成本应按同一商品的单位成本计算。

所以当前文档里的 V1 计算方式，就是对业务公式的落地实现：业务定义“毛利额 = 销售额 - 成本金额”，我们用日门店 SKU 单位成本去计算目标画像成本金额。

举例：

```text
X 商品单位成本 = a
A 画像买了 100 个，销售额 = Q
B 画像买了 200 个，销售额 = W
C 画像买了 300 个，销售额 = E

A 画像毛利额 = Q - 100 * a
B 画像毛利额 = W - 200 * a
C 画像毛利额 = E - 300 * a
```

所以 V1 优先落地口径是：

```text
日门店SKU总成本金额
= 日门店SKU总销售额 - 日门店SKU全链路毛利额

日门店SKU单位成本
= 日门店SKU总成本金额 / 日门店SKU总标准销售量

目标画像日门店SKU成本金额
= 目标画像日门店SKU标准销售量 * 日门店SKU单位成本

目标画像SKU毛利额
= 目标画像SKU销售额 - 目标画像SKU成本金额
```

由于算法 04 统一使用 `sales_standard_qty = weight`，V1 默认不使用销售额占比分摊成本。

只有在个别 SKU 或个别日期出现 `weight` 缺失、`weight <= 0`、计量类型无法识别时，才进入异常处理。异常兜底可以按销售额占比分摊，但必须打标：

```text
cost_allocation_method = SALES_AMOUNT_SHARE_DEGRADED
```

算法 04 不再二次扣减损耗：

```text
不输出损耗诊断
不将损耗分摊给消费者画像
```

正式锚点毛利底线：

```text
target_profile_sku_margin_amt > 0
sku_total_margin_amt > 0
```

任一不为正，不能成为正式锚点。

## 18. 商品属性和商品编码怎么处理

锚点 SKU 要尽量输出：

```text
主材料
肉类部位或商品形态
已有配料
口味
加工方式
烹饪方式
净含量
包装方式
储存温层
品牌
```

V1 如果商品属性缺失，不阻断经营表现计算：

```text
attribute_status = ATTRIBUTE_INCOMPLETE
```

但属性缺失会影响后续新品方向生成，因为新品方向需要知道锚点的主材料、口味、规格、形态等。

SPU 缺失或无法稳定映射时：

```text
standard_product_mode = SKU_ONLY
```

也就是第一期不新增独立换码或替代关系；有商品基础表 SPU 就按 SPU 汇总，没有 SPU 就按销售 SKU 计算，不自动把名称相似商品合并。

## 19. 价格指标和算法 05 边界

算法 04 可以输出当前 SKU 的价格描述：

```text
实付均价
标准化单价
促销前后价格
```

但价格带机会判断属于算法 05。

算法 04 不能提前判断：

```text
哪个新品价格带更好
```

## 20. 四个一级评分维度

算法 04 正式综合得分只看四个一级维度：

| 一级维度 | 业务含义 |
|---|---|
| 目标画像贡献 | 这个 SKU 在目标画像销售里是否重要 |
| 目标画像偏好 | 目标画像是否比其他人群更偏好它 |
| 19:30 前自然动销 | 不靠晚间折扣时，它是否能自然卖动 |
| 商品毛利 | 目标画像和整体 SKU 毛利是否健康 |

不进入综合得分的内容：

```text
订购率
19:30 后折扣阶梯
价格带判断
商品属性完整度
购物篮关联结果
```

这些只做解释、过滤或后续算法输入。

## 21. 综合分怎么合成

算法 04 不使用固定权重。

它先把各个指标做稳健标准化，再用两级 CRITIC 动态赋权：

```text
第一层：每个一级维度内部的二级指标，用 CRITIC 算权重
第二层：四个一级维度之间，再用 CRITIC 算权重
```

CRITIC 的业务含义是：

```text
越能区分 SKU、且和其他指标不重复的信息，权重越高。
```

样本太少时不强行算权重，按业务原文的小样本回退规则处理。

## 22. 锚点组怎么生成

综合分出来后，不用固定阈值划锚点。

业务原文要求：

```text
Jenks + BIC 动态选择 1 到 3 组
```

如果最高组存在，就进入正式锚点准入判断。

如果没有明显高表现组：

```text
result_status = NO_OBVIOUS_HIGH_SKU
```

## 23. 正式锚点怎么准入

进入最高表现组还不够，正式锚点还必须同时满足：

```text
上游版本完整
商品编码、销售、到货、毛利数据完整
当前可订可售
有自然销售窗口
目标画像 SKU 毛利为正
SKU 整体毛利为正
统计证据不是低证据假高分
```

不满足时，可以保留为候选或解释记录，但不能叫正式当前锚点。

## 24. 当前锚点和历史锚点

当前锚点：

```text
当前可订可售
并且通过正式锚点准入
```

历史锚点：

```text
贡献周期内有真实销售且表现较好
但当前不可订不可售
```

历史锚点可以保留消费者和购物篮证据，但进入新品或复开发前，必须再看停售原因、订购表现和相似商品表现。

## 25. 稳定性怎么验证

算法 04 做两类稳定性验证。

门店稳定性：

```text
每次去掉一个门店
重新计算 CRITIC、综合分和 Jenks 分组
看这个 SKU 是否仍然是锚点
```

时间稳定性：

```text
每次去掉一个月份
重新计算 CRITIC、综合分和 Jenks 分组
看这个 SKU 是否仍然是锚点
```

如果依赖少数门店：

```text
store_stability_status = STORE_CONCENTRATED
```

如果依赖某个月：

```text
time_stability_status = TIME_SENSITIVE
```

稳定性状态不直接删除锚点，但会影响后续购物篮和新品方向解释。

## 27. 开发实际要怎么做

开发落地顺序可以理解为：

```text
1. 锁定算法 01、02、03 的正式版本。
2. 按范围、品类、门店群和目标画像筛选有效小票。
3. 先产出 SKU 维度 7 天 19 点前复购表。
4. 聚合 SKU 基础销售、会员、小票、标准销售量。
5. 关联可订可售、进货、毛利、商品属性。
6. 计算偏好、复购、自然动销、毛利和统计证据。
7. 做稳健标准化和两级 CRITIC 动态权重。
8. 用 Jenks+BIC 找高表现组。
9. 做正式锚点准入、当前/历史锚点和稳定性验证。
10. 写入 SKU 表现、标准商品表现、锚点汇总和参数表。
```

开发可以有临时表和过程表，但正式结果按第 2 节的输出表交付。

## 28. 业务验收看什么

业务和采购验收时重点看：

```text
1. 锚点 SKU 是否符合经营事实。
2. 高分 SKU 是否真的有目标画像贡献，而不是全人群都买。
3. 小样本高复购有没有被 Jeffreys 校正。
4. 19:30 前自然动销是否成立。
5. 毛利为正的判断是否符合商品成本口径。
6. 当前不可订不可售的 SKU 是否被放到历史锚点，而不是当前锚点。
7. 时间敏感或门店集中的锚点解释是否合理。
```

## 29. 现在还需要确认什么

这里只保留真正会影响落地的事项。

| 确认项 | 需要谁确认 | 为什么重要 |
|---|---|---|
| `weight` 字段抽样验收 | 数据开发 / 需求评审 | 验收 `sales_standard_qty = weight` 与商品基础表单位是否匹配 |
| `weight` 异常处理 | 数据开发 / 需求评审 | 默认按单位成本乘数量；个别 `weight` 缺失或异常时已接受销售额占比分摊兜底，并必须打标 |

已确认不再作为阻断项：

```text
1. 毛利损耗表可以按数量字段合同交付。
2. 商品属性缺失不阻断算法 04，先标记 ATTRIBUTE_INCOMPLETE。
3. V1 接受 discount_amt > 0 代理促销、SKU_ONLY、前置复购表 mart_sku_repurchase_7d_pre19。
```

## 30. 不要做什么

```text
不要把算法 04 当成新品生成算法。
不要把候选新品当成已经验证过的现有锚点。
不要用固定权重替代 CRITIC。
不要用固定分数线替代 Jenks+BIC。
不要把 1/1 的 100% 复购当成强证据。
不要把 19:30 后销售占比当成自然动销。
不要把订购率扣进综合分。
不要按销售额占比分摊成本作为默认毛利口径。
不要自动合并名称相似但没有商品基础表 SPU 的商品。
不要让大模型替代离线算法判断锚点。
```

## 31. 一句话总结

算法 04 的本质是：

```text
先在目标画像真实买过的现有 SKU 里，找出贡献高、偏好强、自然动销好、毛利健康、证据可靠、稳定性可解释的锚点商品，
再把这些锚点交给后续购物篮和新品机会算法继续推导。
```
