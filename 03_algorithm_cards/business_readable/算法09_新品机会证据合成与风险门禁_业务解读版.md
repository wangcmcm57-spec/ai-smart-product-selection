# 算法 09：新品机会证据合成与风险门禁（业务解读版）

更新时间：2026-09-04

业务原始依据：`01_source_docs/business_algorithm_docs/算法卡_09_新品机会证据合成与风险门禁.md`

## 1. 先用一句话理解

算法 09 要判断：

```text
一个已经由算法 08 整理好的新品候选，
在指定城市/城市群、门店等级、消费者画像和叶子小分类下，
是否具备继续作为新品推进的条件。
```

它不是简单的“风险提醒”。它要把机会证据、当前货盘、历史经营结果、法规规则、价格成本、折扣依赖、毛利压力和外部同质化证据放在一起，输出：

```text
可以继续推进；
可以继续，但必须补条件；
商品方案需要回上游重做；
不应作为新品推进。
```

其中商品状态和 `S` 商品计划上架开始/结束日期已经由算法 08 透传给 09；法规、食品安全、标签、功能声称在 V1 只做风险线索留痕，不作为当前门禁结论输入。

算法 09 判断的是“能不能继续推进”，算法 10 才负责在通过或允许验证的候选中编排推荐优先级和展示摘要。开发需求发布属于算法 10 之后的产品或流程动作，不是 09 的输出动作。

可以把算法 09 理解成新品候选进入开发前的最后一道业务闸口。

这里的“门禁”不是人工审批表，也不是页面展示按钮，而是一组必须离线计算并留痕的判断：

```text
这个候选是不是真的还有新品空间；
公司当前货盘里是不是已经有同款；
历史上高相似商品是不是已经被稳定证明经营失败；
商品名称、配方、标签或功能声称有没有法规和质量风险；
算法 05 给出的规格、价格、成本和毛利能不能在真实经营情景下守住；
如果不能直接通过，是补材料、回上游重做，还是退出本轮新品池。
```

一个完整例子：

```text
算法 08 输出标准候选：Omega-3 鲜鸡蛋 12 枚。

算法 09 会继续判断：
鲜鸡蛋这个主体需求是否成立；
12 枚规格和价格成本是否可行；
公司当前是否已经有同款 Omega-3 鸡蛋；
Omega-3 这个功能声称是否需要检测报告、营养标签或声称依据；
如果材料缺失，是有条件通过，还是必须返回重做；
最后给算法 10 一个明确结论：能不能推进、以什么身份推进、还缺什么。
```

所以算法 09 的核心不是“算一个高低分”，而是把机会和风险拆开判断。

## 2. 最终会输出什么

### 2.1 每个候选最终回答三个问题

对每个“标准新品候选 × 适用业务范围”，算法 09 要回答：

| 要回答的问题 | 输出内容 | 人话 |
|---|---|---|
| 这个对象有没有新品资格 | 最终候选状态 | 正式新品、季节新品、本地试点新品、探索新品，或不具备新品资格 |
| 现在能不能继续走 | 门禁结果 | 通过、有条件通过、返回重做、拒绝 |
| 为什么是这个结果 | 机会证据、风险证据和下一步动作 | 哪些证据支持，哪里有风险，还要补什么或重做什么 |

### 2.2 四种门禁结果

| 结果 | 人话解释 | 后续去向 |
|---|---|---|
| `PASS`（通过） | 当前机会、经营条件和风险检查都满足要求 | 可交给算法 10，进入推荐展示 |
| `CONDITIONAL_PASS`（有条件通过） | 机会成立，但有明确的补证、真实成本或验证条件 | 可交给算法 10，进入条件推荐展示；不能写成正式通过，也不能进入正式试点 |
| `RETURN_FOR_REBUILD`（返回重做） | 候选方向可能还有机会，但规格、价格、成本、属性或数据需要回上游调整 | 回到算法 05、06、07 或 08 重做后，用新版本重新判断 |
| `REJECT`（拒绝） | 命中确定性硬门禁，例如公司已有同款或价格成本没有可行交集；法规硬停不在本版启用 | 退出本轮新品池，保留原因和证据 |

### 2.3 五种候选资格

| 状态 | 人话解释 |
|---|---|
| `FORMAL_NEW_PRODUCT`（正式新品） | 可以按常规新品方向推进 |
| `SEASONAL_NEW_PRODUCT`（季节新品） | 只在明确计划上架窗口内推进，窗口外不能把无销售当成失败 |
| `LOCAL_PILOT_NEW_PRODUCT`（本地试点新品） | 只在稳定的局部城市、门店群或画像范围成立，暂不推广到完整范围 |
| `EXPLORATORY_NEW_PRODUCT`（探索新品） | 有探索信号或早期证据，可以观察和验证，但不能因为门禁通过就升级成正式新品 |
| `NOT_ELIGIBLE_FOR_NEW_PRODUCT`（不具备新品资格） | 当前不应作为新品开发方向推进 |

门禁结果和候选资格不是同一个字段：

```text
门禁结果回答“现在能不能过”；
候选资格回答“即使可以推进，应当以什么方式推进”。
```

业务最常看的主结果是 `new_product_gate_result`。
其他结果表是为了说明为什么通过、为什么有条件通过、为什么返回重做或为什么拒绝。

## 3. 它在整条 AI 选品链路中的位置

```text
算法 01：会员画像
        ↓
算法 02：门店品类等级，确定目标门店范围
        ↓
算法 03：门店群消费者画像贡献，确定目标消费者类型
        ↓
算法 04：目标画像 SKU 表现，确定主体商品和正式锚点
        ↓
算法 05：目标画像商品价格带，确定规格、售价、成本和毛利可行性
        ↓
算法 06：购物篮新品关联，发现内部配方型或场景型新品属性
算法 07：竞品与全球外部趋势新品发现，发现外部属性、竞品和趋势
        ↓
算法 08：新品候选标准化与合并，确定候选到底是什么商品
        ↓
算法 09：新品机会证据合成与风险门禁，判断候选能否继续推进
        ↓
算法 10：新品推荐优先级与开发需求编排，决定先推荐什么、交给采购什么推荐摘要和待补条件
```

算法 09 的上游是算法 08 的标准候选。算法 09 会读取算法 02 至 07 的正式证据做对账和解释，但不重新计算上游算法。

## 4. 算法 09 做什么、不做什么

### 4.1 算法 09 做什么

```text
汇总算法 02 至 07 的正式机会证据；
确认候选的主体、属性、规格和来源是否一致；
检查公司当前货盘是否已有同款或高相似商品；
检查历史相似商品是否存在稳定、可证实的经营失败；
承接法规、食品安全、标签、功能声称和知识产权风险线索，V1 不执行确定性规则门禁；
读取算法 05 的价格、成本和毛利可行性；
检查折扣依赖和真实历史经营情景下的毛利压力；
判断外部同质化与候选差异属性是否有证据；
合成机会证据，确定门禁结果、候选资格和下一步处理信号。
```

### 4.2 算法 09 不做什么

```text
不重新计算会员画像、门店等级、消费者贡献、SKU 锚点、价格带、购物篮或外部趋势；
不直接修改候选的材料、口味、工艺、规格或价格；
不做任何供应商相关判断或触达；
不输出促销、陈列、订购、替换、升级或清退动作；
不把损耗单独做成一项风险分，也不重复扣减已经进入全链路成本的损耗；
不做完整蒙特卡洛利润预测；
不生成跨叶子小分类的统一机会总榜；
不生成可以抵消硬门禁的机会总分。
```

## 5. 正式判断对象和范围

### 5.1 一行结果代表什么

算法 09 的正式判断粒度是：

```text
正式周期
+ 城市/城市群
+ 门店等级
+ 消费者类型
+ 叶子小分类
+ 标准新品候选
```

所以同一个候选在上海 A 级门店和宁波 B 级门店，不能直接共用一个结论。

例如：

```text
青椒黑椒牛柳丝 200g
+ 上海
+ A 级门店
+ 年轻家庭画像
+ 牛肉制品小分类
```

是一个独立判断对象。

### 5.2 切换范围必须重算

切换以下任一内容，都要读取对应范围的上游证据和经营数据重新判断：

```text
城市/城市群；
门店等级；
消费者类型；
叶子小分类；
标准新品候选。
```

不能把不同城市、门店等级或消费者画像的失败概率、毛利情景和门禁结果做平均。

### 5.3 大分类、中分类和全选怎么处理

算法 09 最终按叶子小分类判断：

```text
选择叶子小分类：直接判断该小分类；
选择中分类：展开其中的全部叶子小分类，逐个判断；
选择大分类或全选：继续展开到叶子小分类，分别判断和分组展示。
```

不能把“大分类”“中分类”或“全选”本身当成一个商品分类，也不能把不同叶子小分类放在一起生成一个统一机会总榜。不同小分类的商品、价格、毛利、生命周期和经营指标没有共同比较基础。

## 6. 使用什么数据，哪些数据由谁提供

这一节先把责任边界讲清楚：

```text
算法 02 至 08 的正式结果：系统已经算好，09 只读取，不重新计算；
商品基础、可订可售、价格、折扣、毛利等经营数据：数据开发按数据合同接入和验收；
公司毛利底线、目标毛利、价格阶梯：由算法 05 使用，09 读取算法 05 的结果；
商品状态和计划上架窗口：数据开发从 SAP POP 落 `dim_product_status`，算法 08 透传给 09；
法规、食品安全、标签和功能声称规则：V1 只留痕，确定性规则边界留待后续版本落成规则资产。
```

业务不需要手工给每个候选打分，也不需要手工生成历史相似商品清单。
业务真正要补的是规则边界：什么能过、什么要补材料、什么必须硬停。

### 6.1 上游算法正式结果

| 来源 | 09 使用什么 | 作用 |
|---|---|---|
| 算法 02 | 目标城市/城市群、门店等级和门店集合 | 确定候选适用的门店范围 |
| 算法 03 | 目标消费者类型及其贡献、稳定性 | 判断候选服务的目标画像是否成立 |
| 算法 04 | 主体商品、正式锚点和目标画像表现 | 防止关联商品或外部热词替换主体商品 |
| 算法 05 | 推荐规格、建议售价、单位成本、成本上限、毛利目标和可行性 | 判断价格和经营条件 |
| 算法 06 | 内部候选属性、购物篮规则和证据 | 判断是否有真实内部新品属性来源 |
| 算法 07 | 外部候选属性、竞品、趋势、图片和风险线索 | 判断外部证据、差异属性和法规风险 |
| 算法 08 | 标准候选、范围候选、属性来源和候选快照 | 作为 09 的正式候选入口 |

算法 09 不把查询筛选条件当成算法输入事实。城市、画像和小分类是计算范围；候选、规格、成本和证据来自算法链路和正式数据表。

成本优先直接从门店商品日价格表读取，不单独依赖 SRM；V1 先用价格表里的仓、商品、采购结算价、当天采购价和出库到店含税成本做成本口径。

### 6.2 商品基础和经营数据

算法需要从商品基础表和经营数据中确认：

```text
商品主体、销售商品编码、SPU、叶子小分类；
主材料、配料、口味、工艺、形态、规格、计量类型、包装和场景；
商品状态编码、商品状态名称、`S` 商品计划上架开始和结束日期；
当前可订可售状态；
历史到货、销售、折扣、收入、全链路成本和全链路毛利；
历史商品的生命周期和退出状态。
```

商品基础表的 SPU 可以帮助判断同一标准商品，但不能自动等同于完整换码关系、替代关系或历史退出原因。

### 6.3 法规规则数据

法规、食品安全、标签、功能声称和知识产权的确定性判断需要使用版本化规则资产；V1 第一版不启用这套门禁，只把 07 传来的风险线索记录到留痕里，不把它单独升级成 `CONDITION_REQUIRED` 或 `CONDITIONAL_PASS`。

```text
法规知识库保存有效规则、条款、适用分类、适用属性和生效时间；
确定性规则引擎执行规则匹配和条件判断；
AI 只负责从候选名称、配方、标签或外部资料中提取结构化字段，并生成“为什么命中这条规则”的说明；
AI 不能自行生成检测值、认证、配方比例或法律结论。
```

V1 第一版不启用法规确定性规则：有算法 07 风险线索时，09 只记录风险线索和待补信息，不把它升级成当前门禁结论；没有风险线索时，09 不写“法规已通过”，也不因为规则库未启用而把所有候选打回。

例如：

```text
候选名称里出现 Omega-3；
AI 提取出功能声称词 = Omega-3；
V1 第一版法规规则未启用，算法 09 只把它作为功能声称风险线索留痕；
当前版不输出法规已通过，也不直接输出法规硬停；
最终门禁结果仍由机会证据、价格成本和历史经营等因素决定。
```

检测报告、标签依据和适用标准不是算法 09 自己发明的要求，必须来自质量、法务或公司规则资产。

## 7. 数据周期、版本和运行时间

### 7.1 四类数据使用不同时间口径

| 数据类型 | 使用口径 |
|---|---|
| 算法 02 至 07 机会证据 | 同一个最近 3 个完整自然月的正式版本 |
| 当前货盘 | 执行门禁时最新的公司级可订可售快照 |
| 法规规则 | V1 第一版不启用确定性规则；后续启用时读取执行门禁时已经生效的最新规则版本 |
| 历史失败和毛利情景 | 使用满足质量要求的历史生命周期，优先使用同季节和近期数据 |

不能使用数据截止时间之后的数据评价当期候选。

### 7.2 正式运行和即时复核

```text
日常：算法 07 可以采集外部趋势和风险预览，但预览不覆盖正式结果；
月度：冻结算法 02 至 07 的正式版本，运行算法 08 和 09，生成正式门禁结果；
后续开发推进前：复核当前货盘是否变化；法规规则后续启用后，再一并复核法规变化并必要时重新运行 09；
法规或食品安全事件：后续规则启用后立即触发受影响候选重算。
```

算法 10 只使用最新且仍有效的 09 结果，不在查询时重新做 09 门禁。

### 7.3 哪些变化需要新候选

以下内容变化时，不得沿用旧候选的门禁结果：

```text
主材料；关键配料；口味；功能属性；工艺；规格或计量类型；
建议售价变化到另一个算法 05 可行区间；候选商品名称中的主体或关键属性。
```

只修正数据错误、商品实体没有变化时，可以保留候选身份，但必须生成新的运行版本和复核记录。

## 8. 完整运行流程

业务上可以先把 09 的运行流程压缩成五层判断：

```text
第一层：候选能不能进入 09；
第二层：机会证据是否最低成立；
第三层：当前货盘和历史经营是否有硬风险；
第四层：法规线索是否留痕，价格、成本和毛利是否过关；
第五层：把结论写成通过、有条件通过、返回重做或拒绝。
```

下面的 14 步是开发和评审用来落地这五层判断的展开版本。

### 第一步：锁定本次运行版本

算法先锁定：

```text
本次运行编号；正式周期；数据截止时间；
02 至 08 上游版本；商品基础快照；商品状态版本；法规规则版本或 V1 未启用状态；
相似模型、历史失败模型和毛利情景版本。
```

这样以后能够回答：这个候选当时为什么通过，使用的是哪一版数据和规则。

### 第二步：读取算法 08 的标准候选

只有算法 08 已准备好的候选才能进入 09：

```text
READY_FOR_ALGORITHM_09：候选身份、主体、属性、规格和价格上下文已准备好；
READY_WITH_ESTIMATED_COST：可以评估，但成本仍是估算值，后续必须补真实成本。
```

如果候选是 `S` 季节品但计划上架开始或结束日期缺失，08 会写 `SEASON_WINDOW_INCOMPLETE`。这类候选只要其他核心条件齐全，仍然可以进入 09；09 不能输出正式季节推荐信号，而是写成需要补齐季节窗口的条件。

以下候选不进入 09 的正式门禁：

```text
缺少主体、小分类、明确规格或属性来源；
缺少算法 05 的价格可行性结果；
算法 08 注册异常；
无法确认候选适用范围。
```

这类候选由算法 08 保留来源和异常，等待上游补齐后重跑。

正式候选和探索候选都可以进入 09 做证据和风险判断，前提是候选已经满足算法 08 的进入条件。探索候选即使通过风险门禁，也必须继续保留“探索”身份，不能升级成正式新品。

### 第三步：做核心数据完整性检查

核心数据缺失时，09 不能继续生成可发布结论，应输出“返回重做”或“不可评估”：

```text
正式叶子小分类映射；
标准候选和范围候选身份；
具象商品名称和规格；
商品名称各属性的来源；
算法 05 价格成本可行性；
当前公司级可订可售货盘快照；
算法 07 法规、标签、食品安全或功能声称风险线索传递状态。
```

外部趋势、竞品图片、社媒口碑、历史高相似经营情景等增强证据缺失时，不自动拒绝，但必须记录缺失状态，并判断是否需要有条件通过。

### 第四步：确认最低新品机会证据

以下四项基础条件必须全部满足：

```text
算法 02：目标门店等级群存在且版本有效；
算法 03：目标消费者类型和贡献结构明确；
算法 04：主体商品需求成立；
算法 05：规格、售价、成本和目标毛利存在可行交集。
```

同时，算法 06 或算法 07 至少要有一条可追溯的新品属性来源：

```text
算法 06：正式或探索购物篮中的配方型、属性型或场景型机会；
算法 07：正式或探索外部竞品、趋势或属性机会。
```

不适用不等于零分。例如：

```text
Omega-3 鲜鸡蛋没有购物篮配方属性：购物篮属性写“不适用”，不能填 0；
青椒黑椒牛柳丝当前没有正式外部趋势，但内部购物篮证据成立：外部证据写“无外部观察”，不能填 0。
```

主体需求不成立、价格成本没有可行交集、候选属性没有来源或候选无法保持小分类时，不能靠高趋势或低风险抵消。

### 第五步：判断当前货盘是否已有同款或高相似商品

当前货盘检查的是公司全量可订可售商品，不只检查目标城市。

```text
公司已经有的商品，即使还没有进入目标城市，也不是新品开发；
它属于现有商品引入、经营或货盘问题。
```

相似判断不是只看名字，而是看五个字段：

```text
品型、口味、规格、百克标价、工艺。
```

V1 用加权 Gower 式 kNN 算相似度，权重固定为：

```text
品型 30%；
口味 25%；
规格 20%；
百克标价 15%；
工艺 10%。
```

其中：

```text
品型按层级相似算；
口味和工艺按标签集合的交并比算；
规格和百克标价按稳健数值距离算，再截断到 0 到 1。
```

两类标签集合都为空时，按数据治理规则记为不适用；可用字段太少时，只能先放进灰区复核，不能直接当同款。

V1 已确认按 `0.85` 作为高相似硬门槛：五字段得分达到 `0.85`、至少 4 个字段可用且硬边界都通过，才进入高相似硬门禁；`0.70` 到 `0.85` 或字段不足时进入灰区复核。

判断顺序：

```text
同一商品编码、同一正式 SPU 或明确同一标准实体
-> 同款，硬门禁，REJECT；

高相似达到 V1 硬门禁阈值且硬边界通过
-> 硬门禁，REJECT；

五字段相似得分处于灰区，或可用字段不足导致无法确认是否重复
-> 有条件通过，要求重复关系复核；

主材料、关键配料、功能属性、口味、工艺、规格或消费场景发生有证据的实质变化
-> 可以继续检查，但不能只凭名称变化解除重复门禁。
```

### 第六步：使用历史相似商品判断经营失败风险

这里必须把“系统观察到的事实”和“商品为什么退出”分开。

#### 系统能观察到什么

算法不能用“小票没有销售”直接判断商品停止订购。

算法必须读取数据合同中的门店商品每日可订可售表，在“日期 + 门店 + 销售 SKU”粒度观察：

```text
商品何时从可订或可售变成不可订、不可售；
停止前是否持续负全链路毛利；
停止前 19:30 前自然动销是否不足；
停止前是否长期依赖晚间折扣；
之后是否恢复可订或可售。
```

其中：

```text
可订可售状态表：识别“状态发生变化”这个事实；
小票、折扣和毛利数据：描述停止前的经营表现；
SPU：只能辅助归并同一标准商品，不能替代正式换码关系。
```

如果真实数据库已经有完整表和字段，开发直接映射到数据合同口径；如果真实表缺字段或粒度不完整，开发需要加工补齐合同表。无论哪种情况，都不能用“没有销量”替代“已经停止订购”。

#### 业务原文要求区分什么

业务原文要求历史退出至少区分：

```text
真正经营失败；
季节结束；
正常换码或 SPU 迁移；
供应中断；
法规或食品安全退出；
经营策略调整；
仍在售但尚未退出；
退出原因未知。
```

这些是后续规则资产要区分的退出结局，不是算法可以只靠小票自动计算出来的完整原因。

#### V1 没有退出原因时怎么处理

当前 V1 已有 SAP POP 商品状态和 `S` 商品计划上架窗口，但没有正式换码关系、替代关系和稳定历史退出原因字段。因而：

```text
算法可以识别“可订可售状态变化”和“停止前经营表现”；
算法可以知道商品是不是 S 季节品，以及计划上架窗口是否齐全；
算法不能把这些信号直接写成“经营失败原因”；
历史退出原因写 UNKNOWN_EXIT（原因未知）；
历史结局写 UNCERTAIN_OUTCOME（结局不确定）；
历史失败门禁写 INSUFFICIENT_HISTORICAL_EVIDENCE（历史证据不足）；
不得因为这类不确定历史记录拒绝新品候选。
```

只有未来具备正式退出原因、换码关系，且历史失败规则的阈值与验证通过后，历史同款或高相似失败才可能触发硬拒绝。判断条件仍必须同时满足：

```text
候选与历史商品是同款或高相似；
历史结局能确认是经营失败，而不是季节、换码或供应原因；
失败概率高于经过时间外回测得到的动态阈值；
可信区间、样本量和稳定性满足要求；
没有足以改变结论的结构性差异。
```

历史模型的特征重要性只能说明模型使用了哪些信号，不能单独证明“这个信号就是商品经营失败的原因”。失败原因还需要准实验、匹配、分层抽样或业务复核等因果证据支持。

### 第七步：承接法规、食品安全和功能声称风险线索

法规留痕有三个角色：

```text
法规知识库：保存有效规则、条款、分类和生效时间；
确定性规则引擎：按规则执行匹配和条件判断；
AI：提取候选名称、配方、标签和外部资料中的结构化字段，并生成规则命中说明。
```

AI 不能自己判断法律条款是否失效，也不能生成不存在的认证、检测值或配方比例。

后续规则启用后，需要检查的风险包括：

```text
原料能否进入目标食品分类；
添加剂和使用限量；
营养或功能声称的适用条件；
商品名、标签和广告表述；
过敏原和必要标签字段；
国内生产、包装和冷链硬性要求；
商标、专利和受保护工艺名称；
规则的生效和失效时间。
```

Omega-3 案例的正确理解是：

```text
算法 07 发现 Omega-3 是外部属性或趋势；
V1 第一版法规规则未启用，算法 09 只把它作为功能声称风险线索留痕；
当前版不输出 `CONDITION_REQUIRED` / `CONDITIONAL_PASS`；
不能输出法规已通过，也不能直接输出法规硬停。
```

这里的检测报告、营养标签和声称依据，来自业务原文中的 Omega-3 案例；它们不是所有功能词都自动使用同一套材料。不同声称需要什么材料，必须由质量/法务规则明确。
V1 第一版只记录“需要补适用规则或材料范围”和“补齐后必须重算”，不负责收集材料或替业务确认材料真伪。

### 第八步：读取算法 05，判断静态价格和毛利

算法 09 不重新计算算法 05，只读取：

```text
建议规格；
建议零售价；
全链路单位成本；
成本谈判上限；
公司毛利底线和目标毛利；
价格成本可行交集状态；
成本是否为估算值。
```

判断原则：

```text
没有价格成本可行交集 -> 不能继续作为可开发新品；
有可行交集且成本为真实成本 -> 进入后续经营检查；
有可行交集但成本是估算值 -> 可以继续，但必须补真实成本条件。
```

算法 09 不直接修改商品价格和规格。

### 第九步：检查折扣依赖风险

算法使用历史真实经营数据观察：

```text
19:30 前自然售罄率是否偏低；
19:30 后价格弹性是否偏高；
折扣依赖和全链路毛利压力是否同时成立。
```

V1 用两个核心指标来合成折扣依赖风险分：

```text
19:30 前自然售罄率 = 19:30 前销售标准量 / 当日有效可售标准量

晚间价格弹性 = 晚间折扣后销量提升 / 折扣深度
```

再在同口径样本池里用 CRITIC 算权重，把两个指标合成一个折扣依赖风险分。风险分按分位切四档：

```text
P20 及以下：低依赖
P20 到 P50：中依赖
P50 到 P80：高依赖
P80 及以上：严重依赖
```

判断上，`19:30 前自然售罄率低 + 晚间价格弹性高` 才说明更依赖折扣；真正要不要退回重做，还要再看毛利压力。

这里的 19:30 是业务判定切点；如果现有底层经营表只有 19 点前/后字段，需要数据开发在时段加工里明确映射或补加工，不能把 19 点字段和 19:30 字段混用。

折扣依赖和毛利压力一起决定动作：

| 结果组合 | 处理动作 |
|---|---|
| 低/中依赖，毛利压力通过 | 继续推进 |
| 高/严重依赖，但毛利压力通过 | 保留观察线索，不单独阻断 |
| 低/中/高依赖，毛利压力需要补证 | 有条件通过，只能进入条件推荐和待补条件 |
| 严重依赖，且毛利压力需要补证 | 返回重做，优先降本、改规格或改价格 |
| 任意折扣依赖，毛利压力已经不成立 | 返回重做；若算法 05 无任何价格毛利可行交集，则拒绝 |

所以，折扣风险本身不等同于硬拒绝；它要和毛利压力一起决定是观察、验证还是重构。

### 第十步：用真实历史情景做毛利压力测试

算法 09 不做完整蒙特卡洛模拟。原因是 V1 需要保留可以让业务复算的真实经营情景，而不是生成看似精确、却无法解释的利润概率。

情景来自历史相似商品的真实门店日，至少保留：

```text
到货数量；
19:30 前销售数量；
折扣档销量；
候选建议售价；
候选全链路单位成本；
情景收入、全链路成本、全链路毛利和毛利率。
```

如果历史样本足够，系统用 K-medoids 聚类选择代表情景；每个 medoid 必须是真实历史门店日，不是模型虚构的一天。

称重商品和计件商品分开计算，公斤和件数不能相加。销售量明显超过到货量的异常日不能进入情景库。

业务只需要理解三种结果：

```text
基准和不利情景都守住目标毛利 -> 经营压力可接受；
基准可行但不利情景失守 -> 需要降本、调规格、调价格或小范围验证；
基准情景已经低于目标毛利 -> 返回重做。
```

没有足够高相似历史商品时，系统分层回退；回退后仍不足，输出“毛利压力证据不足”，不能虚构情景。

### 第十一步：判断外部同质化和差异属性

外部竞品相似，不等于公司当前货盘已有同款。

```text
内部货盘同款 -> 可以触发新品重复硬门禁；
外部竞品相似 -> 只能说明市场已有类似方向，不能单独拒绝；
明确知识产权侵权 -> V1 第一版只留痕；后续法规知识库和确定性规则启用后，才可按法规硬门禁处理。
```

候选的差异属性必须有来源，例如：

```text
标准属性；
算法 06 的购物篮属性；
算法 07 的竞品、趋势或痛点证据；
可解释的竞品属性覆盖率。
```

不能用 AI 自动生成的营销文案冒充商品差异证据。

### 第十二步：合成机会证据，但不生成总分

算法 09 不输出 0 到 100 的“AI 机会总分”。原因是：

```text
目前没有完整、无偏且口径一致的新品成功标签；
不同候选可能由购物篮、外部趋势等不同路径产生；
硬风险不能被高机会分抵消；
固定权重无法解释为什么是 30% 或 20%。
```

机会证据先分层：

```text
内部和外部共同收敛的正式证据；
单路径正式证据；
成熟市场差异化空白；
正式季节证据；
局部门店群证据；
新兴或海外领先探索证据；
原始信号。
```

同一证据层级内，只比较共同适用维度：

```text
目标消费者主体需求稳定性；
算法 05 价格和成本可行空间；
历史毛利不利情景稳健性；
竞品差异属性证据；
跨门店和月份稳定性；
风险证据完整度。
```

某项指标对候选不适用时写“`NOT_APPLICABLE`（不适用）”，不能填 0 伪装成表现差。

同一范围内，若候选 A 在所有共同适用维度都不差于候选 B，并且至少一个维度更好，A 才可以支配 B。这里不是说 A 有业务权力，而是说 B 在同一比较范围内没有额外优势，不需要重复占一个机会位置。没有互相支配关系的候选并列保留。

Pareto 比较只发生在相同的周期、城市/城市群、门店等级、消费者画像、叶子小分类和证据层级内，不跨叶子小分类排名。

### 第十三步：按风险优先级生成最终结论

单项风险不用“高、中、低”，而用能决定动作的状态：

| 状态 | 人话 |
|---|---|
| `CLEAR` | 当前检查通过 |
| `OBSERVED_NON_BLOCKING` | 发现了信息，但当前不阻断 |
| `CONDITION_REQUIRED` | 必须补材料或完成验证 |
| `REBUILD_REQUIRED` | 商品方案或数据需要重做 |
| `HARD_STOP` | 命中确定性硬门禁 |
| `NOT_EVALUABLE` | 缺少有效规则或核心数据，当前不能判断 |

多个风险同时出现时，最终结果按以下顺序确定：

```text
REJECT
> RETURN_FOR_REBUILD
> CONDITIONAL_PASS
> PASS
```

高机会证据不能抵消硬门禁。即使最终拒绝，其他已经发现的机会和风险原因仍然要保存。

### 第十四步：确定候选资格和下一步处理信号

风险门禁只能保留、降级或退出，不能把探索证据升级成正式证据。

下一步处理信号的业务含义是：

| 结果组合 | 下一步处理信号 |
|---|---|
| 通过 + 正式新品 | 正式推荐信号 |
| 通过 + 季节新品 + 计划上架窗口齐全 | 季节推荐信号 |
| 条件通过 + S 商品计划上架窗口缺失 | 条件推荐信号和补窗口条件，不能输出正式季节推荐信号 |
| 通过 + 本地试点新品 | 局部试点推荐信号，具体试点范围由后续模块确定 |
| 通过 + 探索新品 | 探索推荐信号，仍保留探索身份 |
| 有条件通过 | 条件推荐信号，写明必须解除的条件；不能进入正式试点 |
| 返回重做 | 回到上游重构，不发布当前候选 |
| 拒绝 | 退出新品池，不进入推荐展示 |

算法 09 不替采购决定订购、陈列、促销或具体试点门店。

## 9. 业务最需要看的十类正式结果

算法 09 正式输出十类结果。业务不需要逐张看字段，但要知道每类表分别保存什么：

| 中文用途 | 英文表名 | 一行代表什么 | 业务用来做什么 |
|---|---|---|---|
| 运行批次 | `new_product_gate_run` | 一次 09 运行 | 查本次使用的周期、数据和规则版本 |
| 候选输入快照 | `new_product_candidate_snapshot` | 一个候选在本次运行时的完整输入 | 防止候选后来被静默修改 |
| 当前货盘相似证据 | `candidate_assortment_similarity` | 候选与一个当前商品的相似关系 | 判断公司是否已有同款或高相似品 |
| 历史失败评估 | `candidate_historical_failure` | 候选与一个历史相似商品的经营结局评估；V1 第一版仅作占位或证据不足留痕 | 后续判断是否存在可证实的历史失败风险；当前版不触发历史失败硬拒绝 |
| 法规规则命中 | `candidate_regulation_evidence` | 候选命中的一条法规/质量规则；V1 第一版仅承接算法 07 风险线索或占位 | 后续说明通过、补证、人工复核或硬停依据；当前版不把法规线索改成门禁结论 |
| 毛利压力情景 | `candidate_margin_stress_scenario` | 候选代入一个真实历史经营情景的结果 | 检查不利经营情景下毛利能否守住 |
| 机会证据合成 | `candidate_opportunity_evidence` | 一个候选在一个范围内的机会证据汇总 | 说明需求、价格、购物篮和外部证据是否成立 |
| 单项风险证据 | `candidate_risk_evidence` | 一个候选的一项风险 | 说明风险状态、原因、证据和解除条件 |
| 最终门禁结果 | `new_product_gate_result` | 一个候选在一个正式范围内的最终结论 | 算法 10 和产品默认读取的主结果 |
| 复核审计 | `new_product_gate_review_audit` | 一次人工复核和重算过程 | 保存新旧结果和审计闭环，不是每个候选都要审批 |

最终结果至少要让业务看到：商品名和规格、适用范围、候选资格、门禁结果、机会依据、风险原因、补证条件、下一步处理信号和结果有效时间。

## 10. 人工复核什么时候发生

不是每个候选都需要人工审批。

以下情况才会触发复核或审计：

```text
发现商品主体、分类、规格、当前货盘或历史换码关系的数据错误；
相似关系处于灰区；
算法结果需要依据新增的有效证据重新判断；
业务申请例外审批。
```

算法 09 只定义“需要补什么条件”和“补齐后必须重算”的结果，不在本期定义材料由谁提交、存在哪里、如何审核的产品流程。无论证据从哪里补入，重算必须生成新的运行批次，保留新旧结果和变化原因；也不能直接把 `HARD_STOP` 改成 `PASS` 或删除历史失败证据。

## 11. 四个完整业务例子

以下例子用于业务和开发验收，是模拟数据，不代表生产结果或法律结论。

### 11.1 例子一：PASS，青椒黑椒牛柳丝 200g

```text
算法 04：黑椒牛柳丝是目标画像下的正式锚点；
算法 06：青椒是稳定购物篮配方属性；
算法 07：外部竞品和痛点也支持蔬菜搭配方向；
算法 05：200g、建议售价和成本存在可行交集；
当前货盘：没有青椒黑椒牛柳丝同款；
历史失败：没有达到硬门禁条件的高相似失败商品；
法规和标签：第一版未启用法规确定性规则，算法 07 未传递风险线索；
基准和不利毛利情景：都能守住目标毛利。
```

结果：

```text
门禁结果 = PASS
候选资格 = FORMAL_NEW_PRODUCT
下一步处理信号 = 正式推荐信号
```

### 11.2 例子二：PASS，Omega-3 鲜鸡蛋 12 枚

```text
算法 04：鲜鸡蛋主体需求成立；
算法 05：12 枚规格和建议售价存在价格成本可行交集；
算法 06：鸡蛋和鲜奶只说明早餐场景，不作为 Omega-3 来源；
算法 07：发现 Omega-3 外部趋势和属性；
当前货盘：普通鲜鸡蛋 12 枚，但功能属性有来源，不能只因主体相同就判同款；
算法 07 传递 Omega-3 功能声称风险线索；
V1 第一版未启用法规确定性规则。
```

结果：

```text
门禁结果 = PASS
候选资格 = FORMAL_NEW_PRODUCT
下一步处理信号 = 正式推荐信号
```

它可以被记录为正式机会候选；法规风险线索只做留痕，不单独把结果降成有条件通过。具体材料清单留给后续版本的规则资产。

### 11.3 例子三：RETURN_FOR_REBUILD，香辣鸡腿肉家庭装 500g

```text
算法 05 静态价格成本存在可行交集；
但在真实基准经营情景中，毛利率已经低于公司目标毛利；
需要重新设计规格、价格或商品结构。
```

结果：

```text
门禁结果 = RETURN_FOR_REBUILD
候选资格 = NOT_ELIGIBLE_FOR_NEW_PRODUCT
下一步处理信号 = 返回上游重做
```

算法 09 不直接把 500g 改成 300g，也不直接修改建议售价。重构后必须生成新候选版本，重跑 05、08 和 09。

### 11.4 例子四：REJECT，当前货盘同款盐焗鸡翅 220g

```text
公司当前货盘存在盐焗鸡翅 220g；
可订可售状态有效；
商品编码或正式 SPU 关系确认是同一标准商品。
```

结果：

```text
门禁结果 = REJECT
候选资格 = NOT_ELIGIBLE_FOR_NEW_PRODUCT
原因 = 公司当前货盘已有同款
下一步处理信号 = 退出新品池
```

即使该商品还没有进入目标城市，也属于已有商品的区域引入，不属于新品开发。

## 12. 第一版已确认口径

算法 09 第一版已确认：商品状态和 `S` 商品计划上架窗口由 `dim_product_status` 支撑，并通过算法 08 进入 09。历史退出归因、换码替代、供应策略、法规食安这些后续规则资产不作为本版业务确认阻断，也不让业务逐个候选手工判断。

第一版已经固定的口径是：

| 事项 | 第一版执行方式 |
|---|---|
| 成本来源 | 直接读取 `mart_store_sku_daily_price`，优先使用采购结算价、当天采购价和出库到店含税成本 |
| 折扣依赖 | 使用 19:30 前自然售罄率、19:30 后价格弹性、CRITIC 权重和 P20/P50/P80 分位分层 |
| 当前货盘同款和高相似 | 使用品型、口味、规格、百克标价、工艺五字段相似度，按 0.85 硬门槛和 0.70 灰区门槛执行 |
| 商品状态和计划上架窗口 | 读取算法 08 透传的 `product_status_code`、`seasonality_status`、`season_start`、`season_end`；`SEASON_WINDOW_INCOMPLETE` 可进入 09，但只能形成补窗口条件 |

以下事项第一版不做业务确认，只做降级留痕：

| 后续规则资产 | 第一版怎么处理 |
|---|---|
| 历史退出原因 | 写 `UNKNOWN_EXIT` 或证据不足，不触发历史失败硬拒绝 |
| 真正经营失败 | 不输出 `PERFORMANCE_FAILURE_EXIT` 或 `CONFIRMED_FAILURE` |
| 历史退出中的季节结束归因 | 商品状态可用于避免把 S 状态直接写成失败，但不能替代退出原因、换码、供应或策略归因 |
| 正式换码、SPU 迁移和替代关系 | 仅用商品基础表 SPU 辅助当前货盘判断，不用于历史失败硬拒绝 |
| 供应中断和经营策略调整 | 不做正式退出归因，只保留风险线索 |
| 法规、食品安全、标签和功能声称规则 | 第一版只做留痕，不做法规硬停结论；算法 07 有风险线索时不单独改动当前门禁结果 |

也就是说，第一版可以完整输出 09 的结果表，但这些未启用模块不能写成“已通过”，也不能触发硬拒绝。

### 12.1 业务不需要手工提供的内容

以下由系统或数据开发完成：

```text
候选和历史商品的相似度计算；
历史相似商品清单生成；
机会证据和风险证据汇总；
版本锁定、运行批次、重算和审计；
K-medoids 真实情景选择；
Pareto 同层候选比较；
把已确认的业务规则落成规则表和执行逻辑。
```

后续版本建设规则资产时，业务、商品、质量和法务再补充规则边界，复核重点词和重点小分类，并处理系统无法判断的专业灰区。

### 12.2 开发需要验收或映射、但不需要业务手工提供的数据

| 数据 | 当前状态 | 开发如何处理 |
|---|---|---|
| 门店商品每日可订可售表 | 数据合同已定义为日期 + 门店 + 销售 SKU 粒度，字段包括订购 SKU、是否可售、是否可订和更新时间 | 真实库已完整时直接映射；缺字段或粒度不完整时按合同加工补齐；不能用无销量替代可订可售状态 |
| 门店商品日价格表 | 数据合同已定义；包含仓、商品、采购结算价、当天采购价、出库到店含税成本和成交价 | V1 成本优先直接读取价格表，不单独接 SRM |
| 历史经营、折扣和毛利数据 | 数据合同已定义；实际字段完整性需开发验收 | 用于描述停售前经营表现和毛利压力，不能单独证明退出原因 |
| SPU 归并 | 商品基础表已定义 | 仅用于同一标准商品辅助归并，不替代正式换码或替代关系 |

### 12.3 V1 当前没有、但不能硬猜的数据

```text
正式换码关系；
正式替代关系；
稳定历史退出原因；
完整覆盖所有品类和所有声称的法规知识库内容。
```

这些数据缺失时，算法必须按降级状态输出，不能把缺失数据当成“没有关系”，也不能把历史下架直接当成经营失败。

## 13. 业务验收看什么

业务验收不需要看模型代码，但要用固定案例确认：

```text
同一范围内是否只有一条最终门禁结果；
候选规格、主体和属性是否都能追溯到来源；
公司已有同款是否被拒绝；
外部竞品相似是否没有被误写成内部同款；
季节结束是否没有被当作经营失败；
退出原因未知时是否没有硬拒绝；
Omega-3 等功能声称风险线索是否只留痕，不被写成已通过或待补条件；
静态价格和真实毛利压力情景是否分别判断；
不同小分类是否没有互相排名；
探索候选通过门禁后是否仍保留探索身份；
有条件通过是否只进入条件推荐和待补条件，而不是正式试点；
返回重做和拒绝候选是否不能进入算法 10 推荐展示或后续开发发布流程；
人工复核是否只能补证和触发重算，不能覆盖硬门禁。
```

历史失败模型还必须使用时间外数据验证，检查概率校准和实际损益净收益，不能只用训练集准确率或单一 AUC 判断可以上线。

## 14. 不能做什么

```text
不能生成固定权重机会总分或风险总分；
不能让高机会证据抵消法规、货盘或其他硬门禁；
不能把停止订购直接当作历史失败；
不能把 S 状态季节结束当作失败；
不能把仍在售商品直接标记为成功；
不能因相似灰区直接拒绝新品；
不能把公司已有商品跨区域引入写成新品开发；
不能把外部竞品相似直接写成内部重复；
不能单独计算、展示或重复扣减损耗风险；
不能用历史最差单日冒充正式不利毛利情景；
不能在同一候选 ID 下静默修改商品；
不能由算法 09 修改商品规格、价格或配方；
不能做供应商相关判断或触达；
不能让人工复核直接把 HARD_STOP 改成 PASS；
不能跨叶子小分类生成统一新品机会榜；
不能让 RETURN_FOR_REBUILD 或 REJECT 候选进入算法 10 推荐展示或后续开发发布流程。
```

## 15. 一句话总结

```text
算法 08 先把候选整理成“它到底是什么商品”；
算法 09 再把机会、经营和风险证据放在一起，判断“它现在能不能继续作为新品推进”；
算法 10 最后决定“通过或允许验证的候选中，先推荐哪个、给采购什么开发要求”。
```
