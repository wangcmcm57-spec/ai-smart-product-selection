# 算法05_目标画像商品价格带_业务解读版

更新时间：2026-08-04

业务原始依据：`01_source_docs/business_algorithm_docs/算法卡_05_目标画像商品价格带.md`

## 1. 先用一句话理解

这个算法要判断：

```text
在某个城市算法区域、某个门店等级群、某个品类和某个消费者画像里，
目标消费者真实愿意用什么价格买同类商品；
如果我们准备开发一个候选新品，它的成本、目标毛利和竞对价格能不能支撑这个售价。
```

它不是简单算“均价多少”，也不是直接拍一个“低价/中价/高价”。

它要把三件事放在一起看：

```text
消费者价格接受：历史真实成交价格集中在哪里
经营可行性：这个价格能不能覆盖成本和目标毛利
外部参照：竞对同款或高度相似商品价格是否支持这个方案
```

一个例子：

```text
上海 A 级门店群里，
常规时段型-小家庭-中频-价格非敏感会员，
买 10-12 枚鲜鸡蛋的自然成交价格主要集中在 16.80-18.40 元。

如果候选新品是 Omega-3 鲜鸡蛋 12 枚，
算法 05 会继续判断：
成本做到多少以内才有目标毛利？
17.90 元这个价格是不是落在消费者核心价格带里？
竞对同款是不是也在类似价格区间？
```

## 2. 最终会输出什么

算法 05 正式输出 6 张结果表。

| 表 | 一行代表什么 | 用途 |
|---|---|---|
| `mart_target_profile_price_band` | 一个周期 + 一个范围 + 一个品类 + 一个消费者画像 + 一个可比商品组 + 一个规格段的价格带 | 保存内部消费者自然价、促销价、时段折扣价，以及需求支撑和稳定性 |
| `mart_product_attribute_price_premium` | 一个可比商品组里某个商品属性的价格溢价 | 判断功能、口味、品牌、包装等属性是否能解释更高价格 |
| `mart_target_profile_time_discount_curve` | 一个 19:30 后折扣档的成交和售罄表现 | 解释晚间折扣接受情况，不和自然价格混算 |
| `mart_candidate_product_price_feasibility` | 一个候选商品 + 一个成本估算版本在某个价格带下是否可行 | 输出建议零售价、成本谈判上限、是否需要降本或重构 |
| `mart_price_band_stability_audit` | 一次稳定性重算结果 | 证明价格带不是被某个月、某些门店或少数会员带偏 |
| `mart_competitor_price_validation_result` | 一个候选商品和一个竞对商品的价格验证结果 | 判断竞对同款/高相似价格是否支持或提示风险 |

最重要的是区分两类结果：

```text
内部价格带：
即使还没有候选新品成本，也能先用历史小票算出来。

候选商品可行性：
必须先有候选商品方案和成本估算结果后才能算。
这里的候选商品方案不是来自 Doris 小票，也不是来自毛利损耗表，也不是采购前端手动录入。
它来自系统主动推荐链路中形成的候选商品记录。
```

所以“候选商品成本从哪里进入算法”，用在这里：

```text
进入 mart_candidate_product_price_feasibility，
用于计算全链路成本、最低可行售价、成本谈判上限、建议零售价和开发动作。
```

它对应的关键字段是：

| 英文字段 | 中文字段 | 从哪里来 | 用来干什么 |
|---|---|---|---|
| `candidate_product_id` | 候选商品 ID | 系统候选商品记录 / 候选商品池 | 标识要评估的候选新品 |
| `candidate_spec_version` | 候选规格版本 | 系统候选商品规格记录 | 标识本次规格、净含量、包装、配方版本 |
| `candidate_cost_version` | 候选成本估算版本 | 系统候选成本估算结果 | 标识本次成本估算口径，避免后续成本更新覆盖历史 |
| `main_material_estimated_cost` | 主材料估算成本 | 现有商品成本数据估算 | 估算候选商品主要原料成本 |
| `packaging_estimated_cost` | 包装估算成本 | 包装形态、规格和包装方式估算 | 估算候选商品包装成本 |
| `optional_other_attributable_estimated_cost` | 其他可归因估算成本 | 后续可识别的加工、物流或其他成本 | V1 可为空，有数据后纳入全链路成本 |

V1 已确认：候选商品成本不是直接读取真实报价表，而是先产出候选商品成本估算结果。

估算逻辑：

```text
候选商品主材料成本
-> 从数据库已有商品成本数据中找相同或最接近的主材料成本

候选商品包装成本
-> 按包装形态和规格做智能估算
```

例子：

```text
候选商品 = HPP 鸡胸肉
主材料成本 = 参考现有鸡胸肉成本
包装成本 = 根据候选包装规格估算
```

没有候选成本时，算法 05 仍然可以输出目标画像内部价格带，但不能完整输出：

```text
recommended_retail_price
cost_negotiation_ceiling
required_cost_reduction
development_action
```

这些候选决策字段只能输出 `NOT_APPLICABLE` 或 `SOURCE_MISSING`。

这些英文结果字段的中文含义：

| 英文字段 | 中文字段 | 业务含义 |
|---|---|---|
| `candidate_product_id` | 候选商品 ID | 候选新品的唯一编码，来自系统候选商品记录或候选商品标准化结果，不来自小票，也不是采购前端筛选条件 |
| `candidate_spec_version` | 候选规格版本 | 候选商品本次规格、净含量、包装、配方的版本，例如 HPP 鸡胸肉 200g/袋 |
| `recommended_spec` | 建议规格 | 候选规格展示字段，优先读取候选规格记录中的规格文本；缺规格文本时由净含量、标准单位和包装类型标准化生成，例如 200g/袋、500g/盒、6枚/盒 |
| `candidate_cost_version` | 候选成本估算版本 | 本次主材料成本、包装成本等估算口径的版本 |
| `recommended_retail_price` | 建议零售价 | 在消费者价格带、毛利要求和可执行价格点内选出的建议售卖价格 |
| `cost_negotiation_ceiling` | 成本谈判上限 | 为了达到目标毛利，采购谈判时的最高可接受成本 |
| `required_cost_reduction` | 需降本金额 | 当前估算成本高于成本上限时，需要降低的成本金额 |
| `development_action` | 商品开发动作 | 输出可开发、需降本、谨慎试点、需要重构或不推荐 |

## 3. 它在 AI 选品链路中的位置

```text
算法 01：会员画像
        ↓
算法 02：门店品类等级
        ↓
算法 03：门店群消费者画像贡献
        ↓
算法 04：目标画像 SKU 表现，找到现有锚点商品
        ↓
算法 05：目标画像商品价格带，判断价格和成本是否可行
       ↙                               ↘
算法 06：购物篮关联（并行证据）   算法 07：竞品与外部趋势（外部验证证据）
        ↓                               ↓
算法 08：新品候选标准化与合并
        ↓
算法 09：新品机会证据合成与风险门禁
        ↓
算法 10：新品推荐优先级与开发需求编排
```

算法 05 读取算法 01-04 的正式结果，不重新贴会员画像，不重新给门店评级，不重新判断主力消费者，也不重新寻找锚点 SKU。

它做的是：

```text
对算法 04 找到的同类现有商品和目标画像历史成交，
计算目标消费者可接受价格带；
再把候选新品成本、目标毛利和竞对价格放进去做可行性判断。
```

算法 05 和算法 06、07 的关系：

```text
算法 06：购物篮关联
-> 和算法 05 是并行证据，不是算法 05 的前置条件。
-> 06 主要回答“目标画像买了锚点 SKU 后，还常和什么一起买”，用于生成组合方向或新品搭配方向。

算法 07：竞品与外部趋势
-> 可以作为算法 05 的外部价格验证来源。
-> 如果算法 07 已经输出竞对证据表，05 读取代表竞品 ID、证据类型和相似版本，再 join 外部竞品快照表读取价格；如果 07 尚未完成，05 仍可先输出内部消费者价格带，竞对验证状态标记为缺失。
```

简单理解：

```text
05 负责价格能不能成立。
06 负责搭配/购物篮机会有没有。
07 负责外部竞对和趋势证据。
后面 09/10 会把这些证据合起来做新品候选和推荐优先级。
```

它不做：

```text
不直接决定开发什么商品
不跳过历史差销和当前货盘过滤
不把 19:30 后清货价当新品自然售价
不把竞对标价当成我方消费者一定接受的价格
```

算法 05 的整体计算顺序是：

```text
先算内部价格带
-> 再算候选价格可行性
-> 最后补算竞对价格验证
```

实际运行时，算法 05 分三段：

```text
第一段：离线批量计算内部价格带
每月固定运行，使用最近 3 个完整自然月。
按城市算法区域 + 品类 + 门店群 + 消费者画像 + 可比商品组 + 规格段计算价格带。
这一步不需要候选新品，也不依赖采购前端查询。
输出 mart_target_profile_price_band、属性溢价、时段折扣曲线和稳定性审计。

第二段：对系统候选新品做价格可行性判断
当系统候选商品记录形成后，将 candidate_product_id、candidate_spec_version、candidate_cost_version 和成本估算字段带入算法 05。
算法 05 读取第一段已经沉淀的内部价格带，再叠加候选成本、公司毛利目标和价格点规则。
输出 mart_candidate_product_price_feasibility。

第三段：补算竞对价格验证
算法 07 先输出竞对证据表和代表竞品 ID 列表，再由算法 05 读取 `representative_competitor_ids`、`evidence_metric_type`、`competitor_similarity_version` 和竞品快照价格。
05 先把代表竞品 ID 拆成逐 `competitor_sku_id` 明细，再读取外部价格，映射出 `match_type`、`match_confidence`、`match_evidence_json` 和 `attribute_difference_json`，最后算出 `competitor_price_index` 并输出竞对价格验证结果。
```

采购前端的交互位置是：

```text
采购选择城市、消费者画像、品类、门店群等查询条件；
系统读取已经计算好的价格带、候选商品可行性、风险门禁和推荐优先级结果；
最终展示可推荐商品、建议价、成本上限、降本要求和开发动作。
```

```text
Doris 小票的 store_id 对齐门店编码
Doris 小票的 weight 是销售标准量

```

## 5. 数据周期和版本怎么理解

正式价格带使用最近 3 个数据完整自然月。

例如 2026 年 7 月运行：

```text
price_period_start = 2026-04-01
price_period_end   = 2026-06-30
```

同一批算法 05 结果必须锁定同一套版本：

```text
会员画像版本
门店品类等级版本
消费者贡献版本
SKU 表现版本
商品分类和属性版本
城市算法区域版本
促销/调价口径版本
到货和毛利数据版本
竞对数据版本
价格带算法版本
```

这里有一个容易混淆的点：

```text
如果上游算法版本变化，内部价格带要重算。
如果只是候选商品成本估算版本变化，不改历史消费者价格带，只重算候选商品可行性。
```

原因是：

```text
消费者历史接受价来自内部交易事实；
候选成本只影响“这个候选商品在这个价格带下能不能赚钱”。
```

## 6. 计算范围和结果粒度

算法 05 的比较范围沿用算法 02-04：

```text
CITY：单城市
CITY_CLUSTER：业务配置的城市算法区域
门店群：指定 final_level 或 ALL_RATED
消费者画像：算法 01 的 final_profile
品类：大类 / 中类 / 小类，按任务指定，不混算
```

价格带主表一行代表：

```text
一个周期
+ 一个城市算法区域
+ 一个品类
+ 一个门店群
+ 一个消费者画像
+ 一个可比商品组
+ 一个规格段
+ 一个标准计价单位
```

候选商品可行性表比价格带多三个键：

```text
candidate_product_id
candidate_spec_version
candidate_cost_version
```

这就是为什么“内部价格带”和“候选商品可行性”不能混成一张简单结果。

## 7. 先过滤和对账什么

先只保留正常完成的正向销售：

```text
order_status = 'os.completed'
is_return = 0
usual_amt > 0
weight > 0
```

做目标画像价格带时还要保留有效会员：

```text
is_customer = 1
customer_id 非空
customer_id 不以“6”开头
```

商品必须能完成三类映射：

```text
交易商品编码能对齐商品基础表
商品能归到目标品类
商品能转换为可比标准计价单位
```

实际到货用于防止“卖完了但其实只到了 1 件”的误判：

```text
净到货量 = 门店实际收货量
```

如果：

```text
全日标准销售量 / 实际到货标准量 > 1.10
```

说明可能存在跨日销售、到货缺失或单位错误，标记：

```text
OVERSELL_ABNORMAL
```

这类门店 SKU 日不能进入正式价格带和需求验证，也不能把售罄率强行截断成 100%。

所有有效商品行必须唯一进入下面四类之一：

```text
自然价格流
促销价格流
19:30 及之后时段折扣流
异常 / 排除流
```

对账原则是：

```text
分流前有效目标画像商品行数
= 自然流 + 促销流 + 时段折扣流 + 异常/排除流
```

一条记录不能同时进自然价和促销价。

## 8. 三套价格流怎么理解

算法 05 必须把三套价格分开算。

| 价格流 | 用途 | 不能怎么用 |
|---|---|---|
| 19:30 前非促销自然价格 | 新品自然定价的主要内部依据 | 不能混入促销、会员价或晚间折扣 |
| 19:30 前商品促销价格 | 看促销接受和促销依赖 | 不能替代自然价格带 |
| 19:30 及之后时段折扣价格 | 看晚间折扣接受曲线和深折扣依赖 | 不能拉低新品自然售价 |

标准单位价公式：

```text
standard_unit_price
= line_transaction_amt / sales_standard_qty
```

当前数据合同里：

```text
line_transaction_amt = Doris usual_amt
sales_standard_qty = Doris weight
```

这是一版可落地口径：

```text
transaction_price_source = DORIS_USUAL_AMT_V1
```

如果后续正式促销/调价明细能提供更严格的券前商品成交价，必须用新的价格来源版本重算，不能悄悄覆盖旧口径。

`weight` 在小票里不是单纯“重量”，而是计价数量：

```text
称重商品：weight 表示计价重量
计件商品：weight 表示件数、盒数、袋数、只数等计价数量
```

算法要同时保留两种价格：

```text
每份价：顾客和采购容易理解，比如 17.90 元/12 枚
标准单位价：算法比较用，比如 1.49 元/枚
```

促销/调价的业务原文理想口径是：

```text
原价、商品促销、会员价、时段折扣、价格生效时间都应有正式明细。
```

V1 已确认：一期不接入正式促销活动表，按小票实际折扣做价格流分流。业务接受 `DISCOUNT_PROXY_V1`。

V1 分流字段：

```text
discount_amt > 0：促销或优惠代理
is_hour_promotion = 1：小时促销代理
毛利损耗表促销折扣额、会员折扣额、时段折扣额：日门店 SKU 汇总校验
```

但必须保留：

```text
promotion_identify_method = DISCOUNT_PROXY_V1
pricing_rule_status = DISCOUNT_PROXY_V1_CONFIRMED
```

意思是：一期价格流用真实小票发生的折扣来识别，比单独依赖活动表更贴近实际成交；但仍要打上 V1 口径标记，后续若有更完整的促销/调价明细，可以用新版本重算。

## 9. 可比商品组和规格段怎么来

价格带不能把所有商品混在一起算。

可比商品组的强匹配条件是：

```text
同一小分类
+ 主材料
+ 商品形态
+ 烹饪/加工方式
+ 计量类型
+ 相近规格段
```

V1 已确认：不新增额外可比商品组配置表。

```text
开发按商品基础表 + 业务原文强匹配规则自动生成可比商品组。
小分类维度已确认足够细，作为可比商品组首要边界。
```

开发理解成两步：

```text
第一步：用小分类、主材料、商品形态、烹饪/加工方式、计量类型生成可比商品组。
第二步：在同一个可比商品组内，再用净含量、枚数、件数等生成相近规格段。
```

例子：

```text
200g 即烹牛柳丝
不能和熟食牛肉混在一起算价格带。

按枚鸡蛋
不能和按 kg 散装蛋品直接混算。
```

功能、口味、品牌、包装、保鲜时效默认是“溢价属性”，不一定直接把商品拆成不同组。

规格段不是人工写死。

算法先把净含量取对数：

```text
z_i = ln(net_content_i)
```

再在同一个可比商品组内，用 Jenks+BIC 动态选择 1 到 4 个规格段：

```text
SSE_K = SUM_i w_i * (z_i - mean_cluster(i))^2

n_eff = (SUM_i w_i)^2 / SUM_i(w_i^2)

BIC_K = n_eff * ln(SSE_K / n_eff) + K * ln(n_eff)
```

选择 `BIC_K` 最小的 K。

用人话说：

```text
算法会自己判断这个品类规格是不是天然分成小份、中份、大份，
而不是人为固定 200g 以下、200-500g、500g 以上。
```

## 10. 两套价格分布权重

算法 05 要同时输出两套价格带。

第一套是会员平衡价格带：

```text
同一个会员在周期内总权重 = 1
买得再多，也不能让一个重度会员完全代表全部消费者。
```

公式：

```text
w_member(m,t) = 1 / n_m
```

它回答：

```text
典型目标消费者愿意接受什么价格？
```

第二套是经营成交价格带：

```text
w_operation(i) = sales_standard_qty_i
```

它回答：

```text
门店实际销量主要落在哪个价格？
```

候选新品内部接受价优先看会员平衡价格带，销量和毛利测算要同时看经营成交价格带。

两套价格带不能事后挑一个对自己有利的来证明结论。

## 11. 自然价格带怎么算

算法 05 不固定用 P25-P75，也不只算平均价。

正式自然价格带用加权 KDE，也就是根据历史成交价生成一条“价格密度曲线”：

```text
f_h(p)
= 1 / (h * SUM_i w_i)
  * SUM_i [w_i * K((p-p_i)/h)]
```

这里的业务含义是：

```text
哪些价格附近成交最集中，哪里就是消费者真实接受的价格中心。
```

带宽 `h` 通过加权留一交叉验证自动选择：

```text
h_star = argmax_h SUM_i w_i * ln(f_{-i,h}(p_i))
```

如果价格分布有多个峰：

```text
峰值 = 一个成交价格中心
峰与峰之间的谷值 = 自然价格带边界
```

如果只有一个峰：

```text
算法寻找“覆盖更多成交”和“价格区间变宽”之间的拐点，
这个拐点对应核心价格带。
```

如果有效价格点太少或全部一样：

```text
SINGLE_PRICE_POINT：所有有效成交价格完全相同
DISCRETE_PRICE_DISTRIBUTION：只有少量离散价格点
```

这种情况下不能伪造连续曲线，但仍要输出可解释的离散价格结果和证据状态。

## 12. 19:30 前需求支撑怎么看

价格高不代表消费者真的能接受，还要看这个价格段在 19:30 前有没有真实动销。

业务原文公式：

```text
price_segment_pre1930_sell_through
= SUM(该价格段 19:30 前标准销售量)
  / SUM(对应门店 SKU 日实际到货标准量)
```

字段落地：

```text
分子：由 Doris 小票按 inc_time < 19:30:00、非促销自然价格流计算标准销售量
分母：由 `mart_sku_margin_loss.receipt_qty` 或 `mart_sku_margin_loss.receipt_weight_kg` 生成实际到货标准量
```

注意：

```text
不能先算每个 SKU 日售罄率再简单平均。
必须先汇总销量和到货，再计算整体售罄率。
```

为什么要做收缩？

```text
如果某 SKU 某天只到货 1 件，19:30 前卖掉 1 件，
原始售罄率是 100%，但证据很弱。
```

按件或枚数商品使用 Beta-Binomial 经验贝叶斯，称重或体积类使用分层 Beta 回归。

业务含义是：

```text
到货越少，算法越保守；
到货越充分，结果越接近真实观测。
```

必须同时输出：

```text
valid_store_cnt
valid_store_sku_day_cnt
actual_arrival_exposure
local_evidence_weight
sell_through_interval
```

## 13. 属性溢价怎么理解

属性溢价回答：

```text
在规格、城市、门店和时间尽量可比时，
某个功能、口味、品牌或包装属性
对应多少稳定价格差异？
```

它不能用两个商品均价差替代。

业务原文模型：

```text
ln(standard_unit_price_i)
= alpha
+ beta_spec * ln(net_content_i)
+ SUM_a beta_a * attribute_{i,a}
+ city_effect
+ store_group_effect
+ week_effect
+ error_i
```

如果 `Omega-3` 的系数是 0.116，则：

```text
premium_omega3 = exp(0.116)-1 = 12.3%
```

这说明：

```text
在可比条件下，Omega-3 属性对应约 12.3% 的价格差异。
```

但它不是因果证明。

如果样本少，要做分层收缩：

```text
beta_shrunk
= lambda * beta_raw
  + (1-lambda) * beta_parent

lambda = tau^2 / (tau^2 + SE^2)
```

业务含义是：

```text
本地样本稳定，就更多相信本地；
本地样本少或波动大，就适度参考上一级稳定水平。
```

属性缺失时不能用众数乱填。

如果所有 Omega-3 商品都刚好是同一品牌、同一包装，算法无法拆出：

```text
Omega-3 独立溢价
品牌独立溢价
包装独立溢价
```

只能输出：

```text
Omega-3 + 品牌 + 包装组合溢价
```

并标记不可拆分。

## 14. 毛利、成本和建议价怎么结合

目标毛利不是拍脑袋固定。

先看同城市群、同可比商品组、同门店群的历史商品：

```text
sku_full_chain_margin_rate
= SUM(full_link_margin_amt) / SUM(sales_amt)
```

`full_link_margin_amt` 和 `sales_amt` 来自 `mart_sku_margin_loss`。算法使用汇总毛利额和销售额，不对每日毛利率简单平均，也不重复扣损耗。

小规模 SKU 的毛利要收缩：

```text
margin_shrunk_sku
= lambda_sku * margin_raw_sku
  + (1-lambda_sku) * margin_group
```

再对收缩后的毛利率做销售额加权 KDE：

```text
稳定正毛利健康群与低毛利群之间的自然谷值
-> data_margin_floor

稳定正毛利健康群的密度峰值
-> data_margin_target
```

如果公司有硬性毛利要求：

```text
final_margin_floor
= max(data_margin_floor, company_margin_floor)

final_margin_target
= max(data_margin_target, company_margin_target)
```

V1 已确认公司毛利和价格点规则：

| 配置 | V1 口径 |
|---|---|
| 公司毛利底线和目标毛利 | 原始来源为 B1 补充资料；开发运行读取标准配置表 `dim_company_margin_target_config` |
| 价格点上下限 | 由算法 05 算出的消费者核心价格带或扩展价格带决定，不再要求业务额外列上下限 |
| 价格点步长 | 从标准规则表 `dim_price_point_rule_config.price_step_amt` 读取，V1 默认每 1 元一个价格点 |
| 价格尾数 | 从标准规则表 `dim_price_point_rule_config.price_tail` 按品类和单位读取，算法只能在这些尾数生成的价格点中选建议价 |
| 生效日期 | 按配置版本维护；未提供失效日期时，视为当前有效配置 |

V1 价格尾数规则：

| 品类 | 单位 | 价格尾数 |
|---|---|---|
| 蔬菜 | kg | 0.98 |
| 水果 | kg | 0.98 |
| 猪肉 | kg | 0.98 |
| 肉禽蛋 | kg | 0.90 |
| 冷藏加工 | 份/个 | 0.90 |
| 预制菜 | 份/个 | 0.90 |

价格点生成方式：

```text
可执行价格点 = 整数元 + 品类价格尾数
价格点步长 = 1 元
只保留落在消费者价格带上下限内的价格点
```

例子：

```text
蔬菜价格带 8.50～11.20 元/kg，尾数 0.98
可执行价格点 = 8.98、9.98、10.98

预制菜价格带 15.00～19.00 元/份，尾数 0.90
可执行价格点 = 15.90、16.90、17.90、18.90
```

候选商品成本进入算法的位置在这里：

```text
full_chain_unit_cost
= main_material_estimated_cost
+ packaging_estimated_cost
+ optional_other_attributable_estimated_cost
```

V1 主要使用：

```text
main_material_estimated_cost：主材料估算成本
packaging_estimated_cost：包装估算成本
```

如果后续能稳定拆出加工、物流或其他可归因成本，可以放入 `optional_other_attributable_estimated_cost`，并生成新的成本估算版本。

然后算候选商品满足毛利需要的最低售价：

```text
minimum_floor_price
= full_chain_unit_cost / (1-final_margin_floor)

minimum_target_price
= full_chain_unit_cost / (1-final_margin_target)
```

再和消费者价格带求交集：

```text
目标毛利最低售价
与消费者核心价格带有交集
-> 可以进入开发

只和扩展价格带有交集
-> 谨慎试点

连毛利底线都无法进入扩展价格带
-> 需要降本、改规格、改包装或不推荐
```

反向成本上限：

```text
cost_ceiling_at_price(P, G) = P * (1-G)
```

业务含义是：

```text
如果我们想卖 17.90 元，并要求 25% 目标毛利，
那全链路成本最多只能是 17.90 * 75% = 13.43 元。
```

这就是采购谈判可以拿到的成本上限。

## 15. 竞对价格怎么用

竞对价格是外部验证层，不是内部价格带的替代品。

竞对可比条件：

```text
同一小分类
+ 主材料
+ 商品形态
+ 加工/烹饪方式
+ 功能属性
+ 相近规格段
+ 标准计价单位
+ 同城市或相似城市群
+ 相近渠道类型
```

匹配结果：

```text
EXACT：同款
HIGHLY_SIMILAR：高度相似
CATEGORY_REFERENCE：仅同品类参考
NO_MATCH：无可比商品
```

`CATEGORY_REFERENCE` 不能进入正式竞对等价价格带。

竞对价格也要分流：

```text
日常标价
会员价
促销价
时段折扣价
```

我方价格指数：

```text
competitor_price_index
= our_recommended_standard_price
  / competitor_equivalent_price_center
```

如果我方建议价高于竞对，必须有可识别属性溢价支撑，否则输出：

```text
COMPETITOR_PRICE_RISK
```

一个关键边界：

```text
竞对卖得更贵
不等于我方目标消费者一定接受更高价格。
```

内部核心价格带上限不能因为竞对高价自动上调。

## 16. 19:30 后折扣接受曲线怎么用

19:30 后折扣曲线单独输出，不进入自然价格带。

实际折扣率：

```text
actual_discount_ratio
= stage_actual_unit_price
  / same_sku_day_pre1930_natural_unit_price
```

如果当天 19:30 前没有自然成交，就用当天生效原价；如果两者都没有，该 SKU 日不计算折扣率。

每个折扣档输出：

```text
stage_member_cnt
stage_ticket_cnt
stage_sales_qty
stage_sales_amt
stage_sales_to_arrival
cumulative_sell_through
```

它只能叫：

```text
时段折扣接受曲线
```

除非存在可识别的跨门店、跨日期折扣差异，否则不能叫“价格弹性”，也不能说“降价导致销量增长”。

## 17. 样本不足和稳定性怎么处理

业务原文不使用固定人数门槛。

不是：

```text
少于 100 张小票就回退
```

而是根据本地估计误差、价格波动和有效权重自动决定借数程度。

分层借数顺序：

```text
1. 当前城市群 + 当前画像 + 当前可比组 + 当前规格段
2. 当前城市群 + 当前画像 + 当前可比组，用净含量模型校正规格
3. 当前城市群 + 全部有效画像 + 当前可比组，保留画像偏移项
4. 当前城市群 + 当前小分类 + 相同主材料、形态和加工方式
5. 预先配置的相似城市群 + 当前可比组 + 当前规格段
6. 更大区域数据只作统计先验
```

即使借了上一级数据，结果仍然属于当前城市群和目标画像，不能改成上级范围的结论。

必须输出：

```text
local_evidence_weight
parent_evidence_weight
borrowed_scope_type
borrowed_scope_id
evidence_status
```

稳定性验证包括：

```text
删除月份重算
门店分块 Bootstrap
会员分块 Bootstrap
```

稳定性指标：

```text
density_overlap
interval_jaccard
normalized_center_shift
```

最终稳定等级用 Jenks+BIC 动态分成：

```text
STABLE
NEEDS_ATTENTION
UNSTABLE
```

## 18. 结果状态怎么理解

算法 05 不能只输出一个分数，必须保存状态。

数据证据状态：

| 状态 | 含义 |
|---|---|
| `LOCAL_OBSERVED` | 当前城市群、当前画像、当前可比组有本地实证 |
| `HIERARCHICAL_ESTIMATE` | 本地样本不足，使用分层借数 |
| `EXTERNAL_REFERENCE_ONLY` | 只有外部参考，没有内部消费者成交证据 |
| `DATA_ABNORMAL` | 数据异常，不能发布正式结论 |

价格和毛利状态：

| 状态 | 含义 |
|---|---|
| `TARGET_MARGIN_IN_CORE` | 目标毛利最低售价落在核心价格带 |
| `TARGET_MARGIN_IN_EXTENDED` | 目标毛利最低售价只落在扩展价格带 |
| `FLOOR_MARGIN_IN_CORE` | 毛利底线可进核心价格带，但目标毛利不一定 |
| `FLOOR_MARGIN_IN_EXTENDED` | 毛利底线只进扩展价格带 |
| `NO_FLOOR_INTERSECTION` | 毛利底线也进不了扩展价格带 |

商品开发动作：

| 状态 | 含义 |
|---|---|
| `READY_FOR_DEVELOPMENT` | 核心价格带和目标毛利有交集，证据稳定 |
| `COST_NEGOTIATION_REQUIRED` | 需要降本才能进入更好价格区间 |
| `CAUTIOUS_PILOT` | 只在扩展价格带可行，或证据依赖借数/稳定性需关注 |
| `REDESIGN_REQUIRED` | 需要改规格、包装、配方或成本结构 |
| `NOT_RECOMMENDED` | 关键价格、规格或成本来源缺失，或重构后仍无法形成消费者价格带与毛利底线交集 |

竞对验证状态：

```text
COMPETITOR_VALIDATED
COMPETITOR_PRICE_ADVANTAGE
COMPETITOR_PREMIUM_SUPPORTED
COMPETITOR_PRICE_RISK
NO_COMPARABLE_COMPETITOR
COMPETITOR_DATA_STALE_OR_INVALID
```

## 19. 开发实际要怎么做

开发可以有临时表和过程表，但正式交付以第 2 节的 6 张表为准。

开发顺序可以理解为：

```text
1. 锁定算法 01-04 和基础数据版本。
2. 过滤有效目标画像小票，关联门店、商品、城市算法区域和上游结果。
3. 把商品行分成自然价、促销价、19:30 后时段折扣价、异常排除四类。
4. 生成可比商品组和规格段。
5. 分别用会员平衡权重和经营成交权重计算价格分布。
6. 用 KDE 找核心价格带、扩展价格带和价格中心。
7. 用 19:30 前售罄和到货暴露验证需求支撑。
8. 用特征价格模型计算属性溢价。
9. 用历史全链路毛利动态生成毛利底线和目标。
10. 如果有候选成本，计算成本交集、建议价和开发动作。
11. 如果有竞对结果，计算竞对等价价格和价格指数。
12. 做删除月份、门店分块、会员分块稳定性验证。
13. 写入正式结果表，并输出异常状态和可追溯版本。
```

## 20. 业务验收看什么

数据口径验收：

```text
自然价、促销价、19:30 后折扣价没有混算
19:30 整点成交进入第一档折扣
单位转换可追溯
超卖异常没有进入正式价格带
竞对日常价、会员价、促销价、时段价没有混算
```

公式复算：

```text
标准单位价
会员平衡权重
经营成交权重
Jenks+BIC 规格段
KDE 带宽和峰谷
19:30 前价格段售罄率
属性溢价
毛利底线和目标
成本交集和谈判上限
竞对等价价格和价格指数
```

边界样例要覆盖：

```text
目标毛利与核心价格带有交集
目标毛利只与扩展价格带有交集
毛利底线与扩展价格带无交集
属性缺失

没有可比竞对商品

19:30 整点成交
超卖和单位转换异常
```

业务原文提供的三个演示案例可作为验收复算样例：

| 案例 | 验收重点 |
|---|---|
| 案例 A：Omega-3 鲜鸡蛋 12 枚可进入开发 | 目标毛利与核心价格带有交集，建议价 17.90 元，状态 `READY_FOR_DEVELOPMENT` |
| 案例 B：成本与价格带无交集 | 毛利底线售价超过扩展价格上限，状态 `NO_FLOOR_INTERSECTION` / `REDESIGN_REQUIRED` |
| 案例 C：本地证据少且属性不可拆分 | 输出 `HIERARCHICAL_ESTIMATE`，只能输出组合溢价，不能伪造单项溢价 |

## 21. 现在还需要确认什么

这里只保留会影响算法 05 正式落地的红线。公司毛利底线、目标毛利和 V1 价格点生成规则已经确认，不再作为业务待确认红线。

| 优先级 | 确认项 | 需要谁确认 | 为什么重要 |
|---|---|---|---|
| P2 | 竞对匹配结果、竞对价格快照、图片和来源链接能否按外部数据合同稳定入库 | 数据开发 / 外部数据负责人 | 影响竞对验证状态，但不覆盖内部消费者价格带 |
| P2 | 数据开发是否能实现 KDE、Jenks+BIC、经验贝叶斯、特征价格模型、分层收缩和稳定性重采样 | 数据开发 | 这些是业务原文正式算法，不是普通 SQL 均值分位数能替代 |

## 22. 不要做什么

算法 05 最容易被误做，以下都不能做：

```text
不能将自然、促销和 19:30 后折扣价混成一个价格带
不能遗漏 19:30 整点生效价格和成交
不能用固定 P25-P75 代替真实多峰价格分布
不能将超低清货价当成新品自然定价
不能把一件到货、一件售出的 100% 直接当成强需求
不能使用库存口径替代实际到货
不能将超卖比率截断为 100%
不能把两个商品的简单均价差全部解释为功能属性溢价
不能用众数强行填补未知包装或其他属性
不能在属性完全绑定时伪造独立属性系数
不能在商品名称中加入没有系数或未标记的价值属性
不能用更大区域价格直接替代城市群正式结果
不能在成本与扩展价格带无交集时强行推荐
不能因竞对售价更高就越过内部消费者价格上限
不能在竞对无销量时声称竞对消费者接受某价格
不能用普通品类竞对商品冒充同款或高度相似品
不能将 19:30 后折扣接受曲线直接解释为价格弹性
不能让价格算法跳过历史差销和当前货盘相似品硬过滤
```

## 23. 一句话总结

算法 05 的核心不是“给商品定一个价格”，而是先用目标消费者真实成交算出可接受价格带，再用候选成本、目标毛利和竞对价格判断：这个新品价格方案到底是可开发、需降本、谨慎试点、需要重构，还是不推荐。
