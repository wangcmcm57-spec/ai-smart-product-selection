# 算法08_新品候选标准化与合并_业务解读版

更新时间：2026-08-18

业务原始依据：`01_source_docs/business_algorithm_docs/算法08_新品候选标准化与合并_业务原文.md`

## 1. 先用一句话理解

算法 08 做的是：

```text
把算法 06、07 找到的新品候选，整理成系统里唯一、标准、可追溯的新品候选档案。
```

它解决的是“这个候选到底是谁”，不是“这个候选最终能不能开发”。

一个最简单的例子：

```text
算法 06 从真实购物篮里发现：
买黑椒牛柳丝的人，经常一起买青椒。

算法 07 从外部竞品或趋势里发现：
市场上也有类似青椒黑椒牛柳丝的商品或方向。

算法 08 要做的是：
判断这两条线索说的是不是同一个新品候选；
如果是同一个，就合并成一个标准候选；
如果规格不同，就拆成不同候选；
如果说不清小分类、主体、属性或规格，就先记异常，不进入正式门禁。
```

所以算法 08 可以理解为新品候选进入风险门禁前的“登记处”和“标准化中心”。

## 2. 08 在整条链路里做什么

当前正式链路是：

```text
算法 01：会员画像
        ↓
算法 02：门店品类等级
        ↓
算法 03：门店群消费者画像贡献
        ↓
算法 04：目标画像 SKU 表现，找到主体需求和锚点商品
        ↓
算法 05：目标画像商品价格带，先提供价格带和规格上下文；候选出现后补算价格、成本和毛利可行性
        ↓
算法 06：购物篮新品关联，产生内部新品候选
算法 07：外部竞品与趋势，产生外部新品候选或外部验证
        ↓
算法 08：新品候选标准化与合并
        ↓
算法 09：新品机会证据合成与风险门禁
        ↓
算法 10：新品推荐优先级与开发需求编排
```

算法 08 的上游是算法 04、05、06、07。

算法 08 的下游是算法 09。

算法 08 不重新计算上游结果。

```text
不重新算门店等级；
不重新算消费者画像贡献；
不重新找 SKU 锚点；
不重新算价格带；
不重新找购物篮关联；
不重新抓外部趋势。
```

它只读取上游已经算好的结果，把这些结果拼成一个标准候选档案。

这里要特别注意算法 05 的位置：

```text
没有具体候选前，05 先算目标画像可接受的价格带和规格范围；
06、07 形成具象新品候选后，05 再为这个候选补算建议规格、建议售价、成本和毛利可行性；
08 读取的是这份候选价格可行性结果。
```

### 2.1 08 什么时候运行

算法 08 的正式结果按月生成，不在采购查询时实时重算。

正式运行节奏是：

```text
算法 02、03、04、05、06、07 的月度正式版本冻结
        ↓
算法 08 读取同一批正式版本，生成标准候选和范围候选
        ↓
算法 09 读取 08 的范围候选，做风险门禁
```

也就是说，08 是算法 09 门禁前的一道标准化工序。

它不是每天看到一个外部趋势就直接生成正式推荐。

算法 07 可以更高频地产生日采集、周预警或外部趋势预览，但这些先属于预览信号。

预览信号的处理口径是：

```text
可以进入观察池、预览结果或异常诊断；
不能覆盖月度正式候选；
不能直接进入算法 09 正式门禁；
不能被算法 10 当成正式推荐候选。
```

只有当外部信号被纳入算法 07 月度正式结果，并且和算法 02-06 的正式范围、主体、规格、价格和证据对齐后，才会进入 08 的正式候选注册。

如果上游 02-07 任一正式版本变化，或者候选属性字典、商品命名规则、特殊必填规则、单位换算配置、商品状态版本变化，08 都要生成新的运行批次。

旧结果不能被静默覆盖，原因是后面要能追溯：

```text
当时用的是哪一版上游结果；
当时用的是哪一版规则资产；
当时为什么合并、拆分或进入异常；
当时为什么能进 09，或为什么不能进 09。
```

## 3. 为什么必须有算法 08

没有算法 08，后面会出现四类问题。

### 3.1 同一个候选会重复

```text
算法 06 输出：青椒黑椒牛柳丝 200g
算法 07 输出：青椒黑椒牛柳丝 200g
```

如果不合并，系统可能把它当成两个新品机会。

算法 08 要把它合并成一个标准候选，同时保留两条来源证据。

### 3.2 同方向不同规格会被误合并

```text
青椒黑椒牛柳丝 200g
青椒黑椒牛柳丝 250g
```

它们方向一样，但开发规格不同，不能合并成一个商品。

算法 08 要让它们共享同一个候选方向，但生成两个标准候选。

### 3.3 外部热词可能被错误写进商品名

```text
外部出现“健康早餐趋势”
```

这只能说明场景或趋势，不能直接生成“健康早餐鲜鸡蛋”这种商品名。

算法 08 要检查：每个进入商品名的词，是否真的有标准属性和证据来源。

### 3.4 同一商品在不同经营范围下结果不同

```text
青椒黑椒牛柳丝 200g
```

在上海 A 级门店可能 19.9 元可行，在上海 B 级门店可能 17.9 元才可行。

所以后续算法 09 不能只看商品本身，还要看：

```text
商品 + 城市/城市群 + 门店等级 + 消费者画像 + 小分类 + 价格方案
```

算法 08 要把这个“具体范围下的候选结果”单独生成出来。

## 4. 最终会输出什么

算法 08 正式输出 8 张表。

业务先重点理解两张。

| 中文表名 | 英文表名 | 一行代表什么 | 主要用途 |
|---|---|---|---|
| 标准新品候选注册表 | `new_product_standard_candidate_registry` | 一个具体新品商品实体 | 回答“这个候选到底是什么商品” |
| 新品候选范围结果表 | `mart_new_product_candidate_scope` | 一个标准候选在一个经营范围和价格方案下的结果 | 作为算法 09 风险门禁的直接输入 |

举例：

```text
标准新品候选：
青椒黑椒牛柳丝 200g。

新品候选范围结果：
青椒黑椒牛柳丝 200g
+ 上海
+ A 级门店
+ 年轻家庭画像
+ 牛肉制品小分类
+ 19.9 元价格方案
```

完整 8 张表如下：

| 中文表名 | 英文表名 | 一行代表什么 | 用途 |
|---|---|---|---|
| 候选注册运行批次表 | `new_product_candidate_registry_run` | 一次算法 08 运行 | 记录周期、版本、运行状态和结果数量 |
| 候选来源快照表 | `new_product_candidate_source_snapshot` | 一条上游候选来源 | 保存 06、07 原始候选，异常也保留 |
| 候选属性血缘表 | `new_product_candidate_attribute_lineage` | 一个候选的一个属性来源 | 证明商品名里的词从哪里来 |
| 新品候选方向表 | `mart_new_product_candidate_direction` | 一个新品方向 | 保存“青椒黑椒牛柳丝方向”这类方向 |
| 标准新品候选注册表 | `new_product_standard_candidate_registry` | 一个标准候选商品实体 | 保存具体商品身份 |
| 新品候选范围结果表 | `mart_new_product_candidate_scope` | 一个标准候选在一个范围和价格方案下的结果 | 交给算法 09 |
| 候选合并审计表 | `new_product_candidate_merge_audit` | 一次合并过程 | 证明为什么合并 |
| 候选注册异常表 | `new_product_candidate_registration_exception` | 一条注册异常 | 保存为什么不能进入正式候选 |

## 5. 候选从哪里来

算法 08 自己不发明新品候选。

它的候选主要来自两类。

### 5.1 内部候选来自算法 06

算法 06 从真实小票购物篮里找机会。

它可能输出：

```text
在上海 A 级门店、年轻家庭画像、牛肉制品小分类下，
黑椒牛柳丝这个锚点商品和青椒存在稳定关联，
青椒可以作为牛肉制品新品的配菜属性。
```

这类候选代表：

```text
内部真实消费数据支持这个新品方向。
```

### 5.2 外部候选来自算法 07

算法 07 从外部竞品、趋势、价格、图片、风险线索里找机会。

它可能输出：

```text
外部市场出现 Omega-3 鲜鸡蛋 12枚；
该候选可以映射到内部鲜鸡蛋小分类；
Omega-3 是功能属性；
外部有竞品、价格或趋势证据。
```

这类候选代表：

```text
外部市场或竞品趋势支持这个新品方向。
```

## 6. 候选怎么关联算法 02、03、04、05

算法 08 不是拿一个新品候选回到历史数据里重新计算 02、03、04、05。

正确流程是：

```text
算法 06、07 输出候选时，候选结果里已经要带出范围、主体、属性和证据。

算法 08 读取这些字段，再去核对并拼接算法 02、03、04、05 的正式结果。
```

可以理解成给候选补齐“上下文身份证”。

| 要补齐什么 | 从哪个算法来 | 08 怎么用 |
|---|---|---|
| 城市/城市群、门店等级、小分类范围 | 算法 02 | 确定候选属于哪个经营范围 |
| 消费者画像 | 算法 03 | 确定这个候选服务哪类目标消费者 |
| 主体商品和锚点商品 | 算法 04 | 固定候选主体，防止关联商品或外部热词替换主体 |
| 明确规格、建议售价、成本和毛利状态 | 算法 05 | 判断候选是否具备进入算法 09 的价格和毛利上下文 |
| 内部候选属性和购物篮证据 | 算法 06 | 说明内部为什么会产生这个候选 |
| 外部候选属性和外部证据 | 算法 07 | 说明外部为什么支持或发现这个候选 |

在当前算法卡设计里，算法 06、07 的候选结果表已经包含这些关键信息。

```text
算法 06 至少提供：
当前范围、目标小分类、消费者画像、锚点商品、候选属性、候选规格、购物篮规则证据和候选状态。

算法 07 至少提供：
当前范围、内部小分类映射、标准候选、候选属性、外部证据、内部适配证据、建议规格和价格上下文。
```

举例：

```text
算法 06 给出候选：
青椒黑椒牛柳丝。

它同时要带出：
上海 A 级门店；
年轻家庭画像；
牛肉制品小分类；
黑椒牛柳丝锚点；
青椒这个配菜属性；
购物篮规则证据。
```

算法 08 再去核对：

```text
算法 02 是否有上海 A 级门店的牛肉制品范围；
算法 03 是否有年轻家庭画像贡献；
算法 04 是否有黑椒牛柳丝这个主体锚点；
算法 05 是否给出了该候选的规格、价格、成本和毛利结果。
```

如果都能对上，候选才可能进入正式范围结果。

如果 05 没有价格结果，候选身份可以保留，但不能进入算法 09 正式门禁。

## 7. 08 具体怎么做

算法 08 可以按 8 步理解。

### 第一步：先保存所有来源

算法 06、07 的候选先全部进入来源快照。

即使后面不能注册，也要保留。

原因是：

```text
以后业务问“这个候选为什么没进推荐”，系统能查到原因。
```

### 第二步：补齐经营上下文

08 给每个候选补齐：

```text
城市/城市群；
门店等级；
消费者画像；
小分类；
主体锚点；
规格和价格结果；
内部证据；
外部证据。
```

这一步的目的不是重新算指标，而是确认候选能不能被放到一个明确的经营范围里。

### 第三步：拆成标准属性

候选不能只是一串商品名。

08 要把候选拆成结构化属性。

例如：

```text
青椒黑椒牛柳丝 200g
```

拆成：

| 属性维度 | 内容 | 来源 |
|---|---|---|
| 小分类 | 牛肉制品 | 算法 04/商品基础表/算法 06 或 07 映射 |
| 主体商品 | 牛柳丝 | 算法 04 锚点主体 |
| 配料 | 青椒 | 算法 06 购物篮属性或算法 07 外部属性 |
| 口味 | 黑椒 | 算法 04 锚点或上游属性 |
| 商品形态 | 即烹菜肴/牛柳丝形态 | 算法 04 或商品基础表 |
| 规格 | 200g | 算法 05 |

这一步不是让开发凭感觉拆。

开发版算法卡要把拆分规则落成规则表和处理逻辑。

### 第四步：检查主体和小分类不能跑偏

08 要保证候选还在目标小分类里。

例子：

```text
鲜鸡蛋小分类下，可以形成 Omega-3 鲜鸡蛋；
不能因为出现早餐场景，就生成鲜牛奶新品。
```

这里的关键原则是：

```text
主体商品优先来自算法 04 锚点；
06、07 只能提供允许的创新属性；
06、07 不能替换主体商品。
```

### 第五步：标准化规格

08 使用算法 05 的明确规格。

例如：

```text
0.2kg -> 200g
12枚 -> 12枚
1盒 -> 1盒
```

但 08 不能自己猜规格。

如果只有：

```text
200g 到 250g 规格段
```

没有明确推荐规格点，那么不能生成：

```text
225g
```

只能保留候选方向，等待 05 或业务规则补齐明确规格。

### 第六步：生成标准候选名称

08 用属性和商品命名规则生成名称。

允许：

```text
青椒黑椒牛柳丝 200g
Omega-3 鲜鸡蛋 12枚
```

不允许：

```text
健康新鲜鸡蛋
快手场景菜
网红趋势款
```

原因是这些词没有明确商品身份，不能进入标准候选。

### 第七步：生成候选 ID

08 自动生成 4 类 ID。

这些 ID 不是业务手工输入，是系统根据标准化后的候选内容生成。

| 中文 ID | 英文字段 | 回答的问题 | 示例 |
|---|---|---|---|
| 候选家族 ID | `candidate_family_id` | 这是一类什么商品家族 | 牛肉制品 + 牛柳丝 + 即烹菜肴 |
| 候选方向 ID | `candidate_direction_id` | 这个家族下是什么新品方向 | 青椒 + 黑椒 + 牛柳丝方向 |
| 标准候选商品 ID | `standard_candidate_id` | 这到底是哪一个具体商品 | 青椒黑椒牛柳丝 200g |
| 范围候选结果 ID | `candidate_scope_result_id` | 这个商品在某个范围和价格方案下是否成立 | 青椒黑椒牛柳丝 200g + 上海 + A 级门店 + 年轻家庭画像 + 19.9 元方案 |

### 第八步：合并、拆分、留异常

08 最后做三件事：

```text
同一个候选合并；
不同候选拆开；
缺数据候选留痕。
```

判断方式如下：

| 情况 | 08 怎么处理 |
|---|---|
| 06 和 07 标准化后是同一个候选 | 合并成一个标准候选，保留全部证据 |
| 方向一样但规格不同 | 拆成两个标准候选 |
| 小分类不同 | 不合并，记录分类冲突 |
| 主体不同 | 不合并，记录主体冲突 |
| 属性没有标准代码 | 不进入正式候选名称，记录属性缺失 |
| 规格缺失 | 只保留方向，不生成正式标准候选 |
| 价格结果缺失 | 候选身份可保留，但不能进入算法 09 |

## 8. 标准化规则资产是什么

08 要能稳定判断“是不是同一个候选”，必须先有一套标准化规则资产。

这些规则资产不是让业务一次性手工填完整，也不是让开发凭感觉写。

V1 落地口径是：

```text
已确认接受系统自动生成初版；
系统根据商品基础表、算法 06 输出、算法 07 输出、B3 标准规则和已确认的业务边界生成；
业务、商品、质量只复核高频词、会进入新品名称的词、风险词和重点小分类命名规则。
```

这些规则资产的具体字段、生成规则和异常处理，放在开发版算法卡里定义。

### 8.1 属性字典

属性字典用于回答：

```text
一个词在商品开发里到底是什么属性？
```

例如：

| 词 | 属性维度 | 是否能进入候选名称 |
|---|---|---|
| 鲜鸡蛋 | 主体商品 | 可以 |
| Omega-3 | 功能属性 | 小分类允许时可以 |
| 黑椒 | 口味 | 小分类允许时可以 |
| 青椒 | 配料 | 小分类允许时可以 |
| 健康 | 泛营销词 | 不能直接进入正式候选名称 |

V1 怎么生成：

```text
主体商品、小分类、商品形态：优先来自算法 04 锚点和商品基础表；
配料、口味、功能、工艺：来自算法 06、07 已识别的结构化属性；
无法稳定识别的词：进入观察或异常，不进入正式候选名称。
```

开发版算法卡会把它落成候选商品属性字典。

### 8.2 属性别名和同义词

属性别名和同义词用于回答：

```text
不同写法是不是同一个属性？
```

例如：

```text
Omega-3
欧米伽3
オメガ3
오메가3
```

都应该映射为同一个功能属性。

V1 怎么生成：

```text
主要由算法 07 的外部属性映射生成；
高频词、会进入新品名称的词、风险词需要业务/商品/质量复核；
没有稳定映射的外部词不能进入正式候选名称。
```

开发版算法卡会把它写进候选商品属性字典的别名字段，不单独落一张同义词表。

### 8.3 单位换算规则

单位换算规则用于回答：

```text
不同来源的规格怎么统一？
```

例如：

| 来源规格 | 标准规格 | 说明 |
|---|---|---|
| 0.2kg | 200g | 重量类统一到 g |
| 750ml | 750ml | 体积类统一到 ml |
| 12枚 | 12枚 | 计数类按商品规格展示 |
| 1盒 | 1盒 | 计件商品按商品基础表规格展示 |

V1 怎么生成：

```text
重量：kg、公斤、千克、g、克统一换算；
体积：L、升、ml、毫升统一换算；
计数：枚、个、盒、袋、份、只等保留业务展示单位；
无法识别的单位写 UNKNOWN，不强行换算。
```

开发版算法卡会把它固化为算法 08 的单位换算配置版本。

### 8.4 商品命名规则

商品命名规则用于回答：

```text
一个小分类下，商品名应该按什么顺序拼？
```

它不是营销文案模板。

例如牛肉制品：

```text
配料 + 口味 + 主体商品 + 规格
= 青椒黑椒牛柳丝 200g
```

例如鲜鸡蛋：

```text
功能属性 + 主体商品 + 规格
= Omega-3 鲜鸡蛋 12枚
```

V1 怎么生成：

```text
系统先读取商品基础表中同小分类已有商品名称；
识别同小分类常见命名顺序；
结合算法 06、07 输出的候选属性；
生成或读取商品命名规则初版；
重点小分类由业务/商品抽样复核。
```

开发版算法卡会读取 `dim_product_naming_rule`，特殊商品必填属性读取 `dim_special_product_required_attribute_rule`。

### 8.5 商品状态表

商品状态用于回答：

```text
这个候选关联到的商品，在对应区域是全年品、试卖品、季节品、淘汰品还是备选品？
```

商品状态不再作为规则 Excel 让业务手工维护。当前由数据开发从 SAP POP 平台落 `dim_product_status`。

08 的处理口径是：

| 商品状态 | 08 怎么写 |
|---|---|
| `A` 全年品 | `seasonality_status = YEAR_ROUND`，不带计划上架日期 |
| `S` 季节品且起止日期齐全 | `seasonality_status = SEASONAL`，`seasonal_status = S`，读取计划上架开始/结束日期 |
| `S` 季节品但起止日期缺失 | `seasonality_status = SEASON_WINDOW_INCOMPLETE`，日期缺失字段为空；如果其他核心条件齐全，仍可带着缺失状态进入 09 |
| `O`、`D`、`B` | 透传商品状态，不在 08 做风险拦截，交给 09 判断 |
| 没有关联到商品状态 | 写 `UNKNOWN`，不能按商品名或销量猜 |

## 9. “版本”是什么意思

08 里说的版本，不是让业务每次手工填。

版本是系统记录：

```text
这次算法 08 运行，用的是哪一批上游结果和哪一批规则。
```

为什么要记录版本？

因为后面要能解释：

```text
为什么当时 Omega-3 被识别成功能属性；
为什么当时 200g 和 250g 没合并；
为什么当时某个词不能进入商品名；
为什么某个候选没有进入 09。
```

常见版本如下：

| 中文名称 | 英文字段 | 人话解释 | 谁维护 |
|---|---|---|---|
| 候选属性字典版本 | `attribute_dict_version` | 本次使用哪一版属性字典和别名映射 | 系统生成初版，业务/商品/质量复核重点词 |
| 商品命名规则版本 | `naming_rule_version` | 本次使用哪一版商品命名结构和查重规则 | 系统生成或标准导入，业务/商品复核重点小分类 |
| 特殊必填规则版本 | `special_rule_version` | 本次使用哪一版特殊商品必填属性规则 | 商品/质量复核重点特殊商品 |
| 单位换算版本 | `unit_conversion_version` | 本次使用哪一版单位换算配置 | 数据开发按算法卡配置 |
| 商品状态版本 | `product_status_version` | 本次使用哪一批 SAP POP 商品状态 | 数据开发按基础表合同产出 |
| 商品基础快照版本 | `product_master_version` | 本次使用哪一批商品基础表 | 数据开发按数据合同产出 |
| 候选身份结构版本 | `candidate_identity_schema_version` | 本次候选 ID 用哪些字段生成 | 算法/数据开发维护 |

简单说：

```text
规则变了，要有新版本；
上游结果变了，要有新运行批次；
旧结果不能被静默覆盖。
```

## 10. 算法 05 在 08 里怎么用

算法 05 给 08 的不是“最终推荐结果”，而是候选价格可行性上下文。

08 需要 05 提供：

| 中文字段 | 英文字段 | 08 用来做什么 |
|---|---|---|
| 价格可行性结果 ID | `price_feasibility_result_id` | 生成范围候选结果 ID |
| 推荐规格 | `recommended_spec` | 确定候选是 200g、250g、12枚等 |
| 建议零售价 | `recommended_retail_price` | 传给 09 判断价格和毛利风险 |
| 全链路单位成本 | `full_chain_unit_cost` | 传给 09 判断成本和毛利风险 |
| 成本谈判上限 | `cost_negotiation_ceiling` | 传给 09 和后续采购动作 |
| 毛利底线 | `final_margin_floor` | 判断是否满足公司最低毛利要求 |
| 毛利目标 | `final_margin_target` | 判断是否满足公司目标毛利 |
| 价格证据状态 | `price_evidence_status` | 判断价格结果是否稳定 |
| 毛利状态 | `margin_position_status` | 判断毛利达标、需降本或不可行 |

算法 08 要求算法 05 在同一候选范围下，能够稳定提供唯一价格可行性结果。

算法 05 产出完整价格可行性结果，至少依赖：

```text
公司毛利底线；
公司目标毛利；
可执行价格点规则；
候选规格；
候选成本估算。
```

当前公司毛利底线、目标毛利和 V1 价格点生成规则已经确认：开发运行读取 `dim_company_margin_target_config` 和 `dim_price_point_rule_config`；B1 仅作为毛利配置来源追溯。价格点按品类尾数、默认 1 元步长和消费者价格带上下限生成。

如果算法 05 还没有完成配置落表或没有产出对应候选的价格可行性结果，08 可以保留候选身份，但不能把候选标记为“已准备好进入 09”。

这里的“保留候选身份”是指：

```text
候选来源、候选方向、标准候选和异常原因仍保存在算法 08 表中；
后续算法 05 或规则资产补齐后，可以重跑算法 08；
重跑通过后，候选再进入算法 09。
```

## 11. 08 输出状态怎么被下游使用

08 不直接决定最终推荐结果。

正式推荐优先级应该由算法 10 输出。

但 08 必须给下游留下状态，防止 09、10、Agent 或查询服务把未准备好的候选当成可推荐新品。

两个关键状态：

```text
NOT_READY_MISSING_PRICE_RESULT
中文含义：缺少价格结果，暂时不能进入算法 09 门禁。

REGISTRATION_EXCEPTION
中文含义：候选注册异常，小分类、主体、属性、规格或血缘没有说清楚。
```

下游使用约束是：

```text
算法 09 不能对这类候选做正式门禁；
算法 10 不能把这类候选排进正式推荐；
Agent 或查询服务不能把这类候选返回成“可开发新品”。
```

它们可以出现在：

```text
待补数据列表；
候选异常诊断；
上游重跑清单；
开发评审问题清单。
```

但不能出现在：

```text
正式推荐新品列表；
算法 10 输出的正式采购优先级候选；
采购优先级列表。
```

## 12. 合并和拆分规则

08 的合并不是看名称像不像。

08 的合并规则是：

```text
标准化后的身份字段完全一致，才可以合并。
```

### 12.1 可以合并

```text
算法 06：青椒黑椒牛柳丝 200g
算法 07：青椒黑椒牛柳丝 200g
```

标准化后都是：

```text
小分类 = 牛肉制品
主体 = 牛柳丝
配料 = 青椒
口味 = 黑椒
规格 = 200g
```

结果：

```text
合并成一个标准候选；
内部证据和外部证据都保留。
```

### 12.2 必须拆开

```text
青椒黑椒牛柳丝 200g
青椒黑椒牛柳丝 250g
```

方向一样，但规格不同。

结果：

```text
同一个候选方向；
两个标准候选商品。
```

### 12.3 不能自动拼接

如果算法 06 分别发现：

```text
黑椒牛柳丝 -> 青椒
黑椒牛柳丝 -> 圆葱
```

算法 08 只能得到：

```text
青椒黑椒牛柳丝；
圆葱黑椒牛柳丝。
```

不能自动拼成：

```text
青椒圆葱黑椒牛柳丝。
```

除非算法 06 已经明确输出“青椒 + 圆葱 + 黑椒牛柳丝”这个联合候选。

## 13. 结果状态怎么理解

08 的状态不是最终推荐结论。

它只是告诉下游：

```text
候选来源是什么；
候选证据成熟到什么程度；
候选是否适用于完整范围；
候选是否能进入算法 09。
```

| 中文状态字段 | 英文字段 | 取值和中文含义 |
|---|---|---|
| 来源构成状态 | `source_composition_status` | `INTERNAL_BASKET_ONLY`：只有内部购物篮证据；`EXTERNAL_DISCOVERED_INTERNAL_MATCHED`：外部发现且能匹配内部小分类；`INTERNAL_EXTERNAL_CONVERGED`：内部和外部都支持 |
| 证据成熟度 | `evidence_maturity` | `FORMAL`：正式证据；`EXPLORATORY`：探索证据 |
| 商品状态 | `product_status_code` | `A`：全年品；`O`：试卖品；`S`：季节品；`D`：淘汰品；`B`：备选品 |
| 季节状态 | `seasonality_status` | `SEASONAL`：季节商品且计划上架窗口齐全；`YEAR_ROUND`：全年品；`NON_SEASONAL_OTHER_STATUS`：试卖/淘汰/备选；`SEASON_WINDOW_INCOMPLETE`：S 商品计划上架窗口缺失；`UNKNOWN`：没有状态记录 |
| 范围适用状态 | `scope_applicability_status` | `FULL_SCOPE`：完整目标范围适用；`LOCAL_SUBGROUP`：只适用于局部门店子群 |
| 算法 09 就绪状态 | `algorithm_09_readiness` | `READY_FOR_ALGORITHM_09`：可以进入算法 09；`READY_WITH_ESTIMATED_COST`：成本为估算成本，可以带条件进入算法 09；`NOT_READY_MISSING_PRICE_RESULT`：缺少价格结果，不能进入算法 09；`REGISTRATION_EXCEPTION`：注册异常，不能进入算法 09 |

## 14. 业务验收看什么

业务验收重点看候选合并、拆分、名称、规格、来源和状态是否正确。

技术复算和 ID 稳定性校验放在开发版算法卡中验收。

业务侧重点看：

```text
同一个候选在 06 和 07 同时出现时，是否只生成一个标准候选；
合并后内部证据和外部证据是否都保留；
200g 和 250g 是否没有被误合并；
不同城市、门店等级、消费者画像是否没有被混成一条；
候选名称是否具体，不是泛营销词；
候选名称里的每个词是否有来源；
没有明确规格时，是否没有被强行生成正式候选；
缺价格结果时，是否没有进入 09；
08 是否没有提前做 09 的风险门禁；
最终推荐是否仍然由 09 和 10 决定。
```

## 15. 现在还需要确认什么

当前 08 主流程可以按业务原文理解。

真正还需要确认的是这些落地项。

| 优先级 | 需要谁确认 | 需要确认什么 | 为什么需要 |
|---|---|---|---|
| P1 | 算法/数据开发 | 算法 05 是否能输出唯一稳定的价格可行性结果 ID | 08 要用这个 ID 生成范围候选结果，防止同一个候选匹配到多条价格结果 |
| P1 | 商品/业务/质量 | 高频词、入名词、风险词和重点小分类规则的复核结果 | 已确认 V1 由系统自动生成初版；这里不是让业务从零提供表，而是复核系统生成结果是否可用 |
| P1 | 数据开发/商品 | 单位换算和规格展示规则是否覆盖重点小分类 | 防止 200g、12枚、1盒、1袋这类规格展示错误 |
| P1 | 算法/数据开发 | 算法 06、07 输出的候选 ID、属性代码、证据 ID、候选状态是否冻结 | 08 依赖这些字段做来源快照、属性血缘、合并和异常判断 |
| P1 | 数据开发/商品 | `dim_product_status` 是否按 SAP POP 来源落表，`S` 商品计划上架开始/结束日期是否齐全 | 用来标记季节候选；S 行日期缺失时写 `SEASON_WINDOW_INCOMPLETE`，不默认全年有效；其他核心条件齐全时仍可进入 09 |

## 16. 不要做什么

算法 08 不能做这些事：

```text
不能用名称相似度合并候选；
不能让采购人工指定候选或合并关系；
不能从商品名自由猜没有来源的属性；
不能把外部热词直接写进候选名称；
不能把 200g 和 250g 合并成一个标准候选；
不能把不同城市、门店等级、消费者画像的结果平均；
不能因为当前货盘重复或历史失败提前删除候选；
不能替代算法 09 做风险门禁；
不能替代算法 10 做推荐排序。
```

## 17. 一句话总结

算法 08 是新品候选进入风险门禁前的标准化和合并层。

它把 06、07 的新品候选整理成：

```text
一个标准商品身份；
一个明确规格；
一套可追溯属性；
一组内部和外部证据；
一个具体经营范围和价格方案；
一个是否可进入算法 09 的状态。
```

它解决的是：

```text
候选是谁。
```

它不解决：

```text
候选能不能开发；
候选风险高不高；
候选最终排第几。
```

这些交给算法 09 和算法 10。
