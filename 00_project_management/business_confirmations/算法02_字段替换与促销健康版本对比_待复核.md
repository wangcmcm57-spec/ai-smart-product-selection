## 1. 3个月与6个月数据周期怎么理解

不是先用 6 个月算一版七个维度，再用 3 个月算一版七个维度，然后两版互相比较准确性。

正确理解：

```text
最近 3 个完整自然月：计算正式门店品类等级。
最近 6 个完整自然月：用于参数、阈值、权重回退、滚动稳定性和历史风险线参考。
```

例如 2026 年 7 月运行：

```text
正式评分周期：2026-04-01 ~ 2026-06-30
历史参考周期：2026-01-01 ~ 2026-06-30
```

最终正式表只输出：

```text
2026-04-01 ~ 2026-06-30 的门店品类等级
```

不会额外输出：

```text
2026-01-01 ~ 2026-06-30 的另一版门店品类等级
```

6 个月数据在算法里的作用：

| 使用场景 | 6个月怎么用 | 是否生成正式等级 |
|---|---|---|
| 稳健标准化参数回退 | 当前 3 个月某指标波动太小、MAD 为 0 时，用历史参数兜底 | 否 |
| CRITIC 权重回退 | 当前比较组样本不足或相关矩阵不稳定时，参考历史权重 | 否 |
| 分层稳定性 | 看最近几个滚动窗口中等级数量是否稳定 | 否 |
| 订购健康区间 | 用更多历史 SKU 日训练售罄健康区间 | 否 |
| 损耗风险线 | 用历史损耗率和净贡献关系训练风险线 | 否 |

一句话：

```text
3个月算正式成绩，6个月校准规则和判断稳定性。
```

## 2. 每日可订可售表需要几个月历史

### 2.1 第一版最低要求

如果第一版只要先算正式门店品类等级，至少需要覆盖：

```text
最近 3 个完整自然月
```

因为正式等级就是用这 3 个月计算。

### 2.2 推荐要求

建议开发一次性准备：

```text
最近 6 个完整自然月
```

原因：

```text
1. 业务 02 原文要求最近 6 个月用于稳定性、参数和回退。
2. 货盘宽度、商品效率、订购健康都依赖有效在售 SKU 日。
3. 如果只有 3 个月，可算正式结果，但稳定性与回退能力会变弱。
```

### 2.3 后续增量要求

上线后建议每日增量同步：

```text
T+1 同步上一日门店 SKU 可订可售状态
```

## 3. 可订可售表字段替换建议

业务原文写的是：

```text
listing_status
listing_start_date / listing_end_date
正式上架、停售、下架生效日期
```

如果我们能提供每日可订可售状态，不建议第一期再让开发单独找上下架生效日期。

建议替换为现有可提供字段：

| 业务原逻辑字段 | 第一版建议字段 | 是否需要新增 | 说明 |
|---|---|---|---|
| listing_status | 是否可售 | 不新增 | 每日是否可售可直接代表当天是否在售 |
| listing_status | 是否可订 | 不新增 | 辅助判断供应/订购能力 |
| listing_start_date | 由“可订可售日期 + 是否可售”派生 | 不新增 | 连续不可售转可售的第一天可视为上架开始 |
| listing_end_date | 由“可订可售日期 + 是否可售”派生 | 不新增 | 连续可售转不可售的前一天可视为下架/停售前一天 |
| SKU 编码 | 销售商品编码 | 不新增 | 必须能对齐小票 `article_id` |
| 订购编码 | 订购商品编码 | 不新增 | 用于对齐订购/验收/进货链路 |
| 日期 | 可订可售日期 | 不新增 | 建议统一字段名为“日期”或“可订可售日期” |

第一版可订可售表最小字段：

| 中文字段 | 示例 | 说明 |
|---|---|---|
| 可订可售日期 | 2026-07-01 | 每日状态快照日期 |
| 门店编码 | A1SH | 对齐小票 `store_id` |
| 销售商品编码 | 21231650 | 对齐小票 `article_id` |
| 订购商品编码 | 91001234 | 对齐订购/验收/进货 |
| 是否可售 | 1 | 1 可售，0 不可售 |
| 是否可订 | 1 | 1 可订，0 不可订 |
| 数据更新时间 | 2026-07-02 02:00:00 | 追溯同步时间 |

## 4. “门店 SKU 每日实际收货”字段替换建议

业务原文写的是：

```text
actual_received_weight
actual_received_qty
arrival_cost_amt
```

产品侧已确认：

```text
门店进货数量 = 实际进货口径
```

因此不建议开发再新增一套“实际收货数量/重量”字段。建议在算法卡中直接替换成现有字段描述：

| 业务原逻辑字段 | 第一版建议使用现有字段 | 来源线索 | 第一版判断 | 说明 |
|---|---|---|---|---|
| actual_received_qty | 门店进货数量 | 毛利损耗/商品经营字段 | 可直接取 | 已确认是实际进货口径；用于计件商品售罄率 |
| actual_received_weight | 按重量单位统计的进货重量；没有则由门店进货数量、销售单位、单位重量换算 | 毛利损耗/商品经营字段 + 商品基础表 | 优先直接取；否则计算，待确认 | 称重商品优先用进货重量；如果只有数量，需要确认数量单位是否已是 kg，或用单位重量换算 |
| arrival_cost_amt | 出库到店成本含税 | 毛利损耗/价格字段 | 字段存在，需确认粒度 | 算法里用于到货成本，第一版优先用含税成本；需确认能否到 日期 + 门店 + 销售商品编码 |
| arrival_cost_amt 备选 | 门店进货金额 | 毛利损耗/商品经营字段 | 备选 | 如果出库到店成本含税不可用，再用门店进货金额并打降级标记 |
| pre19_sales_qty | 19点前销售数量 / 19点前销售件数 | 毛利损耗/小票聚合字段 | 优先直接取；没有则待补 | 计件商品使用；Doris 小票明细当前没有独立销售数量字段，不能只靠小票完整还原计件数量 |
| pre19_sales_weight | 19点前销售重量，优先取现有汇总字段；没有则由小票明细计算 | Doris 小票明细 / 毛利损耗聚合 | 可计算，待确认 | 称重商品使用；若源表无直接字段，则按有效小票 `inc_time < 19:00:00` 汇总 `weight` |
| loss_cost_amt | 门店损耗金额 / 门店已知损耗金额 + 门店未知损耗金额 | 毛利损耗字段 | 需要确认 | 业务原文要求损耗成本金额，需确认现字段是否成本口径 |

订购健康可计算：

```text
计件售罄率 = 19点前销售数量 / 门店进货数量
称重售罄率 = 19点前销售重量 / 进货重量
```

需要保留的确认项：

```text
1. 出库到店成本含税是否能按 日期 + 门店 + 销售商品编码 提供。
2. 门店损耗金额是否为成本口径。
3. 19点前销售重量是否已有汇总字段；如没有，则由 Doris 小票明细按 inc_time < 19:00:00 汇总 weight。
4. 进货重量是否已有汇总字段；如没有，需要确认能否由门店进货数量、销售单位和单位重量换算。
5. 如果门店损耗金额不是成本口径，损耗健康第一版需标记 loss_cost_rule_degraded_flag = 1。
```

## 5. 促销健康：完整版 DID vs 第一版降级版

当前已确认：

```text
第一期没有促销活动表。
因此第一期不能完整实现业务原文中的 DID / 匹配促销因果评估。
```

### 5.1 业务原文完整版：DID / 匹配促销因果评估

完整版目标：

```text
判断促销是否真的带来增量净贡献，而不是只看销售额有没有变高。
```

需要数据：

| 数据 | 第一期开发表状态 | 说明 |
|---|---|---|
| 促销活动编码 | 第一期不提供 | 用于识别同一次活动 |
| 活动开始/结束时间 | 第一期不提供 | 用于定义活动前、活动中、活动后 |
| 活动商品 | 第一期不提供 | 需要知道哪些 SKU 参加活动 |
| 活动门店 | 第一期不提供 | 需要知道哪些门店参加活动 |
| 处理组/对照组 | 第一期不提供 | DID 必须有参加组和未参加组 |
| 19点前促销优惠金额 | 有部分字段 | 可用促销折扣额/19点前促销折扣额 |
| 全日净经营贡献 | 有毛利损耗字段 | 需要毛利、损耗口径 |

计算逻辑：

```text
处理组变化 = 参加促销门店活动后指标 - 参加促销门店活动前指标
对照组变化 = 未参加促销门店活动后指标 - 未参加促销门店活动前指标
促销真实增量 = 处理组变化 - 对照组变化
```

公式：

```text
ATT =
(处理组活动后 - 处理组活动前)
-
(对照组活动后 - 对照组活动前)
```

然后计算：

```text
促销增量净贡献 = 实际净经营贡献 - 无促销反事实净经营贡献
促销 ROI = 促销增量净贡献 / 19点前促销优惠金额
增量标准销售额 = 增量销售数量 * 商品非促销期正常单价
促销依赖率 = 增量标准销售额 / 19点前全部标准销售额
promotion_health_score = sqrt(ROI得分 * 非促销依赖得分)
```

完整版优点：

```text
能回答“促销是否真的有效、是否真的赚钱”。
```

完整版缺点：

```text
需要活动表、处理组/对照组、活动前后窗口和反事实估计；开发成本高。
第一期没有促销活动表，因此该版本不能作为第一期正式实现口径。
```

### 5.2 第一版降级版：折扣/时段促销依赖代理

降级版目标：

```text
不判断促销是否带来真实增量，只判断门店品类销售是否高度依赖折扣或时段促销。
```

可用现有字段：

| 指标 | 可用字段 |
|---|---|
| 总折扣 | 优先取总折扣额；没有则由 Doris `discount_amt` 聚合 |
| 促销折扣 | 促销折扣额 |
| 时段折扣 | 优先取时段折扣额；Doris `hour_discount_amt` 仅作备选，且需确认是否需要去重 |
| 19点前促销销售 | 优先取19点前促销销售金额；没有则只能用 `is_hour_promotion = 1` 计算19点前时段促销销售 |
| 19点前销售 | 19点前销售金额 |

建议降级指标：

```text
总折扣率 = 总折扣额 / (实付金额 + 总折扣额)
促销折扣率 = 促销折扣额 / (实付金额 + 总折扣额)
时段折扣率 = 时段折扣额 / (实付金额 + 总折扣额)
19点前促销销售占比 = 19点前促销销售金额 / 19点前销售金额
19点前时段促销销售占比 = 19点前时段促销销售金额 / 19点前销售金额
```

注意：

```text
如果没有“19点前促销销售金额”，只用 Doris is_hour_promotion 计算出来的是“时段促销销售”，不能等同于全部促销销售。
如果使用 Doris hour_discount_amt，需要先确认该字段是否为会员当天同小时累计优惠金额；如果是，不能直接按商品行 sum，需按确认口径去重。
```

如果字段齐全，第一版可计算：

```text
promotion_proxy_dependency_score
= 上述依赖指标做反向稳健标准化后，用 CRITIC 或等权合成
```

反向含义：

```text
折扣率越高，健康分越低。
促销销售占比越高，健康分越低。
```

建议输出标记：

```text
promotion_rule_degraded_flag = 1
promotion_confidence = 中低
promotion_health_method = DISCOUNT_DEPENDENCY_PROXY
```

### 5.3 两个版本对比

| 对比项 | 完整 DID 版本 | 第一版降级版 |
|---|---|---|
| 回答的问题 | 促销是否真的带来增量和净贡献 | 门店品类是否依赖折扣/时段促销 |
| 是否需要促销活动表 | 需要 | 不需要 |
| 是否需要处理组/对照组 | 需要 | 不需要 |
| 是否能算促销 ROI | 可以 | 不可以，只能算折扣依赖风险 |
| 是否能判断促销有效/无效 | 可以 | 不可以 |
| 是否能防止“靠大折扣卖得好”被误判 | 可以 | 可以部分防止 |
| 开发复杂度 | 高 | 中低 |
| 第一版可落地性 | 低，除非业务提供活动表 | 高 |
| 建议用途 | 后续完整版促销健康 | 第一版门店品类等级风险诊断 |

### 5.4 第一期开口径选择

现在已确认第一期没有促销活动表，因此不再询问“是否补促销活动表”。还需要业务确认的是：

```text
第一期是否接受使用“折扣/时段促销依赖代理”作为促销健康的降级口径？
```

如果业务接受降级代理：

```text
使用 promotion_health_method = DISCOUNT_DEPENDENCY_PROXY。
输出 promotion_proxy_dependency_score。
不输出正式促销 ROI。
标记 promotion_rule_degraded_flag = 1。
```

如果业务不接受降级代理：

```text
promotion_health_score = NOT_APPLICABLE。
七个一级维度综合评分时，促销健康不进入综合分。
剩余可用维度按原 CRITIC 权重重算。
```

我的建议：

```text
第一期不要声称实现促销因果健康，也不要输出促销 ROI。
优先把“折扣/时段促销依赖代理”作为诊断字段输出。
是否进入综合分，需要业务确认。
```
