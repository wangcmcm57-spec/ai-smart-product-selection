# 算法 09：新品机会证据合成与风险门禁审阅清单

更新时间：2026-08-21

## 1. 审阅目的

本清单只保留算法 09 真正需要人工判断或补规则的内容。

算法 09 的结论是：

```text
一个已经由算法 08 标准化好的新品候选，
在指定城市/城市群、门店等级、消费者画像和小分类下，
能不能继续作为新品推进。
```

## 2. 已固定口径，业务不用再反复确认

| 已固定口径 | 09 执行方式 |
|---|---|
| 09 只接收算法 08 已准备好的标准候选 | `algorithm_09_readiness` 只有 `READY_FOR_ALGORITHM_09`、`READY_WITH_ESTIMATED_COST` 能进入 09 |
| 09 不生成候选、不改候选 | 主体、属性、规格、价格方案变化时回到 05/06/07/08 生成新候选或新版本 |
| 09 输出四类门禁结果 | `PASS`、`CONDITIONAL_PASS`、`RETURN_FOR_REBUILD`、`REJECT` |
| `CONDITIONAL_PASS` 不是正式通过 | 只能发布待验证开发需求，补齐条件后重跑 09 |
| 当前货盘已有实质同款时不算新品 | 公司级当前可订/可售货盘同款或确认高相似，按当前货盘重复门禁处理 |
| 停止订购不等于经营失败 | 缺正式退出原因时只能写不确定或证据不足，不能硬拒绝 |
| SPU 只做 V1 标准实体辅助归并 | SPU 不能替代正式换码关系、替代关系或历史退出原因 |
| 算法 07 风险线索必须进入 09 | 法规、标签、食品安全、功能声称或知识产权线索不能被忽略 |
| 09 不做供应商判断或触达 | 不做供应商准入、匹配、邀请、评分、排序或触达 |

## 3. 业务、质量、法务、财务真正要补的内容

| 编号 | 需要提供什么 | 最小可用内容 | 用在 09 哪一步 | 提供团队 | 优先级 |
|---|---|---|---|---|---|
| R1 | 法规、质量、标签、功能声称和知识产权规则 | 规则名称、适用小分类或属性、触发条件、必需材料、缺材料处理、硬停条件、依据、生效日期 | 第七步法规门禁；`candidate_regulation_evidence` | 质量/法务/业务 | P0 |
| R2 | 商品季节状态和销售季窗口 | 商品/SPU 或小分类的季节状态、销售季开始和结束、适用范围 | 历史失败判断、季节新品判断 | 商品/业务 | P0 |
| R3 | 估算成本推进口径 | 哪些品类可先以估算成本进入待验证需求，哪些必须先拿真实成本 | 价格毛利门禁；`CONDITIONAL_PASS` 解除条件 | 财务/商品/业务 | P1 |
| R4 | 首批高频、高风险、会进入商品名的词 | 例如 Omega-3、HPP、低钠、高蛋白、无菌蛋；标明优先核验方式 | 法规门禁和属性风险解释 | 质量/商品/法务 | P1 |
| R5 | 历史退出原因判定逻辑 | 经营失败、季节结束、换码或 SPU 迁移、供应中断、法规或食安退出、策略调整、仍在售、未知原因的触发条件、排除条件、优先级和证据要求 | 历史失败门禁 | 业务/商品/营运/数据 | P1 |
| R6 | 真正经营失败判定规则 | 什么情况下能把停订商品确认成经营失败；必须排除季节、换码、供应、法规、策略等原因 | 历史失败硬拒绝 | 业务/商品/经营/财务 | P1 |
| R7 | 换码、SPU 迁移和替代关系 | 旧码新码是否同一标准实体、是否正常迁移、是否替代关系、哪些只是相似不是同一商品 | 当前货盘重复和历史失败排除 | 商品主数据/业务 | P1 |
| R8 | 供应中断和经营策略调整证据 | 哪些记录能证明供应中断或策略调整，冲突时优先级怎么判 | 历史失败排除 | 商品/供应链/业务 | P1 |

说明：

```text
R5-R8 不阻断 09 整体运行，但会阻断“历史失败硬拒绝”。
V1 缺这些规则时，09 不能把历史停订、无销售、负毛利或折扣依赖直接判成经营失败，只能输出不确定、待复核或证据不足。
```

## 4. 开发需要验收，但不需要业务手工补的内容

| 内容 | 开发验收口径 |
|---|---|
| 门店商品每日可订可售表 | 按数据合同读取 `mart_store_sku_daily_sale_order_status`；真实库完整则直接映射，缺字段或粒度不完整则加工补齐；不能用小票无销量替代可订/可售状态 |
| 算法 08 标准候选表 | `mart_new_product_candidate_scope` 必须稳定输出 `standard_candidate_id`、`candidate_scope_result_id` 和 09 就绪状态 |
| 算法 05 价格可行性结果 | 09 只读取 05 结果，不重复确认毛利底线和价格阶梯；若 05 结果缺失，09 输出不可评估或退回重构 |
| 商品相似引擎 | 开发实现相似关系、灰区和阈值版本；不能用名称相似或固定经验阈值替代 |
| 毛利真实情景库 | 开发用真实历史门店日生成基准和不利情景；不能用历史最差单日冒充正式不利情景 |
| 运行批次和审计 | 系统负责版本锁定、重算和新旧结果留痕；人工不能直接覆盖硬门禁 |

## 5. 门禁结果的业务验收

| 门禁结果 | 必须看懂的业务含义 |
|---|---|
| `PASS`（通过） | 当前机会、价格/成本和风险检查都满足推进要求，可交给算法 10 |
| `CONDITIONAL_PASS`（有条件通过） | 机会成立，但必须补材料、补真实成本或完成复核；不能当成正式通过 |
| `RETURN_FOR_REBUILD`（返回重做） | 候选仍可能有机会，但规格、属性、价格、成本或数据需要回上游重做 |
| `REJECT`（拒绝） | 命中确定性硬门禁，例如当前货盘同款、法规硬停或价格成本无可行交集 |

## 6. 本轮重点复核

用户当前只需要重点看：

```text
1. 法规/质量/功能声称规则是否按第 3 节 R1 的格式能补第一版。
2. 商品季节状态和销售季窗口是否能作为基础表或规则资产提供。
3. 估算成本哪些场景可以先做待验证开发需求。
4. 高频词、入名词和风险词第一批是否需要调整。
5. 历史退出原因和真正经营失败规则是否能先补最小版本；不能补时按历史失败不硬拒绝上线。
```

其他字段、版本、表结构和调度逻辑由开发版算法卡验收。
