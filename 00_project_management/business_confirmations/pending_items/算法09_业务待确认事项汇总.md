# 算法09_业务待确认事项汇总

更新时间：2026-08-21

适用范围：算法 09 新品机会证据合成与风险门禁

阅读对象：业务、商品、营运、供应链、质量、法务、财务、采购、产品

本文目的：

```text
把算法 09 当前真正需要业务侧补充或确认的规则逻辑单独放在一个文件里。
业务只需要先看这里，不需要逐页翻算法 09 业务解读版和开发版算法卡。
```

本文不做三件事：

```text
1. 不要求业务手工判断每个候选商品能不能过门禁。
2. 不要求业务手工生成历史相似商品清单。
3. 不把数据开发实现问题当成业务确认问题。
```

## 1. 先看结论

算法 09 最需要业务补充的不是字段，而是规则判定逻辑。

尤其是系统没有正式商品退出原因字段时，业务必须说明：

```text
什么叫真正经营失败；
什么叫季节结束；
什么叫正常换码或 SPU 迁移；
什么叫供应中断；
什么叫法规或食品安全退出；
什么叫经营策略调整；
什么叫仍在售但尚未退出；
什么情况下只能算退出原因未知。
```

如果这些规则没有确认，算法 09 仍然可以运行，但历史失败门禁必须降级：

```text
可以保留历史风险线索；
可以输出证据不足；
不能把停订、无销售、负毛利或折扣依赖直接写成经营失败；
不能因为历史失败触发硬拒绝。
```

## 2. P1：历史退出原因判定逻辑

### 2.1 为什么必须补

算法能从系统里看到：

```text
商品是否可订、可售；
商品是否停止订购；
停止前销售好不好；
停止前毛利好不好；
停止前是否依赖折扣；
后续是否恢复可订可售。
```

但这些只能说明“经营表现和状态变化”，不能直接说明商品为什么退出。

例如：

```text
商品停订了，可能是经营失败；
也可能是季节结束；
也可能是换码；
也可能是供应中断；
也可能是法规或食品安全退出；
也可能是商品策略调整。
```

所以业务需要提供退出原因判定逻辑。

### 2.2 建议业务提供格式

| 退出原因 | 业务要给的判断逻辑 | 需要排除什么 | 可用证据举例 | 能否触发历史失败硬拒绝 |
|---|---|---|---|---|
| 真正经营失败 | 什么情况下可以认定商品因经营表现失败而退出，例如生命周期足够长、自然动销长期差、毛利长期不达标、折扣依赖严重且停订后未恢复 | 季节结束、换码、供应中断、法规退出、策略调整 | 可订可售状态、销售、毛利、折扣、业务确认记录 | 只有规则明确且回测通过后才可以 |
| 季节结束 | 哪些商品是季节商品，销售季什么时候结束，季外停订是否正常 | 非季节商品、提前异常停订 | 商品季节状态、销售季窗口 | 不能触发经营失败硬拒绝 |
| 正常换码或 SPU 迁移 | 旧码和新码是否同一标准实体，什么时候算正常迁移 | 真实淘汰、供应中断 | 商品主数据、换码关系、SPU 关系 | 不能触发经营失败硬拒绝 |
| 供应中断 | 哪些记录证明商品因供应问题停订 | 经营表现失败、策略下架 | 供应商停供、缺货、采购记录 | 不能触发经营失败硬拒绝 |
| 法规或食品安全退出 | 哪些质量、法规或食品安全事件导致退出 | 普通经营失败 | 质量事件、法务规则、监管记录 | 不能按经营失败处理，按法规门禁处理 |
| 经营策略调整 | 什么是货盘策略、区域策略、品牌策略或经营策略调整 | 动销差自然淘汰 | 商品调整记录、经营策略记录 | 不能直接触发经营失败硬拒绝 |
| 仍在售但尚未退出 | 截止日仍可订可售或后续恢复可订可售 | 短期缺货、数据延迟 | 可订可售快照、恢复记录 | 不能当成成功，也不能当成失败 |
| 退出原因未知 | 以上原因都无法确认，或证据不足 | 无 | 缺正式原因、证据冲突 | 不能触发历史失败硬拒绝 |

### 2.3 暂时没有规则时的 V1 降级

如果业务暂时无法提供完整规则，V1 按以下方式处理：

```text
historical_exit_reason = UNKNOWN_EXIT
historical_outcome_status = UNCERTAIN_OUTCOME
historical_failure_gate_status = INSUFFICIENT_HISTORICAL_EVIDENCE
```

人话就是：

```text
历史上可能有风险；
但证据不足；
不能硬拒绝新品候选。
```

## 3. P1：商品季节状态和销售季窗口

### 3.1 为什么必须补

季节商品季外没有销售，不代表消费者不喜欢，也不能当作经营失败。

算法 09 需要知道：

```text
哪些商品、SPU 或小分类属于季节商品；
销售季从什么时候开始；
销售季什么时候结束；
销售季是否每年重复；
季外停订是否属于正常季节结束。
```

### 3.2 建议业务提供格式

| 商品编码 / SPU / 小分类 | 商品名称 / 小分类名称 | 是否季节商品 | 销售季开始 | 销售季结束 | 是否每年重复 | 备注 |
|---|---|---|---|---|---|---|
| 待填 | 待填 | 是 / 否 | 待填 | 待填 | 是 / 否 | 待填 |

不提供时：

```text
不能正式输出 SEASONAL_NEW_PRODUCT；
不能把季节结束当经营失败；
历史失败判断只能降级。
```

## 4. P1：换码、SPU 迁移和替代关系判断

### 4.1 为什么必须补

V1 可以用商品基础表里的 SPU 做标准商品归并，但 SPU 不能完整替代正式换码关系和替代关系。

业务需要说明：

```text
哪些旧码和新码是正常换码；
哪些商品只是 SPU 迁移；
哪些商品是替代关系；
哪些商品虽然相似，但不是同一标准实体。
```

不提供时：

```text
当前货盘可以先用 SPU 辅助判断；
历史失败不能因为缺换码或替代关系硬拒绝；
只能输出相似灰区或证据不足。
```

## 5. P1：供应中断和经营策略调整判断

### 5.1 为什么必须补

算法不能从小票或可订可售状态自动知道商品停订是不是供应原因或策略原因。

业务需要说明：

```text
什么记录能证明供应中断；
什么记录能证明策略调整；
供应中断和经营失败冲突时谁优先；
策略退出和经营失败冲突时谁优先。
```

不提供时：

```text
停订商品不能直接写成经营失败；
历史退出原因只能写 UNKNOWN_EXIT；
历史失败门禁不能硬拒绝。
```

## 6. P1：法规、食品安全、标签和功能声称规则

### 6.1 为什么必须补

算法 09 不能让 AI 自己做法律或质量判断。

业务、质量和法务需要把重点规则说清楚：

| 需要回答的问题 | 以 Omega-3 为例 |
|---|---|
| 哪个商品或声称触发规则 | 鲜鸡蛋商品使用 Omega-3 营养声称 |
| 需要哪些证明材料 | 检测报告、营养标签、声称依据是否都需要 |
| 材料缺失怎么办 | 待补证、人工复核还是直接拒绝 |
| 什么情况硬停 | 禁止使用、检测不合格、食品安全不满足等 |
| 规则依据是什么 | 法规、标准或公司质量规则 |
| 规则什么时候生效 | 生效日期和失效日期 |

不提供时：

```text
法规门禁写 NOT_EVALUABLE；
候选返回重构或待补规则；
不能假装合规通过。
```

## 7. P1：估算成本推进口径

算法 09 会读取算法 05 的价格成本结果。

但如果成本还是估算值，业务需要确认哪些商品能先进入待验证开发需求，哪些必须先拿真实成本。

建议规则：

```text
普通口味、常规规格、原料稳定、历史成本参考充足的候选，可以先用估算成本发布待验证开发需求；
功能声称、特殊工艺、进口或高波动原料、冷链加工成本敏感的候选，必须先拿到真实成本或明确报价后再推进。
```

不提供时：

```text
只能输出 CONDITIONAL_PASS；
不能写成 PASS；
不能进入正式开发或正式试点。
```

## 8. P1：折扣依赖和毛利压力动作边界

算法可以计算：

```text
19:30 前自然动销；
19:30 后折扣依赖；
全链路毛利；
真实历史情景下毛利压力。
```

但业务、财务和商品需要确认：

```text
什么程度算折扣依赖严重；
什么程度必须改规格；
什么程度必须降成本；
什么程度必须改价格；
什么程度可以小范围待验证；
什么程度必须返回重做。
```

不提供时：

```text
算法只能输出风险状态；
动作边界不稳定；
不能稳定判断 RETURN_FOR_REBUILD 或 CONDITIONAL_PASS。
```

## 9. P1：当前货盘同款和高相似业务边界

算法会计算候选和当前货盘商品的相似关系。

但业务需要提供正反例样本，帮助确认：

```text
什么是同款；
什么是高相似；
什么是同方向但还能作为新品；
什么只是换名、轻微规格变化或包装变化；
哪些差异足以构成真实新品差异。
```

不提供时：

```text
同一商品编码或明确同一 SPU 可以硬拒绝；
高相似灰区只能要求复核；
不能因为名称相似直接拒绝新品。
```

## 10. 业务不需要手工提供什么

以下由系统、数据开发或算法开发完成：

```text
历史相似商品清单生成；
候选和当前货盘商品相似度计算；
候选和历史商品相似度计算；
机会证据和风险证据汇总；
版本锁定、运行批次、重算和审计；
K-medoids 真实情景选择；
Pareto 同层候选比较；
把已确认的业务规则落成规则表和执行逻辑。
```

业务、商品、质量、法务和财务只需要确认规则边界、复核重点样例，以及处理系统无法判断的专业灰区。

## 11. 当前可交付口径

在上述规则未全部补齐前，算法 09 可以按 V1 降级方式交付：

```text
可以输出机会证据；
可以输出风险线索；
可以输出有条件通过、返回重做或不可评估；
可以把历史退出原因未知写清楚；
不能把历史停订直接写成经营失败；
不能因为历史失败触发硬拒绝；
不能把法规或功能声称风险写成已通过。
```

一句话总结：

```text
算法 09 能先落地，但“历史失败硬拒绝”和“法规功能声称硬门禁”必须等业务规则明确后才能正式打开。
```
