# AI 选品算法逻辑缺口对比_给业务确认

生成日期：2026-07-17

## 1. 本文目的

当前 AI 选品算法卡最早是从《消费者画像驱动的门店群商品机会模型》原始文档中拆出来的。

在整理算法卡 01、02、03 的过程中发现：

```text
原始文档能说明整体业务路径，但很多算法逻辑没有写到数据开发可直接实现的程度。
```

近期业务补充了以下算法文档：

```text
profile_rules.md
区域门店品类等级算法规则.md
区域门店品类等级Agent能力卡.md
门店中分类分级_四象限_vs_熵权法.xlsx
门店品类场景画像能力卡.md
```

本文用于说明：

```text
1. 原始文档中抽出的算法，哪些已经有完整业务算法逻辑。
2. 哪些算法仍然缺核心逻辑，暂时不能直接写成最终开发算法卡。
3. 需要业务继续补充或确认的问题。
```


## 3. 01 会员画像算法核对

### 3.1 原始文档中的算法内容

原始文档中会员画像算法主要包含：

```text
时间行为：捡漏型 / 上班族晚高峰型 / 常规时段型
家庭规模：大家庭 / 小家庭
消费频次：高频 / 中频 / 低频
价格态度：价格敏感 / 价格非敏感
```

原始文档也提到：

```text
熵权法
动态阈值
异常会员日过滤
19 点前蔬菜行为
促销行为
```

但原始文档存在的问题：

```text
1. 很多阈值没有明确。
2. 时间窗口没有完全固定。
3. 部分指标是方向性描述，不是开发可直接实现的公式。
4. 最终画像标签优先级不够清晰。
5. 捡漏型消费者后续已由业务修正为不再拼家庭规模和价格态度。
```

### 3.2 业务新文档补充内容

`profile_rules.md` 给出了 V4 规则。

核心变化：

```text
primary_profile 是会员唯一一级消费者画像。
V4 删除“日常补货”和“待激活”。
只保留更稳定的人群行为定义。
```

基础字段：

```text
月均小票数 = 会员小票数 / 活跃月份数
客单价 = 会员总消费金额 / 会员小票数
20点后消费金额占比 = 20点后消费金额 / 总消费金额
19点前折扣金额占比 = 19点前折扣金额 / 19点前折前金额
18-19点小票占比 = 18-19点小票数 / 总小票数
有蔬菜小票的19点前蔬菜SKU数 = 会员19点前买过蔬菜的小票中，平均每张小票购买的蔬菜SKU数
```

基础阈值：

```text
高频：月均小票数 >= 8
中频：2 < 月均小票数 < 8
低频：月均小票数 <= 2
大家庭：有蔬菜小票的19点前蔬菜SKU数 >= 3
小家庭：有蔬菜小票的19点前蔬菜SKU数 < 3
捡漏型：20点后消费金额占比 >= 64.31%
价格敏感：非捡漏，且19点前折扣金额占比 >= 14.10%
上班族即时消费：非捡漏，18-19点小票占比 >= 66.67%，且18-19点小票数 >= 2
```

画像优先级：

```text
1. 捡漏型消费
2. 上班族即时消费
3. 价格敏感
4. 常规消费
```

### 3.3 当前判断

01 可以重写。

原因：

```text
业务已经给出明确字段、阈值、优先级和输出画像列表。
```

但需要确认：

```text
01 是否正式以 profile_rules.md 的 V4 作为新口径，替换原来的会员画像算法。
```

### 3.4 仍需业务确认的问题

```text
1. 01 是否确定使用 primary_profile V4 作为唯一画像口径？
2. 月均小票数中的“活跃月份数”如何定义？按自然月、有消费月份，还是数据周期折算？
3. 捡漏型是否正式从 19:30 后改为 20 点后？
4. 上班族是否正式从“晚高峰型”改为“上班族即时消费”，时间窗口为 18-19 点？
5. 价格敏感是否只看 19 点前折扣金额占比？
6. 19 点前折前金额字段是否可从 Doris 或价格表稳定获得？
7. 无蔬菜消费会员如何判断家庭规模？默认小家庭，还是输出未知？
8. 最终标签是否完全使用 profile_rules.md 中的 18 个 primary_profile？
9. 画像是否仍按 store_id + customer_id 粒度输出？
10. 是否需要保留画像置信度、算法版本、阈值版本？
```

## 4. 02 区域门店品类等级算法核对

### 4.1 原始文档中的算法内容

原始文档中门店品类等级算法主要说明：

```text
门店等级不按全店打分，而是在同一品类内比较门店。
粒度为区域组 / 城市 / 门店 / 大类 / 中类 / 小类。
输出 A/B/C/D 门店品类等级。
```

原始文档曾给出固定权重：

```text
销售规模得分 * 0.35
会员客数得分 * 0.20
全链路毛利额得分 * 0.15
门店毛利率得分 * 0.10
19点前销售占比得分 * 0.10
折扣健康度得分 * 0.05
损耗健康度得分 * 0.05
```

原始文档也给出过固定分位等级：

```text
A：前 30%
B：30%-55%
C：55%-80%
D：80% 以后
```

但原始文档存在的问题：

```text
1. 固定权重和动态算法之间口径不清。
2. 销售规模得分内部如何计算不清。
3. 标准化方法不清。
4. 是否强制所有门店品类都分 A/B/C/D 不清。
5. 样本不足、指标缺失、异常值如何处理不清。
6. 四象限、熵权法、多算法验证没有完整展开。
```

### 4.2 业务新文档补充内容

业务新文档明确将 02 升级为：

```text
中位数标准化
熵权法自动计算权重
四象限分析
多算法交叉验证
非强制分级
```

新文档明确禁止：

```text
禁止人工固定权重
禁止 sales_amt 单指标排序
禁止把所有门店品类组强行切成 A/B/C/D
禁止使用极大值、极小值标准化作为主口径
禁止把 hour_discount_rate 纳入品类等级评分
禁止使用全局统一损耗阈值
禁止让缺失毛利率或损耗率的 SKU 参与评分
```

参与熵权法的指标：

正向指标：

```text
sales_amt
member_customer_cnt
full_chain_gross_profit_amt
store_margin_rate
pre19_sales_share
```

反向指标：

```text
promo_discount_rate
loss_rate
```

关键口径：

```text
promo_discount_rate = pre19_promo_discount_amt / pre19_sales_amt
hour_discount_rate 只作为晚间折扣诊断字段，不进入评分
loss_rate 按 region_group + large_category + mid_category + small_category 建立健康度
```

四象限分析：

```text
经营规模轴：sales_amt + member_customer_cnt + ticket_cnt
经营质量轴：full_chain_gross_profit_amt + store_margin_rate + pre19_sales_share + promo_discount_health_score + loss_health_score
```

象限类型：

```text
优势经营型
规模强但质量待改善
潜力培育型
谨慎经营型
```

输出不再只有 A/B/C/D，还包括：

```text
暂不分级
观察型
潜力培育型
质量改善型
谨慎经营型
人工复核
```

Excel 文件也验证了：

```text
主模型：熵权法
四象限：运营诊断视图
```

### 4.3 当前判断

02 可以重写。

原因：

```text
业务已经给出明确算法方向、输入指标、标准化原则、熵权法原则、四象限规则、异常处理和输出字段方向。
```

但这不是简单修订，而是要替换原算法卡中的固定权重和固定分位分级逻辑。

### 4.4 仍需业务确认的问题

虽然 02 可以开始重写，但仍有一些开发落地细节需要业务或数据侧确认：

```text
1. 中位数标准化的具体公式是什么？
   例如：指标值 / 中位数，还是围绕中位数做比例缩放到 0-100？

2. 熵权法是否按每个 region_group + 大类 + 中类 + 小类 单独计算权重？

3. 熵权法中 0 值、负值、缺失值如何处理？

4. Excel 中“高波动样本”如何定义？
   例如是否使用 19点前销售CV 和中类CV_85分位。

5. Excel 中“稳定训练样本”如何定义？
   高波动样本是否不参与权重训练，但仍参与最终评分？

6. 熵权等级 A/B/C/D 如何从 category_score 得出？
   是分位、聚类、自然断点，还是业务另有规则？

7. “熵权分数差异达到有效区分阈值”如何计算？

8. 多算法交叉验证 V1 到底包含哪些算法？
   熵权法 + 四象限是否足够，还是必须加入聚类、稳健排名、时间窗口稳定性？

9. 观察型标签与 A/B/C/D 的最终落表关系是什么？
   category_level 为空还是保留 A/B/C/D，同时 grade_status 标记？

10. 当前 AI 选品项目是否采用营销 Agent 文档中的同一套口径？
    如果是，02 算法卡应命名为“区域门店品类等级算法”，而不是简单“门店品类等级算法”。

11. 输出表是沿用 mart_store_category_level，还是使用业务文档中的 store_category_level_all_categories？
```
