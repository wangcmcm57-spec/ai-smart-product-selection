## 1. 核对结论

以业务最新原始文档为基准，算法 02 的主链路是完整的：

```text
输入基础数据
-> 有效数据过滤
-> 计算七个一级维度

-> Jenks/BIC 动态分层
-> 经营底线修正
-> 输出 mart_store_category_level
```

## 4. 当前和业务最新文档的差异

以下不是业务逻辑错误，而是一期落地时根据现有数据做的适配，需要在开发版算法卡里写清楚。

| 差异点 | 业务最新文档 | 一期落地口径 | 是否可接受 |
|---|---|---|---|
| 城市群配置 | 原文写 CITY / CITY_CLUSTER，并列出 scope 字段 | 一期使用城市算法区域映射表 `dim_city_algorithm_region` | 可接受，本质一致 |
| 在售货盘 | 原文写正式上架、停售、下架、临时停售窗口 | 一期使用每日可订可售状态快照 | 可接受，前提是每日状态快照完整 |
| 实际收货 | 原文写实际收货 | 项目统一改为实际进货 | 可接受，是业务口径名称调整 |
| 促销健康字段 | 原文写小票字段代理 | 一期优先用毛利损耗表折扣额、时段折扣额；Doris 只补 19 点前口径和交易标记 | 必须这样做，因为 Doris `hour_discount_amt` 不是商品行金额 |
| 损耗金额口径 | 原文要求损耗成本金额 | 已确认损耗金额是成本口径 | 一致 |
| 净经营贡献 | 原文写全链路毛利额 - 损耗金额，如全链路毛利已扣损耗则不再扣 | 指标平台公式已扣供应链损耗，但未看到门店损耗；一期暂按全链路毛利额 - 门店损耗金额 | 还需确认正式字段是否已扣门店损耗 |
| 有效营业日 | 原文包括零销售但正常营业且品类正式经营的日期 | 当前一期口径倾向“有销售数据即有效营业日” | 有差异，需要明确为 V1 简化口径，或补门店营业日历/可售日历 |

## 5. 输出开发版算法卡前还需要补清楚的点

这些不是阻止我们写算法卡，而是要写进算法卡的“开发前确认项”或“V1 默认参数”。

| 类型 | 事项 | 建议处理 |
|---|---|---|
| 数据口径 | 全链路毛利额是否已扣门店损耗 | 给数据开发/财务口径负责人确认；未确认前默认 `净经营贡献 = 全链路毛利额 - 门店损耗金额` |
| 数据口径 | 优惠商品毛利率能否按日期 + 门店 + 销售商品编码计算 | 放进开发版确认项；不能到商品行时，用日门店商品近似并打口径标记 |
| 数据口径 | 有效营业日是否接受 V1 的“有销售数据即营业日” | 建议业务确认；严格版需要营业日历、货盘完整性、到货完整性 |
| 参数规则 | CRITIC 中“配对样本不足/相关矩阵不稳定”的阈值 | 开发版需要给 V1 默认值，例如有效门店数、配对样本数、相关矩阵有效率 |
| 参数规则 | 订购健康区间训练的样本不足阈值 | 开发版需要给 V1 默认值，例如分箱最小 SKU 日样本数 |
| 参数规则 | P90/P95/P99 容忍距离如何选择 | 开发版需要定义选择规则，或先用固定默认参数并标记待业务复盘 |
| 参数规则 | 相似经营日的星期、季节、节假日、促销状态如何落地 | 至少需要日期维度表；如果无节假日表，V1 只能先用星期类型和月份近似 |
| 参数规则 | 严重损耗风险线的样本不足和阈值不稳定判定 | 开发版需要定义最小样本数、最小月份数和不发布阈值条件 |
| 工程实现 | Jenks、CRITIC、Isotonic Regression 由谁实现 | 需要数据开发确认 SQL/Python 能力；如果调度平台不支持 Python，需要降级实现方案 |
| 工程实现 | 稳定性抽样是否需要固定随机种子 | 开发版建议固定种子，保证同一版本可复现 |

## 6. 是否可以输出算法卡 02

可以输出。

但输出的算法卡 02 应该明确标记为：

```text
V1 开发评审版
```

不是“全部口径已最终关闭版”。

开发版算法卡应采用以下原则：

```text
1. 业务最新文档已经明确的，直接写成正式规则。
2. 你已经确认的数据口径，直接写成一期口径。
3. 和业务原文有差异的一期适配，必须明确写出原因。
4. 还没有完全确认的地方，不能装作已确认，要写进开发前确认项。
5. 当前旧版开发卡固定权重、固定分位等级等内容必须删除。
```
