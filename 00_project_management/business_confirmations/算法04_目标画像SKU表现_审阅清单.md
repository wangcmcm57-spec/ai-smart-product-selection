## 1. 先说明这次修正了什么

上一版把业务原文中的“锚点识别算法”压缩成了普通 SKU 表现判断，这是不准确的。

本版已经恢复业务原文核心：

```text
四维指标
Jeffreys 统计证据
稳健标准化
两级 CRITIC 动态赋权
Jenks+BIC 动态锚点分组
正式锚点准入
当前锚点与历史锚点
门店稳定性
时间稳定性
SKU 表现明细、标准商品表现、锚点汇总、参数表
```

这份审阅清单只用于看“还有哪些数据落地点需要确认”。

## 3. 已确认的 V1 落地口径

| 事项 | 结论 | 文档标记 |
|---|---|---|
| 第一版没有促销活动表 | 使用 `discount_amt > 0` 做折扣代理 | `promotion_identify_method = DISCOUNT_PROXY_V1` |
| 指标平台不能支持 SKU 维度复购 | 先按业务口径产出前置复购表 | `mart_sku_repurchase_7d_pre19` |
| 第一版没有可靠 SPU / 换码关系 | 允许先按销售 SKU 计算 | `standard_product_mode = SKU_ONLY` |
| 商品属性缺失 | 不阻断经营表现计算 | `attribute_status = ATTRIBUTE_INCOMPLETE` |
| Doris 小票销售标准量字段 | `weight` 是商品行计价数量，可统一映射为销售标准量；称重商品表示计价重量，计件商品表示件数/份数/袋数/只数；单位需商品基础表补充 | `sales_standard_qty = weight` |
| 毛利损耗表数量字段 | 数据开发可按合同交付进货数量、进货重量、订购数量订购单位、订购数量重量口径 | 计件和称重分开计算 |

## 4. 需要数据开发确认的红线

| 编号 | 确认项 | 为什么重要 | 不满足时怎么处理 |
|---|---|---|---|
| D1 | 开发交付时抽样验收 Doris `weight` 在计件商品中的件数/份数/袋数/只数口径是否稳定，并确认商品基础表单位可解释 | 目标画像标准销售量、毛利、售罄率、折扣阶梯 | 异常 SKU 打 `MEASUREMENT_DATA_ERROR` 或 `DATA_INCOMPLETE` |
| D2 | 开发交付的毛利损耗表是否按数据合同实现 | 数据合同已定义为营业日期 + 门店编码 + 交易商品编码；验收时检查全链路毛利额是否在该粒度稳定、唯一、非异常 | 若正式交付未按合同实现，用门店商品日价格表 `出库到店成本含税` 做备选并标记口径 |
| D3 | 开发交付的实际收货/进货字段是否按数据合同可用于售罄率 | 毛利损耗表已定义到营业日期 + 门店编码 + 交易商品编码，并包含门店进货数量、门店进货重量；验收时检查空值和异常 | 字段异常时标记 `received_qty_status = UNKNOWN`，不得填 0 |
| D4 | 开发交付的门店 SKU 可订可售表是否按数据合同实现 | 数据合同已定义为日期 + 门店编码 + 销售商品编码；验收时检查主键唯一、历史周期和是否可订/可售口径 | 若正式交付未按合同实现，不能判断 ACTIVE_ANCHOR |
| D5 | 退货、取消、冲销、测试交易是否已在 Doris 表清洗 | 影响有效交易口径 | 未清洗则算法任务内必须补过滤规则 |

## 6. 不能再问错的问题

下面这些不是“让业务给固定阈值”的问题。

| 错误问法 | 正确处理 |
|---|---|
| 把锚点判断简化成固定阈值问题 | 业务已经给了 CRITIC + Jenks/BIC + 正式锚点准入规则 |
| 锚点是不是表现好就算 | 不是，必须进入最高表现组且满足 7 条准入 |
| 订购率要不要进综合分 | 不进入，只做覆盖解释 |
| 价格是否进算法 04 综合分 | 不进入，由算法 05 处理 |
| 损耗是否要分摊到目标画像 | 不分摊，算法 04 不再二次扣损耗 |

## 7. 可抽取到开发评审会的问题

这一节不是把整份审阅清单交给开发，而是从审阅清单里抽出需要数据开发确认的技术点。开发评审不要只问“能不能建表”，要逐项确认：

```text
1. 是否能按比较组运行稳健标准化。
2. 是否能实现 Jeffreys 95% 下界。
3. 是否能实现两级 CRITIC。
4. 是否能实现 Jenks+BIC 动态分组。
5. 是否能做留一门店、留一月稳定性验证。
6. 是否能输出参数表，保证结果可复算。
7. 是否能追溯到小票、上游版本、商品、到货、毛利和可订可售快照。
```

## 8. 当前结论

算法 04 现在可以按新版业务解读版和新版开发版算法卡进入评审准备。

需求评审时，建议你只重点盯 3 件事：

```text
1. 抽样验收 weight 在计件商品中是否稳定表示购买件数/份数/袋数/只数，并确认商品基础表单位可解释。
2. 个别 weight 异常 SKU 按已接受的销售额占比分摊兜底打标。
3. 毛利损耗表、可订可售表、Doris 有效交易过滤是否按数据合同验收。
```

业务算法逻辑本身不用你重新逐字判断一遍，业务原文已经确认，我们要做的是保证开发版没有漏掉。
