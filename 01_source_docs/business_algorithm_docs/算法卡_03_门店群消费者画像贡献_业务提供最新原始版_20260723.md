# 算法卡 03：门店群消费者画像贡献算法

文档状态：业务规则已确认  
适用范围：门店群主力消费人群识别与 AI 选品  
正式贡献周期：最近 3 个数据完整自然月  
模型更新：每月正式更新  
确认日期：2026-07-20

## 1. 算法澄清表

| 项目 | 业务问题 | 已确认规则 |

| 输出结果 | 最终输出什么 | 各类型会员数、销售额、小票数、占比、贡献得分、主力结果、解释指数、稳定性、质量和版本字段 |
| 验收方式 | 怎么判断合理 | 全量数据对账、公式复算、唯一性检查、分层抽样追溯、稳定性验证和边界场景验证 |

## 2. 算法定位与关联依赖

### 2.1 业务问题

本算法只回答：

```text
同一城市或城市群、同一品类、同一门店品类等级群中，
哪些消费者类型既覆盖较多有效会员，也贡献较多有效会员销售额？
```

算法结果用于确定后续商品分析的目标人群，不直接给出具体商品建议。

### 2.2 三个算法的依赖链

```text
算法 01：会员消费行为画像
确定每名有效会员在正式版本中的唯一 final_profile
        ↓
算法 02：门店品类等级
确定每家门店在具体品类和正式范围中的唯一 final_level
        ↓
算法 03：门店群消费者画像贡献
在同品类、同 final_level 门店群内汇总消费者类型贡献
```

必须遵守：

```text
1. 算法 01 或算法 02 没有正式版本时，算法 03 不得正式运行。
2. 任一上游正式版本变化时，算法 03 必须使用新版本全量重算。
3. 禁止在同一次算法 03 结果中混用不同会员画像版本或门店等级版本。
4. 算法 03 只读取上游 final_profile 和 final_level，不重新判断会员标签或门店等级。
5. 上游质量未通过时只输出诊断状态，不发布主力人群结论。
```

### 2.3 不做的事情

```text
不重新计算会员画像
不重新计算门店品类等级
不比较单个会员的价值
不生成单门店正式主力人群
不使用客单价或主观权重改变主力判定
不直接给出 SKU、新品或购物篮建议
```

## 3. 正式范围与计算粒度

### 3.1 城市或城市群

正式结果沿用算法 02 的评级范围：

```text
CITY：单城市
CITY_CLUSTER：业务配置城市群
```

禁止为了补足样本自动扩大到华东大区、其他城市或其他城市群。

### 3.2 品类颗粒度

支持：

```text
LARGE：大分类
MIDDLE：中分类
SMALL：小分类
```

大、中、小分类必须分别从小票商品明细重新筛选、关联和聚合：

```text
大分类结果 != 下属中分类结果平均
中分类结果 != 下属小分类结果平均
```

### 3.3 门店群范围

支持：

```text
指定 final_level：例如 A、B、C
ALL_RATED：当前范围和品类下全部已有正式等级的门店
```

`ALL_RATED` 必须从底层小票重新聚合。同一会员跨等级、跨门店消费时，在 `ALL_RATED` 中只计一名会员，禁止将各等级结果相加。

没有正式等级的门店不进入门店群，同时输出：

```text
rated_store_cnt
unrated_store_cnt
rated_store_coverage_rate
```

### 3.4 正式结果粒度

贡献明细表唯一粒度：

```text
contribution_model_version
+ contribution_start_date / contribution_end_date
+ scope_version / scope_type / scope_id
+ category_granularity / category_code
+ store_group_type / final_level
+ final_profile
```

同一消费者类型在该粒度下只能有一条结果。

## 4. 数据周期与版本锁定

### 4.1 正式周期

每月使用最近 3 个数据完整自然月。

例如 2026 年 7 月运行：

```text
contribution_start_date = 2026-04-01
contribution_end_date   = 2026-06-30
```

### 4.2 会员画像版本

同一个 3 个月贡献周期只使用周期结束时已正式发布的一个会员画像版本：

```text
profile_model_version = 周期结束时正式有效版本
```

该版本的 `final_profile` 作用于会员在贡献周期内的全部有效消费。禁止每个月使用不同标签后再拼接贡献结果。

### 4.3 门店品类等级版本

使用算法 02 对应同一正式周期发布的 `category_level_model_version` 和 `scope_version` 组建门店群。贡献周期内不按月改变门店群成员。

### 4.4 必须保存的版本血缘

```text
profile_model_version
category_level_model_version
category_mapping_version
scope_version
contribution_algorithm_version
source_data_version
```

## 6. 前置过滤与有效数据

### 6.1 有效会员

完全复用算法 01：

```text
customer_id 非空
customer_id 不以“6”开头
会员画像结果为正式有效状态
同一 profile_model_version 下只有一个 final_profile
```

算法 01 已识别的异常会员日不得重新进入算法 03。

### 6.2 有效交易

完全复用算法 01 的有效交易口径：

```text
保留正常完成的正向销售
剔除退货、取消、冲销和测试交易
剔除销售数量 <= 0 或实付金额 <= 0 的商品行
剔除算法 01 标记的异常会员日交易
```

### 6.3 时间口径

主力贡献使用全天有效消费：

```text
full_day_profile_sales_amt
full_day_profile_member_cnt
full_day_profile_ticket_cnt
```

工作日晚高峰、19:00 前、19:30 后和周末等分时指标只用于解释消费者行为，不进入正式贡献得分。

### 6.4 消费者类型

直接读取算法 01 的 `final_profile`：

```text
捡漏型
上班族晚高峰型-家庭规模-频次-价格态度
常规时段型-家庭规模-频次-价格态度
```

捡漏型是终止标签：

```text
final_profile = 捡漏型
family_level = NOT_APPLICABLE
frequency_level = NOT_APPLICABLE
price_attitude = NOT_APPLICABLE
```

算法 03 禁止重新拼接出“捡漏型-大家庭”等不存在的类型。

## 7. 关联路径与唯一性控制

### 7.1 关联顺序

```text
步骤 1：读取算法 02 正式结果，取得范围、品类、final_level 和门店清单
步骤 2：按门店清单和贡献周期筛选小票商品明细
步骤 3：按交易发生时有效的 SKU 品类映射筛选目标品类
步骤 4：按 customer_id 关联周期末正式会员画像版本
步骤 5：按门店群和 final_profile 从关联明细重新聚合
```

### 7.2 一对多检查

关联前必须验证：

```text
同一画像版本 + customer_id 只有一个 final_profile
同一等级版本 + 范围 + 门店 + 品类只有一个 final_level
同一品类映射版本 + sku_id + 有效日期只有一条有效映射
```

关联后必须对账：

```text
关联前有效会员销售额 = 关联后各消费者类型销售额合计
关联前有效会员商品行数 = 关联后有效会员商品行数
```

不一致时输出 `DUPLICATE_JOIN_ERROR`，禁止发布正式结果。

### 7.3 会员去重

```text
profile_member_cnt = COUNT(DISTINCT customer_id)
```

同一会员在门店群内购买多家门店，只计算一名会员；其在门店群内的全部目标品类有效销售额均需累加。

### 7.4 小票唯一键

优先使用源系统全局唯一 `ticket_id`。若不能保证跨门店唯一，使用：

```text
ticket_key = store_id + business_date + pos_id + source_ticket_no
```

同一张小票购买多个目标品类 SKU 时：

```text
品类销售额 = 小票中目标品类商品实付金额合计
品类小票数 = 1
```

同一张小票可以分别进入不同品类计算，但在同一个品类内只能计数一次。

## 8. 基础聚合指标

在同一正式门店群内，对每个 `final_profile` 计算：

```text
profile_member_cnt = 去重有效会员数
profile_sales_amt  = 目标品类全日有效会员销售额
profile_ticket_cnt = 目标品类有效会员小票数
profile_avg_ticket_amt = profile_sales_amt / profile_ticket_cnt
```

门店群分母：

```text
group_member_cnt = COUNT(DISTINCT 全部已贴标有效 customer_id)
group_sales_amt  = SUM(全部已贴标有效会员目标品类销售额)
group_ticket_cnt = COUNT(DISTINCT 全部已贴标有效会员目标品类 ticket_key)
group_avg_ticket_amt = group_sales_amt / group_ticket_cnt
```

主力人群判定只使用有效会员内部数据，不使用非会员销售作为分母。

### 8.1 画像内部占比

```text
member_share = profile_member_cnt / group_member_cnt
sales_share  = profile_sales_amt / group_sales_amt
ticket_share = profile_ticket_cnt / group_ticket_cnt
```

所有有效消费者类型应满足：

```text
SUM(member_share) = 100%
SUM(sales_share)  = 100%
```

因为同一会员在同一画像版本只有一个 `final_profile`，跨门店去重后会员占比可以直接相加。

### 8.2 全量经营覆盖诊断

以下字段只用于解释数据覆盖，不进入主力得分和主结论：

```text
member_sales_coverage_rate
= 已贴标有效会员销售额 / 门店群目标品类全部有效销售额

member_ticket_coverage_rate
= 已贴标有效会员小票数 / 门店群目标品类全部有效小票数

profile_link_success_rate
= 成功关联正式画像的有效会员数 / 应关联正式画像的有效会员数
```

正式发布要求 `profile_link_success_rate = 100%`。否则只生成诊断结果 `PROFILE_LINK_INCOMPLETE`。

## 9. 贡献得分

### 9.1 公式

```text
profile_contribution_score
= 2 * sales_share * member_share
  / (sales_share + member_share) * 100
```

当 `sales_share + member_share = 0` 时不执行除法，也不生成该消费者类型结果行。

### 9.2 为什么使用调和平均

调和平均要求销售贡献和会员覆盖同时较高：

```text
销售占比高、会员占比低 -> 得分被会员覆盖限制
会员占比高、销售占比低 -> 得分被销售贡献限制
两项同时高             -> 得分较高
```

它避免使用人工固定权重，也避免少数高客单会员直接成为主力人群。

### 9.3 不进入正式得分的指标

```text
ticket_share
profile_avg_ticket_amt
复购率
门店覆盖率
分时段消费占比
全量销售覆盖率
```

这些指标用于解释主力人群为什么形成，不改变正式主力判定。

### 9.4 解释指数

```text
人均消费贡献指数 = sales_share / member_share
到店活跃指数     = ticket_share / member_share
客单指数         = profile_avg_ticket_amt / group_avg_ticket_amt
```

业务解释：

```text
人均消费贡献指数 > 1：该类型人均销售贡献高于门店群平均
到店活跃指数 > 1：该类型人均到店小票贡献高于门店群平均
客单指数 > 1：该类型目标品类客单高于门店群平均
```

指数只提供解释，不新增“核心贡献型”“高价值小众型”等第二套消费者分类。

## 10. 主力消费者类型判定

### 10.1 候选分组

在同一门店群内，将所有有效消费者类型的 `profile_contribution_score` 从低到高排序，尝试：

```text
K = 1：不分高低组
K = 2：低贡献组 + 高贡献组
```

相同贡献得分不得被拆到不同组。

### 10.2 Jenks 自然断点

对 K=2 的所有连续切分位置，计算组内平方误差：

```text
SSE_K = SUM((score_i - 当前组均值)^2)
```

选择 `SSE_2` 最小且不拆分同分类型的断点。

### 10.3 BIC 选择 K

```text
BIC(K) = N * ln(SSE_K / N + epsilon) + K * ln(N)
epsilon = 1e-12
```

规则：

```text
BIC 越小越好
全部贡献得分相同时只允许 K=1
多个候选 BIC 相同时选择更小的 K
```

### 10.4 最终判定

```text
K=2：高贡献组全部输出 is_main_profile = 1
K=1：输出 result_status = NO_OBVIOUS_MAIN，不强制指定正式主力
```

K=1 时，贡献得分最高的类型只输出：

```text
is_relative_main_candidate = 1
is_main_profile = 0
```

最高分并列时，所有并列类型均为相对主力候选。该字段不改变算法 01 的消费者画像。

### 10.5 单一消费者类型

只有一种有效消费者类型时不运行 Jenks/BIC：

```text
result_status = SINGLE_PROFILE
is_main_profile = 1
profile_contribution_score = 100
```

这只表示当前有效会员消费结构单一，不代表经营价值或商品机会一定更高。

### 10.6 排名与主力覆盖

```text
contribution_rank = DENSE_RANK() OVER (ORDER BY profile_contribution_score DESC)

main_member_coverage_rate
= SUM(主力类型 profile_member_cnt) / group_member_cnt

main_sales_coverage_rate
= SUM(主力类型 profile_sales_amt) / group_sales_amt
```

同分类型使用相同排名，不得用消费者类型编码强行拆分业务排名。

`NO_OBVIOUS_MAIN` 时两个主力覆盖率记为 `NOT_APPLICABLE`。

## 11. 稳定性验证

稳定性用于解释正式结论是否受少数会员或特殊月份影响，不修改完整周期的正式主力判定。

### 11.1 会员级 Bootstrap

抽样单位必须是会员，不能独立抽小票：

```text
1. 在当前门店群全部有效会员中有放回抽样。
2. 每轮样本会员数等于原有效会员数。
3. 被抽中会员携带周期内全部目标品类有效小票和销售额。
4. 每轮重新计算占比、贡献得分、Jenks 和 BIC。
5. 记录每种消费者类型被判为主力的次数。
```

自动停止规则：

```text
每完成 250 轮检查一次
至少运行 1,000 轮
最多运行 10,000 轮

MCSE = sqrt(p * (1-p) / B)
```

其中 `p` 为当前主力入选率，`B` 为已运行轮数。当所有消费者类型的 `MCSE <= 0.01` 时自动停止。

输出：

```text
bootstrap_iterations
bootstrap_main_rate
bootstrap_main_rate_ci_lower_95
bootstrap_main_rate_ci_upper_95
bootstrap_mcse
```

不再使用“固定抽 80%、固定重复 500 次、80% 以上才稳定”等人工经验规则。

### 11.2 留一月验证

正式周期为连续 3 个完整自然月，保持周期末正式会员画像标签和门店群不变：

```text
验证 1：删除第 1 月，使用第 2 月 + 第 3 月重算
验证 2：删除第 2 月，使用第 1 月 + 第 3 月重算
验证 3：删除第 3 月，使用第 1 月 + 第 2 月重算
```

```text
time_main_rate
= 被判为主力的有效验证次数 / 有效验证总次数
```

某次删除月份后完全没有有效会员消费时，该次不进入分母。有效验证少于 2 次时：

```text
time_stability_status = INSUFFICIENT_TIME_SAMPLE
time_main_rate = NOT_APPLICABLE
```

业务解释：

```text
Bootstrap：主力结论是否受少数会员影响
留一月验证：主力结论是否受某个特殊月份影响
```

## 12. 小样本、零分母与异常处理

### 12.1 不设置人工最小样本门槛

```text
消费者类型会员数 > 0 且存在有效销售 -> 保留并参与计算
消费者类型会员数 = 0                -> 不生成结果行
```

不使用“至少 10 名会员”或“至少 30 张小票”等人工阈值。小人群通过原始会员数、小票数、Bootstrap 和时间稳定性披露不确定性。

### 12.2 零样本规则

```text
没有有效会员消费：NO_MEMBER_CONSUMPTION，不生成贡献明细和主力结论
sales_share + member_share = 0：不执行贡献得分除法
只有一种有效类型：SINGLE_PROFILE，直接判为主力
profile_ticket_cnt = 0 但 profile_sales_amt > 0：TRANSACTION_DATA_ERROR
```

### 12.3 结果状态

```text
SUCCESS                   正常生成明显主力人群
SINGLE_PROFILE            只有一种有效消费者类型
NO_OBVIOUS_MAIN           没有明显分离的主力结构
NO_RATED_STORE            没有可用正式等级门店
CATEGORY_MAPPING_ERROR    品类映射缺失或一对多
PROFILE_LINK_INCOMPLETE   应关联会员未 100% 关联正式画像
NO_MEMBER_CONSUMPTION     没有有效会员消费
DUPLICATE_JOIN_ERROR      关联造成明细、销售额或小票膨胀
TRANSACTION_DATA_ERROR    销售额、小票数或交易主键异常
UPSTREAM_VERSION_ERROR    上游正式版本缺失或混用
```

### 12.4 禁止跨范围回退

出现异常时：

```text
不扩大到其他城市或华东大区
不合并其他门店等级
不以中分类结果替代小分类结果
不使用非正式会员画像或门店等级
```

`SINGLE_PROFILE` 和 `NO_OBVIOUS_MAIN` 是有效业务结果，不属于数据错误。

## 15. 完整演示案例

以下均为产研复算用模拟数据，不代表生产实时结果。

### 15.1 案例 A：存在明显主力人群

范围：

```text
2026 年 4—6 月
上海
即烹类 / 牛肉制品
A 级门店群
```

底表聚合：

| 消费者类型 | 会员数 | 销售额 | 小票数 |
|---|---:|---:|---:|
| 常规时段型-小家庭-中频-价格非敏感 | 3,500 | 340 万元 | 15,000 |
| 上班族晚高峰型-小家庭-中频-价格非敏感 | 3,000 | 320 万元 | 12,000 |
| 捡漏型 | 2,000 | 180 万元 | 9,000 |
| 常规时段型-大家庭-高频-价格敏感 | 1,500 | 160 万元 | 5,000 |
| 合计 | 10,000 | 1,000 万元 | 41,000 |

贡献计算：

| 消费者类型 | 会员占比 | 销售占比 | 贡献得分 |
|---|---:|---:|---:|
| 常规时段型-小家庭-中频-价格非敏感 | 35% | 34% | 34.49 |
| 上班族晚高峰型-小家庭-中频-价格非敏感 | 30% | 32% | 30.97 |
| 捡漏型 | 20% | 18% | 18.95 |
| 常规时段型-大家庭-高频-价格敏感 | 15% | 16% | 15.48 |

第一类复算：

```text
2 * 0.35 * 0.34 / (0.35 + 0.34) * 100 = 34.49
```

排序：

```text
15.48、18.95、30.97、34.49
```

Jenks/BIC：

```text
K=1：SSE_1 = 252.91，BIC_1 = 17.97

K=2 最优断点位于 18.95 和 30.97 之间：
低贡献组 = 15.48、18.95
高贡献组 = 30.97、34.49
SSE_2 = 12.21，BIC_2 = 7.24
```

因为 `BIC_2 < BIC_1`，高贡献组的两个消费者类型为主力人群：

```text
主力会员覆盖率 = 35% + 30% = 65%
主力销售覆盖率 = 34% + 32% = 66%
result_status = SUCCESS
```

采购解释：

> 该门店群存在两个明显主力人群，合计覆盖 65% 的有效会员并贡献 66% 的有效会员销售额。后续商品分析应同时关注常规时段小家庭和晚高峰小家庭需求。

### 15.2 案例 B：不存在明显主力人群

假设四种消费者类型的会员数占比和销售额占比均为 25%：

```text
每类贡献得分
= 2 * 0.25 * 0.25 / (0.25 + 0.25) * 100
= 25.00
```

全部得分相同，只允许 K=1：

```text
result_status = NO_OBVIOUS_MAIN
is_main_profile = 0
main_member_coverage_rate = NOT_APPLICABLE
main_sales_coverage_rate = NOT_APPLICABLE
```

四种类型并列最高分：

```text
is_relative_main_candidate = 1
```

采购解释：

> 该门店群消费者贡献结构较均衡，当前不存在统计上明显分离的主力人群，不应强制指定某一种消费者类型作为正式主力。

### 15.3 案例 C：只有一种有效消费者类型

假设通过全部质量校验后只存在捡漏型：

```text
有效会员数 = 1,200
有效会员销售额 = 82 万元
有效会员小票数 = 3,200
```

```text
会员数占比 = 100%
销售额占比 = 100%
贡献得分 = 2 * 1 * 1 / (1 + 1) * 100 = 100
```

不运行 Jenks/BIC：

```text
result_status = SINGLE_PROFILE
is_main_profile = 1
main_member_coverage_rate = 100%
main_sales_coverage_rate = 100%
```

采购解释：

> 当前有效会员消费中只有捡漏型，因此捡漏型是主力人群。贡献得分 100 只表示消费结构单一，不代表其经营价值或商品机会必然更高。

## 16. 开发与业务验收

### 16.1 全量数据对账

每个门店群必须满足：

```text
各类型销售额合计 = 门店群已贴标有效会员销售额
各类型小票数合计 = 门店群已贴标有效会员小票数
各类型会员数合计 = 门店群去重有效会员数
SUM(sales_share)  = 100%
SUM(member_share) = 100%
```

允许的浮点误差不超过 `0.01%`。

### 16.2 公式复算

开发需逐字段复算：

```text
member_share
sales_share
ticket_share
profile_contribution_score
三个解释指数
Jenks SSE
BIC
主力会员和销售覆盖率
Bootstrap MCSE
time_main_rate
```

### 16.3 标签与唯一性

```text
同一结果唯一键只能有一行
同一会员只能关联一个 final_profile
同一门店品类只能关联一个 final_level
同分消费者类型不得被拆入不同贡献组
捡漏型不得带家庭、频次或价格态度后缀
```

### 16.4 分层抽样追溯

按城市或城市群、品类颗粒度和门店等级分层抽取至少 30 个门店群结果，逐层追溯：

```text
主力结果
-> 消费者类型聚合
-> 会员画像结果
-> 小票和商品明细
-> 门店品类等级结果
```

人工复核只用于发现数据和解释问题，不直接修改当前正式主力判定。

### 16.5 边界场景

必须自动验证：

```text
没有正式等级门店
没有有效会员消费
画像关联不完整
只有一种消费者类型
全部贡献得分相同
同一会员跨门店、跨等级消费
同一张小票包含多个目标品类 SKU
大、中、小分类分别重算
关联维表一对多导致金额膨胀
```

## 17. 不能做的事

```text
不能把非会员销售放进主力人群贡献得分分母
不能先算各门店占比再做门店平均
不能把各门店等级结果相加生成 ALL_RATED
不能平均下一级品类结果生成上一级结果
不能用固定销售占比阈值或人工权重判定主力
不能因为样本较小直接删除真实消费者类型
不能用客单价、小票占比或门店覆盖率改变正式主力标签
不能在算法 03 中重新生成会员画像或门店等级
不能在上游异常时自动扩大区域或合并门店等级
不能只输出主力名称而不保留会员数、销售额、占比、参数和版本血缘
```
