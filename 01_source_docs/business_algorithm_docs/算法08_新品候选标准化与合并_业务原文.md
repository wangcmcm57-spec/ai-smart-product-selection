# 算法卡 08：新品候选标准化与合并算法

文档状态：V1 开发候选版，算法内容已完整固化；正式上线前按版本治理流程审批生效  
适用范围：将算法 04—07 形成的具象新品候选统一标准化、生成稳定候选身份、合并多来源证据，并向算法 09 输出可门禁的候选快照  
唯一业务目标：新品开发  
正式计算粒度：周期 + 城市/城市群 + 门店等级 + 消费者类型 + 叶子小分类 + 标准新品候选  
正式运行：算法 02—07 月度版本冻结后运行；算法 09 风险门禁前运行  
生成日期：2026-07-31

## 1. 算法澄清表

| 项目 | 业务问题 | 正式规则 |
|---|---|---|
| 算法名称 | 第 8 个算法叫什么 | 新品候选标准化与合并算法 |
| 业务目标 | 解决什么问题 | 将算法 06、07 产生的具象候选，与算法 02—05 的门店、画像、主体、规格和价格证据拼成唯一、可追溯、可复算的标准候选 |
| 算法边界 | 是否重新提出新品 | 不重新发明候选；只标准化、注册、合并和输出异常，不新增任何没有上游证据的材料、配料、口味、功能、工艺或规格 |
| 执行位置 | 为什么算法 08 在算法 09 前执行 | 算法 08 是标准候选注册层；正式链路是算法 04—07 → 算法 08 → 算法 09 → 算法 10 |
| 计算对象 | 按谁计算 | 按一个标准新品候选在一个城市/城市群、门店等级、消费者类型和叶子小分类范围内计算 |
| 正式粒度 | 一条范围结果代表什么 | 周期 + 城市/城市群 + 门店等级 + 消费者类型 + 叶子小分类 + `standard_candidate_id` |
| 候选身份 | 同一商品在不同范围是否不同 ID | 商品身份使用同一个 `standard_candidate_id`；不同范围分别生成 `candidate_scope_result_id`，证据、价格和状态不混算 |
| 方向与商品 | “黑椒即烹牛肉方向”是否等于候选商品 | 不等于；方向使用 `candidate_direction_id`，正式候选必须是具体商品名称和明确规格，例如“青椒黑椒牛柳丝 200g” |
| 候选入口 | 哪些上游候选进入 | 正式、季节、局部试点和探索具象候选均进入；原始趋势词、普通共现、类别占位词和属性不完整方向只进入异常审计，不进入正式候选表 |
| 人工干预 | 采购能否手工指定候选、属性或合并关系 | 不能；采购筛选条件只改变查询范围，不能改变候选身份、证据等级、属性、合并结果或状态 |
| 上游依赖 | 读取哪些算法 | 直接读取算法 02—07 的正式结果；算法 01 通过算法 03—07 间接传递画像版本；算法 09 是下游，不是输入 |
| 主体来源 | 商品主体从哪里来 | 必须来自算法 04 锚点及正式叶子小分类，算法 06、07 不能用关联商品或外部热词替换主体 |
| 规格来源 | 规格从哪里来 | 使用算法 05 对当前范围输出并被算法 06、07引用的明确规格；只有规格段、没有明确规格时不能形成标准候选 |
| 新品属性来源 | 配料、口味、功能或工艺从哪里来 | 至少来自算法 06 的可追溯购物篮配方属性，或算法 07 的可追溯外部新品属性 |
| 商品名称 | 如何保证名称具体 | 使用叶子小分类命名模板和标准属性词典自动拼接；每个名称词元都必须有属性代码和证据 ID |
| 价格作用 | 价格是否属于商品身份 | 不属于 `standard_candidate_id`；价格、成本和毛利属于范围方案，进入 `candidate_scope_result_id` 和算法 09 快照 |
| 多来源合并 | 算法 06、07 指向同一商品怎么办 | 对标准化后的候选身份做精确相等合并，证据 ID 做去重并集；不按名称相似度或人工判断合并 |
| 近似候选 | 200g 与 250g 是否合并 | 不合并；共享方向 ID，但生成不同标准候选 ID |
| 属性冲突 | 青椒与圆葱是否自动拼成一个新品 | 不自动拼接；独立规则产生独立候选，只有上游存在经过验证的联合属性候选时才形成组合商品 |
| 同义词 | Omega-3、欧米伽3、オメガ3怎么处理 | 只有算法 07 已映射为同一标准属性代码时合并；算法 08 不做新的模糊文本匹配 |
| 候选状态 | 08 是否决定最终推荐 | 不决定；输出注册状态、证据成熟度、范围适用性和算法 09 就绪状态，最终能否开发由算法 09 门禁和算法 10 编排决定 |
| 排序与评分 | 是否生成候选机会分 | 不生成固定权重分或排序分；算法 08 是身份与证据注册算法，不评价哪个候选更值得做 |
| 已有商品排除 | 是否在 08 排除当前在售或历史差销相似品 | 不排除；标准候选全部传递给算法 09，由统一商品相似引擎执行当前货盘和历史失败门禁 |
| 输出结果 | 最终输出什么 | 运行批次、来源快照、属性血缘、方向注册、标准候选注册、范围结果、合并审计和异常审计八张表 |
| 验收方式 | 如何证明结果正确 | 固定载荷哈希复算、同义词收敛、输入顺序不变性、跨范围隔离、属性不可凭空增加、算法 09 字段对账和同版本重复运行一致性 |

## 2. 算法定位与全链路

### 2.1 十个算法的新品开发链路

```text
算法 01：为会员生成固定消费者画像
        ↓
算法 02：为门店在每个品类生成唯一正式等级
        ↓
算法 03：识别门店等级群中的主力消费者类型及贡献
        ↓
算法 04：识别目标画像真实购买的高表现现有锚点商品
        ↓
算法 05A：先给出目标规格、消费者价格带和建议价格上下文
        ↓
算法 06：从真实小票购物篮提取可进入新品的配方属性
算法 07：从竞品、社媒和全球趋势提取或验证新品属性
        ↓
算法 05B：对算法 06/07 的具象来源候选补算成本、毛利和价格可行性
        ↓
算法 08：统一属性、名称、规格、候选 ID、范围结果和证据血缘
        ↓
算法 09：执行当前货盘、历史失败、法规、价格毛利和其他风险门禁
        ↓
算法 10：将通过门禁的候选编排为采购优先级和开发动作
```

算法 08 是标准候选注册层，必须在算法 09 风险门禁前运行。研发调度按 `04/05/06/07 → 08 → 09 → 10` 执行。

### 2.2 本算法做什么

```text
读取算法 06 和 07 的原始候选记录
核对算法 02—05 的范围、主体、规格、价格和版本
将属性映射结果转换为统一标准代码载荷
按规则生成具体商品名、明确规格和展示名
生成候选家族、候选方向、标准候选和范围结果四级 ID
精确合并算法 06、07 的同一候选并保留全部证据
自动拆分规格不同或属性互斥的候选
输出算法 09 所需的不可变候选快照
保存所有未进入正式候选表的原因和原始证据
```

### 2.3 本算法不做什么

```text
不重新计算会员画像、门店等级或主力消费者
不重新计算 SKU 表现、价格带、购物篮规则或外部趋势
不使用大模型自由生成材料、口味、功能、工艺或规格
不把宽泛趋势词直接写进商品名
不把不同来源的独立热词做笛卡尔积
不使用采购手工指定商品作为算法证据
不按名称文本相似度合并候选
不设置人工相似阈值、固定权重或机会总分
不排除当前货盘和历史失败相似品
不执行法规、食品安全、毛利或同质化门禁
不匹配供应商、不选择供应商、不邀请供应商报价
不决定最终 P0/P1/P2 优先级
```

## 3. 四级对象和唯一粒度

### 3.1 候选家族 `candidate_family_id`

表示同一叶子小分类、主体和商品形态下的一组可能新品，不包含创新属性、规格和价格。

```text
叶子小分类
+ 主体商品
+ 商品形态
```

示例：

```text
即烹类/牛肉制品 + 牛柳丝 + 条丝状
```

家族只用于产品聚合展示，不能作为正式开发商品。

### 3.2 候选方向 `candidate_direction_id`

表示已经具备可追溯创新属性、但不包含明确规格和价格的商品方向。

```text
候选家族
+ 所有身份属性代码
```

示例：

```text
青椒 + 黑椒 + 牛柳丝
```

方向仍不能直接发布开发需求，因为供应商不知道应开发多少克或多少枚。

### 3.3 标准候选 `standard_candidate_id`

表示可以明确描述商品实体的候选：

```text
候选方向
+ 计量类型
+ 明确规格值
+ 明确规格单位
```

示例：

```text
青椒黑椒牛柳丝 200g
```

相同标准候选在上海 A 级门店和上海 B 级门店使用同一个 `standard_candidate_id`。

### 3.4 范围候选结果 `candidate_scope_result_id`

表示一个标准候选在具体业务范围和价格方案下的一次正式结果：

```text
正式周期
+ 城市/城市群
+ 门店等级
+ 消费者类型
+ 叶子小分类
+ standard_candidate_id
+ 算法 05 价格可行性结果 ID
+ 候选注册版本
```

同一标准候选在不同门店等级或消费者类型下必须生成不同范围结果，不能平均销售、价格、画像和购物篮证据。

### 3.5 正式结果唯一键

```text
candidate_registry_version
+ formal_period_start
+ formal_period_end
+ target_city_group_id
+ final_level
+ final_profile
+ leaf_category_id
+ standard_candidate_id
+ price_feasibility_result_id
```

同一唯一键只能存在一条有效范围结果。

## 4. 数据周期、版本和不可变性

### 4.1 正式周期

正式候选使用算法 02—07 同一组最近 3 个完整自然月版本。

```text
formal_period_start = 上游正式周期开始日
formal_period_end   = 上游正式周期结束日
data_cutoff_at      = 本次候选注册允许使用的数据截止时间
```

算法 07 日采集和周预警结果可以进入预览运行，但不能覆盖月度正式候选。

```text
run_type = FORMAL_MONTHLY
或
run_type = EXTERNAL_SIGNAL_PREVIEW
```

预览运行只写预览表或预览分区，不进入算法 09 正式门禁。

### 4.2 必须锁定的版本

```text
candidate_registry_version
candidate_identity_schema_version
profile_model_version
category_level_model_version
consumer_contribution_model_version
sku_performance_model_version
price_band_model_version
basket_algorithm_version
external_trend_version
product_master_version
category_mapping_version
attribute_ontology_version
category_development_rule_version
unit_conversion_version
name_template_version
```

任一上游正式版本变化时生成新的候选运行批次，不能静默覆盖历史结果。

### 4.3 哪些变化会改变标准候选 ID

以下任一标准身份字段变化时生成新的 `standard_candidate_id`：

```text
叶子小分类变化
主体商品变化
主材料或关键配料变化
口味变化
功能属性变化
工艺或商品形态变化
叶子小分类身份模板要求的包装属性变化
计量类型变化
明确规格值或规格单位变化
候选身份结构版本发生不兼容升级
```

### 4.4 哪些变化不改变标准候选 ID

```text
目标城市或城市群变化
门店等级变化
消费者类型变化
建议售价变化
全链路成本变化
成本谈判上限变化
证据数量增加
新增竞品图片或社媒证据
同一标准代码的展示中文名称修正
风险门禁结果变化
```

这些变化生成新的范围结果、运行版本或证据快照，不改变商品实体身份。

### 4.5 价格变化与算法 09 的衔接

价格不属于 `standard_candidate_id`，但属于 `candidate_scope_result_id`。算法 05 的建议售价进入新的可行区间或价格结果版本变化时：

```text
standard_candidate_id 保持不变
price_feasibility_result_id 变化
candidate_scope_result_id 变化
算法 09 必须重新门禁
```

这样既能识别“还是同一个商品”，也能防止旧价格方案继承新方案的门禁结果。

## 5. 输入数据和前八套算法接口

### 5.1 算法接口矩阵

| 来源 | 是否直接读取 | 算法 08 使用字段 | 作用 |
|---|---|---|---|
| 算法 01 | 间接 | `profile_model_version` | 通过算法 03—07 锁定会员画像版本，不重新读取会员明细 |
| 算法 02 | 直接 | `scope_id`、`final_level`、门店集合、等级版本、`assortment_method` | 锁定候选适用门店等级群；第一期正式货盘口径为 `ACTUAL_RECEIPT_ASSORTMENT_V1` |
| 算法 03 | 直接 | `final_profile`、主力状态、会员数/占比、销售额/占比、稳定性、结果 ID | 锁定候选适用消费者类型和贡献证据 |
| 算法 04 | 直接 | 锚点 ID、主体、叶子小分类、商品形态、`is_formal_anchor`、毛利与稳定性、结果 ID | 固定候选主体，禁止关联商品或外部热词替换主体 |
| 算法 05 | 直接 | 明确规格、计量单位、建议售价、成本、成本上限、毛利目标、价格状态、结果 ID | 固定规格并生成范围价格方案 |
| 算法 06 | 直接 | 候选 ID、配方属性、购物篮规则 ID、候选状态、范围、季节和证据 ID | 输入内部购物篮具象候选 |
| 算法 07 | 直接 | 标准候选 ID、外部属性、候选来源状态、趋势状态、内部适配、图片和证据 ID | 输入外部发现候选或对内部候选做外部验证 |
| 算法 09 | 不作为上游 | `new_product_candidate_snapshot` 字段契约 | 算法 08 输出必须满足该契约，算法 09 负责风险门禁 |

### 5.2 算法 02 等级输入条件

```text
算法 02 final_level IS NOT NULL
AND result_status NOT IN (DATA_INCOMPLETE, NOT_CALCULABLE)
AND scope_version IS NOT NULL
AND category_level_model_version IS NOT NULL
```

低置信度由算法 02 的 `confidence_level` 原样传递，不由算法 08删除或升级。`DATA_INCOMPLETE` 或 `NOT_CALCULABLE` 无法形成正式范围候选，写入异常表。

算法 02 第一版正式货盘字段：

```text
assortment_method = ACTUAL_RECEIPT_ASSORTMENT_V1
```

未来每日在售货盘入湖，只增加计划货盘执行诊断，不改变算法 09 的候选身份。

### 5.3 算法 03 消费者输入条件

算法 08 对算法 03 中所有存在有效消费的消费者类型保留范围结果，不只保存主力人群：

```text
final_profile IS NOT NULL
AND result_status NOT IN (DATA_INCOMPLETE, UPSTREAM_VERSION_ERROR)
```

产品可以默认展示 `is_main_profile = 1`，但页面筛选不能删除底层其他有效消费者类型结果。

### 5.4 算法 04 主体输入条件

正式候选优先读取：

```text
is_formal_anchor = 1
```

探索候选只允许读取算法 04 自动生成的回退锚点，并必须同时满足：

```text
calculation_status IN (SINGLE_SKU, NO_OBVIOUS_HIGH_SKU)
AND orderable_sellable_flag = 1
AND target_profile_sku_margin_amt > 0
AND sku_total_margin_amt > 0
AND evidence_status = SUFFICIENT
AND natural_sales_status = VALID
```

算法 04 最新毛利口径必须原样传递：

```text
target_profile_sku_margin_amt
= target_profile_sku_sales_amt - target_profile_sku_cost_amt

sku_total_margin_amt
= sku_total_sales_amt - sku_total_cost_amt
```

算法 08 不再次扣减损耗，也不重新判断锚点得分。

### 5.5 算法 05 规格和价格输入

算法 05 在本链路中分两次提供结果：

```text
05A：在没有具象候选时计算目标规格、价格带和建议价格上下文
05B：算法 06/07 形成具象来源候选后，计算该候选的成本和毛利可行性
```

标准候选身份至少需要 05A 提供：

```text
recommended_spec_value
recommended_spec_unit
measurement_type
price_band_model_version
```

范围结果同时读取 05B：

```text
recommended_retail_price
full_chain_cost
cost_negotiation_ceiling
final_margin_floor
final_margin_target
core_intersection_json
extended_intersection_json
evidence_status
margin_position_status
development_action
price_feasibility_result_id
```

`mart_candidate_product_price_feasibility` 必须补充稳定的 `price_feasibility_result_id`。若物理表第一版尚无该字段，算法 08按该表正式唯一键生成：

```text
price_feasibility_result_id
= "PF_" + HEX(SHA256(canonical_price_result_key))
```

规范键至少包含：

```text
price_band_model_version
formal_period
scope_version
target_city_group_id
final_level
final_profile
leaf_category_id
comparable_product_group_id
specification_segment_id
source_candidate_id
candidate_spec_version
supplier_quote_version
margin_policy_version
```

字段为空时保留显式 `null`，不能通过删除空字段制造相同哈希。

算法 05 只有规格段、没有明确建议规格时：

```text
registration_status = REGISTRATION_EXCEPTION
exception_code = EXACT_SPEC_MISSING
```

算法 08 不从规格段中点、均值或众数擅自生成规格。

### 5.6 算法 06 候选输入

允许进入来源快照的候选状态：

```text
FORMAL_NEW_PRODUCT
SEASONAL_NEW_PRODUCT
LOCAL_PILOT_NEW_PRODUCT
EXPLORATORY_NEW_PRODUCT
```

不进入正式候选注册表：

```text
NOT_ELIGIBLE_FOR_NEW_PRODUCT
ATTRIBUTE_INCOMPLETE
RAW_COOCCURRENCE
NO_COOCCURRENCE
NO_VALID_ANCHOR_BASKET
```

算法 06 的锚点必须来自算法 04 自动结果。任何 `manual_selected_flag = 1`、采购上传或页面手工指定来源均自动写入异常表：

```text
exception_code = MANUAL_SOURCE_NOT_ALLOWED
```

### 5.7 算法 07 候选输入

除候选身份和外部证据外，图片必须作为同一算法 07 运行快照的外键证据传递：

```text
primary_image_id
primary_image_source_run_id
image_match_validation_status
copyright_or_authorization_status
```

`primary_image_id` 为非空时，后三项也必须非空；图片与 `standard_candidate_id` 不一致、校验未通过或授权状态不允许展示时，将 `primary_image_id` 置空并保留图片异常码，不改变候选身份。

允许进入正式或探索候选注册：

```text
candidate_development_status = PENDING_ALGORITHM_08_GATE
或
candidate_development_status = EXPLORATORY_PENDING_ALGORITHM_08_GATE
```

以下仅保存来源证据，不进入标准候选注册：

```text
RAW_EXTERNAL_SIGNAL
EXTERNAL_TREND_NOT_LOCALLY_MATCHED
CATEGORY_MAPPING_GAP
REGULATORY_STOP
明确下降且不支持开发的外部趋势状态
```

`NO_EXTERNAL_OBSERVATION` 不是反对证据。内部算法 06 候选成立时，外部无观测不会阻断注册。

## 6. 候选入口与自动状态

### 6.1 所有来源先进入来源快照

算法 06、07 每条候选或异常信号先生成不可变来源快照：

```text
source_snapshot_id
= SHA256(
    source_algorithm_code
    + source_algorithm_version
    + source_run_id
    + source_candidate_id
    + canonical_source_payload
  )
```

来源快照保证被排除的原始信号也能追溯，不允许直接删除。

### 6.2 正式注册的最低结构条件

标准候选注册必须同时满足：

```text
目标城市/城市群存在
AND final_level 存在
AND final_profile 存在
AND leaf_category_id 存在
AND 算法 04 主体商品代码存在
AND 至少一条算法 06 或 07 新品属性来源存在
AND 所有进入名称的属性都有标准代码和证据 ID
AND 算法 05 明确规格值、单位和计量类型存在
AND 品类保持检验通过
AND 候选名称模板可生成具体商品名
```

这一步只验证候选是否可以被明确描述，不判断是否值得开发。

### 6.3 算法 09 就绪状态

```text
READY_FOR_ALGORITHM_09
身份、范围、规格、价格、成本和证据字段完整

READY_WITH_ESTIMATED_COST
算法 05 已使用估算成本且存在可行区间；交给算法 09 输出成本补证条件

NOT_READY_MISSING_PRICE_RESULT
商品身份成立，但算法 05 尚无范围价格可行性结果

REGISTRATION_EXCEPTION
候选身份、分类、属性、规格或血缘不完整
```

算法 05 输出 `NO_FLOOR_INTERSECTION`、`REDESIGN_REQUIRED` 或 `NOT_RECOMMENDED` 时，算法 08 仍注册并传给算法 09。算法 08 不能抢先做风险拒绝。

### 6.4 不允许人工升级

```text
探索来源进入算法 09后仍是探索来源
缺失证据不能由采购说明替代
属性冲突不能由采购选择一个值后继续
人工修改商品名不能生成新的属性代码
采购点击“采纳”不能改变注册状态
```

数据修复或上游证据更新后，必须重跑相应上游算法和算法 08。

## 8. 属性和规格标准化

### 8.1 标准代码优先，不解析展示名称

算法 08 只接受上游结构化代码：

```text
属性代码存在 -> 使用代码
只有文字、没有代码 -> ATTRIBUTE_CODE_MISSING
代码版本不存在 -> ATTRIBUTE_ONTOLOGY_VERSION_MISSING
代码已停用且无替代码 -> ATTRIBUTE_CODE_RETIRED
```

算法 08 不调用大模型从“健康鲜鸡蛋”“场景快手菜”等文字中猜属性。

### 8.2 同义词收敛

同义词必须先由算法 07 的版本化映射转换为同一标准代码：

```text
Omega-3
欧米伽3
オメガ3
오메가3
-> ATTR_FUNCTION_OMEGA3
```

映射通过算法 07 的正式误报控制后，算法 08只比较标准代码。未通过映射的原始词进入异常表，不能参与商品命名。

### 8.3 标准规格单位

```text
WEIGHT：统一为 g
VOLUME：统一为 ml
COUNT：统一为 count
LENGTH：统一为 mm，仅在叶子规则允许时使用
```

转换公式：

```text
canonical_spec_value
= source_spec_value * unit_conversion_factor
```

示例：

```text
0.2kg * 1000 = 200g
0.75L * 1000 = 750ml
12枚 * 1 = 12count
```

转换使用十进制定点数，保留至 6 位小数后删除末尾 0，不使用二进制浮点近似参与哈希。

### 8.4 规格冲突

```text
算法 05 recommended_spec = 200g
算法 07 参考竞品规格 = 250g
```

算法 07 的 250g 是外部参考规格，不能覆盖算法 05 的范围建议规格。正式候选使用 200g，并把 250g 保存在外部证据差异字段。

如果算法 06、07 的候选声明规格与其引用的算法 05 结果不一致：

```text
registration_status = REGISTRATION_EXCEPTION
exception_code = UPSTREAM_SPEC_LINEAGE_CONFLICT
```

算法 08不自行选择其中一个。

### 8.5 缺失规格

```text
只有“200—250g规格段”
没有算法 05 推荐规格点
```

输出：

```text
direction_status = DIRECTION_REGISTERED
standard_candidate_status = NOT_CREATED
exception_code = EXACT_SPEC_MISSING
```

方向可以保留用于后续重算，但不得显示成可发布开发需求的商品。

## 9. 商品名称自动生成

### 9.1 三个名称字段

```text

= 不含规格的具体商品名

recommended_spec
= 标准化后的明确规格

candidate_display_name
= candidate_product_name + 空格 + recommended_spec
```

示例：

```text

```

### 9.2 名称词元来源

```text

-> 功能属性
-> 口味
-> 主体商品

```


这些名称不是由明确材料、口味、功能、工艺和规格构成，不能进入候选表。

## 11. 多来源精确合并

### 11.1 合并键

只有以下字段完全相等时合并：

```text
standard_candidate_id
+ formal_period
+ target_city_group_id
+ final_level
+ final_profile
+ leaf_category_id
```

不同范围的证据不能合并到同一范围记录。

### 11.2 合并不是覆盖

对相同候选执行集合并集：

```text
internal_evidence_ids
= SORT_UNIQUE(算法 04、05、06 证据 ID)

external_evidence_ids
= SORT_UNIQUE(算法 07 证据 ID)

attribute_source_ids
= SORT_UNIQUE(全部身份属性来源 ID)

source_candidate_ids
= SORT_UNIQUE(算法 06、07 候选 ID)
```

不得用算法 07 的一条外部证据覆盖算法 06 的购物篮证据，也不得只保留“最强证据”而删除其他血缘。

### 11.3 来源构成状态

```text
算法 06 有有效候选 AND 算法 07 有同一标准候选
-> INTERNAL_EXTERNAL_CONVERGED

只有算法 06 有有效候选
-> INTERNAL_BASKET_ONLY

只有算法 07 有有效候选且内部适配通过
-> EXTERNAL_DISCOVERED_INTERNAL_MATCHED
```

`NO_EXTERNAL_OBSERVATION` 不把 `INTERNAL_BASKET_ONLY` 降级为无效。

### 11.4 输入顺序不影响结果

以下两批输入必须得到相同 ID、状态和证据集合：

```text
[算法06候选A, 算法07候选A]
[算法07候选A, 算法06候选A]
```

实现必须先标准化、排序和去重，再生成载荷和哈希。

### 11.5 不使用候选名称相似度

```text
青椒黑椒牛柳丝 200g
青泡椒黑椒牛柳丝 200g
```

若标准属性代码不同，则是不同候选。算法 08不设置文本相似度阈值进行合并。

候选与当前货盘或历史商品的概率相似关系由算法 09 的统一商品相似引擎计算。

## 12. 证据成熟度、季节和范围状态

### 12.1 三个独立状态轴

算法 08 不把所有业务含义压成一个标签，分别保存：

```text
evidence_maturity
seasonality_status
scope_applicability_status
```

### 12.2 证据成熟度

按所有身份关键属性的最弱证据确定：

```text
全部身份关键属性都有正式来源
-> evidence_maturity = FORMAL

任一身份关键属性只有探索来源
-> evidence_maturity = EXPLORATORY
```

算法 04 主体正式、算法 07 的 Omega-3 属性仍是探索趋势时，整个 Omega-3 鸡蛋候选仍为探索候选。

### 12.3 季节状态

```text
商品端 seasonal_status = S
AND season_start IS NOT NULL
AND season_end IS NOT NULL
-> seasonality_status = SEASONAL

否则
-> seasonality_status = YEAR_ROUND
```

缺少季节窗口时：

```text
seasonality_status = SEASON_WINDOW_INCOMPLETE
algorithm_09_readiness = REGISTRATION_EXCEPTION
```

### 12.4 范围适用性

```text
上游证据在完整目标门店群稳定成立
-> scope_applicability_status = FULL_SCOPE

只在算法 04、06 或 07 已验证的稳定门店子群成立
-> scope_applicability_status = LOCAL_SUBGROUP
```

算法 08只继承上游状态，不重新选择试点门店。

### 12.5 映射到算法 09 的上游候选状态

```text
evidence_maturity = EXPLORATORY
-> upstream_candidate_status = EXPLORATORY_NEW_PRODUCT

否则 seasonality_status = SEASONAL
-> upstream_candidate_status = SEASONAL_NEW_PRODUCT

否则 scope_applicability_status = LOCAL_SUBGROUP
-> upstream_candidate_status = LOCAL_PILOT_NEW_PRODUCT

否则
-> upstream_candidate_status = FORMAL_NEW_PRODUCT
```

季节和局部属性仍保存在独立字段中，单一状态字段不会删除信息。

## 13. 冲突、拆分和异常处理

### 13.1 可自动合并的情况

```text
不同语言映射为同一标准属性代码
0.2kg 与 200g 转换后完全一致
算法 06 与算法 07 产生相同标准载荷
相同候选从正向和反向购物篮规则获得多条证据
相同候选在不同外部平台出现
```

### 13.2 必须拆分的情况

```text
规格不同
标准属性代码不同
工艺不同
商品形态不同
叶子小分类不同
季节版本对应不同商品实体
```

拆分后可以共享家族 ID 或方向 ID，但不能共享标准候选 ID。

### 13.3 禁止自动组合

算法 06 分别存在：

```text
黑椒牛柳丝 => 青椒
黑椒牛柳丝 => 圆葱
```

算法 08只能生成：

```text
青椒黑椒牛柳丝
圆葱黑椒牛柳丝
```

不能生成：

```text
圆葱青椒黑椒牛柳丝
```

只有算法 06 已输出经过联合验证的三项候选时，算法 08才注册组合商品。

### 13.4 属性互斥

标准属性词典必须维护互斥组代码，例如：

```text
MEAT_STATE_RAW
MEAT_STATE_COOKED
```

同一来源候选同时命中互斥属性：

```text
registration_status = REGISTRATION_EXCEPTION
exception_code = MUTUALLY_EXCLUSIVE_ATTRIBUTES
```

算法 08不选择其中一个，也不让采购选择。

### 13.5 分类冲突

以下必须一致：

```text
算法 04 主体叶子小分类
算法 06/07 候选目标叶子小分类
算法 05 可比商品组所属叶子小分类
正式商品分类映射版本
```

不一致时：

```text
registration_status = REGISTRATION_EXCEPTION
exception_code = LEAF_CATEGORY_LINEAGE_CONFLICT
```

### 13.6 版本冲突

同一正式范围候选引用不同周期的算法 02—07 版本：

```text
registration_status = REGISTRATION_EXCEPTION
exception_code = UPSTREAM_VERSION_BUNDLE_CONFLICT
```

不允许使用“最新的一条”自动覆盖其他周期证据。

### 13.7 价格结果多条有效

同一唯一键出现多条同时有效的算法 05 价格结果：

```text
registration_status = REGISTRATION_EXCEPTION
exception_code = MULTIPLE_ACTIVE_PRICE_RESULTS
```

只有源系统已标记唯一有效版本，或旧版本已明确失效时，算法 08才读取当前有效结果。

## 14. 无人工干预约束

### 14.1 算法 08 中不存在的字段

正式计算表禁止出现会改变算法结论的字段：

```text
manual_selected_flag
manual_merge_flag
manual_attribute_value
manual_candidate_name
manual_priority
manual_score
manual_threshold
buyer_override_status
```

审计表可以记录页面操作，但操作结果不能写回候选身份和正式状态。

### 14.2 采购筛选的正确作用

采购选择城市、门店等级、消费者类型和品类时：

```text
只过滤已经计算完成的 candidate_scope_result_id
不触发修改 standard_candidate_id
不重新拼接属性
不改变证据成熟度
不改变算法 09 就绪状态
```

### 14.3 数据修正

采购发现名称或分类错误时，只能提交数据问题：

```text
修正商品主数据、属性词典或上游证据
-> 生成新版本
-> 重跑受影响上游算法
-> 重跑算法 08
```

旧结果保留，不允许直接编辑正式候选行。

### 14.4 业务规则与人工判断的区别

正式商品分类、属性词典、单位换算和叶子小分类身份模板属于版本化基础规则，不属于单次运行人工干预。规则变更必须：

```text
有新版本号
有生效时间
有变更原因
重跑受影响候选
保留历史版本
```

## 15. 完整计算过程

### 15.1 第一步：读取来源快照

```text
source_rows
= 算法 06 新品候选结果
UNION ALL
  算法 07 最终新品候选结果
```

每条来源记录先保存，不能先做 Top N 或页面筛选。

### 15.2 第二步：关联范围和上游证据

```text
source_rows
JOIN 算法 02 门店品类等级结果
  ON scope_version + final_level + leaf_category_id
JOIN 算法 03 消费者贡献结果
  ON scope + final_level + final_profile + leaf_category_id
JOIN 算法 04 锚点结果
  ON scope + final_level + final_profile + leaf_category_id + anchor_product_id
LEFT JOIN 算法 05B 价格可行性结果
  ON scope + final_level + final_profile + leaf_category_id + source_price_result_id
```

算法 02—04 任一关联缺失、多对多或周期不一致时进入异常表。算法 05B 未命中时保留商品身份并标记 `NOT_READY_MISSING_PRICE_RESULT`；算法 05B 多条同时有效时进入 `MULTIPLE_ACTIVE_PRICE_RESULTS`。

### 15.3 第三步：构造标准属性载荷

```text
主体属性 <- 算法 04
规格与范围价格 <- 算法 05
配方属性 <- 算法 06
功能/口味/工艺/外部属性 <- 算法 07
分类和允许维度 <- 正式分类及叶子专用规则
显示词 <- 标准属性词典
```

算法 08不从商品名称反向猜结构化字段。

### 15.4 第四步：分类和属性校验

```text
检查叶子小分类一致性
检查每个属性维度是否允许
检查必需身份维度是否齐全
检查属性互斥组
检查属性证据 ID
检查主体不可替换
```

任何失败都写异常状态，不进行人工兜底。

### 15.5 第五步：规格转换

```text
标准规格值 = 来源规格值 * 单位换算系数
```

结果与算法 05 的明确建议规格比对。相同后进入身份载荷，不同则输出规格血缘冲突。

### 15.6 第六步：生成名称

```text
标准属性词元
-> 按 name_token_order_json 排序
-> 删除重复词元
-> 拼接主体词元
-> 生成 candidate_product_name
-> 追加 recommended_spec 生成 candidate_display_name
```

名称只是标准载荷的显示结果，不能反过来决定候选 ID。

### 15.7 第七步：生成四级 ID

```text
family payload -> candidate_family_id
direction payload -> candidate_direction_id
candidate payload -> standard_candidate_id
scope payload -> candidate_scope_result_id
```

哈希计算使用第 10 章固定规则。

### 15.8 第八步：精确合并来源

```text
GROUP BY candidate_scope_result_id
```

对证据数组排序去重，重新计算来源构成状态。不得对销售额、Lift、趋势概率或价格做简单平均；原指标留在各自证据表。

### 15.9 第九步：确定状态轴和就绪状态

```text
身份属性证据 -> evidence_maturity
商品 S 状态和季节窗口 -> seasonality_status
上游门店稳定范围 -> scope_applicability_status
价格与成本字段完整度 -> algorithm_09_readiness
```

### 15.10 第十步：输出算法 09 快照

只有以下状态进入算法 09 正式输入队列：

```text
READY_FOR_ALGORITHM_09
READY_WITH_ESTIMATED_COST
```

身份成立但缺少价格结果的候选保留在算法 08，不得冒充已进入风险门禁。

## 20. 完整案例三：青椒与圆葱不得无证据拼接

### 20.1 两条独立规则

```text
RULE_01：黑椒牛柳丝 => 青椒
RULE_02：黑椒牛柳丝 => 圆葱
```

算法 06 没有输出通过验证的：

```text
黑椒牛柳丝 + 青椒 + 圆葱
```

### 20.2 算法 08 结果

```text
候选 A：青椒黑椒牛柳丝 200g
候选 B：圆葱黑椒牛柳丝 200g
```

两个候选分别生成标准载荷和 ID。

禁止结果：

```text
圆葱青椒黑椒牛柳丝 200g
```

原因：算法 08的输入集合是上游原子候选，不是属性热词集合；算法不执行跨候选笛卡尔积。

## 21. 完整案例四：同一候选跨范围

标准候选：


## 24. 开发实现要求

### 24.1 结构化处理

必须使用结构化 JSON、数组和属性词典处理候选，不得使用字符串包含关系判断商品身份。

错误示例：

```text
candidate_name LIKE '%牛柳%'
```

正确示例：

```text
product_subject_code = SUBJECT_BEEF_STRIPS
```

### 24.2 幂等运行

相同输入快照、版本和规范化规则重复运行：

```text
standard_candidate_id 完全一致
candidate_scope_result_id 完全一致
candidate_payload_hash 完全一致
证据数组排序完全一致
正式结果行数完全一致
```

### 24.3 原子写入

一次正式运行只有在八张表全部成功后才发布：

```text
run_status = PUBLISHED
```

任一表失败：

```text
run_status = FAILED
正式读取视图继续指向上一已发布版本
```

### 24.4 版本时间旅行

开发必须能按以下字段恢复任一历史候选：

```text
candidate_registry_run_id
candidate_registry_version
formal_period
source_snapshot_id
upstream_model_versions
attribute_ontology_version
category_development_rule_version
unit_conversion_version
name_template_version
```

### 24.5 数值精度

```text
金额：DECIMAL(18,6) 或更高
规格：DECIMAL(18,6)
概率：DECIMAL(18,12)
哈希输入中的数值：定点十进制字符串
```

禁止使用格式化后的百分数字符串参与计算和哈希。

## 25. 产研与业务验收

### 25.1 上游版本对账

任选一个范围候选，必须能追溯：

```text
算法 02 门店等级结果 ID和版本
算法 03 消费者贡献结果 ID和版本
算法 04 锚点结果 ID和版本
算法 05 规格价格结果 ID和版本
算法 06 购物篮候选及规则 ID
算法 07 外部候选及证据 ID
```

任一缺失时不能输出 `READY_FOR_ALGORITHM_09`。

### 25.2 固定哈希复算

使用第 10 章和第 19.3 节的八个固定载荷，产研必须得到完全相同的 SHA-256：

```text
family hash
beef direction hash
200g candidate hash
250g candidate hash
scope result hash
candidate payload hash
Omega-3 direction hash
Omega-3 candidate hash
```

任一字符、数组顺序或数值格式导致不同哈希都必须定位到规范化步骤。

### 25.3 输入顺序不变性

对同一批来源随机打乱至少 100 次：

```text
候选数量不变
候选 ID 不变
证据集合不变
状态不变
```

随机次数只是软件测试覆盖次数，不是业务阈值；固定测试种子并保存。

### 25.4 同义词验收

已由算法 07 映射为 `ATTR_FUNCTION_OMEGA3` 的四种语言必须得到同一个方向 ID和候选 ID。

未通过算法 07 正式映射的词必须进入异常表，不得因为字面相似被算法 08 合并。

### 25.5 单位转换验收

```text
0.2kg = 200g
200000mg = 200g
0.75L = 750ml
12枚 = 12count
```

等价规格必须生成相同候选 ID；不同计量维度必须输出异常。

### 25.6 分类保持验收

固定边界案例：

```text
鸡蛋候选不能吸收净菜属性
牛肉制品候选不能使用牛肉丸主体
禽类菜肴候选不能生成“禽类菜肴快手菜”占位名
大分类、中分类和全选必须展开叶子小分类后分别注册
```

### 25.7 不组合验收

只有两条独立二项规则时，系统必须生成两个候选，不得生成三属性组合候选。

输入真实多项规则后，才允许生成对应组合候选。

### 25.8 跨范围隔离

同一标准候选在不同城市、等级或画像下：

```text
standard_candidate_id 相同
candidate_scope_result_id 不同
价格和证据不互相覆盖
```

### 25.9 无人工字段验收

扫描正式表结构和计算 SQL：

```text
不存在 manual_* 改写字段
不存在 buyer_override 参与计算
不存在固定权重总分
不存在人工相似阈值
不存在按商品名 LIKE 合并
```

### 25.10 算法 08 接口验收

算法 08 中 `READY_FOR_ALGORITHM_09` 的每一条范围候选，必须完整映射到算法 09 `new_product_candidate_snapshot`。

算法 09 门禁结果必须同时保存：

```text
standard_candidate_id
candidate_scope_result_id
candidate_payload_hash
```

### 25.11 业务抽样验收

业务抽样只检查算法解释是否符合原始证据，不直接改结论。抽样应覆盖：

```text
购物篮正式候选
外部正式候选
探索候选
季节候选
局部范围候选
同方向不同规格
跨范围同一候选
属性冲突异常
规格缺失异常
外部无观测的内部候选
```

发现问题后修正上游数据或规则版本并重跑。
