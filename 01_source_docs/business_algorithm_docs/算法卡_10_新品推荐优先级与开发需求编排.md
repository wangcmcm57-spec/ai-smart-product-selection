# 算法卡 10：新品推荐优先级与开发需求编排算法

版本：V1.0
整理日期：2026-07-31
唯一业务场景：新品开发
正式计算粒度：周期 + 城市/城市群 + 门店等级 + 消费者类型 + 叶子小分类 + 范围新品候选
读者：业务、产品、数据研发、算法研发、测试与验收人员

## 1. 算法澄清表

| 澄清项 | 需要回答的问题 | 算法 10 正式口径 |
|---|---|---|
| 算法名称 | 第 10 个算法叫什么 | 新品推荐优先级与开发需求编排算法 |
| 业务目标 | 解决什么问题 | 将算法 01—09 已经识别、标准化并通过门禁的具体新品，自动整理成采购可理解、可追问、可发布的新品开发结论 |
| 计算对象 | 按谁计算 | 按算法 09 的 `candidate_scope_result_id` 计算；同一商品在不同范围、等级、画像或价格方案下分开编排 |
| 正式粒度 | 一条结果代表什么 | 算法版本 + 门禁运行 + 周期 + 城市群 + 门店等级 + 消费者类型 + 叶子小分类 + `candidate_scope_result_id` |
| 物理顺序 | 算法编号是否就是运行顺序 | 不是；正式后半段链路为 04—07 → 09 → 08 → 10 |
| 使用数据 | 需要哪些数据 | 算法 01—09 正式结果、版本和证据 ID；不从文本名称反推属性 |
| 门禁关系 | 10 能否改算法 08 结果 | 不能；`REJECT` 与 `RETURN_FOR_REBUILD` 永远不得被提升为可发布 |
| 候选修改 | 10 能否改商品名、规格或价格 | 不能；商品实体变化回到 09，价格或成本方案变化回到 05 并生成新范围结果 |
| 主力人群 | 是否在 10 里重新判定 | 不重新判定；直接读算法 03 的会员数占比、销售额占比和 `is_main_profile` |
| 分数 | 是否生成 0—100 机会分 | 不生成；现阶段没有完整、无偏的历史新品成功标签，不伪造权重和成功概率 |
| 优先级 | 没有总分怎么排 | 使用门禁状态、证据层级、Pareto 前沿和前沿后验稳定概率；实质并列不强行拆分 |
| 人工干预 | 采购能否选权重、改排名或手工提升 | 不能；查询选项只改变展示范围，不改证据、前沿、门禁、队列或结论 |
| 全选 | 选择全部等级、画像或品类时怎么算 | 展开到每个正式门店等级、消费者类型和叶子小分类分别编排，不跨组求平均或总排名 |
| 候选数量 | 是否只保留 Top N | 不是；底表保留全部候选，产品默认展示可发布队列和第一前沿 |
| 文本解释 | 结论怎样保证不编造 | 先生成结构化事实载荷和确定性模板文本；LLM 只可改写，新增事实校验失败时回退模板 |
| 开发需求 | 是否自动产生 | 对门禁允许的候选自动生成版本化草稿；缺字段不猜测，输出不完整状态和上游重建字段 |
| 产品交互 | 采购采纳是否改算法 | 不改；采纳只生成流程事件并冻结开发需求草稿版本 |
| 输出结果 | 最终输出什么 | 运行批次、输入快照、证据维度、推荐优先级、自动解释、开发需求草稿、范围汇总、审计八张表 |
| 样例 | 需要怎样演示 | 至少演示正式通过、待补条件、退回重构、硬拒绝和无支配并列五类完整计算 |
| 验收方式 | 产研怎么判断正确 | 固定载荷哈希复算、门禁不可提升、Pareto 复算、后验收敛、范围隔离、事实文本对账、开发需求完整性和无人工字段验收 |

## 2. 算法定位与全链路

### 2.1 十套算法如何服务同一个新品选品目标

```text
算法 01：确定会员属于哪一种消费者类型
        ↓
算法 03：确定指定门店群和品类下的主力消费人群及贡献

算法 02：确定每家门店在品类下唯一的经营等级
        ↓
算法 03—07：在同一城市群、等级、画像和叶子小分类内计算

算法 04：找到目标画像真正偏好且经营成立的现有锚点商品
        ↓
算法 05：生成候选规格、建议价、成本上限和毛利交集
算法 06：从真实小票中提炼可转化为新品的配方型属性
算法 07：从竞品、全球趋势、社媒口碑和行业证据发现或验证新品属性及图片
        ↓
算法 09：把多来源属性标准化为“具体商品名 + 明确规格”和唯一范围实例
        ↓
算法 08：合成机会证据，检查当前货盘、历史失败、法规、价格毛利和同质化风险
        ↓
算法 10：将门禁结果编排为采购能理解的推荐队列、自动结论和开发需求草稿
```

### 2.2 物理运行顺序

```text
01 + 02
-> 03
-> 04
-> 05 + 06 + 07
-> 09
-> 08
-> 10
```

算法编号是业务模块编号，不表示 08 必须在 09 之前运行。

### 2.3 本算法做什么

```text
保留全部门禁结果
自动映射推荐行动队列
按同范围证据层级和 Pareto 前沿编排
计算第一前沿的后验稳定概率
生成可追溯的采购语言解释
生成具体新品开发需求草稿
为采购追问保留 01—09 全链路 ID 和原始值
```

### 2.4 本算法不做什么

```text
不重新贴会员画像
不重新计算门店品类等级
不改主力消费人群
不重新评分锚点 SKU
不重新估计规格、价格、成本或毛利
不重新挖掘 FP-Growth 规则
不重新抓取或评分外部趋势
不生成新属性、新商品名或新规格
不覆盖算法 08 门禁
不生成人工权重总分
不将不同叶子小分类强行排成一张榜单
不选择供应商或判断供应商准入风险
不自动对供应商发送邀请
```

供应商匹配和邀请是采购采纳后的下游流程，不属于本算法的选品判断。

## 3. 正式粒度、范围和唯一性

### 3.1 范围候选是最小对象

算法 10 的最小对象不是商品名，而是：

```text
candidate_scope_result_id
```

原因：

```text
同一个青椒黑椒牛柳丝 200g
在上海 A 级门店和 B 级门店
可能有不同的目标画像、建议价、毛利条件和门禁结果
```

### 3.2 正式结果唯一键

```text
recommendation_algorithm_version
+ gate_run_id
+ formal_period_start
+ formal_period_end
+ target_city_group_id
+ final_level
+ final_profile
+ leaf_category_id
+ candidate_scope_result_id
```

同一唯一键只能有一条正式推荐结果。

### 3.3 可比较单元

`comparison_cell_id` 由算法 08 按以下字段生成，算法 10 只读取并用同一规范化载荷复算验证：

```text
formal_period_start
+ formal_period_end
+ target_city_group_id
+ final_level
+ final_profile
+ leaf_category_id
+ season_comparison_bucket
+ evidence_tier
+ new_product_gate_result
+ applicable_metric_signature
```

只在同一 `comparison_cell_id` 内计算 Pareto 前沿和实质排名。算法 10 复算值与算法 08 不一致时输出 `COMPARISON_CELL_MISMATCH`，不自行选择任一版本继续排序。

### 3.4 为什么不跨叶子小分类排名

```text
鲜鸡蛋的枚数、复购和功能属性
不能与即烹牛肉的重量、售罄和配方关联直接相加
```

选择大分类、中分类或全部品类时，系统展开所有叶子小分类，在前端分组展示，不生成跨品类的“机会总榜”。

### 3.5 门店等级全选

```text
选择 A + B + C
-> 分别读取 A、B、C 三个正式等级的范围候选
-> 分别编排
-> 不合并消费者占比、价格、证据或门禁
```

不使用门店等级字母作为商品候选的加减分。A 级只是一个独立适用范围，不表示该范围所有新品必然优于 B 级范围。

### 3.6 消费者类型全选

```text
选择全部画像
-> 每个 final_profile 独立返回结果
-> 不把不同画像的小票和价格证据平均
```

默认主结论的人群取算法 03 结果：

```text
SUCCESS / SINGLE_PROFILE
-> 默认展示 is_main_profile = 1

NO_OBVIOUS_MAIN
-> 显示“消费结构均衡，无明显主力人群”
-> 各画像独立展示
-> 不强制选出一种主力画像
```

## 4. 数据周期、版本与快照

### 4.1 正式周期

算法 10 本身不引入新的销售窗口，使用算法 08 已锁定的正式周期：

```text
算法 02—07 机会证据：同一最近 3 个数据完整自然月
算法 09 候选注册：同一正式周期和版本包
算法 08 货盘与法规：门禁运行时最新有效快照
算法 10 编排：只读同一 gate_run_id 的冻结结果
```

### 4.2 必须锁定的版本

```text

recommendation_action_mapping_version
recommendation_dimension_schema_version
pareto_algorithm_version
pareto_uncertainty_version
gate_evidence_tier_version
gate_common_dimension_contract_version
gate_comparison_cell_schema_version
explanation_template_version
requirement_schema_version
candidate_registry_version
gate_algorithm_version
profile_model_version

price_band_model_version
basket_algorithm_version
external_trend_version

```

### 4.3 不允许混用版本

以下任一情况直接输出 `UPSTREAM_VERSION_BUNDLE_CONFLICT`：

```text
同一 candidate_scope_result_id 关联两个 gate_run_id
门禁快照 candidate_payload_hash 与算法 09 不同
算法 03—07 证据周期不一致
算法 08 读取的候选注册版本与算法 10 不同
属性字典、分类规则或图片校验版本无法追溯
```

版本冲突的候选保留在输入快照和审计表，不进入可发布队列。

## 5. 前九套算法输入接口

### 5.1 接口矩阵

| 算法 | 算法 10 读取什么 | 在结论中解释什么 | 不允许的做法 |
|---|---|---|---|
| 01 会员画像 | `final_profile`、`model_version` 和标签结构 | 目标人群的行为含义 | 在 10 里重新贴标签或改画像 |
| 02 门店品类等级 | 城市群、唯一 `final_level`、门店数和算法 02 正式唯一键 | 候选适用的门店群 | 将 A/B/C 字母当成候选加减分 |
| 03 消费者贡献 | 会员数、销售额、小票、客单、占比、主力标记和稳定性 | 谁在买、占多少会员和销售 | 用候选商品表现反向修改主力人群 |
| 04 目标画像 SKU 表现 | 锚点商品、渗透、偏好、复购、自然动销、毛利和稳定性 | 为什么从这个现有高价值商品出发 | 将锚点商品直接当成已开发新品 |
| 05 目标画像价格带 | 规格、建议价、全链路成本、成本上限、毛利目标、可行区间和竞对价格 | 为什么是这个规格和价格 | 根据优先级临时调价或改成本 |
| 06 购物篮新品关联 | 锚点、关联商品、正反向 Confidence、Support、Lift 后验区间、稳定性和配方属性 | 哪条真实小票规则引入了哪个新品属性 | 把餐食互补商品擅自写进配方 |
| 07 竞品与全球趋势 | 渠道渗透、趋势后验、社媒净推荐代理值、差异属性、竞品价格、图片和证据 ID | 外部趋势是生成属性还是只验证内部方向 | 将社媒代理值写成问卷 NPS 或将热词写成商品 |
| 09 候选标准化 | `standard_candidate_id`、`candidate_scope_result_id`、具体名称、规格、属性血缘和图片 | 最终到底开发什么具体商品 | 根据解释文本重新命名或合并候选 |
| 08 证据合成与风险门禁 | 证据层级、门禁结果、最终候选状态、条件、Pareto 前沿、允许动作和风险证据 | 能不能继续、为什么和先做什么 | 用消费证据抵消硬风险或人工改门禁 |

上游物理字段和算法 10 快照字段使用以下显式映射，不允许开发自行猜别名：

```text
算法 01 model_version
-> 算法 03 profile_model_version
-> 算法 10 model_version_bundle_json.profile_model_version

算法 05 mart_candidate_product_price_feasibility.full_chain_cost
-> 算法 09 候选快照 full_chain_unit_cost
-> 算法 10 full_chain_unit_cost

算法 06 rule_status / candidate_status / evidence_level
-> 算法 10 按第5.4节派生 basket_evidence_status
```

算法 02 和 03 当前没有单列结果 ID。算法 10 只为血缘生成引用键，不回写上游：

```text
category_level_row_ref
= "CLR_" + SHA256(
    算法02正式唯一键的规范化JSON
  )

category_level_result_refs_json
= 当前门店群全部 category_level_row_ref 去重、升序后的JSON数组

consumer_contribution_result_ref
= "CCR_" + SHA256(
    算法03正式结果粒度字段的规范化JSON
  )
```

算法 02 正式唯一键必须完整包含：

```text
model_version
scope_version
level_end_date
scope_type
scope_id
store_id
category_granularity
category_code
```

算法 09 当前范围表中的遗留字段 `category_level_result_ids` 和 `consumer_contribution_result_ids` 没有在算法 02、03 中定义统一物理 ID 生成规则，因此算法 10 不直接把这两个字段当成权威血缘。V1 处理如下：

```text
按算法02正式唯一键生成 category_level_result_refs_json
按算法03正式结果粒度生成 consumer_contribution_result_ref
遗留ID数组如存在，只写入 legacy_lineage_ids_json 供迁移审计
遗留ID不得参与JOIN、身份哈希、状态映射或业务排序
```

同一算法 03 正式粒度必须只生成一个 `consumer_contribution_result_ref`；算法 02 因一个门店群包含多家门店，可以生成多个门店行引用，并以去重升序数组保存。

```text
contribution_model_version

contribution_end_date
scope_version
scope_type
scope_id
category_granularity
category_code
store_group_type

```

上述前11个范围和画像字段共同组成算法 03 正式结果粒度，并用于生成 `consumer_contribution_result_ref`。它是算法 10 的只读血缘引用，不冒充算法 03 已存在的物理字段。

### 5.3 算法 04 锚点与新品的边界

```text
锚点：黑椒牛柳丝 200g
算法 06 配方属性：青椒
算法 09 标准候选：青椒黑椒牛柳丝 200g
```

算法 10 的文本必须写成“基于高表现锚点及购物篮属性引出新品”，不得写成“青椒黑椒牛柳丝已经是历史高表现商品”。

### 5.4 算法 06 和 07 的不适用状态

```text
Omega-3 鲜鸡蛋没有配方型购物篮属性，
且叶子小分类规则明确该候选不需要购物篮配方来源
-> basket_evidence_status = NOT_APPLICABLE

存在算法 06 正式候选和 source_rule_id_list
-> basket_evidence_status = FORMAL

购物篮路径适用，但算法 06 没有正式规则
-> basket_evidence_status = NO_FORMAL_RULE

青椒黑椒牛柳丝可能没有正式增长趋势
-> external_evidence_status = NO_EXTERNAL_OBSERVATION
```

`basket_evidence_status` 是算法 10 的派生接口状态，不是算法 06 的物理字段。算法 10 只能读取算法 06 的 `rule_status`、`candidate_status`、`evidence_level`、`source_rule_id_list` 和叶子小分类适用规则进行确定性映射。不适用、未观测与 0 分完全不同，不得写0、不得填补平均值，也不得把“没有正式规则”写成“没有小票”。

## 6. 前置校验和候选池

### 6.1 全量输入池

算法 10 先读取指定 `gate_run_id` 的全部 `new_product_gate_result`，不在读取时做 Top N、页面筛选或只保留 `PASS`。

```text
all_gate_rows
= SELECT *
  FROM new_product_gate_result
  WHERE gate_run_id = :gate_run_id
```

### 6.2 必须通过的唯一性检查

```text
每个 candidate_scope_result_id 在同一 gate_run_id 只有一条结果
每个 candidate_scope_result_id 只关联一个 standard_candidate_id
每个 recommendation_result_id 只关联一个 candidate_scope_result_id
候选快照 candidate_payload_hash 与算法 09 一致
城市群、等级、画像和叶子小分类与证据表一致
```

### 6.3 核心输入字段

```text
candidate_scope_result_id
standard_candidate_id
candidate_product_name
recommended_spec
recommended_retail_price
full_chain_unit_cost
cost_negotiation_ceiling
final_margin_target
target_city_group_id
final_level
final_profile
leaf_category_id
candidate_source_status
evidence_tier
new_product_gate_result
final_candidate_status
blocking_reason_codes
condition_reason_codes
condition_to_clear
pareto_front_id
allowed_next_action
primary_image_id
primary_image_source_run_id
image_match_validation_status
copyright_or_authorization_status
candidate_payload_hash
```

以上任一核心身份或门禁字段缺失，输出：

```text
recommendation_status = NOT_CALCULABLE
recommendation_reason_code = CORE_INPUT_MISSING
```

不允许用展示名、上一期结果或其他城市结果补值。

### 6.4 门禁与最终候选状态一致性

| 门禁结果 | 允许的最终候选状态 | 不一致处理 |
|---|---|---|
| `PASS` | `FORMAL_NEW_PRODUCT` / `SEASONAL_NEW_PRODUCT` / `LOCAL_PILOT_NEW_PRODUCT` / `EXPLORATORY_NEW_PRODUCT` | 阻断本次编排 |
| `CONDITIONAL_PASS` | 保留上游有效候选状态 | 阻断本次编排 |
| `RETURN_FOR_REBUILD` | `NOT_ELIGIBLE_FOR_NEW_PRODUCT` | 阻断本次编排 |
| `REJECT` | `NOT_ELIGIBLE_FOR_NEW_PRODUCT` | 阻断本次编排 |

不一致原因码：

```text
GATE_CANDIDATE_STATUS_CONFLICT
```

### 6.5 候选池不删除退回和拒绝记录

```text
可推荐池：PASS / CONDITIONAL_PASS 且候选状态有效
不可推荐池：RETURN_FOR_REBUILD / REJECT
```

两个池都输出正式结果，保证采购能查到“为什么没有推荐”，也保证数据开发能做全量对账。

## 7. 无人工干预的行动队列

### 7.1 队列是业务状态，不是分数

正式队列：

```text
READY_TO_PUBLISH
READY_FOR_SEASONAL_DEVELOPMENT
READY_FOR_LOCAL_PILOT
CONDITION_FIRST
EXPLORATORY_RESEARCH
RETURN_FOR_REBUILD
NOT_RECOMMENDED
```

不把队列转换为 P0/P1/P2 加权分。产品界面以状态分组展示。

### 7.2 确定性映射表

| `new_product_gate_result` | `final_candidate_status` | `recommendation_action_queue` | 允许的流程动作 |
|---|---|---|---|
| `PASS` | `FORMAL_NEW_PRODUCT` | `READY_TO_PUBLISH` | 生成正式开发需求草稿 |
| `PASS` | `SEASONAL_NEW_PRODUCT` | `READY_FOR_SEASONAL_DEVELOPMENT` | 生成带正式季节窗口的开发需求草稿 |
| `PASS` | `LOCAL_PILOT_NEW_PRODUCT` | `READY_FOR_LOCAL_PILOT` | 生成局部门店群验证需求草稿 |
| `PASS` | `EXPLORATORY_NEW_PRODUCT` | `EXPLORATORY_RESEARCH` | 生成探索研究需求，不写成正式立项 |
| `CONDITIONAL_PASS` | 任一有效候选状态 | `CONDITION_FIRST` | 生成补证/验证需求，不允许正式发布 |
| `RETURN_FOR_REBUILD` | `NOT_ELIGIBLE_FOR_NEW_PRODUCT` | `RETURN_FOR_REBUILD` | 返回指定上游算法重构 |
| `REJECT` | `NOT_ELIGIBLE_FOR_NEW_PRODUCT` | `NOT_RECOMMENDED` | 退出当期新品池 |

### 7.3 映射校验

算法 10 的队列必须与算法 08 `allowed_next_action` 一致：

```text
READY_TO_PUBLISH
<-> PUBLISH_FORMAL_DEVELOPMENT_REQUIREMENT

READY_FOR_SEASONAL_DEVELOPMENT
<-> PUBLISH_SEASONAL_DEVELOPMENT_REQUIREMENT

READY_FOR_LOCAL_PILOT
<-> PUBLISH_LOCAL_PILOT_REQUIREMENT

EXPLORATORY_RESEARCH
<-> PUBLISH_EXPLORATORY_DEVELOPMENT_REQUIREMENT

CONDITION_FIRST
<-> PUBLISH_VALIDATION_REQUIREMENT

RETURN_FOR_REBUILD
<-> RETURN_TO_UPSTREAM_REBUILD

NOT_RECOMMENDED
<-> EXIT_NEW_PRODUCT_POOL
```

不一致时输出 `ACTION_MAPPING_CONFLICT`，不以算法 10 自行选择其中一个。

### 7.4 不使用固定 Top N

```text
底表输出同范围全部候选
第一前沿有5个候选 -> 保留5个
只有1个候选 -> 保留1个
没有可推荐候选 -> 输出范围空结果及各原因数量
```

页面默认只展示某队列或第一前沿是产品分页规则，不能删除底层记录。

## 8. 证据层级和不生成机会总分

### 8.1 为什么不生成 0—100 总分

```text
没有完整的历史新品提案全量数据
没有对未入选新品的反事实观测
上市成功受供应、执行、陈列、订货和季节等后续因素影响
购物篮路径与外部趋势路径的专属指标不同
硬风险不能被高机会分抵消
固定 30%/20% 等权重无法用业务数据证明
```

因此 V1 输出“队列 + 证据层级 + Pareto 前沿 + 稳定概率”，不将其伪装成新品成功概率。

### 8.2 证据层级沿用算法 08

V1 只读取 `evidence_tier_version = EVIDENCE_TIER_V1`：

```text
INTERNAL_EXTERNAL_FORMAL_CONVERGED
SINGLE_PATH_FORMAL
MATURE_MARKET_DIFFERENTIATED_GAP
FORMAL_SEASONAL
LOCAL_STABLE_SUBGROUP
EMERGING_OR_OVERSEAS_EXPLORATORY
RAW_SIGNAL
```

算法 10 不修改 `evidence_tier`，只使用算法 08 正式版本的层级顺序做分组。

### 8.3 证据层级不允许跨门禁补偿

```text
内外部共同收敛 + REJECT
-> 仍然 NOT_RECOMMENDED

单路径正式证据 + PASS
-> 可进入对应发布队列

海外领先探索 + PASS
-> 仍然 EXPLORATORY_RESEARCH
```

### 8.4 未来什么时候才能生成成功概率

只有当后续试点与上市闭环形成以下数据时，才可新建独立预测模型：

```text
所有被提案候选，不只是被采纳候选
清晰的上市、未上市和退出原因
统一的成功观察窗口和叶子品类口径
供应、订货、价格、促销和执行变量
未采纳候选的选择偏差校正或随机试点
```

未满足前不在 V1 留一个“手工填权重”入口。

## 9. Pareto 共同证据维度合同

### 9.1 维度记录必须结构化

算法 08 `common_dimension_metrics_json` 中的每个元素必须包含：

```text
metric_code
metric_value_raw
metric_value_comparable
metric_unit
direction
applicability_status
point_source_table
point_source_result_id
uncertainty_method
uncertainty_ref_id
uncertainty_group_id
model_or_rule_version
stored_precision
```

`direction` 只允许：

```text
HIGHER_BETTER
LOWER_BETTER
```

`applicability_status` 只允许：

```text
APPLICABLE
NOT_APPLICABLE
NOT_EVALUABLE
```

### 9.2 六个通用维度

| 维度代码 | 业务含义 | 比较值 | 方向 |
|---|---|---|---|
| `TARGET_DEMAND_STABILITY` | 锚点主体需求是否跨门店和月份稳定 | 适用的留一门店与留一月份锚点保持率中的最小值 | 越高越好 |
| `PRICE_COST_FEASIBILITY_SLACK` | 消费者核心价格带中有多少空间同时满足成本毛利 | 核心可行交集宽度 / 核心价格带宽度 | 越高越好 |
| `MARGIN_STRESS_BUFFER` | 不利真实情景下距目标毛利还有多少余量 | 最不利有效情景毛利率 - 目标毛利率 | 越高越好 |
| `DIFFERENTIATION_EVIDENCE` | 候选相对当前货盘和市场高相似品的实质差异证据 | 有属性来源支持的结构性差异后验概率 | 越高越好 |
| `CROSS_BLOCK_STABILITY` | 候选证据是否依赖某家门店、某个月或某个外部来源 | 所有适用稳定性验证率的最小值 | 越高越好 |
| `RISK_EVIDENCE_COMPLETENESS` | 应评估的风险是否全部有结果 | 已评估适用风险数 / 应评估适用风险总数 | 越高越好 |

### 9.3 具体公式

#### 9.3.1 目标需求稳定性

```text
TARGET_DEMAND_STABILITY
= min(
    leave_one_store_anchor_rate,
    leave_one_month_anchor_rate
  )
```

若只有一个维度适用，取该值并保留不适用原因；两个都不可评估时记为 `NOT_EVALUABLE`，不填0。

#### 9.3.2 价格成本可行余量

```text
core_band_width
= member_natural_core_upper
  - member_natural_core_lower

core_feasible_width
= max(
    0,
    core_intersection_upper
    - core_intersection_lower
  )

PRICE_COST_FEASIBILITY_SLACK
= core_feasible_width / core_band_width
```

若核心价格带是单一离散价格点，使用算法 05 已输出的离散可行价格点占比：

```text
PRICE_COST_FEASIBILITY_SLACK
= feasible_core_price_point_count
  / core_price_point_count
```

不在算法 10 伪造连续区间。

#### 9.3.3 毛利压力余量

```text
MARGIN_STRESS_BUFFER
= min(valid_scenario_margin_rate)
  - final_margin_target
```

只使用算法 08 已判定有效的情景 medoid。异常到货或超卖情景不重新放回计算。

#### 9.3.4 差异化证据

```text
DIFFERENTIATION_EVIDENCE
= P(
    structurally_distinct = 1
    AND exact_equivalent = 0
    | all validated similarity evidence
  )
```

该概率由算法 08 统一相似引擎产生，算法 10 不通过名称编辑距离重算。

#### 9.3.5 跨数据块稳定性

设适用的稳定性结果集为 `S_i`：

```text
S_i 可包含：
算法 04 留一门店锚点保持率
算法 04 留一月锚点保持率
算法 05 价格带重抽样稳定率
算法 06 门店×月份规则稳定率
算法 07 外部趋势时间外稳定率
```

```text
CROSS_BLOCK_STABILITY
= min(S_i)
```

不适用项不进入 `S_i`；`S_i` 为空时记 `NOT_EVALUABLE`。

#### 9.3.6 风险证据完整度

```text
RISK_EVIDENCE_COMPLETENESS
= evaluated_applicable_risk_count
  / applicable_risk_count
```

不适用风险不进入分母，`NOT_EVALUABLE` 不得计为已评估。

### 9.4 路径专属维度

```text
购物篮路径：Lift、正反向 Confidence、自然篮子稳定性
外部路径：趋势后验、渠道渗透、社媒净推荐代理值、扩散概率
```

只有当两个候选的 `applicable_metric_signature` 一致时，路径专属维度才可参与同一次 Pareto 比较。否则两个候选视为不可比，分别保留。

### 9.5 数值精度与等值

```text
先按来源表 stored_precision 四舍五入
再进行 Pareto 比较
```

不在算法 10 设置“相差 5% 算相同”等人工容差。两个存储值相同才视为该维度相同。

## 10. Pareto 非支配分层

### 10.1 支配定义

对同一 `comparison_cell_id` 内的候选 A 和 B，A 支配 B 当且仅当：

```text
对所有共同适用维度 j：
value_Aj 不劣于 value_Bj

AND

至少存在一个维度 k：
value_Ak 严格优于 value_Bk
```

对 `HIGHER_BETTER`：

```text
value_Aj >= value_Bj
```

对 `LOWER_BETTER`：

```text
value_Aj <= value_Bj
```

### 10.2 不可评估不是0

```text
任一候选在应用维度为 NOT_EVALUABLE
-> 不参与该比较单元的正式 Pareto
-> 进入 CONDITION_FIRST 或数据修复状态
```

`NOT_APPLICABLE` 维度不进入签名，不会因没有外部趋势而被填0。

### 10.3 非支配分层步骤

```text
第 1 步：找出所有没有被其他候选支配的候选
-> pareto_front_id = 1

第 2 步：暂时移除第 1 前沿
-> 在剩余候选中再找非支配集
-> pareto_front_id = 2

持续迭代直到所有候选都分层
```

### 10.4 单候选与全并列

```text
比较单元只有1个候选
-> pareto_front_id = 1
-> singleton_cell_flag = 1

所有候选互不支配
-> 全部 pareto_front_id = 1
-> substantive_tie 不因系统需要显示顺序而被拆除
```

### 10.5 与算法 08 前沿对账

算法 10 对点估计重算前沿后，必须与算法 08 `pareto_front_id` 完全一致。

```text
一致
-> pareto_reconciliation_status = MATCHED

不一致
-> pareto_reconciliation_status = MISMATCH
-> 本次运行不得发布
```

算法 10 不以自己的前沿静默覆盖算法 08。

## 11. Pareto 前沿后验稳定性

### 11.1 为什么还要做稳定性

点估计的第一前沿可能受小样本、某家门店、某个月份或后验不确定性影响。算法 10 不用人工分数打破并列，而是回到上游不确定性，计算：

```text
如果重复从当前证据生成可能的真实值，
该候选有多少次仍在第一 Pareto 前沿？
```

### 11.2 不确定性方法与来源

| `uncertainty_method` | 使用场景 | 第 b 次取值方式 |
|---|---|---|
| `POSTERIOR_JOINT_DRAW` | Jeffreys、Dirichlet、分层贝叶斯、相似后验 | 从上游保存的联合后验或可复算参数取联合样本 |
| `STORE_MONTH_BLOCK_BOOTSTRAP` | 门店×月份稳定性 | 以门店×自然月为块有放回抽样，每次抽取与原始块数相同的块 |
| `MEMBER_CLUSTER_BOOTSTRAP` | 画像贡献或会员簇内重复行为 | 以会员 ID 为簇有放回抽样，保留该会员全部小票 |
| `SCENARIO_DISTRIBUTION_DRAW` | 毛利压力情景 | 按算法 08 情景 medoid 的估计权重抽取；权重缺失时不自动等权，记为不可评估 |
| `DETERMINISTIC_VALUE` | 法规状态、分类映射等确定性值 | 所有重复中保持同一值 |

### 11.3 保留联合相关性

多个维度来自同一个后验或同一组重抽样时，必须使用同一 `uncertainty_group_id` 和同一次联合取值。

```text
错误：
单独抽复购率、偏好指数和会员渗透率，破坏它们的共同会员分母

正确：
对同一会员抽样结果一次性重算三个指标
```

### 11.4 可重复种子

第 b 次抽样的随机流由以下规范载荷生成：

```text
sampling_seed_b
= LOWER_64_BITS(
    SHA256(
      recommendation_run_id
      + comparison_cell_id
      + uncertainty_group_id
      + b
      + pareto_uncertainty_version
    )
  )
```

同一输入和版本必须生成完全相同的取值序列。

### 11.5 每次重算前沿

对第 b 次取值：

```text
1. 生成每个候选在每个适用维度的 value_ij^(b)
2. 按第 10 章使用相同方向和精度重算非支配层
3. 记录 front_id_i^(b)
```

### 11.6 第一前沿概率

对候选 i：

```text
I_i^(b)
= 1, if front_id_i^(b) = 1
  0, otherwise
```

```text
front_1_probability_i
= SUM_b(I_i^(b)) / B_valid
```

`front_1_probability` 表示“前沿结论对当前证据不确定性的稳定程度”，不是新品上市成功概率。

### 11.7 自动收敛，不使用固定 500 次

取值量使用 `B = 2^m` 逐轮加倍。每轮计算：

```text
MCSE_i
= sqrt(
    front_1_probability_i
    * (1-front_1_probability_i)
    / effective_draw_count_i
  )
```

后验链存在自相关时，`effective_draw_count_i` 使用初始正序列自相关法估计的有效样本量，不直接用原始取值数。

正式结果将 `front_1_probability` 保留两位小数。对每个候选，以下条件同时成立时停止：

```text
按 0.01 精度四舍五入后的 front_1_probability
连续两轮不变

AND

1.96 * MCSE_i < 0.005
```

`0.005` 来自两位小数存储单位 `0.01` 的一半，是数值精度要求，不是业务通过阈值。

### 11.8 未收敛处理

当技术运行超过平台最大计算时间或有效取值不足时：

```text
pareto_stability_status = COMPUTE_NOT_CONVERGED
front_1_probability = NULL
recommendation_status = NOT_READY_FOR_FORMAL_ORDER
```

保留点估计前沿和所有中间取值统计，但不以一个未收敛概率排正式次序。平台资源上限是运行参数，不得改变已收敛候选的业务判定。

## 12. 优先级、并列与确定性展示顺序

### 12.1 不同行动队列不做业务总排名

```text
READY_TO_PUBLISH
READY_FOR_SEASONAL_DEVELOPMENT
READY_FOR_LOCAL_PILOT
CONDITION_FIRST
EXPLORATORY_RESEARCH
RETURN_FOR_REBUILD
NOT_RECOMMENDED
```

七者是不同工作队列，不把它们转换为一个数值相加。产品可以将“可发布”作为默认页签，但底表无跨队列的第1、2、3名。

`RETURN_FOR_REBUILD` 和 `NOT_RECOMMENDED` 保留算法 08 的点估计前沿及全部证据用于审计，但不生成采购优先级：

```text
front_1_probability = NULL
pareto_stability_status = NOT_APPLICABLE_GATE_BLOCKED
substantive_rank = NULL
substantive_tie_flag = 0
```

阻断候选不能因为在阻断队列内部“相对更好”而获得采购推进顺序。

### 12.2 同队列实质排序键

以下五个可行动队列在各自队列和范围内生成实质顺序：

```text
READY_TO_PUBLISH
READY_FOR_SEASONAL_DEVELOPMENT
READY_FOR_LOCAL_PILOT
CONDITION_FIRST
EXPLORATORY_RESEARCH
```

实质顺序只使用：

```text
evidence_tier_order ASC
pareto_front_id ASC
front_1_probability DESC
```

`evidence_tier_order` 直接读算法 08 的版本化层级映射，算法 10 无可编辑配置。

### 12.3 实质并列

当两个候选的以下字段完全一致时：

```text
recommendation_action_queue
evidence_tier
pareto_front_id
front_1_probability
```

输出：

```text
substantive_tie_flag = 1
substantive_rank = 相同 DENSE_RANK
```

产品必须同时展示它们各自的优势，不得将后台行顺序解释为业务优劣。

### 12.4 技术行顺序

数据库导出必须有稳定行顺序时，在全部实质键之后追加：

```text
candidate_scope_result_id ASC
```

同时保存：

```text
technical_row_number
technical_tiebreak_only_flag = 1
```

### 12.5 排名不使用的字段

```text
门店等级字母
采购点击数
采购手工收藏
商品名字典序
图片是否好看
供应商是否主动联系
人工“我觉得有趋势”标记
```

## 13. 主力消费人群在推荐中的作用

### 13.1 主力人群是适用范围，不是一个人工加分项

同一个 `final_profile` 的候选共享算法 03 的人群结构，因此 `member_share` 和 `sales_share` 用于：

```text
说明该新品服务的人群规模
展示会员数占比与销售额占比
对全部画像查询做分组
```

它们不在同一画像候选内重复加分，避免所有候选都被加上相同数值。

### 13.2 产品端必须展示的结构

```text
消费者类型
是否主力人群
有效会员数
会员数占比
有效会员销售额
销售额占比
小票数
客单价
主力判定稳定性
```

### 13.3 无明显主力人群

```text
result_status = NO_OBVIOUS_MAIN
```

时不生成“主力消费人群是X”的句子，模板改为：

```text
该门店群在当前叶子小分类下消费者贡献结构较均衡，
没有统计上明显分离的主力人群。以下建议按所选画像单独计算，
不代表该画像被强制定义为主力。
```

### 13.4 捡漏型展示约束

捡漏型直接读算法 01 `final_profile = 捡漏型`：

```text
不追加大/小家庭
不追加高/中/低频
不追加价格敏感/非敏感
```

算法 10 不从商品价格或折扣重新组合捡漏型名称。

## 14. 季节、局部和探索候选

### 14.1 正式季节窗口

算法 10 读取 S 状态商品的正式上下架日期，自动生成：

```text
season_window_status = BEFORE_CURRENT_WINDOW
season_window_status = ACTIVE
season_window_status = AFTER_CURRENT_WINDOW
```

当期销售季结束后，不把候选改成全年商品，而是保留下一个有效季节窗口或等待商品主数据发布下一季窗口。

### 14.2 局部试点范围

`LOCAL_PILOT_NEW_PRODUCT` 使用算法 08 已输出的稳定正向门店子群证据。算法 10 只能将下游需求范围写成：

```text
applicable_subgroup_evidence_ids
scope_applicability_status = LOCAL_STABLE_SUBGROUP
```

不根据采购点选自动换成其他门店。具体试点门店选择是后续实验设计模块，不在算法 10 中加一个人工列表。

### 14.3 探索候选

```text
PASS + EXPLORATORY_NEW_PRODUCT
-> EXPLORATORY_RESEARCH
```

可生成研究需求草稿，但文本必须写：

```text
当前为探索方向，用于补充本地需求、法规或供给证据，
不是已经通过正式立项的新品。
```

### 14.4 待补条件

`CONDITIONAL_PASS` 不参与 `READY_TO_PUBLISH` 的正式排名。自动结论必须优先展示：

```text
condition_reason_codes
condition_to_clear
condition_evidence_ids
allowed_next_action = PUBLISH_VALIDATION_REQUIREMENT
```

即使该候选在机会证据中属于第一前沿，也不能隐藏条件。

## 15. 自动结论的事实载荷与文本生成

### 15.1 先生成事实，后生成文本

每条推荐先生成 `recommendation_fact_payload_json`，至少包含：

```text
范围事实
主力消费者事实
具体商品和规格事实
锚点商品行为事实
购物篮属性事实
外部趋势与竞品事实
价格、成本和毛利事实
门禁、条件和允许动作事实
图片 ID、来源类型和授权状态
全部证据 ID 和版本
```

### 15.2 必须出现的采购层事实

```text
建议开发的具体商品名 + 明确规格
城市/城市群 + 门店等级 + 消费者类型 + 叶子小分类
会员数、会员数占比、销售额、销售额占比、小票数和客单
现有高表现锚点是什么
哪个新品属性来自购物篮或外部证据
建议售价、成本上限和目标毛利
门禁结果和下一步动作
```

### 15.3 确定性模板分支

#### 15.3.1 正式可发布

```text
{city_group} / {final_level}级门店在{leaf_category}下，
{final_profile}覆盖{member_share}的有效会员并贡献{sales_share}的有效会员销售额。
现有锚点{anchor_product} 的{anchor_evidence_summary}；
{new_attribute_source_summary}。
建议开发“{candidate_product_name} {recommended_spec}”，建议零售价{price}，
全链路成本上限{cost_ceiling}，目标毛利率{margin_target}。
当前货盘、历史失败、法规与价格毛利门禁通过，
可生成正式开发需求。
```

#### 15.3.2 待补条件

```text
“{candidate_display_name}”的新品机会证据已成立，但当前门禁结果为待补条件。
必须先完成：{condition_to_clear}。
当前只能发布验证需求，不能表述为“已正式通过”。
```

#### 15.3.3 退回重构

```text
“{candidate_display_name}”当前不进入新品推荐队列。
原因：{rebuild_reason}。
需要按{upstream_rebuild_target}重构商品实体、规格或价格方案，
生成新范围候选后重跑算法 05—10。
```

#### 15.3.4 拒绝

```text
“{candidate_display_name}”已退出当期新品池。
硬拒绝原因：{blocking_reason_text}。
该结论不因高消费需求、外部趋势或采购采纳而改变。
```

### 15.4 LLM 改写的边界

LLM 可以将确定性模板改写成更简洁的采购语言，但必须先产生一个候选文本，再通过自动事实校验。

```text
允许：调整语序、去除重复、转换为更通俗的句子
不允许：新增商品属性、价格、比例、趋势、风险、因果或行动
```

### 15.5 自动事实校验

系统对生成文本执行：

```text
1. 所有数字、百分比、金额和规格必须匹配事实载荷的格式化值
2. 所有商品名、属性、画像和品类词必须出现在载荷或版本化业务词典
3. 门禁状态、条件和允许动作必须完全一致
4. 禁止“必然热销”“成功率”“竞对消费者接受”等无证据表述
5. 必须包含状态分支要求的全部关键事实
```

任一项失败：

```text
llm_paraphrase_status = REJECTED_FACT_MISMATCH
final_explanation_text = deterministic_template_text
```

不进入人工判断补文字。

## 16. 购物篮、外部趋势、竞品和图片的结论组装

### 16.1 购物篮只使用真实规则输出

对 `BASKET_RECIPE` 候选，自动结论必须同时展示正向和反向指标：

```text

```

### 16.2 配方属性和连带商品分开

```text

-> 关联商品的允许属性可写入新品开发需求

餐食互补/场景关联
-> 只写入 basket_context_products_json
```

```text

```

### 16.3 外部趋势分支

| 外部状态 | 结论中的准确说法 |
|---|---|
| `FORMAL_GROWING_TREND` | 该属性在指定外部市场和数据窗口中存在通过贝叶斯 FDR 的增长证据 |
| `MATURE_MARKET_GAP` | 成熟主体存在有证据的差异化空白或改良约束，不是“渗透低所以必然有机会” |
| `OVERSEAS_LEADING_EXPLORATORY` | 海外领先信号已发现，但本地证据仍属探索 |

| `RAW_EXTERNAL_SIGNAL` | 只有原始信号，不得写成正式趋势 |

必须展示：

```text

后验中位数和95%可信区间
来源平台、市场和周期
“社媒净推荐代理值”标签
```

不得省略“代理值”三个字。

### 16.5 竞品图片与商品一致性

算法 10 只使用算法 07 已校验图片，必须同时满足：

```text
JOIN external_candidate_image AS image
  ON image.run_id = recommendation.primary_image_source_run_id
 AND image.image_id = recommendation.primary_image_id

image.standard_candidate_id = recommendation.standard_candidate_id
image.is_primary_image = 1
image.copyright_or_authorization_status 允许展示
image_match_validation_status = PASSED
OCR 和属性不与候选冲突
```

算法 07 早于算法 09 运行，因此最终商品身份以算法 09 的 `standard_candidate_id` 为准。算法 09 注册时已经完成一次图片候选身份对账；算法 10 只复核“来源运行 + 图片 ID + 最终标准候选 ID”三者一致，不在此处重新做模糊图片匹配。算法 07 与算法 09 的候选身份不一致时必须输出 `IMAGE_CANDIDATE_ID_MISMATCH` 并置空图片，不能选择其中一个 ID 继续展示。

图片回退顺序不在 10 里重新决定，直接沿用 07：

```text
同款竞品真实图
-> 经校验的高相似竞品参考图
-> 已标识的 AI 开发示意图
-> NO_VALID_IMAGE
```

鸡蛋候选不得使用净菜或牛肉图，青椒黑椒牛柳丝不得使用牛肉丸或牛肉面图。

## 18. 缺失、冲突和异常处理

### 18.1 不允许默认补值

```text
缺外部证据 != 外部得分0
缺购物篮属性 != 关联得分0
缺成本下限 != 成本下限0
缺包装 != 自动使用同品类众数包装
缺图片 != 使用其他商品图
```

### 18.2 商品身份冲突

```text
推荐商品名或规格与算法 09 不一致
-> CANDIDATE_IDENTITY_CONFLICT

standard_candidate_id 相同但身份载荷不同
-> IMMUTABLE_CANDIDATE_PAYLOAD_CONFLICT

candidate_scope_result_id 相同但价格或范围载荷不同
-> IMMUTABLE_SCOPE_PAYLOAD_CONFLICT
```

以上全部阻断正式发布，不用算法 10 文本覆盖。

### 18.3 图片冲突

```text
primary_image_id 与 standard_candidate_id 不一致
-> IMAGE_CANDIDATE_MISMATCH

授权状态不允许展示
-> IMAGE_NOT_AUTHORIZED

没有通过校验图片
-> primary_image_id = NULL
-> image_status = NO_VALID_IMAGE
```

没有图片不改商品身份，也不调低门禁结果；产品显式告知“暂无已校验商品图”。

### 18.4 主力人群冲突

```text
算法 10 查询主力画像，但算法 03 is_main_profile = 0
-> PROFILE_MAIN_STATUS_CONFLICT

算法 03 result_status = NO_OBVIOUS_MAIN，但文本生成“主力人群是”
-> EXPLANATION_PROFILE_FACT_CONFLICT
```

### 18.5 门禁结果变更

新的货盘、法规、历史失败或成本数据生成新 `gate_run_id` 后：

```text
旧 recommendation_result 保留
新 gate_run_id 生成新 recommendation_run_id
不更新旧行
采纳事件保留当时快照哈希
```

### 18.6 异常不跨范围回退

```text
上海 A 级结果异常
不用上海 B 级或华东整体结果替代

目标画像证据缺失
不用全部画像平均结果替代

叶子小分类模板缺失
不用中分类通用模板生成模糊商品需求
```

## 20. 完整计算过程

本章的“完整计算”是指将算法 01—09 的正式结果按身份、范围、周期和版本串成一条可复算证据链，不是在算法 10 中重新拟合前置模型。

```text
算法 10 可以做：
按上游同一公式复核加减乘除、区间、状态映射和哈希
对账上游已储存结果
对同一可比较单元复算 Pareto 前沿
生成行动队列、自动结论和开发需求草稿

算法 10 不可以做：
重新训练算法 01—08 的模型
修改上游分类、阈值、后验、商品身份或门禁结果
把上游缺失值自动补成0
为了得到可发布结论而擅自改规格、售价或商品属性
```

上游复核值与已储存值超过规定精度时，记录 `UPSTREAM_RECALC_MISMATCH`，当前范围结果进入 `NOT_CALCULABLE`，不选择其中一个值继续发布。

### 20.1 第一步：创建运行批次

```text
读取算法 10 版本
读取 candidate_registry_run_id
读取 gate_run_id
读取正式周期和数据截止时间
构造规范化运行载荷
生成 recommendation_run_id
```

### 20.2 第二步：冻结全量门禁结果

```text
input_rows
= 指定 gate_run_id 的全部 new_product_gate_result
```

每条输入先写入快照表，不先排名、筛选、去重或只保留可发布记录。

### 20.3 第三步：对账算法 09 候选身份

```text
input_rows
JOIN mart_new_product_candidate_scope AS scope
  ON scope.candidate_registry_run_id = input_rows.candidate_registry_run_id
 AND scope.candidate_scope_result_id = input_rows.candidate_scope_result_id
JOIN new_product_standard_candidate_registry AS candidate
  ON candidate.candidate_registry_run_id = input_rows.candidate_registry_run_id
 AND candidate.standard_candidate_id = input_rows.standard_candidate_id
```

只用 `candidate_scope_result_id` 或 `standard_candidate_id` 关联会在历史追加批次中串版本，必须与 `candidate_registry_run_id` 组成联合关联键。

校验：

```text
商品名和规格
城市群、等级、画像、叶子小分类
价格与成本方案
candidate_payload_hash
属性来源 ID
图片 ID
```

### 20.4 第四步：关联算法 01—07 解释证据

```text
算法 01 -> final_profile 含义与版本
算法 02 -> 门店等级范围、正式唯一键和引用键
算法 03 -> 主力人群规模、占比和稳定性
算法 04 -> 锚点商品、偏好、复购、自然动销和毛利
算法 05 -> 规格、价格、成本、毛利与竞对价格
算法 06 -> 购物篮规则、配方属性和场景商品
算法 07 -> 外部趋势、竞品、社媒代理值、图片和改良约束
```

任何 JOIN 多对多导致候选数膨胀时，输出 `DUPLICATE_EVIDENCE_JOIN_ERROR`。

### 20.5 第五步：校验版本包

```text
对账周期
对账模型版本
对账分类与属性版本
对账货盘和法规快照
对账候选和门禁哈希
```

版本冲突记录保留在快照和审计表，不进入正式队列。

### 20.6 第六步：生成推荐结果 ID

```text
candidate_scope_result_id
+ gate_run_id
+ recommendation_algorithm_version
-> recommendation_result_id
```

候选输入顺序不得改变任何 ID。

### 20.7 第七步：映射行动队列

按第 7 章确定性映射：

```text
new_product_gate_result
+ final_candidate_status
+ allowed_next_action
-> recommendation_action_queue
```

三个字段不一致时不猜测正确结果。

### 20.8 第八步：展开共同证据维度

将 `common_dimension_metrics_json` 展开为一行一维度，写入证据维度表。

```text

校验不确定性引用
校验存储精度
```

### 20.9 第九步：继承并验证可比较单元

```text
读取算法 08 comparison_cell_id_from_gate
按范围键 + 季节比较桶 + 证据层级 + 门禁状态 + 适用指标签名
复算 comparison_cell_id_recomputed
两者一致 -> comparison_cell_id = comparison_cell_id_from_gate
两者不一致 -> COMPARISON_CELL_MISMATCH + NOT_CALCULABLE
```

对同一单元的候选数、指标数和缺失状态进行对账。

### 20.10 第十步：复算点估计 Pareto 前沿

```text
按存储精度四舍五入
按指标方向计算支配关系
执行逐层非支配分组
与算法 08 pareto_front_id 对账
```

### 20.11 第十一步：计算前沿后验稳定性

对五个可行动队列，按第11章读取联合后验、门店×月份块、会员簇和情景分布，逐轮加倍取值数直至数值收敛。

`RETURN_FOR_REBUILD` 和 `NOT_RECOMMENDED` 不执行后验稳定性抽样，按第12.1节写入不适用状态；仍保留并对账算法08的点估计前沿。

### 20.12 第十二步：生成实质优先级与并列

```text
队列内分组
-> evidence_tier_order
-> pareto_front_id
-> front_1_probability
-> DENSE_RANK 生成 substantive_rank
-> 识别 substantive_tie_flag
```

`candidate_scope_result_id` 只在此后生成技术行顺序。

### 20.13 第十三步：生成结构化事实和自动解释

```text
生成 recommendation_fact_payload_json
生成 deterministic_template_text
可选调用 LLM 改写
执行数字、商品、属性、状态和动作事实校验
失败时回退确定性模板
```

### 20.14 第十四步：生成开发需求草稿

```text
读取叶子小分类 requirement_schema_version
将候选属性、价格、成本、范围和证据映射到草稿
生成 development_requirement_draft_id
计算必填字段完整性
根据队列和完整性生成 publication_type 与 can_publish_requirement
```

### 20.15 第十五步：原子写入和运行完成

```text
写入8张结果表的临时分区
检查输入数 = 推荐结果数 + 不可计算异常数
检查唯一键
检查哈希和血缘
检查队列与门禁一致
检查文本事实和草稿完整性
全部通过后一次性切换正式分区
```

任一核心检查失败时，`run_status = FAILED`，不暴露半批次新结果。

### 27.1 比较单元

```text
周期：2026年4—6月

门店等级：A
```

### 27.2 共同维度

| 维度 | A | B | 优势 |
|---|---:|---:|---|
| `TARGET_DEMAND_STABILITY` | 0.90 | 0.82 | A |
| `PRICE_COST_FEASIBILITY_SLACK` | 0.70 | 0.76 | B |

### 27.3 支配判定

```text

B 在价格成本空间和差异化证据上优于 A

```

### 27.4 后验前沿稳定性

假设自动收敛时：

```text
B_valid = 65,536

A 在第一前沿的次数 = 41,288
B 在第一前沿的次数 = 38,011
```

复算：

```text
front_1_probability_A
= 41,288 / 65,536
= 0.6300

front_1_probability_B
= 38,011 / 65,536
= 0.5800
```

有效取值量等于原始取值量时：

```text
MCSE_A
= sqrt(0.63*0.37/65,536)
= 0.001886

1.96*MCSE_A
= 0.003697
< 0.005

MCSE_B
= sqrt(0.58*0.42/65,536)
= 0.001928

1.96*MCSE_B
= 0.003779
< 0.005
```

且两位小数结果连续两轮未变，因此收敛。

`A在第一前沿` 和 `B在第一前沿` 不是互斥事件：同一次后验取值中，A 和 B 可以同时位于第一前沿。因此：

```text
两个候选的第一前沿次数之和可以大于 B_valid
front_1_probability_A + front_1_probability_B 不需要等于1
front_1_probability 不是新品成功率
```

### 27.5 展示顺序与业务解释

```text
A 与 B 都在第一 Pareto 前沿
A 的前沿稳定概率高于 B
-> A 在列表中先展示
```

正确解释：

```text
两个候选在不同证据维度各有优势，都属于第一前沿。
A 在当前证据不确定性下保持第一前沿的稳定性更高，
因此默认先展示；这不表示它的新品成功概率更高。
```

### 27.6 完全实质并列

若两者最终都为：

```text

evidence_tier = SINGLE_PATH_FORMAL
pareto_front_id = 1
front_1_probability = 0.63
```

则：

```text
substantive_rank_A = substantive_rank_B
substantive_tie_flag_A = 1
substantive_tie_flag_B = 1
```

数据库可以按 `candidate_scope_result_id` 显示一个稳定行顺序，但界面必须标识“并列候选”。

## 28. 开发实现要求

### 28.1 结构化计算优先

```text
候选身份 -> 结构化 ID 和属性表
证据维度 -> 结构化维度表
门禁映射 -> 版本化状态映射
Pareto -> 数值比较
草稿 -> 品类模板和属性投影
文本 -> 最后一层展示
```

禁止从 `final_explanation_text` 再解析价格、人群、配料或门禁状态。

### 28.2 非支配算法

对每个可比较单元，可使用标准 fast non-dominated sorting。单元候选量较小时，双重循环的清晰实现优先于难以验证的近似算法。

伪代码：

```text
remaining = all candidates in comparison_cell_id
front_no = 1

while remaining is not empty:
  current_front = []

  for a in remaining:
    dominated = false
    for b in remaining:
      if b dominates a:
        dominated = true
        break
    if not dominated:
      current_front.append(a)

  assign front_no to current_front
  remaining = remaining - current_front
  front_no = front_no + 1
```

### 28.3 数值类型

```text
金额：DECIMAL(18,4)
比率和概率原值：DECIMAL(20,10)
正式 front_1_probability：DECIMAL(5,2)
正式排名比较：使用来源 stored_precision 规范化值
哈希：CHAR(64)
ID：前缀 + CHAR(64)
```

中间统计保留更高精度，不用页面展示值重算。金额计算禁止使用 `FLOAT/DOUBLE`；对外展示到分时统一使用十进制定点 `ROUND_HALF_UP`：

```text
17.90 * (1-25%)
= 13.4250
-> 展示及算法05/09合同值 13.43
```

算法 10 的权威输入仍是算法 05 经算法 09 固化后的金额字段；本规则用于复核和跨语言一致性，不允许算法 10 用页面值反向覆盖上游原值。

### 28.4 幂等性

同一：

```text

```

