# 算法卡开发可直接交付复核模板

用途：后续每张算法卡在声明“可直接开发”前，必须由一名不了解上下文的真实数据开发按本模板走完一遍。模板检查的是“能否得到唯一、可复算、可追溯的实现”，不是只检查业务原文有没有被摘录。

## 使用规则

```text
1. 先冻结算法编号、职责、不做什么、上游、下游和正式运行顺序。
2. 先读取 04_algorithm_cards/算法文档输出规范.md 和 03_data_contracts/，再写待确认项。
3. 业务原文承接矩阵、业务解读版、开发版和审阅清单逐项交叉检查；任何一份出现不同英文枚举、字段名或版本口径，都视为不通过。
4. 只要开发仍需自行猜字段、聚合、阈值、优先级、空值或重跑版本，就不能标记“可直接开发”。
5. 每次检查必须留下：检查日期、检查人/角色、扫描命令、反例结果、阻断项和仍需真实数据验收项。
```

## A. 职责和上下游

| 检查项 | 必须回答 |
|---|---|
| 编号和名称 | 当前算法编号、正式名称是否与上游/下游文档一致 |
| 做什么 | 一句话说明比较对象、范围、结果和用途 |
| 不做什么 | 明确不承担的预测、因果、画像、审批或页面实时计算 |
| 上游 | 读取哪些正式表和哪个发布版本；是否会重复计算上游 |
| 下游 | 哪些算法/查询读取本结果；读取条件是否明确 |
| 顺序 | 离线预计算、参数训练、正式结果、前端查询顺序是否唯一 |

## B. 运行流程

必须标明：

```text
离线批量产出哪些过程表、参数表、正式结果表；
候选商品、成本、竞对或其他后续输入何时进入；
前端是查询条件还是算法输入事实；查询是否只读已发布结果；
空候选、缺成本、缺竞对、缺参数时仍输出什么、什么字段为空、什么状态生效；
同版本重跑、规则升级、范围变化分别如何处理。
```

## C. 输入表、字段、主键和关联

逐张输入表检查：

```text
正式表名、粒度、主键、字段中文名/英文名/类型/是否必须/来源/注释；
关联键、关联方向、时间有效条件、是否一对多；
数据合同已明确的事实不得再写成业务待确认；
旧表名、别名和未冻结表名不得混入开发交付。
```

## D. 去重和过滤

```text
每张源表先按合同主键验重；重复时是阻断、去重还是汇总必须写死；
交易状态、退货、取消、测试、非正值的字段和枚举必须可执行；
规则版本和 SQL/程序摘要必须登记，规则只能新增版本，不能原地修改；
过滤会员指标和非会员指标的边界必须分别写清。
```

## E. 中间粒度

检查每一步的一行代表什么：

```text
明细 -> 日 + 门店 + SKU -> 门店 + 品类 -> 比较组；
SUM、COUNT、COUNT DISTINCT 的对象和去重键；
多仓、多验收商品、多来源候选是否会重复放大金额、数量或样本；
大/中/小类是否都从底层重新聚合，不能平均下级结果。
```

## F. 每个公式的分子、分母和空值

逐公式建立“小账本”：

| 项目 | 必须写清 |
|---|---|
| 分子 | 来源字段、过滤条件、聚合方式、正负号 |
| 分母 | 来源字段、粒度、是否去重、是否允许为 0/负数 |
| 分母为 0 | NULL、NOT_APPLICABLE 或 NOT_CALCULABLE 的唯一选择 |
| 分子为 0 | 若分母为正，保留合法数值 0，不当缺失 |
| 负数 | 有效经营结果还是异常；是否保留、是否剔除训练 |
| 缺失 | 维度缺失、降置信、等级上限或整行不可计算 |
| 可复算字段 | 比率/得分是否保留必要分子、分母或参数摘要 |

不能用一个“缺失时重算”概括所有公式；必须列出每个关键比率的具体行为。

## G. 参数训练和选参

动态参数必须闭合：

```text
候选集合如何生成；
训练样本粒度、最小样本数、候选质量门；
“稳定、显著、接近、较优”等词如何量化；
评价指标分母为 0 的处理；
排序字段、升降序、并列决胜；
唯一 AUTO_PUBLISHED 约束；
生效开始/结束日期和主任务查参 SQL；
无候选、全不稳定、历史参数缺失时的降级；
候选、发布、退役、不采用是否可在数据库复核。
```

业务没有确认的阈值不能伪装成业务规则；若采用 V1 开发默认值，必须标明“默认值”、写入运行参数并在模型版本中留痕。

## H. 状态和枚举

建立“正文公式—输出字段—状态约束—审阅清单”交叉表，检查：

```text
同一含义只有一个英文名称和一组枚举；
*_status、*_flag、*_method、*_source 均有允许值、中文含义、触发条件；
JSON 数组/对象说明键、值和空数组写法；
数值字段不写 NOT_APPLICABLE 等字符串，状态另列字段；
SUCCESS、NOT_CALCULABLE、DATA_INSUFFICIENT、UNSTABLE 等状态可由 SQL 唯一判断。
```

## I. 正式输出表字段合同

每张正式输出表必须单独检查：

```text
表名、一行代表什么、主键/唯一键；
字段表头严格为：中文字段名 | 英文字段名 | 类型建议 | 是否必须 | 字段来源 | 中文注释；
状态字段在同一字段表和状态约束中闭环；
缺失、不适用、降级、不可计算时每个字段如何写；
下游需要的模型版本、范围版本、规则版本、运行ID和清单摘要是否存在。
```

## J. 版本、发布和重跑

至少演练四条路径：

```text
首次运行：生成范围/规则/模型版本和发布指针；
源数据修正重跑：沿用同一版本和原快照，只更新运行审计；
范围或规则变化：新版本与旧版本共存，不能物理覆盖；
参数/逻辑变化：模型清单摘要改变，发布指针原子切换。
```

正式结果写入前必须校验结果、参数、规则摘要和发布指针完全一致；失败时整批回滚。

## K. 下游读取

必须给出下游唯一查询逻辑：

```text
先按算法编码、数据周期、目标范围读取唯一 AUTO_PUBLISHED 发布指针；
再用指针中的模型版本 + scope_version + 规则版本关联正式结果；
禁止按 MAX(version)、MAX(calculated_at) 或最新更新时间猜版本；
NOT_CALCULABLE 不得被当成最低等级或 0 分。
```

## L. 反例验收

至少准备并复算以下样例：

```text
正常样本；
分母为 0、分子为 0、负毛利/负贡献；
输入字段缺失、源表缺分区、主键重复；
一对多、多对一、多仓、多验收商品；
同分、并列排序、所有分数相同；
样本不足、参数全不稳定、历史参数缺失；
多条底线同时触发；
范围删除后旧版本重跑；
会员规则 V1/V2 同周期共存；
能形成正式主键但不能计算、连主键都不能形成。
```

每个反例要有输入、预期字段值、状态、是否落正式表和审计表位置。

## M. 静态扫描和交叉一致性

交付前固定执行：

```bash
git diff --check
```

并扫描：

```text
逻辑字段名、建议类型、物理表名待开发确认、待开发确认、需要用户确认、是否能到、字段中文注释补充、英文枚举中文注释、状态枚举表、采购手动输入候选、可比商品组字典；
已废弃表名 data_agent.dws_member_order_item_detail_df_all、dws_member_order_item_detail_df_all；
旧审批枚举 APPROVED、PENDING_APPROVAL、REJECTED（若不是历史说明）；
正文/字段合同/状态约束/审阅清单的版本、枚举和表名交叉引用。
```

命中项必须逐条判断，不能以“只是示例”跳过。最终结论只能写成：

```text
业务原文已承接 / 可进入开发评审 / 可直接开发
```

只有 P0 级的不确定实现全部清零，且 L、M 通过，才允许使用“可直接开发”。
