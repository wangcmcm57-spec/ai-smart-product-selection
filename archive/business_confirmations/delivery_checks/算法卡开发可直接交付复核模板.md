# 算法卡开发可直接交付复核模板

版本：V1.1
状态：后续算法卡整理、修复、复核的强制前置模板
适用范围：算法 01-10 及以后新增算法
维护位置：archive/business_confirmations/delivery_checks/

V1.1 变更：正式交付物精简为业务解读版和开发版算法卡；既有承接矩阵与审阅清单冻结归档，不再要求日常同步维护。

## 0. 使用规则（必须执行）

本模板不是参考建议，而是算法卡开发交付前的强制复核闸门。

后续任何算法卡出现以下动作时，必须先阅读本文件并按本文件留下复核证据：

~~~
新建算法卡
修复算法卡
补充数据字段、公式、阈值或状态
修改输入/输出表
修改上游或下游依赖
声称“可以交付开发”
~~~

执行顺序固定为：

~~~
1. 先读 AGENTS.md。
2. 再读 04_algorithm_cards/算法文档输出规范.md。
3. 再读 03_data_contracts/ 中与本算法有关的正式数据合同。
4. 冻结算法编号、名称、职责边界和上下游顺序。
5. 阅读本模板，在当前工作记录中完成本算法复核。
6. 内部逐章承接业务原文，再修改业务解读版和开发版算法卡；无需新增或更新承接矩阵、审阅清单。
7. 通过字段级交付闸门、数据质量验收和文本扫描后，才能给出交付结论。
~~~

没有完成上述步骤，不得把算法卡表述为“开发可直接使用”。

### 0.1 运行自动化边界

算法按已登记的规则、参数和版本自动运行。业务人工复核的是运行结果，不是算法运行前的批准按钮。

~~~
允许：系统自动读取已发布的规则/参数，自动计算并写入结果表。
允许：结果生成后由业务查看、抽样、对账和提出重跑要求。
禁止：把业务查看或人工 APPROVED 设为算法 02 等后续算法的运行前置条件，除非业务原文明确要求该人工门禁。
~~~

如果项目存在审批状态，必须明确它属于：

~~~
规则/参数发布状态
结果复核记录状态
还是算法运行前置状态
~~~

不能仅因为字段取值为 APPROVED，就推断“必须有人点击后才能跑算法”。

## 1. 本次算法身份冻结表

修改任何逻辑前先填写，不能用历史编号或旧顺序代替当前正式口径。

| 项目 | 本次确认内容 |
|---|---|
| 算法编号 | 例如：算法 02 |
| 算法名称 | 例如：门店品类等级 |
| 本算法回答什么问题 | 用一句业务语言写清楚 |
| 本算法明确不做什么 | 写出边界，防止职责越界 |
| 上游正式表/算法 | 写正式表名和算法编号 |
| 下游正式使用方 | 写正式表名、算法编号或业务用途 |
| 正式运行顺序 | 写当前唯一顺序，不保留历史反向解释 |
| 本次修复范围 | 只列本次允许修改的章节和文件 |
| 不在本次范围内的内容 | 防止顺手改变原始业务逻辑 |

| 业务解读版 | 04_algorithm_cards/business_readable/ |  |  |  |

## 3. 业务原文逐章承接检查

复核过程必须按业务原文的实际章节逐项检查，不能只笼统判断“已承接”。本节检查可保留在当前工作记录中，不要求另建承接矩阵文件。

| 业务原文章节 | 业务规则/公式/阈值/状态/输出 | 业务解读版位置 | 开发版位置 | 是否完整承接 | V1 是否适配 | 适配原因/风险 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

逐章至少检查：

~~~
算法目标和使用边界
输入数据和业务对象
过滤规则和有效数据定义
公式、权重、阈值和动态分层
缺失、异常、不适用和不可计算处理
版本、范围、调度和重跑规则
正式输出表、参数表和解释表
明确禁止的事情
~~~

V1 如果改变数据来源或实现方式，必须同时写清：业务原文怎么写、V1 怎么落地、为什么这样落地、是否阻断正式结果。

## 4. 输入字段物理合同检查（本次审计漏洞的核心修复）

不能只检查“公式有没有”。必须逐个字段确认开发拿到后能判断“用哪张表、哪一行、哪种含义、能不能加总”。

### 4.1 每个输入字段的强制登记表

| 中文字段名 | 英文字段名 | 物理表名 | 表粒度 | 主键/唯一键 | ETL 来源/转换 | 字段真实含义 | 是否可直接聚合 | 聚合前去重/关联规则 | 同名字段差异 | 缺失/异常写法 | 数据合同依据 |
|---|---|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  |  |  |  |

字段表必须能回答：

~~~
1. 这个字段来自哪张正式表、哪一列？
2. 一行数据代表什么？字段是行级、订单级、会员日级、门店商品日级还是其他粒度？
3. 主键是什么，物理表是否真的唯一？
4. 字段是原始值、ETL 计算值还是本算法派生值？
5. 能否直接 SUM、COUNT、去重或做比率？不能时应如何先聚合？
6. 同名字段在不同表中是否含义不同？
7. 一个字段是否已经包含另一个字段？例如总折扣是否已包含时段折扣？
8. 空值、0、负数、NOT_APPLICABLE 和数据不足分别代表什么？
~~~

### 4.2 数据合同事实与待确认项的边界

如果 03_data_contracts/ 已明确表名、字段含义、粒度、主键和关联字段，不得继续写成“待用户确认”。只能写成：

~~~
按数据合同已定义为……
开发交付时验收是否实际按合同产出。
~~~

只有以下事项才可保留为业务/开发待确认：

~~~
数据合同尚未定义的业务含义
多个正式来源冲突且无法由合同裁决
影响正式计算结果的新增规则、阈值或版本选择
生产交付尚未证明唯一、完整或稳定的事实
~~~

### 4.3 字段包含关系和口径参数

只要存在“字段 A 是否包含字段 B”的可能，必须登记运行口径参数，不能让开发通过字段值猜口径。

| 参数名 | 中文含义 | 允许值 | 当前采用值 | 写入位置 | 未登记时处理 |
|---|---|---|---|---|---|
|  |  |  |  | 运行清单、模型清单摘要、结果血缘 | 阻断正式计算或按明确降级规则处理 |

参数登记必须闭环到：

~~~
运行清单
模型清单摘要
正式结果血缘/审计字段
~~~

例如折扣字段包含关系必须登记 promotion_discount_scope（促销折扣口径），不能仅靠以下组合推断：

~~~
discount_amt = 0
discount_amt = hour_discount_amt
discount_amt > 0 且 hour_discount_amt = 0
discount_amt > 0 且 hour_discount_amt > 0
~~~

这些组合只能用于数据质量对账，不能替代字段口径登记。

## 5. 运行参数、版本和重跑规则

| 参数/版本 | 中文含义 | 来源 | 可选值/格式 | 首次运行 | 同版本重跑 | 规则变更重算 |
|---|---|---|---|---|---|---|

| 区域映射快照 | 本批次锁定的城市算法区域映射 | 调度运行清单/批次快照 | 生效日期或快照标识 | 与统一批次版本一起锁定 | 沿用原快照 | 新批次重新锁定 |
| 数据周期 |  |  |  |  |  |  |
| 规则版本 |  |  |  |  |  |  |
| 字段口径参数 |  |  |  |  |  |  |

必须明确：

~~~
一批数据只能对应一个 algorithm_batch_version，且算法 01～10 共用。
源数据修正重跑必须沿用原 algorithm_batch_version 和原区域映射快照。
业务规则或范围映射变化默认从下一完整月数据窗口的新批次生效，不得生成算法独立版本号。

## 6. 公式、指标和字段来源闭环

每个公式都必须能追溯到字段合同和聚合步骤。

| 指标/结果字段 | 公式 | 每个输入字段来源 | 计算粒度 | 分子/分母 | 缺失或不适用处理 | 可复算字段 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

重点检查：

~~~
百分比、得分、等级判断是否保留可复算分子/分母或参数。
公式中的字段是否和输出字段合同使用同一个英文名。
同名字段是否在公式中明确带表名或来源别名。
跨表关联是否会重复放大金额或数量。
金额、数量、重量、件数是否混用。
时间边界是否明确为左闭右开或业务约定。
~~~

## 8. 正式输出表字段级交付闸门

先列出所有过程表、参数表、审计表和正式下游读取表，标明用途。正式结果表逐张检查：

~~~
一行代表什么
主键或唯一键
完整字段合同
状态字段允许取值
缺失、不适用、降级写法
~~~

正式输出字段表表头必须严格使用：

~~~
中文字段名 | 英文字段名 | 类型建议 | 是否必须 | 字段来源 | 中文注释
~~~

字段来源必须能定位到：

~~~
基础表

~~~
状态字段 | 中文字段名 | 允许取值 | 中文含义 | 触发条件
~~~

## 9. 运行流程和自动化执行

业务解读版和开发版都必须回答：

~~~
1. 哪些结果是离线批量预计算。
2. 哪些结果依赖上游候选、成本、竞对或规则输入。
3. 哪些结果由前端直接读取，不在查询时实时重算。
4. 前端输入是筛选条件还是算法事实；没有业务原文依据时不得写成手动录入候选。
5. 开发先产出哪些前置表，再产出哪些正式结果表。
6. 无候选、无成本、无竞对、无规则等场景下，哪些表仍输出，哪些字段写缺失状态。
7. 结果生成后业务如何查看和复核；复核不能反向成为算法运行前置条件。
~~~

## 10. 字段级真实数据验收

至少准备一个可复核样例，不能只验收最终等级或最终标签。

| 验收层级 | 必须输出的证据 | 通过条件 |
|---|---|---|
| 输入明细 | 原始行、主键、来源表、过滤前后记录数 | 主键重复和异常关联可解释 |
| 字段含义 | 字段样例、业务解释、来源/ETL | 和数据合同一致 |
| 聚合对账 | 分组前后行数、金额/数量/重量 | 无重复放大，误差在约定范围 |
| 公式复算 | 分子、分母、中间值、结果 | 可由输出字段复算 |
| 状态处理 | 缺失、0、负数、不适用样例 | 写法和状态枚举一致 |
| 版本血缘 | 模型、范围、规则、周期、重跑原因 | 可追溯、可重跑 |
| 最终结果 | 正式表样例和唯一键 | 一行代表和主键一致 |

验收记录至少包含：样例范围、SQL/脚本、输入行数、输出行数、对账差异、失败样例和处理结论。

## 13. 本次修改交付说明

每次向用户交付前，必须主动列出：

~~~
1. 变更文件：完整相对路径。
2. 核心修改点：按文件说明，不只说“已优化”。
3. 未修改的原始业务逻辑：明确哪些内容保持不变。
4. 已通过的验证：命令、样例或扫描结果。
5. 仍需用户复核的红线：只列真正会影响结果或交付的事项。
6. 当前开发结论：三类结论中选择一类。
~~~

本模板本身的维护规则：

~~~
如果后续算法卡复核再次发现新的系统性漏洞，先更新本模板，再修算法卡。
更新模板后，后续算法卡必须按新版本重新过闸。
~~~
