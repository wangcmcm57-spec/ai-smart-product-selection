# 算法09_业务待确认事项汇总

更新时间：2026-09-04

适用范围：算法 09 新品机会证据合成与风险门禁

阅读对象：业务、商品、营运、供应链、质量、法务、财务、采购、产品

本文目的：

```text
把算法 09 后续版本需要业务侧补充的规则资产单独放在一个文件里。
第一版已确认的折扣依赖、成本来源和当前货盘相似口径不再作为待确认问题重复出现。
```

本文不做三件事：

```text
1. 不要求业务手工判断每个候选商品能不能过门禁。
2. 不要求业务手工生成历史相似商品清单。
3. 不把数据开发实现问题当成业务确认问题。
```

## 1. 先看结论

算法 09 第一版已经确认：商品状态和 `S` 商品计划上架窗口按 `dim_product_status` 与算法 08 快照读取；折扣依赖、成本来源、当前货盘同款和高相似边界按 V1 算法口径执行，不再要求业务单独补规则。

以下业务确认项第一版暂不做，只作为后续规则资产建设方向：

```text
什么叫真正经营失败；
什么叫季节结束；
什么叫正常换码或 SPU 迁移；
什么叫供应中断；
什么叫法规或食品安全退出；
什么叫经营策略调整；
什么叫仍在售但尚未退出；
什么情况下只能算退出原因未知。
```

这些规则第一版不做时，算法 09 仍然可以完整输出，但相关门禁必须降级：

```text
可以保留历史风险线索；
可以输出证据不足；
不能把停订、无销售、负毛利或折扣依赖直接写成经营失败；
不能因为历史失败触发硬拒绝。
```

## 2. 后续版本：历史退出原因判定逻辑

### 2.1 为什么后续要补

算法能从系统里看到：

```text
商品是否可订、可售；
商品是否停止订购；
停止前销售好不好；
停止前毛利好不好；
停止前是否依赖折扣；
后续是否恢复可订可售。
```

但这些只能说明“经营表现和状态变化”，不能直接说明商品为什么退出。

例如：

```text
商品停订了，可能是经营失败；
也可能是季节结束；
也可能是换码；
也可能是供应中断；
也可能是法规或食品安全退出；
也可能是商品策略调整。
```

所以后续版本需要补退出原因判定逻辑；第一版不要求业务补齐。

### 2.2 建议业务提供格式

| 退出原因 | 业务要给的判断逻辑 | 需要排除什么 | 可用证据举例 | 能否触发历史失败硬拒绝 |
|---|---|---|---|---|
| 真正经营失败 | 什么情况下可以认定商品因经营表现失败而退出，例如生命周期足够长、自然动销长期差、毛利长期不达标、折扣依赖严重且停订后未恢复 | 季节结束、换码、供应中断、法规退出、策略调整 | 可订可售状态、销售、毛利、折扣、业务确认记录 | 只有规则明确且回测通过后才可以 |
| 季节结束 | 哪些商品是季节商品，计划上架窗口结束是否等于正常季节结束，季外停订是否正常 | 非季节商品、提前异常停订 | SAP POP 商品状态、计划上架开始/结束日期、实际上下架记录 | 不能触发经营失败硬拒绝 |
| 正常换码或 SPU 迁移 | 旧码和新码是否同一标准实体，什么时候算正常迁移 | 真实淘汰、供应中断 | 商品主数据、换码关系、SPU 关系 | 不能触发经营失败硬拒绝 |
| 供应中断 | 哪些记录证明商品因供应问题停订 | 经营表现失败、策略下架 | 供应商停供、缺货、采购记录 | 不能触发经营失败硬拒绝 |
| 法规或食品安全退出 | 哪些质量、法规或食品安全事件导致退出 | 普通经营失败 | 质量事件、法务规则、监管记录 | 不能按经营失败处理，按法规门禁处理 |
| 经营策略调整 | 什么是货盘策略、区域策略、品牌策略或经营策略调整 | 动销差自然淘汰 | 商品调整记录、经营策略记录 | 不能直接触发经营失败硬拒绝 |
| 仍在售但尚未退出 | 截止日仍可订可售或后续恢复可订可售 | 短期缺货、数据延迟 | 可订可售快照、恢复记录 | 不能当成成功，也不能当成失败 |
| 退出原因未知 | 以上原因都无法确认，或证据不足 | 无 | 缺正式原因、证据冲突 | 不能触发历史失败硬拒绝 |

### 2.3 暂时没有规则时的 V1 降级

第一版按以下方式处理：

```text
historical_exit_reason = UNKNOWN_EXIT
historical_outcome_status = UNCERTAIN_OUTCOME
historical_failure_gate_status = INSUFFICIENT_HISTORICAL_EVIDENCE
```

人话就是：

```text
历史上可能有风险；
但证据不足；
不能硬拒绝新品候选。
```

## 3. 已确认 V1：商品状态和 S 计划上架窗口

### 3.1 当前怎么落地

商品状态不再由业务在 09 单独补 Excel。当前按基础数据合同落地：

```text
数据开发从 SAP POP 平台落 dim_product_status；
算法 08 读取并透传 product_status_code、seasonality_status、season_start、season_end；
算法 09 只读取算法 08 快照，不从商品名、销量曲线或停订事实反推状态。
```

### 3.2 S 日期缺失时怎么处理

季节商品季外没有销售，不代表消费者不喜欢，也不能当作经营失败。

如果 `product_status_code = S` 但计划上架开始或结束日期缺失：

```text
08 写 seasonality_status = SEASON_WINDOW_INCOMPLETE；
09 允许候选继续进入门禁；
09 生成 SEASON_WINDOW 条件风险；
无更高风险时输出 CONDITIONAL_PASS；
不能输出正式季节推荐信号；
不能把季节相关停订或无销售写成经营失败。
```

### 3.3 后续版本还需要什么

后续如果要打开历史失败硬判定，还需要补“历史退出中的季节结束归因规则”，不是再新增一张算法 09 临时季节表。

后续规则要回答：

```text
计划上架窗口结束是否一定代表正常季节结束；
提前停订是否异常；
跨区域、跨年份的 S 状态怎么处理；
是否存在每年重复的销售季规则；
季节结束、换码、供应中断和经营失败冲突时谁优先。
```

## 4. 后续版本：换码、SPU 迁移和替代关系判断

### 4.1 为什么后续要补

V1 可以用商品基础表里的 SPU 做标准商品归并，但 SPU 不能完整替代正式换码关系和替代关系。

后续版本需要说明：

```text
哪些旧码和新码是正常换码；
哪些商品只是 SPU 迁移；
哪些商品是替代关系；
哪些商品虽然相似，但不是同一标准实体。
```

第一版不提供时：

```text
当前货盘可以先用 SPU 辅助判断；
历史失败不能因为缺换码或替代关系硬拒绝；
只能输出相似灰区或证据不足。
```

## 5. 后续版本：供应中断和经营策略调整判断

### 5.1 为什么后续要补

算法不能从小票或可订可售状态自动知道商品停订是不是供应原因或策略原因。

后续版本需要说明：

```text
什么记录能证明供应中断；
什么记录能证明策略调整；
供应中断和经营失败冲突时谁优先；
策略退出和经营失败冲突时谁优先。
```

第一版不提供时：

```text
停订商品不能直接写成经营失败；
历史退出原因只能写 UNKNOWN_EXIT；
历史失败门禁不能硬拒绝。
```

## 6. 后续版本：法规、食品安全、标签和功能声称规则

### 6.1 为什么后续要补

算法 09 不能让 AI 自己做法律或质量判断。

后续版本由业务、质量和法务把重点规则说清楚：

| 需要回答的问题 | 以 Omega-3 为例 |
|---|---|
| 哪个商品或声称触发规则 | 鲜鸡蛋商品使用 Omega-3 营养声称 |
| 需要哪些证明材料 | 检测报告、营养标签、声称依据是否都需要 |
| 材料缺失怎么办 | 待补证、人工复核还是直接拒绝 |
| 什么情况硬停 | 禁止使用、检测不合格、食品安全不满足等 |
| 规则依据是什么 | 法规、标准或公司质量规则 |
| 规则什么时候生效 | 生效日期和失效日期 |

第一版不提供时：

```text
法规规则不启用硬门禁；
算法 07 有风险线索时只留痕，不驱动当前门禁；
不能假装合规通过。
```

## 7. 已确认算法 09 V1 口径：估算成本推进口径

这项不再要求业务单独给 SRM 接入口径。算法 09 V1 按 `mart_store_sku_daily_price` 合同主键读取成本，派生仓商品日成本口径；取值优先 `purchase_settlement_price`，再看 `daily_purchase_price` 和 `outbound_arrival_cost_tax_included`。

业务后续如果要补，只需要补基础数据表和校准样本，不再重复确认成本来源链路。

## 8. 已确认算法 09 V1 口径：折扣依赖和毛利压力动作边界

这项不再单独找业务给阈值。算法 09 V1 已固定用 `19:30 前自然售罄率 + 19:30 后价格弹性 + CRITIC 权重 + P20/P50/P80 分位` 来分层；如果底表只有 19 点前/后字段，由开发在时段加工中显式映射或补加工。

折扣依赖档位与毛利压力组合后的动作已按 V1 执行：低/中依赖且毛利通过可继续推进，高/严重依赖但毛利通过只留观察线索，毛利需要补证时进入 `CONDITIONAL_PASS` 或 `RETURN_FOR_REBUILD`，算法 05 无可行交集才 `REJECT`。

## 9. 已确认算法 09 V1 口径：当前货盘同款和高相似业务边界

这项也不再单独要求业务补一套口径。算法 09 V1 已固定五字段相似度：品型、口味、规格、百克标价、工艺。

五字段相似度采用加权 Gower 式 kNN，权重分别是 30%、25%、20%、15%、10%。V1 以 `0.85` 作为高相似硬门槛，`0.70` 到 `0.85` 或字段不足时进入灰区复核；不再让业务重新解释同款和高相似的边界。

## 10. 业务不需要手工提供什么

以下由系统、数据开发或算法开发完成：

```text
历史相似商品清单生成；
候选和当前货盘商品相似度计算；
候选和历史商品相似度计算；
机会证据和风险证据汇总；
版本锁定、运行批次、重算和审计；
K-medoids 真实情景选择；
Pareto 同层候选比较；
把已确认的业务规则落成规则表和执行逻辑。
```

后续版本建设规则资产时，业务、商品、质量、法务和财务再补充规则边界，复核重点样例，并处理系统无法判断的专业灰区。

## 11. 当前可交付口径

在上述规则未全部补齐前，算法 09 可以按 V1 降级方式交付：

```text
可以输出机会证据；
可以输出风险线索；
可以输出有条件通过、返回重做或不可评估；
可以基于 `dim_product_status` 识别商品状态和 S 计划上架窗口；
可以把历史退出原因未知写清楚；
不能把历史停订直接写成经营失败；
不能因为历史失败触发硬拒绝；
不能把法规或功能声称风险写成已通过，也不能因为法规留痕单独改成条件通过。
```

一句话总结：

```text
算法 09 能先落地；商品状态和 S 计划上架窗口在 V1 已接入，但“历史失败硬拒绝”和“法规功能声称硬门禁”先不打开，只保留留痕和后续版本资产；S 窗口缺失、价格、成本和验证类原因可以形成有条件通过。
```
