# 上海试点 AI 新品推荐工作台业务需求第一版

更新时间：2026-09-04

文档状态：第一版草案，待业务、产品、数据开发、后端 / Agent 开发共同复核。

## 1. 文档定位

本文用于定义智慧中台内“AI 新品推荐”模块的上海试点业务需求，重点回答：

```text
采购在页面上怎么查；
页面要展示什么；
反馈和埋点怎么收集；
API 和 Harness 后续应该围绕哪些能力拆解；
哪些边界 V1 不做。
```

本文不是算法卡，不替代算法 01～10 的开发版算法卡；本文只描述采购在线使用场景。算法结果仍由离线或准离线任务预先产出，页面查询和 Agent Harness 不实时重算算法。

本版 PRD 已按算法 10 最新 V1 口径约束：页面和 Harness 只展示算法 10 已发布推荐结果，不展示算法 09 中 `RETURN_FOR_REBUILD` 或 `REJECT` 的候选，也不在 V1 回答“为什么某个未展示候选没被推荐”。

## 2. 背景和目标

AI 选品 V1 的核心目标是帮助采购在新品开发前，更快看到可解释、可追溯、可反馈的新品机会。

上海试点模块要解决的问题是：

```text
华东采购需要在智慧中台中，按运营大区、城市和商品分类查询系统已计算好的新品推荐结果；
采购需要看到每个新品方向为什么推荐、面向什么用户画像、竞对价格如何、行业趋势是否支持、是否存在风险；
采购需要对推荐结果做简单反馈，帮助项目侧判断推荐是否符合业务认知，并为后续算法复盘留下记录。
```

本模块第一版目标：

| 目标 | 说明 |
|---|---|
| 能查 | 采购可以按上海试点条件查询新品推荐列表 |
| 能看懂 | 每条推荐能展示推荐理由、用户画像、竞对价格、行业趋势、风险和试点建议 |
| 能反馈 | 采购可以对单条推荐点击“很好 / 不好” |
| 能追溯 | 推荐结果能追溯到算法批次、证据和数据更新时间 |
| 能对接 | 后续 API 和 Harness 可以按固定查询、详情、证据、反馈能力拆解 |

## 3. 试点范围

| 项目 | V1 口径 |
|---|---|
| 试点城市 | 上海 |
| 目标用户 | 华东采购 |
| 业务场景 | 新品推荐场景 |
| 商品范围 | 7 个大分类 |
| 门店范围 | 覆盖上海全部门店群 |
| 入口系统 | 现有智慧中台，作为独立模块接入 |
| 结果来源 | 算法 10 推荐结果及其上游证据，不由页面实时计算 |

说明：

```text
“区域”指运营大区，例如华东 1 区、华东 2 区、华东 3 区，不指上海行政区。
“覆盖上海全部门店群”表示算法结果需要覆盖上海门店群；V1 页面不要求采购手工选择单个门店。
```

## 4. 使用对象和权限

### 4.1 主要用户

| 用户 | 使用目的 |
|---|---|
| 华东采购 | 查询上海新品推荐、查看证据和风险、反馈推荐是否有价值 |

### 4.2 相关角色

| 角色 | 使用目的 |
|---|---|
| 产品 / 项目侧 | 查看采购反馈、判断推荐是否需要调整展示或补数据 |
| 数据开发 | 根据异常和审计排查算法结果表、证据表、数据批次 |
| 后端 / Agent 开发 | 对接查询、详情、证据、反馈、日志接口 |

### 4.3 权限要求

V1 只允许有智慧中台采购权限的用户访问模块。

权限控制至少覆盖：

```text
1. 用户能否进入 AI 新品推荐模块。
2. 用户能否查询上海试点数据。
3. 用户反馈行为是否记录到个人账号或工号。
```

无权限时，页面不展示推荐结果，提示用户当前无权限访问该模块或该区域数据。

## 5. 页面形态

第一版页面采用“结构化筛选 + 推荐结果列表 + 推荐详情 / 证据展示 + 单条反馈”的工作台形态。

建议页面从上到下分为：

| 区域 | 内容 |
|---|---|
| 查询筛选区 | 运营大区、城市、大分类、中分类、小分类、查询按钮、重置按钮 |
| 推荐结果区 | 推荐新品列表、卡片图片位和每条推荐的核心摘要 |
| 推荐详情区 | 推荐理由、用户画像、竞对价格、行业趋势、风险、试点建议 |
| 反馈区 | 每条推荐下方的“很好 / 不好”按钮 |

如果保留自然语言入口，建议作为辅助入口：

```text
采购可以输入“上海牛肉类目有没有适合年轻家庭的新品方向”等问题；
Harness 将自然语言转成结构化查询条件，或针对当前已展示推荐结果做解释；
第一版不要求自然语言入口替代结构化筛选。
```

## 6. 查询条件和交互规则

### 6.1 查询字段

| 查询条件 | 字段含义 | V1 规则 | 是否必选 | 默认值 |
|---|---|---|---|---|
| 运营大区 | 华东下的运营大区，例如华东 1 区、华东 2 区、华东 3 区 | 单选，支持“全部” | 非必选 | 全部 |
| 城市 | 试点城市 | V1 固定上海；页面可展示但不建议让用户切换到非试点城市 | 必选 | 上海 |
| 大分类 | 商品一级分类 | 单选；只展示试点 7 个大分类 | 必选 | 空 |
| 中分类 | 商品二级分类 | 级联大分类；大分类选择后展示可选中分类 | 必选 | 空 |
| 小分类 | 商品叶子或更细分类 | 级联中分类；可不选 | 非必选 | 空 |

### 6.2 分类级联

分类选择采用级联关系：

```text
先选大分类；
再选中分类；
小分类可选；
更换大分类时，自动清空中分类和小分类；
更换中分类时，自动清空小分类。
```

### 6.3 查询按钮

点击“查询”后：

```text
1. 校验大分类和中分类是否已选择。
2. 校验城市是否为上海。
3. 按当前查询条件读取预计算推荐结果。
4. 展示推荐列表、结果数量、结果批次和数据更新时间。
5. 记录一次查询埋点。
```

如果必选条件缺失：

```text
不发起查询；
提示用户补齐大分类和中分类；
页面保留当前已选条件。
```

### 6.4 重置按钮

点击“重置”后：

```text
1. 运营大区恢复为“全部”。
2. 城市恢复为“上海”。
3. 大分类、中分类、小分类清空。
4. 推荐列表清空。
5. 推荐详情清空。
6. 反馈状态清空为当前页面初始状态。
7. 记录一次重置埋点。
```

重置不删除已经写入后端的历史反馈记录。

## 7. 推荐结果展示

### 7.1 列表展示

查询成功后，页面展示推荐新品列表。每条推荐以卡片形式展示，卡片默认保留图片区域。

图片展示规则：

```text
图片已经匹配候选，且授权状态允许展示时，展示真实图片；
无图、授权未知、未授权、图片待复核或图片身份不匹配时，展示占位或隐藏真实图；
前端不能自行用外部图片兜底替换；
图片不可展示原因需要由接口返回，供页面提示和审计追溯。
```

每条推荐至少展示：

| 展示项 | 说明 |
|---|---|
| 推荐新品名称 | 候选展示名，含规格时展示规格 |
| 推荐分类 | 大分类、中分类、小分类 |
| 适用范围 | 上海、运营大区或门店群 / 门店等级等适用范围 |
| 推荐展示标签 | 正式推荐、季节推荐、局部试点、探索推荐、条件推荐 |
| 推荐理由摘要 | 一句话说明为什么值得看 |
| 用户画像 | 目标消费者画像，例如年轻家庭、品质型等 |
| 建议价格 | 建议零售价或价格区间；缺失时展示“价格待补” |
| 竞对价格 | 竞对商品价格或价格区间；缺失时展示“暂无竞对价格” |
| 行业趋势 | 行业趋势摘要；缺失时展示“暂无趋势证据” |
| 风险提示 | 无明显风险、需补材料、价格风险、法规风险等摘要 |
| 试点建议 | 是否建议试点、建议试点范围或待补条件 |
| 结果更新时间 | 推荐批次或数据截止时间 |

V1 列表不展示“不推荐”标签。算法 09 中 `RETURN_FOR_REBUILD` 和 `REJECT` 的候选不进入算法 10 推荐展示表，也不出现在采购推荐列表中。

### 7.2 详情展示

用户点击某条推荐后，展示该推荐的详情。详情至少包含：

| 模块 | 展示内容 |
|---|---|
| 推荐结论 | 推荐展示标签、推荐状态、同范围优先级 |
| 推荐理由 | 系统生成的最终解释文本，必须基于结构化事实；如启用大模型润色，事实校验失败时回退模板文案 |
| 用户画像 | 目标画像名称、画像贡献、销售额 / 会员占比等摘要 |
| 内部证据 | 锚点商品表现、购物篮关联、价格带或毛利可行性摘要 |
| 竞对价格 | 竞品名称、平台、规格、价格、价格时间和来源 |
| 行业趋势 | 趋势方向、外部来源、时间、趋势强弱或摘要；V1 不得写成 Social NPS 或消费者口碑结论 |
| 风险和门禁 | 当前货盘、历史失败、法规、毛利、图片授权等风险结论 |
| 试点建议 | 建议试点门店群、试点范围、试点注意事项、待补条件 |
| 追溯信息 | 推荐运行批次、推荐结果 ID、证据 ID、数据截止时间 |

### 7.3 展示优先级和排序

默认排序读取算法推荐结果，不由前端重新计算。

排序规则：

```text
1. 优先读取算法 10 输出的 recommendation_display_order。
2. 同范围内展示算法 10 的 substantive_rank。
3. 如果存在技术行号，只作为稳定展示顺序，不解释成业务优先级。
4. 前端不允许通过“很好 / 不好”即时改变排序。
5. front_1_probability 只表示第一前沿稳定性，不展示或解释成新品成功概率。
```

### 7.4 分页和数量

V1 建议：

```text
每页默认展示 20 条；
支持分页或加载更多；
页面展示当前查询条件下的总结果数；
没有结果时展示空态，不展示假推荐。
```

## 8. 反馈和埋点需求

### 8.1 反馈入口

每条推荐下方展示两个按钮：

```text
很好
不好
```

反馈对象是一条推荐结果，不是整页查询结果。

### 8.2 反馈规则

| 规则 | V1 口径 |
|---|---|
| 反馈粒度 | 用户 + 推荐运行批次 + 推荐结果 ID |
| 是否必须反馈 | 非必须 |
| 是否允许同一用户重复反馈同一推荐 | 允许修改选择，但以后端最后一次有效反馈作为当前反馈状态 |
| 是否影响当前推荐排序 | 不影响 |
| 是否影响后续算法 | V1 只沉淀反馈日志，后续复盘时再决定是否进入算法迭代 |
| 是否写回算法 10 | 不写回算法 10 正式结果表，不改变推荐标签、排序、门禁或解释 |
| 反馈存储位置 | 写入产品反馈日志或埋点系统；如后续需要进入算法复盘，单独设计反馈汇总表 |
| 是否需要备注 | V1 不强制；后续可扩展“不好原因” |

### 8.3 反馈后的页面状态

点击“很好”后：

```text
很好按钮高亮；
不好按钮恢复未选中；
提示“已记录反馈”。
```

点击“不好”后：

```text
不好按钮高亮；
很好按钮恢复未选中；
提示“已记录反馈”。
```

反馈失败时：

```text
提示“反馈提交失败，请稍后重试”；
不改变后端反馈状态；
前端可以保留临时点击状态，但需要在刷新或重查后以后端状态为准。
```

### 8.4 埋点事件

V1 至少埋点以下事件：

| 事件 | 触发时机 | 关键字段 |
|---|---|---|
| `ai_selection_page_view` | 进入模块页面 | 用户 ID、角色、时间、来源菜单 |
| `ai_selection_query_click` | 点击查询 | 用户 ID、运营大区、城市、大分类、中分类、小分类、查询来源 |
| `ai_selection_reset_click` | 点击重置 | 用户 ID、重置前筛选条件 |
| `ai_selection_result_exposure` | 推荐结果出现在列表可视区域 | 用户 ID、查询 ID、推荐运行批次、推荐结果 ID、展示顺序、推荐标签 |
| `ai_selection_detail_open` | 打开推荐详情 | 用户 ID、查询 ID、推荐运行批次、推荐结果 ID |
| `ai_selection_feedback_good_click` | 点击很好 | 用户 ID、查询 ID、推荐运行批次、推荐结果 ID、当前筛选条件 |
| `ai_selection_feedback_bad_click` | 点击不好 | 用户 ID、查询 ID、推荐运行批次、推荐结果 ID、当前筛选条件 |
| `ai_selection_api_error` | 查询、详情或反馈接口失败 | 用户 ID、接口名、错误码、查询条件 |

埋点字段至少包含：

```text
user_id
user_role
session_id
event_time
region_id / region_name
city_id / city_name
major_category_id / major_category_name
middle_category_id / middle_category_name
leaf_category_id / leaf_category_name
query_id
recommendation_run_id
recommendation_result_id
recommendation_display_label
recommendation_display_order
page_no
source
```

### 8.5 埋点和算法审计边界

反馈和曝光属于产品应用层事件，不属于算法 10 V1 的计算输出。

边界规则：

```text
查询筛选条件可以由查询服务写入算法 10 审计表，审计类型为 QUERY_FILTER；
曝光、详情打开、很好、不好、接口错误等前端事件写入埋点或产品反馈日志；
这些事件不得改写 recommendation_display_label、recommendation_display_order、new_product_gate_result、final_explanation_text；
如果后续要把采购反馈用于算法优化，必须另建离线复盘链路，不在页面点击后即时重算。
```

## 9. 空态、异常和降级

### 9.1 初始状态

用户刚进入页面时：

```text
城市默认上海；
运营大区默认全部；
大分类、中分类、小分类为空；
不展示推荐列表；
提示用户选择大分类和中分类后查询。
```

### 9.2 必选条件缺失

如果大分类或中分类未选择：

```text
不发起查询；
在对应字段附近提示必选；
保留用户已选条件。
```

### 9.3 无推荐结果

如果接口返回空列表：

```text
展示“当前条件下暂无新品推荐结果”；
展示当前查询条件；
展示结果批次或数据截止时间；
不生成兜底推荐。
```

### 9.4 推荐结果未产出或批次不可用

如果算法 10 最新成功批次不存在，或当前查询条件对应结果未产出：

```text
展示“当前条件下推荐结果尚未生成”；
提示用户稍后再查或联系项目侧；
后端记录异常日志。
```

### 9.5 数据过期

如果推荐结果超过约定更新时间：

```text
页面仍可展示结果；
必须展示数据更新时间或数据截止时间；
必要时提示“当前结果为上一批次结果”。
```

### 9.6 接口失败

接口失败时：

```text
展示失败提示；
允许用户重试；
保留筛选条件；
不清空已有成功查询结果，除非用户点击重置。
```

### 9.7 无权限

无权限时：

```text
不展示推荐数据；
提示无权限访问；
记录权限拦截日志。
```

## 10. 数据时效和批次展示

V1 查询默认读取最新成功推荐批次。

更新频率以算法 10 发布批次为准：

```text
正式运行默认跟随算法 10 月度正式运行；
算法 09 门禁因新成本、新法规、新货盘或证据修正重算后，算法 10 生成新的推荐批次；
历史周期修复或规则版本变化时，可由数据侧触发回溯重算；
页面和 Harness 只读最新 run_status = SUCCESS 的发布批次，不控制算法调度。
```

页面需要展示：

| 字段 | 说明 |
|---|---|
| 推荐运行批次 | 当前结果来自哪次算法 10 运行 |
| 数据截止时间 | 算法结果使用的数据截止到什么时候 |
| 结果生成时间 | 推荐结果什么时候生成 |

V1 不要求采购切换历史批次。历史批次查询可作为后续能力。

## 11. API 需求边界

API 是页面和 Harness 读取结构化结果的唯一入口。页面和 Harness 不直接读取 Doris 明细表，也不直接读取算法 01～09 的底层明细。

V1 后端至少需要支持：

| API 能力 | 业务用途 | 主要读取或写入 |
|---|---|---|
| 查询筛选项 | 返回运营大区、城市、7 个大分类、中分类、小分类级联选项 | 组织 / 类目字典，或算法 10 已发布结果中的可选范围 |
| 查询推荐列表 | 按筛选条件返回推荐新品列表 | `mart_new_product_recommendation_priority` + `new_product_recommendation_display_brief` |
| 查询推荐详情 | 按推荐结果 ID 返回单条推荐完整信息 | `new_product_recommendation_display_brief` + `new_product_recommendation_explanation` |
| 查询证据明细 | 按推荐结果 ID 返回内部证据、竞对价格、行业趋势和风险证据 | `new_product_recommendation_display_brief.detail_module_json`、`new_product_recommendation_evidence_dimension`、证据来源 ID |
| 写入反馈 | 记录用户对单条推荐的“很好 / 不好”反馈 | 产品反馈日志或埋点系统，不写回算法 10 正式结果表 |
| 写入行为日志 | 记录查询、曝光、详情打开、错误等行为 | 查询筛选审计可写算法 10 审计；其他前端事件写产品行为日志 |

API 查询必须遵守：

```text
1. 只读取已发布成功批次的推荐结果。
2. 默认城市为上海。
3. 大分类和中分类为必传条件。
4. 小分类为空时，返回该中分类下所有小分类推荐。
5. 反馈写入不改变当前推荐结果和排序。
6. 只返回算法 10 已输出的推荐展示结果，即 PASS / CONDITIONAL_PASS 进入 10 后生成的推荐行。
7. 不提供 RETURN_FOR_REBUILD / REJECT 候选的推荐列表、展示摘要或不推荐追问解释。
8. 不返回 0-100 机会分、新品成功概率、无来源口碑结论或供应商匹配结论。
```

## 12. Harness 需求边界

Harness 是 Agent 的控制层，不是算法计算层。

V1 Harness 支持以下能力：

| 能力 | 说明 |
|---|---|
| 意图识别 | 判断用户是在查推荐、看已展示推荐的原因、看风险、看趋势、看竞对价格、看试点建议、反馈结果 |
| 参数抽取 | 从用户问题中抽取运营大区、城市、大分类、中分类、小分类、推荐结果 |
| 参数补齐 | 缺少必填条件时，一次只追问一个关键条件 |
| 工具调用 | 调用固定 API 查询列表、详情、证据和反馈 |
| 结果解释 | 把 API 返回的结构化结果解释成采购能看懂的话，只解释当前可见推荐候选 |
| 安全护栏 | 不实时重算、不跨城市借结果、不编造证据、不修改算法结论 |

Harness 示例：

| 用户问题 | Harness 行为 |
|---|---|
| 上海华东 1 区牛肉类有什么新品推荐 | 抽取区域、城市、分类，调用推荐列表 API |
| 为什么推荐这个 | 基于当前选中且已展示的推荐结果，调用详情和证据 API |
| 这个风险是什么 | 调用当前推荐的风险证据，解释门禁和风险状态 |
| 竞对价格怎么样 | 调用证据明细，返回竞对价格摘要 |
| 这个不错 | 如果当前上下文存在推荐结果，写入“很好”反馈；否则追问是哪条推荐 |

Harness 禁止行为：

```text
不能直接读 Doris 明细表；
不能实时重算算法 01～10；
不能把“没有数据”解释成“机会低”；
不能跨非上海城市生成推荐；
不能自己修改推荐展示标签、排序和门禁结论；
不能解释未进入算法 10 V1 展示结果的候选为什么没被推荐；
不能把 `RETURN_FOR_REBUILD` 或 `REJECT` 候选包装成推荐结果；
不能生成无依据的成功率、0-100 机会分、销量预测或确定性承诺；
不能把外部趋势、榜单、文章或竞品价格写成 Social NPS 或消费者口碑结论；
不能让大模型新增商品属性、价格、风险、趋势、供应商或开发动作。
```

## 13. 验收标准

### 13.1 页面功能验收

| 验收项 | 通过标准 |
|---|---|
| 筛选项 | 能展示运营大区、城市、大分类、中分类、小分类 |
| 必选校验 | 未选大分类或中分类时不能查询 |
| 分类级联 | 更换上级分类时，下级分类自动清空 |
| 查询 | 选择上海 + 大分类 + 中分类后能返回推荐结果或明确空态 |
| 重置 | 点击后条件和结果恢复初始状态 |
| 图片 | 每条推荐卡片有图片区域；无授权、无图或不匹配时展示占位或隐藏真实图 |
| 详情 | 能查看推荐理由、用户画像、竞对价格、行业趋势、风险、试点建议 |
| 反馈 | 每条推荐能点击很好 / 不好，并有即时反馈状态 |

### 13.2 数据结果验收

| 验收项 | 通过标准 |
|---|---|
| 数据范围 | 查询结果只返回上海试点范围内结果 |
| 分类范围 | 大分类限定在试点 7 个大分类内 |
| 推荐来源 | 每条推荐都能关联推荐运行批次和推荐结果 ID |
| 推荐资格 | 列表只展示算法 10 已输出的推荐结果；不出现 `RETURN_FOR_REBUILD` 或 `REJECT` 候选 |
| 推荐标签 | 推荐展示标签只能是正式推荐、季节推荐、局部试点、探索推荐、条件推荐 |
| 证据完整性 | 推荐理由、画像、竞对价格、行业趋势、风险中缺失项必须有明确缺失展示 |
| 排序一致性 | 页面排序与算法 10 输出排序一致 |
| 反馈不改结果 | 点击很好 / 不好后当前推荐排序和推荐结论不变化 |
| 禁用表述 | 页面不展示 0-100 机会分、新品成功概率或 Social NPS / 口碑结论 |

### 13.3 埋点验收

| 验收项 | 通过标准 |
|---|---|
| 查询埋点 | 每次点击查询生成查询事件 |
| 曝光埋点 | 推荐结果展示时能记录曝光 |
| 详情埋点 | 打开详情能记录事件 |
| 反馈埋点 | 很好 / 不好分别能记录事件 |
| 错误埋点 | 查询失败、反馈失败、无权限能记录错误或拦截事件 |
| 算法审计边界 | 只有查询筛选审计可进入算法 10 审计；曝光、点击、反馈写产品行为日志或反馈日志 |

### 13.4 Harness 验收

| 验收项 | 通过标准 |
|---|---|
| 查推荐 | 能把自然语言问题转成结构化查询 |
| 补参数 | 缺大分类或中分类时能追问 |
| 看原因 | 能基于推荐详情解释原因 |
| 看风险 | 能基于风险证据解释风险 |
| 写反馈 | 当前上下文明确推荐结果时能写入很好 / 不好 |
| 护栏 | 不编造结构化结果中不存在的事实，不解释未展示候选的不推荐原因，不生成成功概率或口碑结论 |

## 14. 不在 V1 范围

V1 不做：

```text
1. 非上海城市推荐。
2. 多城市对比。
3. 采购手工录入候选商品让系统实时判断。
4. 前端实时重算算法。
5. 大模型直接读 Doris 明细表。
6. 供应商匹配、供应商触达、报价排序。
7. 新品开发审批流。
8. 采购修改算法推荐结论或排序。
9. 历史批次切换和批次对比。
10. 复杂反馈问卷。
11. `RETURN_FOR_REBUILD` / `REJECT` 候选的列表展示、详情展示和不推荐原因追问。
12. 0-100 机会分、新品成功概率、Social NPS 或消费者口碑结论。
13. 采纳、拒绝处理、开发需求发布材料。
```

## 15. 依赖项

| 依赖 | 说明 |
|---|---|
| 算法结果表 | 算法 10 推荐结果、解释、证据、范围汇总等表需要产出 |
| 数据合同 | 城市、运营大区、分类、门店群、商品、竞对、趋势等字段口径需要稳定 |
| 类目字典 | 7 个大分类及其下中分类、小分类需要可查询 |
| 组织区域字典 | 华东运营大区与上海门店范围需要可查询 |
| 权限系统 | 需要识别用户是否有模块访问和上海试点数据权限 |
| 埋点系统 | 需要支持页面行为和反馈事件采集 |
| 产品反馈日志 | 需要记录用户对单条推荐的很好 / 不好反馈，不写回算法结果 |
| 图片展示规则 | 需要后端返回图片匹配、授权和展示状态，前端按状态展示真实图、占位或隐藏 |
| 后端 API | 需要提供筛选项、推荐列表、详情、证据、反馈、日志能力 |
| Harness | 需要提供意图识别、参数抽取、工具调用和解释能力 |

## 16. 风险和应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 算法结果表未按期产出 | 页面无法展示真实推荐 | 前端先接 mock 数据，正式验收必须切真实 API |
| 竞对价格或行业趋势缺失 | 推荐解释不完整 | 页面展示明确缺失状态，不编造竞对或趋势 |
| 分类口径不统一 | 查询条件和结果对不上 | 先统一 7 个大分类及中小分类字典 |
| 运营大区和门店群映射不清 | 查询结果覆盖范围不明确 | 由业务 / 数据确认运营大区到上海门店群的映射 |
| 排除候选被误展示 | 采购看到不该进入 V1 的候选 | API 只读算法 10 推荐展示结果，阻断 `RETURN_FOR_REBUILD` / `REJECT` |
| 图片授权不清 | 页面误用不可展示图片 | 后端返回图片展示状态，前端只在可展示状态下展示真实图 |
| 采购误以为点击反馈会立即改变推荐 | 业务预期偏差 | 页面和培训中说明反馈用于后续复盘，不影响当前排序 |
| Harness 解释过度 | 产生无依据判断 | 强制基于 API 返回事实解释，缺数据时明确说缺失；禁止成功概率、口碑和未展示候选原因追问 |

## 17. 待复核点

本版需要业务和开发重点复核：

```text
1. 试点 7 个大分类的具体名称和编码。
2. 华东 1 区、华东 2 区、华东 3 区等运营大区是否都覆盖上海门店。
3. 页面是否需要展示“门店群”筛选项，还是只在结果中展示适用门店群。
4. 城市在 V1 是否固定不可切换为上海，还是允许选择但只开放上海。
5. 自然语言入口是否进入第一版页面，还是先由结构化筛选承载查询。
6. “很好 / 不好”是否允许用户修改反馈。
7. “不好”是否需要在 V1 增加可选原因。
8. 图片无授权、无图或不匹配时，页面采用占位还是直接隐藏真实图。
9. 竞对价格和行业趋势缺失时的展示文案是否符合业务预期。
10. 推荐结果批次展示是否只展示最新成功批次，还是页面需要展示“上一批次结果”的提示样式。
11. 采购是否需要导出推荐列表；本版暂未纳入 V1。
```
