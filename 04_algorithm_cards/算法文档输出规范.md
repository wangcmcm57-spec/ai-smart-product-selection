# AI 选品算法文档输出规范

生成日期：2026-07-23
最近更新：2026-09-23

## 1. 文档共识

后续每个算法日常固定维护两类正式文档：

```text
业务解读版
开发版算法卡
```

业务解读版先让产品、业务、采购能看懂。

开发版算法卡再给数据开发落地实现。

既有业务原文承接矩阵和审阅清单保留为冻结历史材料，不再随算法卡日常修复同步更新，也不再要求新建。

交付前仍需在当前工作中逐章核对业务原文，但核对结论直接落实到业务解读版、开发版算法卡和本次交付说明，不再复制成两份独立材料。

原始业务文档只做溯源，不直接修改。

## 2. 业务逻辑判断护栏

文档规范只约束表达方式，不替代业务算法判断。

每次整理算法时必须遵守：

```text
1. 业务最新原始文档是算法逻辑基准。
2. 先冻结算法编号、算法名称、职责边界和上下游运行顺序，不能沿用旧编号或历史反向依赖。
3. 业务解读版只能把复杂逻辑讲清楚，不能改算法结论。
4. 为了可读性删除的内容，只能是旧版本说明、二期内容、产品展示、过重技术细节，不能删除正式算法规则。
5. 业务原文已有的公式、阈值、分层规则、异常处理、输出状态，必须在业务解读版或开发版算法卡中有对应表达。
6. 如果项目一期需要做字段适配，必须明确标注为“V1 落地口径”，不能伪装成业务原文规则。
7. 如果发现业务原文缺公式、缺阈值、缺字段口径，必须进入“现在还需要确认什么”，不能自行补成已确认规则。
```

### 2.0 算法编号和职责校验

如果业务原文、历史草稿或旧目录中出现算法编号调整，必须先做编号职责校验，再输出两份正式文档。

校验项固定为：

```text
算法编号
算法名称
本算法做什么
本算法不做什么
上游读取谁
下游交给谁
正式运行顺序
```

当前 08/09 正式口径：

| 算法 | 名称 | 职责 |
|---|---|---|
| 算法 08 | 新品候选标准化与合并 | 注册候选、标准化属性/名称/规格、生成 ID、合并来源、输出 09 快照 |
| 算法 09 | 新品机会证据合成与风险门禁 | 读取 08 标准候选，汇总机会证据，执行当前货盘、历史失败、法规、毛利等门禁 |

正式顺序：

```text
算法 04/05/06/07 -> 算法 08 -> 算法 09 -> 算法 10
```

不得再写成“算法 09 标准化、算法 08 门禁”，也不得保留“09 在 08 前执行”的旧解释。

每个算法在输出业务解读版和开发版算法卡前，必须完成一次业务原文内部承接核对：

```text
业务原文章节
业务原文核心逻辑
业务解读版对应位置
开发版算法卡对应位置
是否完整承接
如果 V1 改了数据来源或落地方式，为什么改
```

业务解读版用于理解，开发版算法卡用于落地。真正会阻断开发的风险集中写入开发版算法卡的待确认项或本次交付说明。

## 2.1 业务原文内部承接核对

逐章核对业务原文是每个算法卡输出的必走环节，但不再要求生成独立承接矩阵文件。

不能跳过原文核对直接写业务解读版或开发版算法卡。

内部核对必须逐章检查：

```text
1. 业务原文中的算法目标是否保留。
2. 业务原文中的输入数据是否保留。
3. 业务原文中的公式、权重、阈值、动态分层、统计处理是否保留。
4. 业务原文中的异常处理、状态字段、边界场景是否保留。
5. 业务原文中的输出表、参数表、解释表是否保留。
6. 业务原文中的“不能做的事”是否保留。
```

如果业务原文内容很多，业务解读版可以换成人话表达，但不能少掉正式算法规则。

如果为了 V1 落地改变数据来源，必须在开发版算法卡的边界说明或本次交付说明中写清楚：

```text
业务原文怎么写
V1 怎么落地
为什么这样落地
是否需要业务或数据开发确认
```

## 2.2 数据合同事实核验硬规则

写“待确认项”前，必须先检查数据合同目录：

```text
03_data_contracts/
```

如果数据合同已经明确了表粒度、主键、关联字段，就不能再向用户反复提问。

只能改成：

```text
按数据合同已定义为……
开发交付时验收是否按合同产出
```

当前已知事实：

| 表 | 数据合同粒度 / 主键 | 后续文档写法 |
|---|---|---|
| `mart_sku_margin_loss` 毛利损耗表 | 营业日期 + 门店编码 + 交易商品编码 | 已定义到日 + 门店 + 销售 SKU，不再问用户是否能到该粒度 |
| `mart_store_sku_daily_price` 门店商品日价格表 | 日期 + 门店编码 + 销售商品编码 + 验收商品编码 | 已定义到日 + 门店 + 销售 SKU + 验收 SKU，不再问用户是否能到该粒度 |
| `mart_store_sku_daily_sale_order_status` 门店商品每日可订可售表 | 日期 + 门店编码 + 销售商品编码 | 已定义到日 + 门店 + 销售 SKU，不再问用户是否能到该粒度 |
| `dim_sku` 商品基础表 | 一行一个商品 / 销售条码 | 已定义交易商品编码对齐小票 `article_id` |
| `dim_store` 门店基础表 | 一行一个门店 | 已定义门店编码对齐小票 `store_id` |
| Doris 小票商品明细表 | `order_item_id` 唯一键 | 已确认当前主表为 `data_agent.dws_member_order_item_detail_df_all_new`；`weight` 是商品行计价数量，算法统一映射为销售标准量；称重商品表示计价重量，计件商品表示件数/份数/袋数/只数；Doris 本身没有单位字段，单位需从商品基础表取得 |

开发评审时可以确认：

```text
实际交付是否按合同实现
主键是否唯一
字段是否有空值或口径差异
历史周期是否足够
```

但不能把“数据合同已经定义的粒度”继续作为让用户反复确认的问题。

## 3. 业务解读版怎么写

业务解读版的目标是：

```text
让用户、业务方、采购和开发评审人员先理解：
这个算法为什么存在
读取什么数据
按什么业务逻辑计算
最后输出什么
哪些口径还没确认
```

业务解读版不是开发实现文档，也不是产品原型文档。

业务解读版必须优先按下面顺序写：

```text
1. 先用一句话理解
2. 最终会输出什么
3. 它在 AI 选品链路中的位置
4. 一期用哪些底层数据
5. 数据周期怎么理解
6. 比较范围或计算范围怎么来
7. 核心业务对象怎么定义
8. 先过滤什么数据
9. 核心维度分别看什么
10. 每个维度怎么算
11. 综合分怎么合成
12. 等级、标签或结果怎么生成
13. 经营底线、风险或置信度怎么处理
14. 开发实际要怎么做
15. 业务验收看什么
16. 现在还需要确认什么
17. 不要做什么
18. 一句话总结
```

如果某个算法没有“等级、综合分、经营底线、风险、置信度”等模块，可以删除对应章节，但不能打乱整体阅读顺序。

不同类型算法允许使用更贴合业务的章节名，但要保持同样的信息顺序。例如：

```text
核心维度分别看什么
```

可以在画像贡献类算法中改成：

```text
基础指标怎么算
画像贡献占比怎么算
贡献得分怎么算
主力消费者类型怎么判定
```

## 4. 业务解读版章节要求

### 4.1 先用一句话理解

必须用一句业务语言解释算法，不使用公式、表名和工程术语开头。

句式建议：

```text
这个算法要判断：在什么范围里，比较什么对象，得到什么结论。
```

如果出现容易误解的词，必须马上解释。

示例：

```text
“会员覆盖”不是会员贡献会员规模，而是这个消费者类型里有多少购买会员。
```

### 4.2 最终会输出什么

必须提前说明最终输出表和一行代表什么。

必须包含：

```text
正式结果表名
结果粒度
一条示例
结果给后续哪个算法或业务动作使用
```

如果一个算法输出多张正式表，要先说清楚每张表的区别。

不要只在文档后半部分才写输出表。

### 4.3 它在 AI 选品链路中的位置

必须说清楚：

```text
上游依赖谁
本算法做什么
下游给谁用
本算法不做什么
```

如果算法只读取上游结果，必须明确：

```text
不重新计算上游算法
不重新贴标签
不重新评级
```

### 4.3.1 运行流程必须写清楚

每个算法都必须在业务解读版和开发版算法卡中写清楚“运行流程 / 开发执行流程”。不能只写算法目标、字段、公式和输出表。

必须回答：

```text
1. 哪些结果是离线批量预计算。
2. 哪些结果依赖候选商品、成本、竞对或其他后续输入。
3. 哪些结果是前端查询时直接读取，不在查询时实时重算。
4. 采购前端输入的是筛选条件还是算法输入事实。
5. 如果业务原文没有明确“手动录入”，不得推断成采购手动输入。
6. 开发应该先产出哪些前置表，再产出哪些正式结果表。
7. 无候选、无成本、无竞对等场景下，哪些表仍可输出，哪些字段必须输出缺失状态。
```

推荐写法：

```text
第一段：离线批量预计算什么。
第二段：候选、成本、竞对等后续输入什么时候进入。
第三段：前端查询读取哪些已计算结果。
```

对于推荐链路类算法，必须特别区分：

```text
系统候选商品记录 / 候选商品池：算法链路产生或标准化后的候选对象。
采购前端查询条件：城市、消费者画像、品类、门店群等筛选条件。
算法正式结果表：数据开发离线或准离线产出的可读取结果。
```

不能把“采购选择查询条件”写成“采购手动输入候选商品、规格、成本”。

### 4.4 一期用哪些底层数据

只列本期实际要用的数据。

不要列暂停表、二期表或未来增强表。

每张表只写：

```text
这张表用来干什么
关键关联字段是什么
```

详细字段清单放开发版算法卡。

### 4.5 数据周期和范围

必须讲清楚：

```text
用几个月数据
正式结果多久更新
比较范围是什么
是否允许跨城市/跨区域回退
是否有版本锁定
```

如果有“3 个月算正式结果、6 个月做参数参考”这种规则，必须用例子解释，避免误解成两版结果。

### 4.6 过滤、关联和口径

业务解读版可以写过滤和关联，但必须用业务语言解释“为什么要这样做”。

不要只写技术条件。

推荐格式：

```text
先讲业务原则
再讲当前 V1 可以落地的字段
最后列开发版需要确认的字段口径
```

示例：

```text
业务原则：只保留正常完成的正向销售。
V1 字段：order_status、is_return、refund_type、usual_amt。
待开发确认：取消、冲销、测试交易在 Doris 里对应哪些状态。
```

关联唯一性检查必须配例子解释。

不要只写：

```text
同一版本 + id 只能有一条
```

要说明如果不唯一，会导致什么后果：

```text
同一会员同一版本有两个画像，会导致同一笔销售被算进两个消费者类型。
```

### 4.7 算法步骤

复杂算法必须拆成业务步骤，不要一次性堆公式。

推荐写法：

```text
第一步：先算什么
第二步：再算什么
第三步：最后怎么判定
```

公式可以写，但每个公式后必须补一句业务解释。

例如：

```text
调和平均的作用是：只有会员覆盖和销售贡献同时高，得分才高。
```

### 4.8 输出字段

业务解读版只写字段组和业务含义。

不要展开完整开发字段清单。

完整字段名、类型、是否必须、中文注释放开发版算法卡。

### 4.9 开发实际要怎么做

这一节只写开发流程，不写完整 SQL、不写复杂参数表。

目标是让读者知道：

```text
开发会按什么顺序把数据算出来
最终会写到什么表
哪些过程表只是中间计算
```

### 4.10 业务验收看什么

验收要按层次写：

```text
数据是否对
公式是否对
结果是否合理
边界场景是否处理
```

不要把所有验收点混成一张长表。

### 4.11 现在还需要确认什么

只保留真正会影响落地的未确认项。

不要展示“已明确事项”。

每个确认项必须写：

```text
确认项
需要谁确认
为什么重要
```

### 4.12 不要做什么

必须列出最容易被误做的事项。

重点写：

```text
不能误用的数据
不能错误平均或相加
不能用旧规则
不能让大模型替代离线算法
不能只输出结果不保留过程证据
```

## 5. 业务解读版写作规则

业务解读版只讲当前确认的一期规则。

不要写：

```text
旧版本怎么改来的
业务以前怎么说
二期能力
已经明确的确认项
给业务的话术
过多数据库排查细节
产品端展示设计
页面交互设计
完整 SQL
完整建表 DDL
过多统计学术语堆叠
```

需要写：

```text
这个算法解决什么问题
输入哪些表
每张表用来干什么
一步一步怎么算
最终输出哪张表
输出结果给谁用
还剩哪些关键口径没确认
```

凡是没有业务依据或数据依据的规则，必须标记：

```text
待业务确认
待数据开发确认
V1 试跑建议，不是正式规则
```

不能把推测写成已确认事实。

如果某个规则来自业务原始文档，按业务原始文档写。

如果某个规则是根据现有数据做的一期适配，必须说明：

```text
这是 V1 落地口径
为什么要这样适配
是否需要数据开发或业务确认
```

业务解读版不要使用“建议”“可能”“最好”堆满全文。

确实未确认的地方，集中放在“现在还需要确认什么”。

## 6. 业务解读版自检清单

每次输出业务解读版后，必须自检：

```text
1. 是否先讲清楚这个算法在做什么。
2. 是否提前写了最终输出表和结果粒度。
3. 是否只保留本期会用的数据表。
4. 是否删除旧版本说明、二期内容、产品展示和过重开发细节。
5. 每个核心公式后是否有业务解释。
6. 每个容易误解的词是否配了例子。
7. 是否把“已明确事项”从确认清单里删除。
8. 是否只保留真正待确认项。
9. 是否说明本算法不做什么。
10. 是否能让非算法背景的人读懂主流程。
```

## 7. 开发版算法卡怎么写

开发版算法卡必须比业务解读版更细，能够让数据开发据此实现。

固定包含：

```text
1. 算法目标
2. 适用范围
3. 输入表清单
4. 输入字段清单，含中文注释
5. 字段映射关系
6. 数据过滤规则
7. 中间指标计算逻辑
8. 标签、评分、分层或推荐结果生成逻辑
9. 缺失值、异常值、不适用值处理
10. 输出表结构
11. 主键和唯一性要求
12. 参数表和版本字段
13. 调度周期
14. 验收样例
15. 数据质量验收清单
```

开发可以使用临时表或过程表，但文档必须明确最终正式交付表。

## 8. 正式文档和冻结历史材料的边界

业务确认材料目录已经按用途拆分：

| 子目录 | 用途 |
|---|---|
| `archive/business_confirmations/pending_items/` | 需要业务集中补充或确认的事项 |
| `archive/business_confirmations/review_checklists/` | 已冻结的历史审阅清单，不再日常维护 |
| `archive/business_confirmations/source_traceability/` | 已冻结的历史业务原文承接矩阵，不再日常维护 |
| `archive/business_confirmations/delivery_checks/` | 输出前逐项核对和交付前复核结论 |

| 文档 | 主要读者 | 目标 | 是否作为开发主交付 |
|---|---|---|---|
| 业务原文承接矩阵 | 你、我、项目侧复核人 | 历史阶段的逐章溯源记录 | 否，冻结归档，不再日常维护 |
| 业务解读版 | 你、业务、采购、产品、开发评审参与者 | 先理解算法为什么这么做、结果怎么用 | 否，可作为评审前理解材料 |
| 开发版算法卡 | 数据开发、后端开发、产品验收 | 明确字段、公式、表结构、调度和验收 | 是 |
| 审阅清单 | 你、产品负责人、项目侧评审人 | 历史阶段的人工红线记录 | 否，冻结归档，不再日常维护 |

业务解读版不追求把每个 SQL 细节写完。

开发版算法卡必须能支撑开发排期、建表、写 SQL/Python、跑数和对数。

历史审阅清单不是开发任务清单，也不是直接交给开发照做的算法卡。当前红线以开发版算法卡和本次交付说明为准。

对外交付时：

```text
给数据开发：开发版算法卡为主，必要时附业务解读版帮助理解。
给业务确认：业务解读版为主，必要时附 pending_items/ 中的业务待确认汇总。
给项目内部复核：以开发版算法卡、数据合同和本次交付说明为准；仅在需要追溯旧决策时查看冻结历史材料。
```

## 9. 后续算法卡执行顺序

每个算法固定按这个流程推进：

```text
1. 读取业务最新原始算法文档
2. 读取数据合同和 Doris 表结构，形成字段事实表：字段是否存在、字段值形态、能否直接聚合、是否需要商品/门店/价格等主数据补充
3. 抽取算法目标、输入、输出、核心逻辑
4. 内部逐章核对业务原文，发现缺口直接回写两份正式文档
5. 输出或更新业务解读版
6. 根据业务原文和数据合同输出或更新开发版算法卡
7. 将真正阻断开发的红线集中写入开发版待确认项或本次交付说明
8. 做最终自检：业务原文关键字、输出表、状态、参数表、V1 口径是否一致
9. 开发试跑后，用验收样例和业务抽样结果复核
```

任何算法卡交付前必须通过 4 个硬闸：

```text
闸 1：业务原文正式规则均能在两份正式文档中找到对应表达。
闸 2：开发版待确认项和交付说明不重复询问数据合同已经明确的事实。
闸 3：开发版算法卡没有把 V1 落地口径写成业务原文规则。
闸 4：旧版、废弃版或试运行版已标记，避免开发误用。
```
