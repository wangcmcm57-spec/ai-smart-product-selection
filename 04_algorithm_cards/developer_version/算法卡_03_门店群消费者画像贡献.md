## 1. 算法目标

本算法用于识别同一城市算法区域、同一品类、同一门店品类等级群中的主力消费者类型。

它只回答：

```text
在某个城市算法区域 + 某个品类 + 某个门店等级群里，
哪些消费者类型既覆盖更多有效购买会员，又贡献更多有效会员销售额？
```

输出结果供后续算法读取：

```text
目标画像 SKU 表现算法
新品候选标准化与合并算法
新品机会证据合成与风险门禁算法
新品推荐优先级与开发需求编排
AI 商品机会推荐表
```

本算法不做：

```text
不重新计算会员画像
不重新计算门店品类等级
不生成单门店正式主力人群
不直接推荐 SKU 或新品
不使用非会员销售进入主力贡献得分
不使用客单价、小票占比或人工权重改变正式主力判定
```

## 3. 计算周期、版本与开发执行流程

算法 03 按月离线批量计算。全链路调度明确传入 `algorithm_batch_version（统一算法批次版本）`；算法 03 只读取该批次已经正式发布的算法 01 画像、算法 02 门店品类等级、共享城市区域映射快照和本批锁定商品分类，再把有效会员小票聚合到城市算法区域、品类、门店等级群和消费者画像粒度。算法 03 不在查询时重新贴画像、评级或重算贡献。

前端和后续算法只读取已发布的 `mart_store_group_consumer_contribution` 和 `mart_store_group_consumer_summary`。采购侧查询城市、品类、门店等级或消费者画像时，只过滤已计算结果，不触发画像贡献实时重算。

正式贡献周期：

```text
最近 3 个数据完整自然月
```

例如 2026 年 7 月运行：

```text
contribution_start_date = 2026-04-01
contribution_end_date   = 2026-06-30
```

更新规则：

```text
每月正式更新一次。
algorithm_batch_version = 'BATCH_' + DATE_FORMAT(contribution_end_date, 'yyyyMM')。
算法 01、02、03、城市算法区域映射快照和本批商品分类必须使用同一个 algorithm_batch_version。
同一完整月窗口重跑沿用原 algorithm_batch_version，只用 run_id、updated_at、rerun_reason 区分运行。
规则、已核实退款枚举或分类口径变化默认从下一完整自然月批次生效；历史批次继续读取原批次锁定快照和代码发布记录。
```

正式结果必须保存：

```text
algorithm_batch_version
contribution_start_date
contribution_end_date
algorithm_02_release_id
source_data_version
run_id
```

V1 口径：

```text
算法 03 的已贴标会员交易必须直接继承算法 01 固定的有效会员过滤条件，并调用与算法 01、02 相同的公共实现；不建立或传递独立会员过滤版本字段。

`source_data_version` 是本次运行输入数据的追溯属性，补数重跑可更新，用于核对小票、门店数据与 02 结果；不能决定或替换商品分类来源，也不是第二套业务版本。

商品分类按 `dim_sku` 合同第 4 节的 `category_read_binding_json` 读取既有留存数据，不新增分类快照。公共调度在 01/02 首个分类读取任务前绑定，03 从 02 既有配置读取并核对同一绑定；补交易不改变分类读取位置及边界。V1 不做逐日分类回溯，历史原分类无法重读时阻断重跑，不用当前商品表补造。
```

算法 03 不生成 `consumer_contribution_model_version`、`profile_model_version`、`category_level_model_version`、`category_mapping_version`、`scope_version` 或其他算法独立版本号。实现追溯通过 `run_id（运行ID）`关联平台不可变代码发布记录，不在两张正式结果表建立第二套版本体系。

final_level IN ('A','B','C','D')
result_status = 'SUCCESS'

读取算法必须按以下顺序：

1. 按 algorithm_code=ALGO_02、明确的 algorithm_batch_version、release_status=AUTO_PUBLISHED 找到唯一记录；02 结果的 run_id/source_data_version 与之匹配。
2. 展开 `rating_group_evidence_json`，按 `scope_type + scope_id + category_granularity + category_code` 唯一匹配当前评分组。组键不含门店等级；必须先通过组级判断，再划分 FINAL_LEVEL 或 ALL_RATED。
3. 对象的 `checked_run_id` 等于 latest_run_id；`rating_validation_ref` 定位本次运行的输入、参数和等级验证；对象缺失/重复、运行不一致或证明不可读时写 UPSTREAM_RATING_UNRELIABLE。读取批次 rating_population_evidence_json.blocked_scope_ranges（结构与通配规则见 02 第 15.0.2 节）；命中未解除范围阻断时不可读，字段缺失不能默认空数组。source_delivery_check_ref/rating_validation_ref 必须验证内容与当前组及运行一致，非空字符串本身不算通过证据。
4. `rating_group_status=RELIABLE` 才可使用 SUCCESS 行。BLOCKED_SOURCE_GAP、BLOCKED_UNVERIFIED 均阻断整个受影响评分组及其全部等级群；不能过滤掉有问题门店后继续用其他等级。根据 02 依赖证据传播到相关中类、大类和参数共享组，不跨城市或批次回退。
5. 可靠组再判断覆盖证据。只有该组对象满足下列条件，才计算未评级门店数和覆盖率：

```text
rating_population_completeness_status = PASSED
source_delivery_status = COMPLETE
source_delivery_check_ref 非空且可定位本组实际应交/实交范围
source_missing_store_day_cnt = 0
unmapped_store_source_record_cnt = 0
unmapped_scope_source_record_cnt = 0
unmapped_category_source_record_cnt = 0
expected_key_missing_result_cnt = 0
unexpected_result_key_cnt = 0
expected_rating_key_cnt = result_rating_key_cnt
result_rating_key_cnt = 03 实际读取的本组 SUCCESS + NOT_CALCULABLE 唯一键数
```

这些键及类型均是 02 第 15.0.2 节组对象的正式合同，不是结果表物理列。计数 NULL 不当 0。跨组相同源异常不可简单加总；本组源证据必须包含关联前无法映射的记录。

可靠组只缺覆盖证据时：`unrated_store_cnt=NULL`、`rated_store_coverage_rate=NULL`、`store_coverage_status=UNAVAILABLE`，贡献可继续。此例外必须有 02 第 6.5.2 节规定的独立等级可靠性证明；已知漏交尚未消除、只有 SUCCESS 标记或仅批次 UNAVAILABLE 均不足以放行。证据自相矛盾（例如标 RELIABLE 却有未消除的已知源缺口，或结果实际读取键数与同运行证据不符）按 UPSTREAM_RATING_UNRELIABLE 阻断，不能降级为仅覆盖字段为空。

历史记录无新增 JSON 时，先按 02 第 6.5.3 节核验原始留存数据再消费，不回填原配置；原配置没有 category_read_binding_json 时，仅可读取商品合同第 4.2 节经原始留存数据核实后补充的公共审计来源证明，不默认采用当前分类；缺少原分类绑定时还须遵守商品合同的历史重跑阻断规则。

## 7. 关联路径与质量闸门

### 7.1 关联顺序

```text
1. 锁定 `algorithm_batch_version（统一算法批次版本）`、贡献周期和 `source_data_version（源数据版本）`。
2. 读取同批次唯一 `mart_store_category_level_run_release`；确认 `algorithm_code='ALGO_02'`、`release_status='AUTO_PUBLISHED'`、周期、最近运行ID和源数据版本均与正式结果一致。
3. 从 `mart_store_category_level` 读取同一 `algorithm_batch_version`、`calculation_end_date = contribution_end_date` 的正式结果；`SUCCESS` 行得到门店群。只有发布记录的应评级行集完整性证据通过时，`NOT_CALCULABLE` 行才用于未评级门店统计。
4. 从 Doris 小票表读取贡献周期内 valid_all_txn。
5. valid_all_txn 关联本批锁定 dim_sku 分类，筛选目标品类；映射缺失/一对多记录必须计入异常，不得静默丢失。
6. 关联 mart_store_category_level，把小票归入对应门店等级群。
7. 对全量有效交易聚合，得到覆盖率分母。
8. 在全量有效交易中筛选会员交易并关联同批次 dim_customer_profile。
9. 按门店群 + 品类 + final_profile 聚合，计算贡献指标。
```

正式运行前必须先完成以下输入闸门；任一闸门失败时，不生成受影响范围的两张正式结果表，只写运行审计/异常记录：

```text
1. order_item_id 去重无冲突。
2. 同一 algorithm_batch_version + customer_id 只有一条 dim_customer_profile。
3. 同一 algorithm_batch_version + 范围 + 门店 + 品类只有一条算法 02 结果；SUCCESS/NOT_CALCULABLE 状态域完整。
4. 同一 algorithm_batch_version 锁定分类下，一个 sku_id 只能命中一组大/中/小分类；未命中源记录数也必须显式核对。
5. 订单明细关联后，一个 order_id 在同一目标品类内最多对应一个 customer_id + final_profile；否则阻断，避免一张小票被多个画像重复计数。
```

### 7.1.1 阻断、空结果与正式表写入边界

按实际依赖确定受影响范围：02 输入缺口可能影响整个同区域同品类评分组、所属上级品类及共享参数依赖组；无法定位时不能擅自缩小范围。已证明独立的其他组继续，不跨批次或城市回退。

| 场景 | 明细表 `mart_store_group_consumer_contribution` | 汇总表 `mart_store_group_consumer_summary` | 运行审计/异常记录 |
|---|---|---|---|
| `UPSTREAM_VERSION_ERROR`、`DUPLICATE_JOIN_ERROR`、`CATEGORY_MAPPING_ERROR`、`TRANSACTION_DATA_ERROR`、`PROFILE_LINK_INCOMPLETE` | 不写受影响范围的正式明细行 | 不写受影响范围的正式汇总行 | 必须写入，记录状态、范围、版本、阻断原因、异常计数和批次 |
| `NO_RATED_STORE` | 不写；不存在合法门店群主键 | 不写；不存在合法门店群主键 | 必须写入，记录应参与门店数、已评级门店数和缺失原因 |
| 已有合法门店群，但 `NO_MEMBER_CONSUMPTION` | 不写；没有 `final_profile` 不得伪造明细行 | 不写；没有有效会员消费时不发布主力汇总结论 | 必须写入，记录门店群和会员消费为 0 |
| 02 组等级已独立证明 RELIABLE，仅覆盖证据不可用 | 写贡献明细；未评级数和覆盖率 NULL，store_coverage_status=UNAVAILABLE | 写主力汇总，覆盖字段同样为空 | 保存同组等级可靠证明与覆盖证据缺失原因 |
| UPSTREAM_RATING_UNRELIABLE：组源数据已知缺口、可靠性未证明或证据矛盾 | 不写受影响评分组全部等级群明细，已有旧结果停止读取 | 不写受影响汇总，已有旧结果停止读取 | 保存源缺口、组状态、依赖传播范围及上游运行ID |
| `SUCCESS`、`SINGLE_PROFILE`、`NO_OBVIOUS_MAIN` | 写正式明细行 | 写正式汇总行 | 写成功审计和对账结果 |

`NO_MEMBER_CONSUMPTION` 和阻断状态均不得用空壳正式结果行伪装成可计算结果；门店群、版本、会员消费为 0 等信息只写入运行审计。

### 7.2 上游版本闸门

同一批结果必须满足：

```text
算法 01、算法 02、算法 03、城市区域快照的 algorithm_batch_version 完全一致
算法 02 发布记录在该 algorithm_batch_version 下唯一且 release_status = AUTO_PUBLISHED
算法 02 正式结果 run_id = 发布记录 latest_run_id = 目标评分组证据 checked_run_id
目标评分组 rating_group_status = RELIABLE 且无未解除范围阻断
01 正式发布按第 5.2.1 节验证；分类读取绑定与共用调度一致
算法 02 正式结果 source_data_version = 发布记录 source_data_version = 算法 03 本批 source_data_version
profile_calculation_end_date = contribution_end_date
category_level_end_date = contribution_end_date
category_level_start_date = contribution_start_date
```

`profile_calculation_end_date = contribution_end_date` 是 V1 的等值契约：算法 03 使用贡献周期结束时正式有效的算法 01 画像版本，并将同一 `final_profile` 应用于整个贡献周期。若后续画像发布机制允许使用覆盖更长周期但结束日期不同的版本，必须先更新接口合同和版本规则，再调整闸门；开发不得自行将等值条件放宽为范围包含。

不满足时：

```text
result_status = 'UPSTREAM_VERSION_ERROR'
按第 7.1.1 节阻断，不写受影响范围的正式明细表和汇总表
```

### 7.3 会员画像唯一性

检查：

```text
同一 algorithm_batch_version + customer_id 只能有一个 final_profile
```

不满足时：

```text
result_status = 'DUPLICATE_JOIN_ERROR'
diagnostic_reason 记录重复 customer_id 和重复画像数量
```

### 7.4 门店品类等级唯一性

检查：

```text
同一 algorithm_batch_version
+ scope_type
+ scope_id
+ store_id
+ category_granularity
+ category_code
只能有一个 final_level
```

不满足时：

```text
result_status = 'DUPLICATE_JOIN_ERROR'
diagnostic_reason 记录重复门店品类等级
```

### 7.5 商品分类唯一性

检查：

```text
同一 algorithm_batch_version 锁定分类 + sku_id 只能命中一个商品分类
valid_all_txn 中无法命中分类的源记录数 = 0
```

不满足时：

```text
result_status = 'CATEGORY_MAPPING_ERROR'
diagnostic_reason 记录未映射或一对多 sku_id 及源记录计数，禁止内连接静默丢失
```

### 7.6 关联后对账

对每个门店群品类检查：

```text
关联前已贴标会员销售额 = 关联后各 final_profile 销售额合计
关联前已贴标会员商品行数 = 关联后各 final_profile 商品行数合计
关联前已贴标会员小票数 = 关联后按 final_profile 去重小票后的合计
```

商品行数、小票数、会员数必须精确一致。按本卡精确金额聚合时金额也须相等；原文 0.01% 仅是浮点对账误差上限，不能用于豁免已知漏行、重复关联或等级可靠性检查。

不满足时：

```text
result_status = 'DUPLICATE_JOIN_ERROR'
不发布正式主力人群结论
```

## 8. 门店群与品类范围

### 8.1 城市算法区域

正式结果支持：

```text
CITY：单城市
CITY_CLUSTER：业务配置城市群
```

范围类型、范围编码和范围名称以算法 02 正式结果及同一 `algorithm_batch_version（统一算法批次版本）`的 `dim_algorithm_batch_city_region_snapshot` 为准；不允许算法 03 读取最新源映射自行重建范围，也不允许扩大到其他城市或城市群。

### 8.2 品类颗粒度

支持：

```text
LARGE：大类
MIDDLE：中类
SMALL：小类
```

每个颗粒度都必须从底层小票重新筛选、关联和聚合：

```text
大类结果 != 下属中类结果平均
中类结果 != 下属小类结果平均
```

### 8.3 门店群类型

支持：

```text
FINAL_LEVEL：指定等级门店群，例如 A / B / C / D
ALL_RATED：当前范围和品类下全部已有正式等级的门店
```

`ALL_RATED` 必须从底层小票重新聚合，不能把 A、B、C、D 四个等级结果直接相加。

原因：

```text
同一会员可能在多个等级门店消费。
如果直接相加，会员数会被重复计算。
```

### 8.4 门店数口径

```text
store_cnt = 当前门店群内参与 03 计算的门店数
rated_store_cnt = 当前范围和品类下算法 02 `result_status = SUCCESS` 的去重门店数
当且仅当算法 02 行集证据通过：
  unrated_store_cnt = 当前范围和品类下算法 02 `result_status = NOT_CALCULABLE` 的去重门店数
  rated_store_coverage_rate = rated_store_cnt / (rated_store_cnt + unrated_store_cnt)
否则：
  unrated_store_cnt = NULL
  rated_store_coverage_rate = NULL
```

这些覆盖字段不进入得分。先通过第 5.3.1 节组级等级可靠性闸门，才讨论覆盖率：本组源交付、映射、清单及结果证据均通过时为 AVAILABLE；仅覆盖证据不足且等级可靠性有独立证明时，两个覆盖字段 NULL、状态 UNAVAILABLE，贡献继续。等级不可靠则整组阻断，不适用仅覆盖字段降级。

## 9. 基础聚合指标

### 9.1 消费者类型指标

在同一个门店群品类下，对每个 `final_profile` 计算：

```text
profile_member_cnt = COUNT(DISTINCT customer_id)
profile_sales_amt = SUM(usual_amt)
profile_ticket_cnt = COUNT(DISTINCT order_id)
profile_avg_ticket_amt = profile_sales_amt / profile_ticket_cnt，当 profile_ticket_cnt > 0；否则 NULL
```

其中：

```text
profile_sales_amt 只统计 valid_profiled_member_txn。
profile_ticket_cnt 在同一个品类内，同一 order_id 只计 1 次。
```

### 9.2 门店群已贴标会员分母

```text
group_member_cnt = COUNT(DISTINCT customer_id)
group_sales_amt = SUM(usual_amt)
group_ticket_cnt = COUNT(DISTINCT order_id)
group_avg_ticket_amt = group_sales_amt / group_ticket_cnt，当 group_ticket_cnt > 0；否则 NULL
```

统计范围：

```text
当前门店群
+ 当前品类
+ 当前贡献周期
+ 全部已贴标会员有效交易
```

### 9.3 全量覆盖率分母

```text
group_total_sales_amt = SUM(valid_all_txn.usual_amt)
group_total_ticket_cnt = COUNT(DISTINCT valid_all_txn.order_id)
profiled_member_sales_amt = group_sales_amt
profiled_member_ticket_cnt = group_ticket_cnt
```

覆盖率：

```text
member_sales_coverage_rate = profiled_member_sales_amt / group_total_sales_amt，当 group_total_sales_amt > 0；否则 NULL
member_ticket_coverage_rate = profiled_member_ticket_cnt / group_total_ticket_cnt，当 group_total_ticket_cnt > 0；否则 NULL
```

业务含义：

```text
贡献分：只在已贴标会员内部判断主力消费者类型。
覆盖率：判断已贴标会员销售能代表全量销售的程度。
```

### 9.4 画像关联成功率

应关联会员：

```text
valid_all_txn 中 is_customer = 1、customer_id 非 NULL 且非空字符串，且不以 '6' 开头，并满足算法 01 有效会员口径的会员
```

成功关联会员：

```text
应关联会员中能关联本次锁定 dim_customer_profile 正式画像的会员
```

公式：

```text
profile_link_expected_member_cnt = COUNT(DISTINCT 应关联正式画像的有效会员)
profile_link_success_member_cnt = COUNT(DISTINCT 成功唯一关联正式画像的有效会员)
profile_link_success_rate = profile_link_success_member_cnt / profile_link_expected_member_cnt
分母为 0 时记 NULL，运行状态为 NO_MEMBER_CONSUMPTION
```

正式发布要求：

```text
profile_link_success_rate = 100%
```

不满足时：

```text
result_status = 'PROFILE_LINK_INCOMPLETE'
不发布正式主力人群结论
```

## 10. 画像贡献占比

对每个 `final_profile` 计算：

```text
member_share = profile_member_cnt / group_member_cnt，当 group_member_cnt > 0；否则不生成正式明细
sales_share  = profile_sales_amt / group_sales_amt，当 group_sales_amt > 0；否则不生成正式明细并记录 TRANSACTION_DATA_ERROR
ticket_share = profile_ticket_cnt / group_ticket_cnt，当 group_ticket_cnt > 0；否则 NULL
```

约束：

```text
SUM(member_share) = 100%
SUM(sales_share) = 100%
```

原文允许浮点对账误差上限为 0.01%；本卡保留该上限但不用于主力分组近似比较。整数计数和精确金额必须相等；6 位占比展示值求和的舍入差按画像数记录，正式分组始终使用第 11.1.1 节计算值。

正式主力判定只使用：

```text
member_share
sales_share
```

`ticket_share` 只用于解释，不改变主力标签。

## 11. 贡献得分

### 11.1 公式

```text
profile_contribution_score =
2 * sales_share * member_share
/ (sales_share + member_share) * 100
```

零分母处理：

```text
sales_share + member_share = 0 时，不执行除法，不生成该消费者类型结果行。
```

### 11.1.1 计算精度、比较与展示

本节为确定性实现约定，不新增业务分组阈值。输入 `usual_amt` 保留合同的 6 位小数，金额先用整数微元或等价精确 DECIMAL 聚合，正式金额字段使用 decimal(38,6)，不能先逐笔舍入到分再相加。金额、计数或中间值溢出、出现非有限值时按 TRANSACTION_DATA_ERROR 阻断受影响范围，不能截断、回绕或填零后发布。

占比、调和平均、SSE、BIC 使用统一十进制计算上下文：50 位有效数字、ROUND_HALF_EVEN；每步运算及 ln 均按此上下文执行。按 `final_profile` UTF-8 字节序固定聚合次序；候选分组按未展示舍入的计算得分升序、同分按画像字节序排列。分组、同分识别、排名、并列最优比较均使用该计算值，不能先四舍五入四位或读取展示字段重算。相同即该上下文计算值相等，不额外增加近似相等阈值；公式中的 epsilon=1e-12 仅用于 BIC 对数，不用于同分判断。

SSE 按各候选分组均值后逐项平方求和，不用可能消减误差的 `SUM(score^2)-SUM(score)^2/N` 替换。BIC 并列选 K=1，SSE_2 并列选较高断点，均按统一精度值比较。等价实现须通过本卡边界样例；浮点实现不能仅以显示相同宣称等价。

占比输出保留 6 位、得分和断点输出保留 18 位，落库时统一 ROUND_HALF_EVEN；界面可显示四位。已舍入占比、客单价不作为后续公式输入；排名/主力标记在舍入前完成。公共运行审计保留每个组和画像的计算得分、候选 SSE/BIC 的完整十进制字符串及代码运行环境，用原始金额/会员数可复算。不得根据两个显示均为 50.0000 的分数强行合并排名。

### 11.2 解释

该公式是销售占比和会员占比的调和平均。

它要求：

```text
人多
+ 买得多
```

同时成立。

典型效果：

```text
销售占比高但会员占比低：得分会被会员覆盖限制
会员占比高但销售占比低：得分会被销售贡献限制
两项同时高：得分较高
```

### 11.3 解释指数

解释指数不参与正式得分。

```text
per_member_contribution_index = sales_share / member_share，当 member_share > 0；否则 NULL
visit_activity_index = ticket_share / member_share，当 member_share > 0 且 ticket_share 非空；否则 NULL
avg_ticket_index = profile_avg_ticket_amt / group_avg_ticket_amt，当两者均非空且 group_avg_ticket_amt > 0；否则 NULL
```

分母为 0、空值或不适用时统一写 NULL，不写 0；`diagnostic_reason` 说明具体原因。正式结果不允许用 0 伪装“不可计算”。

含义：

```text
per_member_contribution_index > 1：该类型人均销售贡献高于门店群平均
visit_activity_index > 1：该类型人均到店小票贡献高于门店群平均
avg_ticket_index > 1：该类型目标品类客单高于门店群平均
```

## 12. 主力消费者类型判定

### 12.1 候选类型

候选类型为同一门店群品类下所有有效 `final_profile`。

保留规则：

```text
profile_member_cnt > 0
profile_sales_amt > 0
```

不设置人工最小样本门槛：

```text
不要求至少 10 名会员
不要求至少 30 张小票
不因小样本直接删除真实消费者类型
```

小样本不确定性由 Bootstrap、留一月验证、原始会员数和小票数披露。

### 12.2 Jenks 自然断点

把同一门店群内所有 `profile_contribution_score` 从低到高排序。

尝试：

```text
K = 1：不分高低组
K = 2：低贡献组 + 高贡献组
```

K=1：

```text
SSE_1 = SUM((score_i - 全体均值)^2)
```

K=2：

```text
枚举所有连续切分位置。
每个切分位置计算左右两组组内平方误差。
选择 SSE_2 最小且不拆分同分类型的断点；如果多个断点的 SSE_2 完全相同，选择较高的 `jenks_break_value`。该并列规则是 V1 的确定性实现规则，不改变“高贡献组为主力”的业务定义。
```

限制：

```text
相同贡献得分（第 11.1.1 节计算值）不得被拆入不同组。
两组都必须非空。
每个候选断点固定取高贡献组最小计算得分，不取相邻分数中点。
K=2 时计算得分 >= 断点进入高贡献组，低于断点进入低贡献组；最终先保留组归属，再按字段精度写展示断点。
```

只有同时满足以下条件才生成 K=2 候选：

```text
有效消费者类型数 N >= 2
贡献得分至少有 2 个不同值
存在不拆分相同得分的连续切分位置，且左右两组均非空
```

### 12.3 BIC 选择 K

公式：

```text
BIC(K) = N * ln(SSE_K / N + epsilon) + K * ln(N)
epsilon = 1e-12
```

其中：

```text
N = 当前门店群有效消费者类型数量
K = 1 或 2
```

选择规则：

```text
BIC 越小越好。
全部贡献得分相同时，只允许 K = 1。
多个候选 BIC 相同时，选择更小的 K。
K=2 不满足有效切分条件时不写入 BIC 候选，`bic_by_k_json` 中对应值写 NULL。
```

断点和 JSON 状态写法：

```text
K=2 且存在有效切分 -> jenks_break_value 写最终断点；K=1、单一消费者类型、无正式结果或无法计算时写 NULL。
sse_by_k_json.status / bic_by_k_json.status = CALCULATED：对应候选值按本节公式计算并可复算。
sse_by_k_json.status / bic_by_k_json.status = NOT_APPLICABLE：单一消费者类型或本结果不需要运行 Jenks/BIC；对应 K 值和 selected_k 写 null。
sse_by_k_json.status / bic_by_k_json.status = NOT_CALCULABLE：上游、核心分母或字段闸门阻断；对应数值写 null，不伪造参数。
```

### 12.4 最终主力判定

如果选择 K=2：

```text
高贡献组全部为正式主力消费者类型
is_main_profile = 1
is_relative_main_candidate = 0
result_status = 'SUCCESS'
目标评分组 rating_group_status = 'RELIABLE'（按第 5.3.1 节，不是结果表新增列）
```

如果选择 K=1：

```text
没有明显主力
result_status = 'NO_OBVIOUS_MAIN'
is_main_profile = 0
is_relative_main_candidate = 0
```

K=1 时，贡献得分最高的类型只作为相对主力候选：

```text
is_relative_main_candidate = 1
```

最高分并列时，所有并列最高分类型均为相对主力候选。

### 12.5 单一消费者类型

如果只有一种有效消费者类型：

```text
不运行 Jenks/BIC
result_status = 'SINGLE_PROFILE'
is_main_profile = 1
profile_contribution_score = 100
selected_cluster_count = 1
is_relative_main_candidate = 0
```

说明：

```text
贡献分 100 只表示当前有效会员消费结构单一。
不代表该人群经营价值必然更高。
```

### 12.6 排名与主力覆盖

排名：

```text
contribution_rank = DENSE_RANK() OVER (ORDER BY 画像贡献计算得分 DESC)
画像贡献计算得分使用第 11.1.1 节未展示舍入值，不使用落库/页面舍入后的数值
```

主力覆盖：

```text
main_member_coverage_rate =
SUM(主力类型 profile_member_cnt) / group_member_cnt

main_sales_coverage_rate =
SUM(主力类型 profile_sales_amt) / group_sales_amt
```

`NO_OBVIOUS_MAIN` 时：

```text
main_member_coverage_rate = NULL
main_sales_coverage_rate = NULL
```

正式明细行的标记闭环：`SINGLE_PROFILE` 只有一行且 `is_main_profile = 1`、`is_relative_main_candidate = 0`；`SUCCESS` 的高贡献组行 `is_main_profile = 1`，其余行均为 `0`；`NO_OBVIOUS_MAIN` 所有行 `is_main_profile = 0`，仅最高贡献并列行 `is_relative_main_candidate = 1`。阻断状态不写正式明细行。

## 13. 稳定性验证

稳定性只用于解释结果可靠性，不修改完整周期的正式主力判定。

### 13.1 会员级 Bootstrap

抽样单位：

```text
会员 customer_id
```

禁止抽样小票。

每轮步骤：

```text
1. 在当前门店群全部有效会员中有放回抽样。
2. 每轮样本会员数等于原始有效会员数。
3. 被抽中的会员携带贡献周期内全部目标品类有效交易，按抽中次数加权；不能 COUNT DISTINCT 后丢掉重复抽中的权重。
4. 重新计算 member_share、sales_share、profile_contribution_score。
5. 重新执行 Jenks/BIC。
6. 记录每个 final_profile 是否被判为主力。
```

实现要求：

```text
先按 customer_id 聚合该会员在本门店群、目标品类、贡献周期内的全部交易；抽样时只抽会员并为被抽会员增加抽样权重，不复制或拆散会员的交易行。
每个门店群品类使用固定 `bootstrap_random_seed`；种子由调度参数按
`seed(algorithm_batch_version, scope_type, scope_id, category_granularity, category_code, store_group_type, final_level)`
确定，同一业务主键重跑必须复用同一种子。种子、抽样单位、批次大小、目标 MCSE、最大轮数和实际轮数必须写入平台公共运行审计；明细写独立 Bootstrap 字段；汇总表的 `quality_metrics_json` 回写 bootstrap_status、bootstrap_iterations 和 bootstrap_mcse（全组最大 MCSE），不在明细重复建 JSON 字段。
抽样结果必须使用与正式计算相同的统一批次、会员过滤公共实现、算法 01 画像、算法 02 门店群和锁定商品分类。
```

自动停止规则：

```text
至少运行 1,000 轮
最多运行 10,000 轮
每 250 轮检查一次
```

MCSE：

```text
MCSE = sqrt(p * (1 - p) / B)
```

其中：

```text
p = 当前消费者类型 Bootstrap 主力入选率
B = 已运行轮数
```

停止条件：

```text
所有消费者类型 MCSE <= 0.01
```

如果达到 10,000 轮仍未达到目标，保留完整 10,000 轮结果并写 MAX_ITERATIONS_REACHED。随机数或中间计算失败写 FAILED，不改完整周期主力判定：bootstrap_iterations 写已完整完成的轮数（首轮失败为 0），入选率、上下限和 MCSE 全部 NULL，不能发布中途失败的部分估计。

SINGLE_PROFILE 不抽样：状态 NOT_APPLICABLE、轮数 0、入选率 1、上下限均为 1、MCSE=0（确定性退化值，不是 0 轮抽样计算得到）。无正式结果时仅在审计写 NOT_APPLICABLE，其余数值 NULL。每轮未抽到某画像时，该画像本轮主力标记为 0，仍在原始画像集合上累计入选率和检查 MCSE；一次抽样中只剩一种画像时按 SINGLE_PROFILE 规则判该类型为主力。每轮会员数及销售额按抽样次数加权汇总，分母使用相同权重。

随机种子生成不能使用进程随机化的内建 hash：对本节主键按固定字段顺序编码为无空格、UTF-8、非 ASCII 转义的 JSON 字符串数组，取 SHA-256 前 8 字节大端无符号整数。会员输入按 customer_id UTF-8 字节序排列，参考抽样使用 Python random.Random(seed).randrange(N) 有放回抽 N 次；Python 运行版本及实现跟随原代码发布记录锁定。同批使用同一输入重跑应得同样序列，补交易造成输入变化时只保证种子及规则不变。

输出字段：

```text
bootstrap_iterations
bootstrap_main_rate
bootstrap_main_rate_ci_lower_95
bootstrap_main_rate_ci_upper_95
bootstrap_mcse
```

V1 95% 区间固定按以下公式计算（稳定性解释口径，不改主力判定）：

```text
bootstrap_main_rate_ci_lower_95 = MAX(p - 1.96 * MCSE, 0)
bootstrap_main_rate_ci_upper_95 = MIN(p + 1.96 * MCSE, 1)
```

### 13.2 留一月验证

正式贡献周期为连续 3 个完整自然月。

验证方式：

```text
验证 1：删除第 1 月，使用第 2 月 + 第 3 月重算
验证 2：删除第 2 月，使用第 1 月 + 第 3 月重算
验证 3：删除第 3 月，使用第 1 月 + 第 2 月重算
```

要求：

```text
algorithm_batch_version 和会员画像保持不变。
门店群成员保持不变。
只改变参与统计的交易月份。
```

公式：

```text
time_main_rate =
被判为主力的有效验证次数 / 有效验证总次数
```

如果删除某个月后没有有效会员消费，该次验证不进入分母。

如果有效验证次数少于 2 次：

```text
time_stability_status = 'INSUFFICIENT_TIME_SAMPLE'
time_main_rate = NULL
```

当有效验证次数不少于 2 次时，按以下唯一规则生成 `time_stability_status`：

```text
将完整周期结论与每次留一月结论都表示为
(result_status, 排序后的正式主力画像列表, 排序后的相对主力候选列表)。
全部有效验证结论与完整周期结论完全一致 -> STABLE
任一有效验证结论不同 -> UNSTABLE
```

不使用“明显波动”等未量化描述，也不使用稳定性结果修改正式主力标签。

### 16.1 汇总聚合与质量 JSON

汇总仍是实体结果表，一行一个第 16 节唯一键，直接由同一运行的贡献明细生成，不重新拼原始小票。

1. 先按汇总键检查明细主键唯一，并校验以下组公共字段在所有画像行完全一致（包含 NULL 一致性）：周期、批次、范围、品类、等级群、上游发布引用、运行字段、store_cnt、rated_store_cnt、group_member_cnt、group_sales_amt、group_ticket_cnt、group_total_sales_amt、group_total_ticket_cnt、profile_link_expected_member_cnt、profile_link_success_member_cnt、unrated_store_cnt、rated_store_coverage_rate、store_coverage_status、selected_cluster_count、result_status、bootstrap_status、bootstrap_iterations、time_stability_status。通过后每个字段只取一次，不能 SUM，也不能直接用 MAX 掩盖冲突。冲突按 DUPLICATE_JOIN_ERROR 阻断。
2. `main_profile_cnt = COUNT(明细中 is_main_profile=1)`。主力会员、主力销售分子分别为这些行的 profile_member_cnt、profile_sales_amt 之和，分母各取一次 group_member_cnt、group_sales_amt；由未展示舍入金额重算覆盖率，不求占比平均。单一画像覆盖率为 1；NO_OBVIOUS_MAIN 主力数 0、主力列表 []、两个主力覆盖率 NULL。
3. main_profiles_json、relative_main_candidates_json 仅收录各自标记为 1 的 final_profile，按计算得分降序、并列按画像 UTF-8 字节序排列；排序不拆分业务同分排名。非适用列表为 []。
4. 会员销售、小票及画像关联覆盖率分别用一次性组分子/分母重算；门店评级覆盖率只在第 5.3.1 节证据通过时重算，否则 NULL。不得把同组重复的总量累加。例如两行都带 group_sales_amt=100，汇总仍为 100，不是 200。
5. `quality_metrics_json` 固定结构如下，不增加第三张结果表：

| JSON 键 | 类型 | 来源与取值 |
|---|---|---|
| `profile_link_success_rate` | number | 同汇总画像关联成功率 |
| `member_sales_coverage_rate` | number/null | 同汇总会员销售覆盖率 |
| `member_ticket_coverage_rate` | number/null | 同汇总会员小票覆盖率 |
| `rated_store_coverage_rate` | number/null | 同汇总门店评级覆盖率；证据不足 null |
| `store_coverage_status` | string | 同汇总 AVAILABLE / UNAVAILABLE |
| `bootstrap_status` | string | 全组共同 CONVERGED / MAX_ITERATIONS_REACHED / FAILED / NOT_APPLICABLE |
| `bootstrap_iterations` | integer | 全组共同的已完整完成轮数，不能按画像相加 |
| `bootstrap_mcse` | number/null | 全组各画像 MCSE 最大值，用于判断是否整体收敛；FAILED 为 null，SINGLE_PROFILE 为 0 |
| `time_stability_status` | string | 同全组 STABLE / UNSTABLE / INSUFFICIENT_TIME_SAMPLE |

所有数值遵循第 11.1.1 节精度，JSON 中比率和 MCSE 最终输出 6 位。明细未运行/失败字段按第 13.1 节处理，不使用跳过 NULL 的 MAX 把失败组伪装为成功。无正式结果时不产生汇总行；只在公共审计记录原因。

## 17. 计算步骤

开发实现按以下顺序执行。

```text
1. 确定贡献周期和 `algorithm_batch_version（统一算法批次版本）`。
2. 校验 01/02/03 与共享城市区域的统一批次、上游发布运行及既有分类读取绑定一致，分类不随 source_data_version 变化。
3. 读取算法 02 V1.9 同批唯一发布记录，校验自动发布、周期、运行ID、输入源及目标评分组 RELIABLE，核对组证据和未解除的范围阻断。
4. 仅对通过可靠性闸门的组，用 SUCCESS 行生成门店群；组覆盖证据通过时统计 NOT_CALCULABLE，否则覆盖字段 NULL。
5. 读取 Doris 小票，生成 valid_all_txn；退款类型非空不直接删除。
6. valid_all_txn 关联本批锁定商品分类，并单独核查未映射/一对多源记录。
7. 按目标品类颗粒度筛选大类、中类、小类。
8. valid_all_txn 关联门店群，得到门店群全量有效交易。
9. 从全量有效交易中筛选会员交易，并关联算法 01 同批正式会员画像。
10. 校验画像关联成功率和关联前后金额、行数、小票数。
11. 按门店群 + 品类 + final_profile 聚合基础指标。
12. 计算 member_share、sales_share、ticket_share。
13. 计算 profile_contribution_score。
14. 用 Jenks/BIC 判定主力消费者类型。
15. 做会员级 Bootstrap。
16. 做留一月验证。
17. 生成贡献明细表。
18. 汇总生成门店群主力人群汇总表。
19. 执行验收对账并原子发布同一 algorithm_batch_version 的两张正式结果表。
```

## 22. 最小计算样例

范围：

```text
2026-04-01 至 2026-06-30
上海
小类：牛肉制品
A 级门店群
```

聚合结果：

| 消费者类型 | 会员数 | 销售额 | 小票数 |
|---|---:|---:|---:|
| 常规时段型-小家庭-中频-价格非敏感 | 3500 | 3400000 | 15000 |
| 上班族晚高峰型-小家庭-中频-价格非敏感 | 3000 | 3200000 | 12000 |
| 捡漏型 | 2000 | 1800000 | 9000 |
| 常规时段型-大家庭-高频-价格敏感 | 1500 | 1600000 | 5000 |

分母：

```text
group_member_cnt = 10000
group_sales_amt = 10000000
group_ticket_cnt = 41000
```

第一类贡献得分：

```text
member_share = 3500 / 10000 = 0.35
sales_share = 3400000 / 10000000 = 0.34
profile_contribution_score =
2 * 0.35 * 0.34 / (0.35 + 0.34) * 100 = 34.49
```

如果 Jenks/BIC 选择 K=2，且高贡献组为：

```text
常规时段型-小家庭-中频-价格非敏感
上班族晚高峰型-小家庭-中频-价格非敏感
```

则：

```text
两个消费者类型 is_main_profile = 1
result_status = SUCCESS
main_member_coverage_rate = (3500 + 3000) / 10000 = 65%
main_sales_coverage_rate = (3400000 + 3200000) / 10000000 = 66%
```
