# 算法06_目标画像购物篮新品关联_业务解读版

更新时间：2026-08-05

业务原始依据：`archive/source_docs/business_algorithm_docs/算法卡_06_目标画像购物篮新品关联.md`

## 1. 先用一句话理解

这个算法要判断：

```text
在某个城市算法区域、某个门店等级、某个叶子小分类和某个消费者画像里，
目标消费者买了一个高表现锚点商品 A 时，
同一张真实小票里还经常一起买什么商品 B；
如果 A 和 B 的关系不是偶然、不是促销带出来、不是缺货误判，
再判断 B 能不能变成这个叶子小分类新品的配料、口味、材料或场景证据。
```

它不是简单算“买 A 的人也买 B”，也不是看到共现就生成新品。

它要连续回答五个问题：

```text
1. 这批目标消费者的小票里，A 和 B 是否真实一起出现？
2. A 和 B 在这些小票发生时，是否本来都有机会被买到？
3. A 和 B 的关联是否强于随机偶然？
4. 这个关联是否在自然成交下也成立，而不是只靠促销或晚间折扣？
5. 这个关联能不能转成新品属性，还是只能说明消费场景？
```

一个例子：

```text
上海 A 级门店群，
上班族晚高峰型-小家庭-高频-价格非敏感会员，
经常购买黑椒牛柳丝 200g。

算法 06 会去看这些会员买黑椒牛柳丝的真实小票：
有没有经常一起买青泡椒？
青泡椒当时是不是有货、可售、未售罄？
黑椒牛柳丝和青泡椒的共同购买是否显著强于随机？
这个关系在 19:30 前自然成交里是否也成立？

如果都成立，并且青椒可以作为牛肉制品的配料属性，
算法 06 才能输出类似“青椒黑椒牛柳丝 200g”的购物篮新品候选。
```

## 2. 最终会输出什么

算法 06 正式输出 6 张结果表。

| 表 | 一行代表什么 | 用途 |
|---|---|---|
| `basket_run` | 一次算法 06 正式运行 | 保存周期、版本、数据快照、运行状态 |
| `basket_scope_summary` | 一个周期 + 一个范围 + 一个叶子小分类 + 一个篮子类型的汇总 | 告诉业务这次到底有多少小票、会员、门店和有效篮子 |
| `basket_itemset_cooccurrence` | 一个真实共现项集 | 保存 FP-Growth 发现的原始共现，不只保留 Top N |
| `basket_association_rule` | 一条 A=>B 或 B=>A 的正反向规则 | 保存四格表、support、confidence、lift、贝叶斯区间和规则状态 |
| `basket_rule_stability` | 一条规则在门店、月份、季节、促销等维度的稳定性结果 | 判断规则是稳定、局部、季节、单月依赖还是促销依赖 |
| `basket_new_product_candidate` | 一条能或不能转成新品的购物篮候选 | 保存候选商品名、规格、属性来源、适用范围和候选状态 |

最重要的是区分两类结果：

```text
购物篮规则：
回答 A 和 B 是否真的经常一起买。

购物篮新品候选：
回答这个 A+B 关系能不能变成一个可开发新品。
```

所以一条强购物篮规则不一定等于一个新品。

例如：

```text
鲜鸡蛋 + 鲜牛奶
可能是很强的早餐消费场景规则，
但鲜牛奶不能变成鲜鸡蛋这个小分类里的配料，
所以不能生成“牛奶鸡蛋”新品。
```

## 3. 它在 AI 选品链路中的位置

```text
算法 01：会员画像
        ↓
算法 02：门店品类等级
        ↓
算法 03：门店群消费者画像贡献
        ↓
算法 04：目标画像 SKU 表现，找到高表现锚点 SKU
        ↓
算法 05：目标画像商品价格带，给候选规格和价格可行性
        ↓
算法 06：目标画像购物篮新品关联，找真实小票里的配方/场景机会
        ↓
算法 08：新品候选标准化与合并
        ↓
算法 09：新品机会证据合成与风险门禁
        ↓
算法 10：新品推荐优先级与开发需求编排
```

算法 06 的购物篮计算硬前置是算法 01-04 的正式结果；当需要补充具象候选的规格、价格和成本上下文时，再读取算法 05 的价格可行性结果。算法 06 不重新贴会员画像，不重新给门店评级，不重新判断主力消费者，不重新寻找锚点 SKU，也不重新计算价格带。

它做的是：

```text
从算法 04 的正式锚点商品出发，
回到底层真实小票，
找目标画像在买锚点商品时还一起买了什么，
再判断这些共同购买关系能不能形成新品属性。
```

算法 06 和算法 05、07 的关系：

```text
算法 05：回答“候选新品卖什么规格、什么价格能不能成立”。
算法 06：回答“候选新品的配方、材料或消费场景有没有真实小票证据”。
算法 07：回答“外部竞品和趋势有没有类似新品或属性证据”。
```

实际运行时，算法 06 是离线或准离线批量计算：

```text
第一步：锁定上游正式版本和本次周期
先锁定算法 01、02、03、04 的版本，以及商品、城市算法区域、可订可售和毛利损耗数据版本；如需生成具象候选规格和价格上下文，再锁定算法 05 的价格可行性结果版本。

第二步：用目标画像真实小票构建购物篮
一张真实小票就是一个篮子，同一会员同一天多张小票不合并。

第三步：计算商品共现和关联规则
先保留真实共现，再用统计规则判断哪些是正式规则、探索规则或原始共现。

第四步：判断能不能转成新品
只有通过自然篮子、品类规则和品类保持检验的配方型关联，才进入新品候选。

第五步：写入正式结果表
产品和下游算法只读正式结果表，不在前端查询时重新扫小票。
```

采购前端只输入查询条件：

```text
城市、门店等级、消费者画像、品类、候选状态等
```

这些查询条件只用来筛选已经算好的结果，不是让采购在前端手工输入 A、B、规则或候选新品。

现有数据合同已经明确：

```text
Doris order_id 已确认全公司唯一，可作为小票篮子键
Doris article_id 对齐商品基础表交易商品编码
Doris store_id 对齐门店编码

可订可售表已到日期 + 门店 + 销售商品编码
毛利损耗表已到营业日期 + 门店 + 交易商品编码
```

一期必须明确的落地边界：

```text
1. `dim_basket_attribute_transfer_rule` 未落表或当前版本未覆盖该品类关系时：
   可以输出购物篮共现和关联规则；
   但不能正式输出 BASKET_RECIPE 新品候选，只能输出 CATEGORY_RULE_NOT_CONFIGURED。

2. 标准商品归并：
   V1 使用商品基础表现有 SPU 做标准商品归并；
   SPU 为空或无法映射时，才按销售 SKU 计算并标记 SKU_ONLY；
   不使用名称相似、换码关系或替代关系做额外合并。

3. 没有商品状态表的 `S` 起止日期时：
   可以按实际可订可售 / 有销售窗口做 V1 时间窗口判断；
   但不能输出 S_SEASONAL_RULE 或 SEASONAL_NEW_PRODUCT。

4. 没有正式促销活动表时：
   已确认 V1 使用 discount_amt > 0 和 is_hour_promotion 做促销/时段折扣代理；
   结果必须保留 DISCOUNT_PROXY_V1 标记。
```

## 5. 数据周期和范围怎么理解

正式评估周期默认使用最近 3 个数据完整自然月。

例如 2026 年 7 月运行：

```text
analysis_period_start = 2026-04-01
analysis_period_end   = 2026-06-30
```

算法 06 的范围由四个条件共同决定：

```text
城市算法区域
门店等级群
消费者画像
叶子小分类
```

只要切换其中任意一个条件，都必须重新从底层小票计算，不能把别的范围的 lift、confidence 或候选新品拿来平均。

例如：

```text
上海 A 级门店 + 上班族晚高峰型 + 牛肉制品
```

和：

```text
上海 B 级门店 + 上班族晚高峰型 + 牛肉制品
```

必须分别算，因为它们的门店、人群、小票和可购买机会都不同。

## 6. 核心业务对象怎么定义

### 6.1 什么是篮子

算法 06 里的“篮子”就是一张真实小票。

```text
basket_id = order_id
```

同一会员同一天买了两次，就有两张篮子，不合并。

同一张小票里同一个 SKU 出现多行时，先合并数量和金额，但判断“是否出现”时只算出现一次。

单商品小票也必须保留，因为它们是分母。

例如：

```text
小票 1：黑椒牛柳丝
小票 2：黑椒牛柳丝 + 青泡椒
小票 3：青泡椒
```

如果删掉小票 1 和小票 3，只保留多商品小票，就会把关联强度人为放大。

### 6.2 什么是锚点 A 和关联商品 B

```text
A = 算法 04 找到的高表现锚点商品
B = 和 A 在同一张真实小票里共同出现的商品
```

算法 06 优先使用算法 04 的正式锚点：

```text
is_formal_anchor = 1
```

如果不是正式锚点，只能作为探索锚点，并打：

```text
EXPLORATORY_ANCHOR
```

### 6.3 为什么要用标准商品

小票里是销售条码，但算法正式关联要落到标准商品。

允许合并的关系只有：

```text
正式 SPU
正式换码关系
正式替代关系
```

不能因为名字像就合并。

例如：

```text
旧码青泡椒 和 新码青泡椒
如果有正式换码关系，可以合并。

散装青泡椒 和 盒装青泡椒
如果没有正式关系，不能只因名称相似自动合并。
```

当前 V1 要按这个顺序处理：

```text
1. 商品基础表有 SPU：
   V1 用现有 SPU 建立标准商品。

2. SPU 为空或无法映射：
   保持销售条码 SKU 粒度，输出 SKU_ONLY。

3. 没有正式换码 / 替代关系：
   不做换码合并，也不做替代合并。
```

## 7. 开发实际计算流程

算法 06 可以按 11 步理解。

### 第一步：锁定上游版本和范围

先确定本次计算的正式范围：

```text
周期
城市算法区域
门店等级群
消费者画像
叶子小分类
算法 04 正式锚点商品
```

同一批结果不能混用多个上游版本。

### 第二步：过滤有效小票

先复用算法 01 的有效会员和有效交易口径：

```text
customer_id 不为空
customer_id 不以“6”开头
不是已确认异常会员日
交易已完成
非退货、取消、冲销
```

再排除：

```text
购物袋
包装费、配送费、服务费、押金
充值、优惠券、虚拟权益行
赠品、零金额行、测试商品、财务占位行
无法映射唯一商品编码的记录
```

### 第三步：构造三类小票集合

算法 06 不是只看买了锚点 A 的小票。

它先建三层集合：

| 集合 | 含义 | 用途 |
|---|---|---|
| `U_global` | 当前范围内全部有效目标画像小票 | 全局背景分母 |
| `U_category` | 包含目标叶子小分类商品的小票，但保留整张小票上的全部商品 | FP-Growth 发现候选项集 |
| `U_anchor` | 包含指定锚点 A 的小票 | 找 A 相关的候选商品 |

关键点：

```text
正式指标不能只用 U_anchor 做全局分母。
否则会把“买 A 的人当然更容易买相关商品”误当成真实强关联。
```

### 第四步：判断 A 和 B 在小票时点是否都有机会被买到

这一步是算法 06 最容易被误解、但非常关键的地方。

不是所有没买 B 的小票都能算作“消费者不买 B”。

如果那张小票发生时 B 已经没货、下架、不可售或售罄，这张小票不能放进 A/B 关系的分母。

因此要为每个商品对 A、B 建立：

```text
U_AB
= 在小票发生时
  A 和 B 均处于有效售卖状态
  均在实际上下架日期内
  当日实际到货量 > 0
  且尚未售罄
  的目标画像小票集合
```

如果没有正式售罄时间，就用：

```text
小票时点前累计销售量 < 门店当日实际到货量
=> 估计仍可购买
```

如果某门店 SKU 日出现：

```text
销售量 > 实际到货量 * 1.10
```

说明可能存在超卖或数据异常，这个门店 SKU 日不能进入正式购买机会分母，也不能简单截断成 100%。

### 第五步：用 FP-Growth 先发现真实共现

发现阶段的目标不是马上推荐新品，而是先把真实共现找出来。

业务原文确认：

```text
discovery_min_count = 1
discovery_min_support = 1 / valid_ticket_count(U_category)
```

意思是：

```text
哪怕只共现 1 次，也先保留下来。
但保留下来只代表“真实发生过”，不代表可以推荐新品。
```

FP-Growth 发现项集后，再用 Association Rules 生成：

```text
A=>B
B=>A
```

正反向都要输出。

### 第六步：构建四格表

对每个 A/B 商品对，在 `U_AB` 内建立四格表：

|  | 包含 B | 不包含 B |
|---|---:|---:|
| 包含 A | `n11` | `n10` |
| 不包含 A | `n01` | `n00` |

含义是：

```text
n11：A 和 B 同时出现的小票数
n10：出现 A 但没出现 B 的小票数
n01：没出现 A 但出现 B 的小票数
n00：A 和 B 都没出现的小票数

N = n11+n10+n01+n00 = valid_ticket_count(U_AB)
```

### 第七步：计算 support、confidence 和 lift

三个指标分别回答不同问题。

| 指标 | 公式 | 业务解释 |
|---|---|---|
| `support(A,B)` | `n11 / N` | A 和 B 在可购买小票里共同出现的比例 |
| `confidence(A=>B)` | `n11 / (n11+n10)` | 买了 A 的小票里，有多少也买了 B |
| `confidence(B=>A)` | `n11 / (n11+n01)` | 买了 B 的小票里，有多少也买了 A |
| `lift(A=>B)` | `support(A,B) / [support(A)*support(B)]` | A 和 B 是否比随机情况下更容易一起出现 |

正反向关系要特别注意：

```text
support(A,B) = support(B,A)
lift(A=>B) = lift(B=>A)
confidence(A=>B) 通常不等于 confidence(B=>A)
```

所以产品不能只看 A=>B，也不能伪造正反向不同的 Lift。

### 第八步：用贝叶斯区间判断是不是偶然

一次共现不能成为正式新品证据。

算法 06 用 Jeffreys-Dirichlet 贝叶斯区间控制小样本误判。

业务原文的核心逻辑是：

```text
(p11,p10,p01,p00)
~ Dirichlet(n11+0.5, n10+0.5, n01+0.5, n00+0.5)
```

这里的 `0.5` 不是业务权重，而是统计先验，用来避免小样本下出现零概率或无限 Lift。

正式规则必须同时满足：

```text
存在真实共现
Lift 95% 后验可信区间下界 > 1
通过贝叶斯 FDR
数值计算已收敛
门店×月份稳定性满足对应应用范围
```

贝叶斯 FDR 的业务含义是：

```text
同一锚点、同一范围内可能发现很多规则，
算法要控制整体误报，
不能每看到一个 lift > 1 就说它是真的。
```

业务原文确认的误报控制上限：

```text
mean(local_false_discovery_rate of selected rules) <= 5%
```

### 第九步：区分自然篮子和促销/时段折扣篮子

算法 06 不删除促销小票，但必须分开看。

| 篮子类型 | 判断规则 | 对新品开发的影响 |
|---|---|---|
| 全量篮子 | 当前范围内全部有效目标画像小票 | 保留真实消费行为 |
| 自然篮子 | A 和 B 都没有限时促销、没有实际时段折扣，且小票时间不晚于 19:30 | 自然需求证据 |
| 促销/时段折扣篮子 | A 或 B 参加限时促销，或存在实际时段折扣，或小票时间晚于 19:30 | 只能解释折扣/促销依赖 |

新品开发判断：

```text
全量成立 + 自然篮子也成立
=> 可进入新品属性判断

全量成立 + 只有促销/折扣篮子成立
=> PROMOTION_DEPENDENT，不生成新品
```

### 第十步：做稳定性和季节性验证

一条规则可能只是某一个门店、某一个月份或某一个会员拉动出来的。

因此要按：

```text
门店 × 自然月
```

分别建立四格表，并用分层贝叶斯汇总。

输出状态包括：

| 状态 | 含义 |
|---|---|
| `CROSS_STORE_MONTH_STABLE` | 跨门店、跨月份稳定 |
| `LOCAL_RULE` | 总体成立，但推广到新门店月份不稳定 |
| `SINGLE_BLOCK_DEPENDENT` | 删除某个门店或月份后关联消失 |
| `EXPLORATORY_RULE` | 只有一个有效门店月份，证据不足 |

如果锚点 A 是 S 状态季节商品，算法只在 SAP POP 计划上架开始到计划上架结束的窗口内计算。

计划上架窗口外没有销售，不代表消费者不喜欢，不能放进分母。

但这一步依赖 `dim_product_status` 的 SAP POP 商品状态和 S 行计划上架日期。

如果商品状态表里某条 `S` 记录缺少开始/结束日期，或者状态记录没同步到：

```text
product_status_code = S
season_start_date
season_end_date
```

算法 06 不能正式判断“计划上架窗口内成立的季节关联”。它最多按当前商品状态表和实际销售窗口做时间窗口解释，并输出：

```text
SEASONAL_STATUS_MISSING
```

这不是业务算法被删掉，而是告诉业务和开发：当前商品状态记录或计划上架日期不完整。

### 第十一步：判断能不能转成新品属性

这是算法 06 和普通购物篮分析最大的区别。

购物篮规则成立，只说明 A 和 B 经常一起买。

能不能生成新品，还要通过：

```text
小分类允许维度
品类保持检验
属性来源追溯
冲突处理
```

只有配方型关联可以直接生成新品属性。

例如：

```text
目标小分类：牛肉制品
锚点 A：黑椒牛柳丝
关联 B：青泡椒
=> 青椒可以作为牛肉制品的配料候选
=> 可生成“青椒黑椒牛柳丝 200g”
```

但：

```text
目标小分类：鲜鸡蛋
锚点 A：鲜鸡蛋
关联 B：鲜牛奶
=> 这是早餐消费场景
=> 不能生成“牛奶鸡蛋”
```

这里还有一个硬前提：

```text
必须命中 `dim_basket_attribute_transfer_rule` 当前有效规则。
```

如果当前规则版本没有覆盖这组锚点品类和关联品类，算法 06 仍然可以说：

```text
A 和 B 的购物篮关联成立
```

但不能继续说：

```text
B 可以成为目标小分类新品属性
```

这时新品候选结果必须写：

```text
candidate_status = CATEGORY_RULE_NOT_CONFIGURED
```

## 8. 购物篮规则怎么变成新品候选

这一段是算法 06 最像“新品开发”的地方，也最容易误解。

购物篮规则成立，只说明：

```text
目标画像消费者在真实小票里经常同时买 A 和 B。
```

但新品候选成立，还要继续判断：

```text
B 能不能成为目标叶子小分类商品的材料、配料、口味、规格、形态或场景属性。
```

### 8.1 强关联会分成三种结果

| 购物篮关系 | 能不能变新品 | 例子 |
|---|---|---|
| 配方型关联 | 可以进入新品候选 | 黑椒牛柳丝 + 青泡椒 -> 青椒黑椒牛柳丝 |
| 场景型关联 | 只能做消费场景证据 | 鲜鸡蛋 + 鲜牛奶 -> 早餐场景，不生成牛奶鸡蛋 |
| 促销/折扣依赖关联 | 不进入新品候选 | 只在促销或晚间折扣时共同购买 |

所以算法 06 不是“看到 A+B 就拼商品名”。

它必须先把 A/B 关系分清楚：

```text
它是配方关系？
还是餐食互补？
还是高频补充？
还是促销折扣带出来的临时关系？
```

只有第一类“配方型关联”能直接进入新品候选。

### 8.2 小分类规则用来判断什么

小分类规则回答的是：

```text
在这个叶子小分类里，哪些属性可以被改，哪些属性不能乱改。
```

例如：

```text
牛肉制品小分类：
可以接受口味变化、配料变化、规格变化。
青椒可以作为配料。

鲜鸡蛋小分类：
主体必须仍然是完整鸡蛋。
牛奶不能变成鸡蛋的配料。
```

如果没有这一步，算法就会把很多“经常一起买”的商品错误拼成新品。

### 8.3 品类保持检验是什么

品类保持检验就是再问一遍：

```text
加入 B 这个属性以后，候选新品还是不是原来的目标小分类？
```

通过：

```text
黑椒牛柳丝 + 青椒
=> 仍然是牛肉制品
=> CATEGORY_PRESERVED
```

不通过：

```text
鲜鸡蛋 + 鲜牛奶
=> 已经不是鲜鸡蛋
=> CATEGORY_CHANGED
```

如果品类保持不通过，购物篮规则可以保留，但新品候选状态必须是：

```text
NOT_ELIGIBLE_FOR_NEW_PRODUCT
```

### 8.4 新品名称怎么生成

新品名称不是大模型自由发挥，也不是把所有关联商品都塞进去。

它按来源逐项拼出：

```text
关联商品 B 提供：青椒
锚点商品 A 提供：黑椒、牛柳丝
算法 05 提供：200g 规格
```

最终得到：

```text
青椒黑椒牛柳丝 200g
```

同时结果表必须保存每个属性来自哪里：

| 属性 | 来源 |
|---|---|
| 青椒 | 关联商品 B + 正式购物篮规则 |
| 黑椒 | 锚点商品 A |
| 牛柳丝 | 锚点商品 A |
| 200g | 算法 05 目标规格 |

这样业务、采购和开发回查时，能知道这个新品不是凭空生成的。

### 8.5 多个关联商品不能随便合并

如果算法发现：

```text
黑椒牛柳丝 => 青椒
黑椒牛柳丝 => 圆葱
```

不能自动生成：

```text
圆葱青椒黑椒牛柳丝
```

只有真实小票里存在：

```text
黑椒牛柳丝 + 青椒 + 圆葱
```

并且三项规则也通过统计验证、自然篮子验证和品类保持检验时，才可以生成三项新品。

否则只能分别生成：

```text
青椒黑椒牛柳丝
圆葱黑椒牛柳丝
```

### 8.6 冲突处理顺序

如果同一条关系同时命中多个状态，按下面顺序处理：

```text
先排除无效数据、同一 SPU、换码组和替代组
再看自然篮子是否成立
再看小分类允许维度
再做品类保持检验
再限制季节、城市、门店等级、消费者画像和月份范围
最后交给后续历史差销、当前货盘和风险算法继续过滤
```

这里的含义是：

```text
低证据规则不能覆盖正式规则。
促销依赖不能伪装成自然需求。
场景互补不能伪装成配方新品。
品类变了就不能强行留在原小分类里。
```

## 9. 一个完整计算例子

假设：

```text
周期：2026 年 4-6 月
城市算法区域：上海
门店等级：A 级
目标画像：上班族晚高峰型-小家庭-高频-价格非敏感
叶子小分类：牛肉制品
锚点 A：黑椒牛柳丝 200g
关联 B：青泡椒 300g
```

先从小票里构建 `U_AB`：

```text
原始目标画像小票 = 1,000
A 和 B 在小票时点都有购买机会的小票 U_AB = 600
```

四格表：

```text
n11 = 15   A 和 B 同时出现
n10 = 65   出现 A 但没出现 B
n01 = 35   没出现 A 但出现 B
n00 = 485  A 和 B 都没出现
N = 600
```

点估计：

```text
support(A,B) = 15 / 600 = 2.50%

confidence(A=>B)
= 15 / (15+65)
= 18.75%

confidence(B=>A)
= 15 / (15+35)
= 30.00%

lift
= 2.25
```

业务解释：

```text
买黑椒牛柳丝的小票里，18.75% 也买了青泡椒。
买青泡椒的小票里，30.00% 也买了黑椒牛柳丝。
Lift = 2.25，说明两者共同出现强于随机情况。
```

然后看贝叶斯结果：

```text
Lift 95% 可信区间 = 1.45-3.18
P(lift>1) = 99.947%
local_false_discovery_rate = 0.053%
```

再看自然篮子：

```text
自然篮子 Lift 95% 区间 = 1.48-3.53
```

说明不是只靠晚间折扣或促销带出来。

最后做新品属性判断：

```text
青椒   <- 关联商品 B 和正式购物篮规则
黑椒   <- 锚点商品 A
牛柳丝 <- 锚点商品 A
200g   <- 算法 05
```

如果品类保持检验通过，输出：

```text
candidate_product_name = 青椒黑椒牛柳丝 200g
candidate_status = FORMAL_NEW_PRODUCT
candidate_source = BASKET_RECIPE
```

## 10. 结果状态怎么理解

算法 06 不能只输出“有 / 没有”，必须区分状态。

### 10.1 购物篮规则状态

| 状态 | 业务含义 |
|---|---|
| `FORMAL_RULE` | 正式规则，统计证据、FDR、稳定性均通过 |
| `EXPLORATORY_RULE` | 有一定证据，但稳定性或样本仍不足 |
| `RAW_COOCCURRENCE` | 真实共现发生过，但不能当成正式规则 |
| `NO_COOCCURRENCE` | 有有效锚点小票，但确实没有共现 |
| `NO_VALID_ANCHOR_BASKET` | 没有有效锚点小票，无法计算 |

### 10.2 新品候选状态

| 状态 | 业务含义 |
|---|---|
| `FORMAL_NEW_PRODUCT` | 可作为正式购物篮新品候选进入算法 08 做标准化与合并 |
| `SEASONAL_NEW_PRODUCT` | 只适用于季节窗口的候选新品 |
| `LOCAL_PILOT_NEW_PRODUCT` | 只适用于局部门店、城市、等级、画像或月份 |
| `EXPLORATORY_NEW_PRODUCT` | 有方向，但证据尚不充分 |
| `NOT_ELIGIBLE_FOR_NEW_PRODUCT` | 关联存在，但不能转成新品属性 |

### 10.3 不能把缺失写成 0

```text
无观测、不适用、来源缺失、计算不稳定
```

都不能写成 0。

例如：

```text
没有有效锚点小票
=> NO_VALID_ANCHOR_BASKET

有共现但证据不足
=> RAW_COOCCURRENCE 或 EXPLORATORY_RULE

只有促销期成立
=> PROMOTION_DEPENDENT

小分类规则缺失
=> CATEGORY_RULE_NOT_CONFIGURED
```

## 11. 开发实际要怎么做

开发可以有过程表，但正式交付以 6 张结果表为准。

建议开发顺序：

```text
1. 创建 basket_run，锁定周期、范围、上游算法版本和数据快照。
2. 从算法 01-04 正式结果中取目标画像、门店群、叶子小分类和锚点商品；需要具象候选规格和价格上下文时，再读取算法 05 价格可行性结果。
3. 从 Doris 小票构建有效篮子，保留单商品篮子，同票同 SKU 先合并。
4. 用商品基础表把 SKU 映射到标准商品；V1 使用现有 SPU 归并，SPU 为空或无法映射时保留 SKU_ONLY，不使用名称相似合并。
5. 构建 U_global、U_category、U_anchor。
6. 对每个候选 A/B 建 U_AB，剔除不可售、未到货、已售罄和超卖异常机会。
7. 用 FP-Growth 发现真实项集，写入 basket_itemset_cooccurrence。
8. 对每个 A/B 生成正反向规则，计算四格表和原始 support、confidence、lift。
9. 计算 Jeffreys-Dirichlet 后验区间、P(lift>1) 和贝叶斯 FDR。
10. 拆分全量、自然、促销/时段折扣篮子，判断是否促销依赖。
11. 做门店×月份稳定性验证；计划上架窗口验证依赖商品状态表中的 `S` 起止日期，拉动月验证依赖算法 04 明确输出拉动月。
12. 做小分类允许维度和品类保持检验；没有小分类新品属性规则时，只输出购物篮规则，不输出正式 BASKET_RECIPE 新品。
13. 写入 6 张正式表，并做主键、版本、数量和小票回查验收。
```

## 12. 业务验收看什么

业务和开发评审时重点看 6 件事。

| 验收点 | 看什么 |
|---|---|
| 范围是否正确 | 城市算法区域、门店等级、消费者画像、叶子小分类是否正确 |
| 小票是否正确 | 是否只用目标画像有效小票，是否保留单商品篮子 |
| 购买机会是否正确 | 未到货、不可售、已售罄、超卖异常是否正确处理 |
| 公式是否正确 | 四格表、support、confidence、lift、贝叶斯区间是否可复算 |
| 规则状态是否正确 | 一次共现、零共现、无锚点、有共现但不稳定是否分开 |
| 新品转化是否正确 | 配方型关联、餐食互补、促销依赖、品类改变是否分开 |

固定复算样例：

```text
N=1,000
n11=15
n10=85
n01=45
n00=855
```

必须得到：

```text
support(A,B)=1.50%
confidence(A=>B)=15.00%
confidence(B=>A)=25.00%
lift(A=>B)=lift(B=>A)=2.50
```

## 13. 现在还需要确认什么

这里只保留真正会影响开发落地或评审验收的红线。

| 优先级 | 确认对象 | 需要评审的红线 |
|---|---|---|
| P1 | 数据开发 | 是否能实现 FP-Growth、Association Rules、Jeffreys-Dirichlet 区间、Lift 后验模拟和贝叶斯 FDR |
| P1 | 业务/商品/数据开发 | `dim_basket_attribute_transfer_rule` 是否按合同落表、当前有效版本是否覆盖重点小分类，并完成抽样验收；未覆盖的品类关系只能输出 `CATEGORY_RULE_NOT_CONFIGURED` |
| P1 | 数据开发 / 商品 | `dim_product_status` 是否按合同落表，S 行开始/结束日期是否齐全；缺失时不能输出正式季节新品 |
| P1 | 算法 04/数据开发 | 算法 04 是否正式输出锚点拉动月集合；如果不输出，算法 06 需要自行按月重算并标记来源 |
| P2 | 数据开发 | 可订可售表是日粒度，`U_AB` 同时可购买集合一期按日粒度落地并保留机会判断口径 |

## 14. 不要做什么

```text
不能把购物篮结果用于促销、陈列或订购协同
不能只用包含锚点的小票计算全局 Lift
不能因为统一固定 min_support 丢掉真实共现
不能将一次共现包装成正式规则
不能只显示 A=>B 而隐藏 B=>A
不能伪造正反向不同 Lift
不能用名称相似自动合并商品编码
不能删除单商品篮子来提高规则
不能把未到货或已售罄解释为消费者不购买
不能把超卖异常截断为 100%
不能只靠促销或时段折扣关系生成新品
不能把餐食互补商品机械拼成新品配料
不能把 A=>B 和 A=>C 擅自拼成三项新品
不能用 AI 品类常识代替品类属性证据
不能在小分类规则缺失时回退到通用模板
不能用购物篮伪造 Omega-3、低胆固醇等外部属性
```

## 15. 一句话总结

算法 06 的关键是：

```text
先用真实小票证明 A 和 B 的共同购买关系；
再用可购买机会、贝叶斯证据、自然篮子、稳定性和品类规则排除误判；
最后只把真正能作为配方型属性的关系转成新品候选。
```
