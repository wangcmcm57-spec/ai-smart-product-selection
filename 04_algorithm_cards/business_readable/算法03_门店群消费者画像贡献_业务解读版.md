## 1. 先用一句话理解

门店群消费者画像贡献算法要做的事是：

```text
在同一个城市算法区域、同一个品类、同一个门店品类等级群里，
判断哪些消费者类型既覆盖了更多有效会员，又贡献了更多销售额。
```

这里的“覆盖了更多有效会员”，不是说会员贡献了会员规模。

它的意思是：

```text
这个消费者类型里有多少购买会员。
```

例如：

```text
上海 + 牛肉制品 + A 级门店群
共有 10,000 个已贴标有效购买会员。

其中：
常规时段型-小家庭-中频-价格非敏感 有 3,500 人
上班族晚高峰型-小家庭-中频-价格非敏感 有 3,000 人
捡漏型 有 2,000 人
```

那么第一类消费者的会员覆盖占比就是：

```text
3,500 / 10,000 = 35%
```

算法 03 要找的是：

```text
人多
+ 买得多
```

同时成立的消费者类型。

## 2. 最终会输出什么

算法 03 输出两张表。

第一张：消费者类型贡献明细表。

```text
mart_store_group_consumer_contribution
```

一行表示：

```text
一个统一算法批次
+ 一个城市算法区域
+ 一个品类
+ 一个门店群
+ 一个消费者类型
```

它回答：

```text
这个消费者类型在这个门店群里，会员数、销售额、小票数和贡献得分是多少？
```

第二张：门店群主力人群汇总表。

```text
mart_store_group_consumer_summary
```

一行表示：

```text
一个统一算法批次
+ 一个城市算法区域
+ 一个品类
+ 一个门店群
```

它回答：

```text
这个门店群最终有没有明显主力消费者类型？
如果有，主力消费者类型是谁？
```

如果门店群的正式业务键已经确定，但贡献周期内确实没有有效会员消费：

```text
消费者类型贡献明细表不伪造空画像行；
门店群主力人群汇总表保留 1 行 NOT_CALCULABLE（不可计算）结果。
```

这样既不会把“没有会员消费”误写成零贡献画像，也不会让一个已知门店群从正式结果中静默消失。

## 3. 它在 AI 选品链路中的位置

算法 03 依赖算法 01 和算法 02。

```text
算法 01：会员画像
-> 每个会员得到唯一 final_profile

算法 02：门店品类等级
-> 每个门店在某个品类下得到唯一 final_level

算法 03：门店群消费者画像贡献
-> 在某个门店等级群里，判断哪些消费者类型是主力
```

算法 03 不直接推荐新品。

它的作用是给算法 04 和后面的新品机会模型确定目标人群。

## 4. 一期用哪些数据

| 数据 | 本算法怎么用 |
|---|---|
| 算法 01 会员画像正式结果表 | 读取会员的 `final_profile` |
| 算法 02 门店品类等级正式结果表 | 读取门店在品类下的 `final_level`，组建门店群 |
| Doris 小票商品明细表 | 统计全量有效销售、已贴标会员销售额、小票数和交易明细 |
| 商品基础表 | 算法 01、02、03 在同一次全链路运行中使用同一份分类，判断商品属于哪个大类、中类、小类 |
| 门店基础表 | 补充门店、城市和门店状态 |
| 统一算法批次城市区域映射快照表 | 确定本批华东全部城市的算法区域；算法 01～03 共用，不自行重建范围 |

关键规则：

```text
算法 03 只读取算法 01 和算法 02 的正式结果。
算法 03 不重新贴会员画像。
算法 03 不重新计算门店品类等级。
```

一期范围不是只跑上海。系统读取该 `algorithm_batch_version（统一算法批次版本）`城市区域快照中已经纳入的华东全部数据，再按各自 `scope_id（算法区域编码）`分别计算，不能用上海样例反推正式范围。

## 5. 数据周期和版本

正式贡献周期：

```text
最近 3 个数据完整自然月
```

例如 2026 年 7 月运行：

```text
contribution_start_date = 2026-04-01
contribution_end_date = 2026-06-30
```

同一个贡献周期只使用一个统一算法批次：

```text
algorithm_batch_version = BATCH_ + contribution_end_date 的 YYYYMM
算法 01 会员画像、算法 02 门店品类等级、算法 03 和城市区域映射快照全部使用同一个 algorithm_batch_version
```

不再为 03 单独生成贡献模型版本，也不再引用画像模型版本、门店等级模型版本、范围版本或商品分类版本作为第二套业务版本。

这里的意思是：

```text
同一批 03 结果，不能一部分会员、门店或城市使用其他 algorithm_batch_version；
同批数据修正重跑仍用原 BATCH_YYYYMM，只更新运行ID、更新时间和重跑原因；
规则或口径变化从下一完整自然月批次生效，不改历史批次。
```

否则结果变化可能不是消费者真的变了，而是上游口径混用了。

V1 商品分类口径已经确定：

```text
不新增分类快照或分类读取绑定。
同一次全链路运行由调度系统锁定同一份 `dim_sku（商品基础表）`商品分类，实际输入表和分区由平台现有任务血缘追溯，不要求算法正式结果新增源数据版本字段或发布记录表。
同批补数或商品数据修正时，01 -> 02 -> 03 按顺序全部重跑。
历史批次若无法核实重读当时的原始分类，就暂停历史重跑，不能用今天的分类补造过去。
```

## 6. 门店群怎么定义

门店群来自算法 02 的 `mart_store_category_level`。

支持两种门店群：

```text
FINAL_LEVEL：指定等级门店群，例如 A 级门店群、B 级门店群
ALL_RATED：当前范围和品类下全部已有正式等级的门店
```

注意：

```text
算法 03 不生成单门店正式结果。
```

它看的是：

```text
一组门店里的消费者结构。
```

`ALL_RATED` 不能把 A、B、C、D 的结果直接相加。

原因是：

```text
同一个会员可能在 A 级门店买过，也在 B 级门店买过。
如果直接把各等级结果相加，这个会员会被重复计算。
```

所以 `ALL_RATED` 必须从底层小票重新聚合。

## 7. 消费者类型怎么来

消费者类型直接读取算法 01 的：

```text
final_profile
```

当前规则：

```text
捡漏型
上班族晚高峰型-家庭规模-消费频次-价格态度
常规时段型-家庭规模-消费频次-价格态度
```

捡漏型是终止标签：

```text
final_profile = 捡漏型
family_level = NOT_APPLICABLE
frequency_level = NOT_APPLICABLE
price_attitude = NOT_APPLICABLE
```

算法 03 不能再给捡漏型拼家庭、频次或价格态度后缀。

算法 01 正式画像还必须提供 `profile_terminal_flag`，算法 03 只做字段完整性和追溯校验，不重新拼画像。业务原文曾列出 `result_status`，但当前正式 `dim_customer_profile` 合同没有该列；V1 以正式发布闸门、版本唯一、`final_profile` 非空和 `profile_terminal_flag` 完整来判断画像是否可消费，不臆造一个不存在的状态字段。

## 8. 有效交易怎么过滤

这里要分两层理解。

第一层：业务原则。

```text
只保留正常完成的正向销售。
剔除退货、退款、取消、冲销、测试交易和异常金额交易。
```

第二层：当前 Doris 可落地字段。

V1 只能执行已经确认存在且含义冻结的字段；取消、冲销、测试交易若没有单独冻结的字段或枚举，不由开发自行猜测，不把“退款类型非空”当成统一剔除条件。

当前已确认的小票表是：

```text
data_agent.dws_member_order_item_detail_df_all_new
```

这张表包含会员和非会员交易，可通过 `is_customer` 区分：

```text
is_customer = 1：会员交易
is_customer = 0：非会员交易
```

V1 分两类口径。

第一类：全量有效交易。

它用于计算门店群目标品类的全部销售额，也就是覆盖率分母。

| 过滤目的 | 字段 | V1 过滤口径 |
|---|---|---|
| 正常完成订单 | `order_status` | `order_status = 'os.completed'` |
| 剔除退货 | `is_return` | `is_return = 0` |
| 剔除非正销售 | `usual_amt` | `usual_amt > 0` |
| 保证有效数量 | `weight` | `weight > 0` |
| 门店有效 | `store_id` | 不为空，并能关联门店基础表 |
| 商品有效 | `article_id` | 不为空，并能关联商品基础表 |

`refund_type` 在 V1 只做退款枚举质量检查。不能因为该字段非空就直接删除一笔已经满足正常完成、非退货、正金额和正数量条件的交易。以后如果真实数据核实出必须剔除的退款枚举，要同时修改算法 01、02、03 的规则和验收样例，并从下一个完整自然月批次生效；已经发布的历史批次继续用原规则重跑，不能原地改口径。

第二类：已贴标会员有效交易。

它用于计算各消费者类型的贡献分。

| 过滤目的 | 字段 | V1 过滤口径 |
|---|---|---|
| 必须是会员交易 | `is_customer` | `is_customer = 1` |
| 会员有效 | `customer_id` | 非 NULL、非空字符串、不以 `6` 开头，并能关联正式会员画像 |

所以：

```text
主力贡献得分 = 只看已贴标会员有效交易
会员销售覆盖率 = 已贴标会员销售额 / 全量有效销售额
```

已贴标会员还必须满足算法 01 已冻结的有效会员规则：`is_customer（是否会员） = 1`、`customer_id（会员ID）`非 NULL 且非空字符串、不以 `6` 开头；同一会员同一天有效小票数超过 5 张时，剔除该会员当天全部交易。算法 03 直接调用与算法 01、02 相同的会员过滤公共实现，不再记录独立会员过滤版本。

小票唯一键已确认：

```text
order_id 全公司唯一。
订单数 / 小票数 = COUNT(DISTINCT order_id)
```

取消、冲销、测试交易 V1 口径已确认：

```text
第一期先使用现有 Doris 字段过滤。
暂不要求新增取消、冲销、测试交易字段。
```

## 9. 关联检查怎么理解

关联检查的核心目的是：

```text
避免一条消费记录被重复计算，或者被归到错误画像、错误门店等级、错误品类。
```

### 9.1 会员画像唯一

规则：

```text
同一 algorithm_batch_version + customer_id 只能有一个 final_profile
```

例子：

| 统一算法批次 | 会员ID | final_profile |
|---|---|---|
| BATCH_202608 | M001 | 常规时段型-小家庭-中频-价格非敏感 |
| BATCH_202608 | M001 | 上班族晚高峰型-小家庭-中频-价格非敏感 |

这是错误数据。

因为同一个会员在同一统一批次里出现了两个画像。

如果拿它去关联小票，M001 的消费可能被算进两个消费者类型，销售额会重复。

### 9.2 门店品类等级唯一

规则：

```text
同一 algorithm_batch_version + 范围 + 门店 + 品类只能有一条算法 02 结果
```

例子：

| 统一算法批次 | 范围 | 门店 | 品类 | final_level |
|---|---|---|---|---|
| BATCH_202608 | 上海 | S001 | 牛肉制品 | A |
| BATCH_202608 | 上海 | S001 | 牛肉制品 | B |

这是错误数据。

因为同一个门店、同一个品类，在同一统一批次里不能既是 A 又是 B。

如果拿它去关联小票，这家门店的牛肉销售会同时进入 A 级门店群和 B 级门店群。

### 9.3 商品品类映射唯一

规则：

```text
V1 由调度系统为本次 01→02→03 全链路锁定同一份 `dim_sku（商品基础表）`分类，具体输入表和分区由平台任务血缘追溯。
同一次全链路运行中，一个 `article_id（商品编码）`只能命中一个品类，而且不能未命中。
```

例子：

| 商品编码 | 小类 |
|---|---|
| 21231650 | 牛肉制品 |
| 21231650 | 调理肉制品 |

这是错误数据。

因为同一个商品在同一次全链路运行读取的商品基础表中，不能同时属于两个小类。

如果拿它去筛选品类，同一笔销售会被算进两个品类。

商品分类变更属于小概率事件，V1 不做历史分类版本回溯。

此外，商品没有匹配到任何品类也不能被内连接悄悄丢掉。算法 03 会单独核对未映射源记录；发现缺失或一对多时记录 `CATEGORY_MAPPING_ERROR（商品分类异常）`，本次整个 `algorithm_batch_version（统一算法批次版本）`不发布两张正式结果表。

### 9.4 算法 02 成功后直接计算覆盖率

`NOT_CALCULABLE（不可计算）`代表“知道这个门店品类应该评级，但条件不足没有算出等级”。算法 02 已经在发布前自行检查源交付、门店/区域/品类映射、唯一键、参数、公式和清单结果双向一致；任一检查失败时整批不发布，算法 03 不启动。

因此算法 03 不重复算法 02 的全量验收。调度确认同批算法 02 任务成功后，直接计算：

```text
未评级门店数 = 本组 NOT_CALCULABLE 去重门店数
评级覆盖率 = 本组已评级门店数 /（已评级门店数 + 未评级门店数）
```

若同批算法 02 任务失败、运行中或批次不一致，算法 03 不启动，也不会出现“只算贡献、把覆盖率留空”的降级路径。

## 10. 基础指标怎么算

在同一个门店群内，对每个消费者类型计算：

```text
profile_member_cnt = 该消费者类型的去重有效会员数
profile_sales_amt = 该消费者类型的目标品类全日有效会员销售额
profile_ticket_cnt = 该消费者类型的目标品类有效会员小票数，COUNT(DISTINCT order_id)
profile_avg_ticket_amt = profile_sales_amt / profile_ticket_cnt
```

门店群整体分母分两类。

第一类：贡献分分母，只看已贴标会员交易。

```text
group_member_cnt = 门店群内全部已贴标有效会员数
group_sales_amt = 门店群内全部已贴标有效会员目标品类销售额
group_ticket_cnt = 门店群内全部已贴标有效会员目标品类小票数，COUNT(DISTINCT order_id)
group_avg_ticket_amt = group_sales_amt / group_ticket_cnt
```

第二类：覆盖率分母，看会员画像能覆盖多少全量销售。

```text
group_total_sales_amt = 门店群内目标品类全量有效销售额，包含会员和非会员
profiled_member_sales_amt = 门店群内目标品类已贴标会员销售额
profile_sales_coverage_rate = profiled_member_sales_amt / group_total_sales_amt
```

业务含义：

```text
贡献分回答：在已贴标会员里，哪个消费者类型最主力？
覆盖率回答：这批已贴标会员销售能代表全量销售的程度有多高？
```

## 11. 画像贡献占比怎么算

每个消费者类型计算三个占比：

```text
member_share = profile_member_cnt / group_member_cnt
sales_share = profile_sales_amt / group_sales_amt
ticket_share = profile_ticket_cnt / group_ticket_cnt
```

业务含义：

| 指标 | 含义 |
|---|---|
| `member_share` | 这个消费者类型覆盖了多少购买会员 |
| `sales_share` | 这个消费者类型贡献了多少会员销售额 |
| `ticket_share` | 这个消费者类型贡献了多少会员小票 |

正式主力判定只用：

```text
member_share
sales_share
```

`ticket_share` 只用于解释。

## 12. 贡献得分怎么算

贡献得分使用调和平均：

```text
profile_contribution_score =
2 * sales_share * member_share
/ (sales_share + member_share) * 100
```

它解决的问题是：

```text
不能只看销售额。
不能只看会员人数。
要找“人多且买得多”的消费者类型。
```

例子：

| 消费者类型 | 会员占比 | 销售占比 | 解释 |
|---|---:|---:|---|
| A 类型 | 35% | 34% | 人多，销售也高，适合作为主力候选 |
| B 类型 | 5% | 30% | 销售高但人数少，可能是小众高客单 |
| C 类型 | 30% | 8% | 人多但购买弱，不应只因人数多成为主力 |

调和平均会压低 B 和 C 这种单边高的类型。

计算中使用高精度数值，最后展示才舍入。两个画像在页面都显示 50.0000，不代表真实计算得分相同；分组与排名看舍入前的值。会员数、销售额等复算依据保留，不用显示占比重新算分。

## 13. 主力消费者类型怎么判定

同一个门店群内，把所有消费者类型按贡献得分排序。

算法只判断两种情况：

```text
K = 1：没有明显高低组
K = 2：低贡献组 + 高贡献组
```

用：

```text
Jenks 自然断点 + BIC
```

来判断是否存在明显高贡献组。

如果选择 K=2：

```text
高贡献组 = 正式主力消费者类型
is_main_profile = 1
result_status = SUCCESS
```

如果选择 K=1：

```text
没有明显主力
result_status = NO_OBVIOUS_MAIN
is_main_profile = 0
```

K=1 时，最高分消费者类型只作为相对主力候选：

```text
is_relative_main_candidate = 1
```

正常比较后选择 K=1，表示算过但不适合分高低组：保留已算出的 SSE/BIC 比较结果，只把断点写空。只有单一消费者类型、不需要运行分组时才标记不适用；数据异常无法计算时写异常审计，不发布正式结果。

它不是正式主力。

只有一种有效消费者类型时：

```text
result_status = SINGLE_PROFILE
is_main_profile = 1
profile_contribution_score = 100
```

这只说明消费结构单一，不代表这个人群的经营价值必然更高。

## 14. 稳定性怎么验证

稳定性只用来解释结果可靠不可靠。

它不修改正式主力判定。

### 14.1 会员级 Bootstrap

Bootstrap 的抽样单位是会员，不是小票。

原因：

```text
如果抽小票，同一个会员的消费会被拆散，会员覆盖占比会失真。
```

每轮做法：

```text
从门店群有效会员中有放回抽样
被抽中的会员带上周期内全部目标品类消费
重新计算贡献得分和主力判定
记录每个消费者类型被判为主力的次数
```

每个门店群按“统一算法批次＋算法区域＋品类＋门店群类型＋门店等级”派生自己的固定随机种子。同一门店群和相同输入重跑时抽样结果一致；不同门店群不共用一个全局固定种子，避免形成相同抽样序列。

停止规则：

```text
至少 1,000 轮
最多 10,000 轮
每 250 轮检查一次
所有消费者类型 MCSE <= 0.01 时停止
```

### 14.2 留一月验证

正式周期是 3 个月。

分别删除一个月再重算：

```text
删除第 1 月：用第 2 月 + 第 3 月
删除第 2 月：用第 1 月 + 第 3 月
删除第 3 月：用第 1 月 + 第 2 月
```

它回答：

```text
主力人群是不是只因为某一个特殊月份才出现？
```

## 15. 最终结果状态

常见状态：

| 状态 | 含义 |
|---|---|
| `SUCCESS` | 正常生成明显主力人群 |
| `SINGLE_PROFILE` | 只有一种有效消费者类型 |
| `NO_OBVIOUS_MAIN` | 没有明显分离的主力结构 |
| `NOT_CALCULABLE` | 门店群业务键已确定，但没有有效会员消费，当前不能计算画像贡献 |
| `NO_RATED_STORE` | 没有可用正式等级门店 |
| `CATEGORY_MAPPING_ERROR` | 品类映射缺失或一对多 |
| `PROFILE_LINK_INCOMPLETE` | 应关联会员未 100% 关联正式画像 |
| `NO_MEMBER_CONSUMPTION` | 没有有效会员消费 |
| `DUPLICATE_JOIN_ERROR` | 关联造成明细、销售额或小票膨胀 |
| `TRANSACTION_DATA_ERROR` | 销售额、小票数或交易主键异常 |
| `UPSTREAM_VERSION_ERROR` | 上游统一批次缺失、混用或同批算法 02 任务未成功 |

`SINGLE_PROFILE` 和 `NO_OBVIOUS_MAIN` 是有效业务结果，不是数据错误。

结果写入边界：

```text
没有正式等级门店（NO_RATED_STORE）：没有合法门店群，不写两张正式结果表，只记录运行审计。
有合法门店群但没有有效会员消费（NO_MEMBER_CONSUMPTION）：消费者类型贡献明细表不写伪造画像行；门店群主力人群汇总表写 1 行 NOT_CALCULABLE（不可计算），主力列表为空、主力覆盖率和聚类结果为空，并在汇总说明中记录原因。
画像关联不完整、统一批次混用、关联一对多、商品分类异常或交易数据异常：属于数据质量阻断，整个 algorithm_batch_version（统一算法批次版本）不发布两张正式结果表，只记录运行审计和异常原因，不能降级写成 NOT_CALCULABLE（不可计算）。
```

`NOT_CALCULABLE（不可计算）`不是最低分、零贡献或人工兜底状态。它只表示“门店群已经明确，但确实没有会员消费可供计算”；不能用它掩盖数据缺失、映射错误或公式错误。

算法 03 由调度系统在同批算法 02 任务成功后启动。算法 02 未成功时算法 03 不运行；成功后直接按同批正式结果中的 `SUCCESS（成功）`和 `NOT_CALCULABLE（不可计算）`计算门店群与覆盖率。

如果已经存在有效会员交易，但金额或全量销售分母出现不合理的 0，则标记 `TRANSACTION_DATA_ERROR`；只有确实没有有效会员消费时才使用 `NO_MEMBER_CONSUMPTION`，避免两个状态含义重叠。

## 17. 开发实际运行流程

算法 03 是月度离线批量计算。开发先确定本次 `algorithm_batch_version（统一算法批次版本）`和贡献周期，调度确认同批算法 02 已完成自行验收并原子发布，再读取同批算法 01 画像、算法 02 等级结果、本批城市区域映射快照和本次全链路运行的商品分类。计算结果先进入本次运行的临时计算区；算法 03 自行完成输入交付、唯一键、映射、状态、公式和预期结果完整性验收后，才原子发布贡献明细表和门店群主力人群汇总表。

前端和后续算法只读取已发布结果。采购查询城市、品类、门店等级或消费者画像时，只是在结果表里筛选，不触发实时重算，也不改变主力人群判断。

采购前端输入的是城市、品类、门店群或消费者画像等查询条件，不是手动录入候选商品、规格或成本；候选商品由后续算法链路产生。本算法也不把查询条件当成算法输入事实。

开发过程可以理解为：

```text
1. 锁定统一算法批次和最近 3 个完整自然月
2. 检查算法 03 所需源表、日期分区和上游正式结果是否完整交付
3. 读取算法 01 同批正式会员画像
4. 调度确认同批算法 02 任务成功，再读取同批正式等级结果并核对周期、主键和状态域
5. 生成本批预期门店群清单：有 `SUCCESS（成功）`等级结果的等级群和 ALL_RATED（全部已评级门店群）均必须列入
6. 用 `SUCCESS（成功）`行组建门店群，用 `NOT_CALCULABLE（不可计算）`行统计未评级门店和覆盖率
7. 读取贡献周期内的小票商品明细
8. 按正常完成、非退货、正金额和正数量过滤交易；refund_type 非空不直接删除
9. 按本次全链路运行的 `dim_sku（商品基础表）`分类筛选目标品类，并检查未映射/一对多源记录
10. 把会员消费关联到同批 final_profile
11. 按门店群 + 品类 + final_profile 聚合
12. 计算 member_share、sales_share、ticket_share
13. 用调和平均计算贡献得分
14. 用 Jenks/BIC 判断是否存在明显主力
15. 做 Bootstrap 和留一月稳定性验证
16. 在临时计算区生成贡献明细和门店群汇总；无有效会员消费的已知门店群生成 NOT_CALCULABLE 汇总
17. 算法 03 自行检查唯一键、映射、状态、公式、金额、小票、画像关联，并让预期门店群清单与临时汇总、预期画像明细键与临时明细双向对账
18. 任一阻断检查失败时，整个统一算法批次不写入、不追加、不覆盖两张正式表；保留上一版可靠结果
19. 全部检查通过后，按同一 algorithm_batch_version（统一算法批次版本）原子发布贡献明细表和门店群汇总表
20. 平台调度把算法 03 同批任务标记为成功，再触发算法 04 或其他下游算法
```

运行依赖和空结果处理：

```text
算法 01、算法 02、城市区域映射、商品分类和交易数据先完成统一批次与源数据检查，再执行聚合。
画像关联、商品分类、统一批次、输入交付、唯一键、公式或双向对账闸门失败时，整个统一算法批次只写平台运行审计，不发布两张正式结果表。
无正式等级门店时没有合法门店群，只写运行审计；已有合法门店群但无会员消费时，贡献明细不写伪造画像行，汇总表写 1 行 NOT_CALCULABLE（不可计算）。
算法 02 同批任务未成功时算法 03 不启动；成功后算法 03 不重复算法 02 的全量验收。
Bootstrap 和留一月验证是批量计算阶段完成的质量指标；前端查询只读取已经发布的质量字段，不实时重算。
```

算法 03 不新建独立运行参数表、发布记录表、配置快照、读取绑定或运行清单摘要；运行异常和对账写平台公共审计，两张正式结果表保留统一批次、本次运行ID和重跑字段，不复制上游证据 JSON 或配置快照。

汇总表保留为实体表。每种画像明细上重复带出的“门店群总销售额、总会员数”只能取一次，不能按画像相加。比如两行都写总销售额 100 万，汇总仍是 100 万；只有各画像自己的销售额才按规则相加。发现重复总量不一致时先报错，不随便取最大值。

Bootstrap 运行失败时，保留完整周期的主力结论，稳定性入选率、区间和误差写空；已完成轮数保留。只有一种画像无需抽样，入选率及区间为 1、误差为 0。汇总质量说明中的误差取各画像最大值，轮数不累加。

如果 02 同批重跑更新了等级，或发现原等级不可靠，旧 03 结果立即停止提供给下游，重算后恢复。01 画像同批替换也一样。这里检查的是已发布结果是否仍可用，不是查询时现场重算。

业务人员在发布后查看和复核结果。业务复核不作为算法 03 运行、发布或触发下游前的人工审批条件；发现问题后通过修正数据或实现并重跑同一批次处理，不直接手改正式结果。

## 18. 业务验收看什么

按业务原文，按城市或城市群、品类颗粒度和门店等级分层抽取至少 30 个门店群结果，从主力人群一路查回画像、原始小票和门店等级，并保存逐层对账。人工复核发现问题后修正数据或实现，不手动改主力名单。这是交付验收的抽查数量，不是算法要求每组至少有多少会员。

第一层：数据是否对。

```text
各消费者类型销售额合计 = 门店群已贴标有效会员销售额
各消费者类型小票数合计 = 门店群已贴标有效会员小票数
各消费者类型会员数合计 = 门店群去重有效会员数
SUM(sales_share) = 100%
SUM(member_share) = 100%
算法 01、02、03 和城市区域快照的 algorithm_batch_version 完全一致
平台调度确认同批算法 02 任务成功后才启动算法 03
商品分类未映射或一对多源记录已显式统计，没有在关联时静默丢失
算法 03 所需源表和日期分区全部交付成功，缺失数据没有被当成零消费
预期门店群数 = 临时汇总表门店群数，双向差异均为 0
预期消费者类型明细键与临时贡献明细键双向差异均为 0
```

第二层：公式是否对。

```text
member_share
sales_share
ticket_share
profile_contribution_score
Jenks SSE
BIC
Bootstrap MCSE
time_main_rate
未评级门店数和评级覆盖率
```

第三层：结果是否合理。

```text
主力消费者类型是否同时具备较高会员覆盖和销售贡献
NO_OBVIOUS_MAIN 是否没有被强行指定主力
SINGLE_PROFILE 是否被解释为消费结构单一
捡漏型是否没有被拆成家庭、频次、价格态度后缀
```

第四层：边界场景是否处理。

```text
没有正式等级门店
有合法门店群但没有有效会员消费时，明细 0 行、汇总 1 行且 result_status（结果状态）= NOT_CALCULABLE（不可计算）
画像关联不完整
只有一种消费者类型
全部贡献得分相同
同一会员跨门店、跨等级消费
同一张小票包含多个目标品类 SKU
关联维表一对多导致金额膨胀
算法 02 同批任务成功时覆盖率可由 `SUCCESS（成功）`与 `NOT_CALCULABLE（不可计算）`行复算
算法 02 同批任务失败或未完成时算法 03 不启动
refund_type 非空但其他有效条件满足时仍保留交易
任一阻断检查失败时整个 algorithm_batch_version（统一算法批次版本）不发布，两张正式表不会出现一张成功、一张失败
同批重跑失败时保留原有可靠正式结果，不用失败暂存结果覆盖
```

以上自动检查通过并原子发布后，业务再抽查至少 30 个门店群结果。业务只复核结果是否合理，不需要在算法运行过程中点击 `APPROVED（人工批准）`或确认后才能发布。

## 19. 开发交付还要验收什么

算法 03 的业务主逻辑完整。

当前只保留会影响开发交付验收的评审事项；数据合同已经明确的表名、粒度、主键和小票键不再重复询问：

| 确认项 | 需要谁确认 | 为什么重要 |
|---|---|---|
| 算法 01 正式 `dim_customer_profile` 是否按统一批次和唯一键稳定产出 | 数据开发 | 影响画像关联成功率和 `PROFILE_LINK_INCOMPLETE` 阻断 |
| 算法 02 正式结果衔接 | 数据开发 | 验收调度只在同批算法 02 自行验收和原子发布成功后启动算法 03，并准确读取等级、状态和品类字段 |
| 算法 02 门店评级覆盖 | 数据开发 | 验收算法 03 直接用同批 `SUCCESS（成功）`与 `NOT_CALCULABLE（不可计算）`行复算未评级门店数和覆盖率，不重复实现算法 02 的源交付与清单对账 |
| 01/02/03 有效交易规则是否使用同一实现 | 数据开发 | 当前 `refund_type` 非空不直接删单；未来枚举变更须三算法同步、下一完整月生效、历史批次不变 |
| Bootstrap 是否能按门店群业务唯一键派生固定种子、执行会员级抽样和 1,000～10,000 轮规则并落审计 | 数据开发 | 影响不同门店群抽样独立性、稳定性指标复现和运行成本 |

## 20. 不要做什么

```text
不要把非会员销售放进主力人群贡献得分分母
不要先算单门店占比再平均成门店群
不要把各门店等级结果相加生成 ALL_RATED
不要平均下一级品类结果生成上一级结果
不要用固定销售占比阈值或人工权重判定主力
不要因为样本较小直接删除真实消费者类型
不要用客单价、小票占比或门店覆盖率改变正式主力标签
不要在算法 03 中重新生成会员画像或门店等级
不要在上游异常时自动扩大区域或合并门店等级
不要只输出主力名称而不保留会员数、销售额、占比、参数和版本血缘
不要生成算法 03 独立模型版本、画像版本、等级版本、分类版本或范围版本；只使用 algorithm_batch_version 关联正式结果
不要新建算法 03 独立运行参数表、配置快照、读取绑定或运行清单摘要
不要绕过平台调度依赖，在同批算法 02 未成功时直接运行算法 03
不要让已知门店群因为没有会员消费而从汇总表静默消失
不要用 NOT_CALCULABLE（不可计算）掩盖输入缺失、映射错误、关联膨胀或公式错误
不要把业务人工复核设置为算法运行、正式发布或触发下游的前置审批
```

## 21. 一句话总结

门店群消费者画像贡献算法的本质是：

```text
先用算法 02 找到某个品类下的一组门店，
再用算法 01 找到这些门店消费会员的画像，
然后判断哪些消费者类型既覆盖更多购买会员，又贡献更多销售额，
为后续 SKU 表现和新品机会分析确定目标人群。
```
