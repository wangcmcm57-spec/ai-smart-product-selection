# 算法03_门店群消费者画像贡献_业务解读版

文档状态：一期业务解读版
依据文档：`archive/source_docs/business_algorithm_docs/算法卡_03_门店群消费者画像贡献_业务提供最新原始版_20260723.md`

## 1. 先用一句话理解

门店群消费者画像贡献算法要做的事是：

```text
在同一个城市算法区域、同一个品类、同一个门店品类等级群里，
判断哪些消费者类型既覆盖了更多有效会员，又贡献了更多销售额。
```

这里的“覆盖了更多有效会员”，不是说会员贡献了会员规模。

它的意思是：

```text
这个消费者类型里有多少购买会员。
```

例如：

```text
上海 + 牛肉制品 + A 级门店群
共有 10,000 个已贴标有效购买会员。

其中：
常规时段型-小家庭-中频-价格非敏感 有 3,500 人
上班族晚高峰型-小家庭-中频-价格非敏感 有 3,000 人
捡漏型 有 2,000 人
```

那么第一类消费者的会员覆盖占比就是：

```text
3,500 / 10,000 = 35%
```

算法 03 要找的是：

```text
人多
+ 买得多
```

同时成立的消费者类型。

## 2. 最终会输出什么

算法 03 输出两张表。

第一张：消费者类型贡献明细表。

```text
mart_store_group_consumer_contribution
```

一行表示：

```text
一个数据周期
+ 一个城市算法区域
+ 一个品类
+ 一个门店群
+ 一个消费者类型
```

它回答：

```text
这个消费者类型在这个门店群里，会员数、销售额、小票数和贡献得分是多少？
```

第二张：门店群主力人群汇总表。

```text
mart_store_group_consumer_summary
```

一行表示：

```text
一个数据周期
+ 一个城市算法区域
+ 一个品类
+ 一个门店群
```

它回答：

```text
这个门店群最终有没有明显主力消费者类型？
如果有，主力消费者类型是谁？
```

## 3. 它在 AI 选品链路中的位置

算法 03 依赖算法 01 和算法 02。

```text
算法 01：会员画像
-> 每个会员得到唯一 final_profile

算法 02：门店品类等级
-> 每个门店在某个品类下得到唯一 final_level

算法 03：门店群消费者画像贡献
-> 在某个门店等级群里，判断哪些消费者类型是主力
```

算法 03 不直接推荐新品。

它的作用是给算法 04 和后面的新品机会模型确定目标人群。

## 4. 一期用哪些数据

| 数据 | 本算法怎么用 |
|---|---|
| 算法 01 会员画像正式结果表 | 读取会员的 `final_profile` |
| 算法 02 门店品类等级正式结果表 | 读取门店在品类下的 `final_level`，组建门店群 |
| Doris 小票商品明细表 | 统计全量有效销售、已贴标会员销售额、小票数和交易明细 |
| 商品基础表 | 使用当前商品分类判断商品属于哪个大类、中类、小类 |
| 门店基础表 | 补充门店、城市和门店状态 |
| 城市算法区域映射表 | 确定城市算法区域和范围版本 |

关键规则：

```text
算法 03 只读取算法 01 和算法 02 的正式结果。
算法 03 不重新贴会员画像。
算法 03 不重新计算门店品类等级。
```

## 5. 数据周期和版本

正式贡献周期：

```text
最近 3 个数据完整自然月
```

例如 2026 年 7 月运行：

```text
contribution_start_date = 2026-04-01
contribution_end_date = 2026-06-30
```

同一个贡献周期只能使用：

```text
一个正式会员画像版本
一个正式门店品类等级版本
一个城市算法区域版本
一个商品基础表分类口径
```

不能把多个版本混在同一批结果里。

这里的意思是：

```text
同一批 03 结果，不能一部分会员用旧画像，一部分会员用新画像；
不能一部分门店用旧等级，一部分门店用新等级；
不能一部分城市用旧区域映射，一部分城市用新区域映射。
```

否则结果变化可能不是消费者真的变了，而是上游口径混用了。

V1 商品分类口径已经确定：

```text
商品分类使用当前商品基础表分类。
不做历史商品分类版本回溯。
```

## 6. 门店群怎么定义

门店群来自算法 02 的 `mart_store_category_level`。

支持两种门店群：

```text
FINAL_LEVEL：指定等级门店群，例如 A 级门店群、B 级门店群
ALL_RATED：当前范围和品类下全部已有正式等级的门店
```

注意：

```text
算法 03 不生成单门店正式结果。
```

它看的是：

```text
一组门店里的消费者结构。
```

`ALL_RATED` 不能把 A、B、C、D 的结果直接相加。

原因是：

```text
同一个会员可能在 A 级门店买过，也在 B 级门店买过。
如果直接把各等级结果相加，这个会员会被重复计算。
```

所以 `ALL_RATED` 必须从底层小票重新聚合。

## 7. 消费者类型怎么来

消费者类型直接读取算法 01 的：

```text
final_profile
```

当前规则：

```text
捡漏型
上班族晚高峰型-家庭规模-消费频次-价格态度
常规时段型-家庭规模-消费频次-价格态度
```

捡漏型是终止标签：

```text
final_profile = 捡漏型
family_level = NOT_APPLICABLE
frequency_level = NOT_APPLICABLE
price_attitude = NOT_APPLICABLE
```

算法 03 不能再给捡漏型拼家庭、频次或价格态度后缀。

算法 01 正式画像还必须提供 `profile_terminal_flag`，算法 03 只做字段完整性和追溯校验，不重新拼画像。业务原文曾列出 `result_status`，但当前正式 `dim_customer_profile` 合同没有该列；V1 以正式发布闸门、版本唯一、`final_profile` 非空和 `profile_terminal_flag` 完整来判断画像是否可消费，不臆造一个不存在的状态字段。

## 8. 有效交易怎么过滤

这里要分两层理解。

第一层：业务原则。

```text
只保留正常完成的正向销售。
剔除退货、退款、取消、冲销、测试交易和异常金额交易。
```

第二层：当前 Doris 可落地字段。

V1 只能执行已经确认存在且含义冻结的字段；取消、冲销、测试交易若没有单独冻结的字段或枚举，不由开发自行猜测，不把“退款类型非空”当成统一剔除条件。

当前已确认的小票表是：

```text
data_agent.dws_member_order_item_detail_df_all_new
```

这张表包含会员和非会员交易，可通过 `is_customer` 区分：

```text
is_customer = 1：会员交易
is_customer = 0：非会员交易
```

V1 分两类口径。

第一类：全量有效交易。

它用于计算门店群目标品类的全部销售额，也就是覆盖率分母。

| 过滤目的 | 字段 | V1 过滤口径 |
|---|---|---|
| 正常完成订单 | `order_status` | `order_status = 'os.completed'` |
| 剔除退货 | `is_return` | `is_return = 0` |
| 剔除非正销售 | `usual_amt` | `usual_amt > 0` |
| 保证有效数量 | `weight` | `weight > 0` |
| 门店有效 | `store_id` | 不为空，并能关联门店基础表 |
| 商品有效 | `article_id` | 不为空，并能关联商品基础表 |

`refund_type` 在 V1 只做退款枚举质量检查。不能因为该字段非空就直接删除一笔已经满足正常完成、非退货、正金额和正数量条件的交易；如果后续冻结了更准确的退款枚举过滤，再作为 V2 规则变更并重跑。

第二类：已贴标会员有效交易。

它用于计算各消费者类型的贡献分。

| 过滤目的 | 字段 | V1 过滤口径 |
|---|---|---|
| 必须是会员交易 | `is_customer` | `is_customer = 1` |
| 会员有效 | `customer_id` | 非 NULL、非空字符串、不以 `6` 开头，并能关联正式会员画像 |

所以：

```text
主力贡献得分 = 只看已贴标会员有效交易
会员销售覆盖率 = 已贴标会员销售额 / 全量有效销售额
```

已贴标会员还必须满足算法 01 已冻结的有效会员规则：`is_customer = 1`、`customer_id` 非 NULL 且非空字符串、不以 `6` 开头；同一会员同一天有效小票数超过 5 张时，剔除该会员当天全部交易。`member_filter_rule_version` 与 `profile_model_version` 分开记录，不能把会员过滤规则版本误写成画像模型版本。

小票唯一键已确认：

```text
order_id 全公司唯一。
订单数 / 小票数 = COUNT(DISTINCT order_id)
```

取消、冲销、测试交易 V1 口径已确认：

```text
第一期先使用现有 Doris 字段过滤。
暂不要求新增取消、冲销、测试交易字段。
```

## 9. 关联检查怎么理解

关联检查的核心目的是：

```text
避免一条消费记录被重复计算，或者被归到错误画像、错误门店等级、错误品类。
```

### 9.1 会员画像唯一

规则：

```text
同一画像版本 + customer_id 只能有一个 final_profile
```

例子：

| 画像版本 | 会员ID | final_profile |
|---|---|---|
| profile_v1 | M001 | 常规时段型-小家庭-中频-价格非敏感 |
| profile_v1 | M001 | 上班族晚高峰型-小家庭-中频-价格非敏感 |

这是错误数据。

因为同一个会员在同一画像版本里出现了两个画像。

如果拿它去关联小票，M001 的消费可能被算进两个消费者类型，销售额会重复。

### 9.2 门店品类等级唯一

规则：

```text
同一等级版本 + 范围 + 门店 + 品类 只能有一个 final_level
```

例子：

| 等级版本 | 范围 | 门店 | 品类 | final_level |
|---|---|---|---|---|
| level_v1 | 上海 | S001 | 牛肉制品 | A |
| level_v1 | 上海 | S001 | 牛肉制品 | B |

这是错误数据。

因为同一个门店、同一个品类，在同一版本里不能既是 A 又是 B。

如果拿它去关联小票，这家门店的牛肉销售会同时进入 A 级门店群和 B 级门店群。

### 9.3 商品品类映射唯一

规则：

```text
V1 使用当前商品基础表分类。
同一商品基础表分类口径下，一个 article_id 只能命中一个品类。
```

例子：

| 商品编码 | 小类 |
|---|---|
| 21231650 | 牛肉制品 |
| 21231650 | 调理肉制品 |

这是错误数据。

因为同一个商品在当前分类口径下不能同时属于两个小类。

如果拿它去筛选品类，同一笔销售会被算进两个品类。

商品分类变更属于小概率事件，V1 不做历史分类版本回溯。

## 10. 基础指标怎么算

在同一个门店群内，对每个消费者类型计算：

```text
profile_member_cnt = 该消费者类型的去重有效会员数
profile_sales_amt = 该消费者类型的目标品类全日有效会员销售额
profile_ticket_cnt = 该消费者类型的目标品类有效会员小票数，COUNT(DISTINCT order_id)
profile_avg_ticket_amt = profile_sales_amt / profile_ticket_cnt
```

门店群整体分母分两类。

第一类：贡献分分母，只看已贴标会员交易。

```text
group_member_cnt = 门店群内全部已贴标有效会员数
group_sales_amt = 门店群内全部已贴标有效会员目标品类销售额
group_ticket_cnt = 门店群内全部已贴标有效会员目标品类小票数，COUNT(DISTINCT order_id)
group_avg_ticket_amt = group_sales_amt / group_ticket_cnt
```

第二类：覆盖率分母，看会员画像能覆盖多少全量销售。

```text
group_total_sales_amt = 门店群内目标品类全量有效销售额，包含会员和非会员
profiled_member_sales_amt = 门店群内目标品类已贴标会员销售额
profile_sales_coverage_rate = profiled_member_sales_amt / group_total_sales_amt
```

业务含义：

```text
贡献分回答：在已贴标会员里，哪个消费者类型最主力？
覆盖率回答：这批已贴标会员销售能代表全量销售的程度有多高？
```

## 11. 画像贡献占比怎么算

每个消费者类型计算三个占比：

```text
member_share = profile_member_cnt / group_member_cnt
sales_share = profile_sales_amt / group_sales_amt
ticket_share = profile_ticket_cnt / group_ticket_cnt
```

业务含义：

| 指标 | 含义 |
|---|---|
| `member_share` | 这个消费者类型覆盖了多少购买会员 |
| `sales_share` | 这个消费者类型贡献了多少会员销售额 |
| `ticket_share` | 这个消费者类型贡献了多少会员小票 |

正式主力判定只用：

```text
member_share
sales_share
```

`ticket_share` 只用于解释。

## 12. 贡献得分怎么算

贡献得分使用调和平均：

```text
profile_contribution_score =
2 * sales_share * member_share
/ (sales_share + member_share) * 100
```

它解决的问题是：

```text
不能只看销售额。
不能只看会员人数。
要找“人多且买得多”的消费者类型。
```

例子：

| 消费者类型 | 会员占比 | 销售占比 | 解释 |
|---|---:|---:|---|
| A 类型 | 35% | 34% | 人多，销售也高，适合作为主力候选 |
| B 类型 | 5% | 30% | 销售高但人数少，可能是小众高客单 |
| C 类型 | 30% | 8% | 人多但购买弱，不应只因人数多成为主力 |

调和平均会压低 B 和 C 这种单边高的类型。

## 13. 主力消费者类型怎么判定

同一个门店群内，把所有消费者类型按贡献得分排序。

算法只判断两种情况：

```text
K = 1：没有明显高低组
K = 2：低贡献组 + 高贡献组
```

用：

```text
Jenks 自然断点 + BIC
```

来判断是否存在明显高贡献组。

如果选择 K=2：

```text
高贡献组 = 正式主力消费者类型
is_main_profile = 1
result_status = SUCCESS
```

如果选择 K=1：

```text
没有明显主力
result_status = NO_OBVIOUS_MAIN
is_main_profile = 0
```

K=1 时，最高分消费者类型只作为相对主力候选：

```text
is_relative_main_candidate = 1
```

K=1、单一消费者类型或当前结果无法计算时，不生成 Jenks 断点；`jenks_break_value` 写空值，SSE/BIC 结果同时标记为“不适用”或“不可计算”，不伪造分组参数。

它不是正式主力。

只有一种有效消费者类型时：

```text
result_status = SINGLE_PROFILE
is_main_profile = 1
profile_contribution_score = 100
```

这只说明消费结构单一，不代表这个人群的经营价值必然更高。

## 14. 稳定性怎么验证

稳定性只用来解释结果可靠不可靠。

它不修改正式主力判定。

### 14.1 会员级 Bootstrap

Bootstrap 的抽样单位是会员，不是小票。

原因：

```text
如果抽小票，同一个会员的消费会被拆散，会员覆盖占比会失真。
```

每轮做法：

```text
从门店群有效会员中有放回抽样
被抽中的会员带上周期内全部目标品类消费
重新计算贡献得分和主力判定
记录每个消费者类型被判为主力的次数
```

停止规则：

```text
至少 1,000 轮
最多 10,000 轮
每 250 轮检查一次
所有消费者类型 MCSE <= 0.01 时停止
```

### 14.2 留一月验证

正式周期是 3 个月。

分别删除一个月再重算：

```text
删除第 1 月：用第 2 月 + 第 3 月
删除第 2 月：用第 1 月 + 第 3 月
删除第 3 月：用第 1 月 + 第 2 月
```

它回答：

```text
主力人群是不是只因为某一个特殊月份才出现？
```

## 15. 最终结果状态

常见状态：

| 状态 | 含义 |
|---|---|
| `SUCCESS` | 正常生成明显主力人群 |
| `SINGLE_PROFILE` | 只有一种有效消费者类型 |
| `NO_OBVIOUS_MAIN` | 没有明显分离的主力结构 |
| `NO_RATED_STORE` | 没有可用正式等级门店 |
| `CATEGORY_MAPPING_ERROR` | 品类映射缺失或一对多 |
| `PROFILE_LINK_INCOMPLETE` | 应关联会员未 100% 关联正式画像 |
| `NO_MEMBER_CONSUMPTION` | 没有有效会员消费 |
| `DUPLICATE_JOIN_ERROR` | 关联造成明细、销售额或小票膨胀 |
| `TRANSACTION_DATA_ERROR` | 销售额、小票数或交易主键异常 |
| `UPSTREAM_VERSION_ERROR` | 上游正式版本缺失或混用 |

`SINGLE_PROFILE` 和 `NO_OBVIOUS_MAIN` 是有效业务结果，不是数据错误。

结果写入边界：

```text
没有正式等级门店（NO_RATED_STORE）：没有合法门店群，不写两张正式结果表，只记录运行审计。
有合法门店群但没有有效会员消费（NO_MEMBER_CONSUMPTION）：不写两张正式结果表，只记录运行审计；不得伪造空画像行或主力汇总行。
画像关联不完整、版本混用、关联一对多、商品分类异常或交易数据异常：属于阻断，不写受影响范围的正式结果，只记录运行审计和异常原因。
```

如果已经存在有效会员交易，但金额或全量销售分母出现不合理的 0，则标记 `TRANSACTION_DATA_ERROR`；只有确实没有有效会员消费时才使用 `NO_MEMBER_CONSUMPTION`，避免两个状态含义重叠。

## 16. 输出字段主要有哪些

消费者类型贡献明细表主要包含：

| 字段组 | 业务含义 |
|---|---|
| 周期与版本 | 使用哪个贡献周期、画像版本、门店等级版本、范围版本 |
| 范围与品类 | 城市算法区域、品类颗粒度、品类编码、品类名称 |
| 门店群 | 门店群类型、门店等级、门店数、已评级门店覆盖 |
| 消费者类型 | `final_profile` |
| 原始指标 | 会员数、销售额、小票数、客单价 |
| 占比和得分 | 会员占比、销售占比、小票占比、贡献得分、排名 |
| 主力判断 | 是否正式主力、是否相对主力候选 |
| 解释指数 | 人均消费贡献指数、到店活跃指数、客单指数 |
| 稳定性 | Bootstrap 结果、留一月验证结果 |
| 质量状态 | 画像关联率、会员销售覆盖率、结果状态、诊断原因 |

门店群主力人群汇总表主要包含：

```text
周期、范围、品类、门店群
主力消费者类型数量
主力消费者类型列表
相对主力候选列表
主力会员覆盖率
主力销售覆盖率
结果状态
质量指标
计算时间
```

## 17. 开发实际运行流程

算法 03 是月度离线批量计算。开发先锁定算法 01、02 的正式版本和本次贡献周期，再读取贡献周期内的小票明细做聚合，最后发布贡献明细表和门店群主力人群汇总表。

前端和后续算法只读取已发布结果。采购查询城市、品类、门店等级或消费者画像时，只是在结果表里筛选，不触发实时重算，也不改变主力人群判断。

采购前端输入的是城市、品类、门店群或消费者画像等查询条件，不是手动录入候选商品、规格或成本；候选商品由后续算法链路产生。本算法也不把查询条件当成算法输入事实。

开发过程可以理解为：

```text
1. 锁定算法 01 的正式会员画像版本
2. 锁定算法 02 的正式门店品类等级版本
3. 读取贡献周期内的小票商品明细
4. 过滤有效交易和有效会员
5. 按商品基础表当前分类筛选目标品类
6. 按门店等级组建门店群
7. 把会员消费关联到 final_profile
8. 按门店群 + 品类 + final_profile 聚合
9. 计算 member_share、sales_share、ticket_share
10. 用调和平均计算贡献得分
11. 用 Jenks/BIC 判断是否存在明显主力
12. 做 Bootstrap 和留一月稳定性验证
13. 输出贡献明细表和门店群汇总表
```

运行依赖和空结果处理：

```text
算法 01、算法 02、商品分类快照和交易快照先完成版本闸门，再执行聚合。
画像关联、商品分类或版本闸门失败时，受影响范围只写运行审计，不发布正式结果。
无正式等级门店或有门店群但无会员消费时都只写运行审计，不发布空壳正式结果。
Bootstrap 和留一月验证是批量计算阶段完成的质量指标；前端查询只读取已经发布的质量字段，不实时重算。
```

## 18. 业务验收看什么

第一层：数据是否对。

```text
各消费者类型销售额合计 = 门店群已贴标有效会员销售额
各消费者类型小票数合计 = 门店群已贴标有效会员小票数
各消费者类型会员数合计 = 门店群去重有效会员数
SUM(sales_share) = 100%
SUM(member_share) = 100%
```

第二层：公式是否对。

```text
member_share
sales_share
ticket_share
profile_contribution_score
Jenks SSE
BIC
Bootstrap MCSE
time_main_rate
```

第三层：结果是否合理。

```text
主力消费者类型是否同时具备较高会员覆盖和销售贡献
NO_OBVIOUS_MAIN 是否没有被强行指定主力
SINGLE_PROFILE 是否被解释为消费结构单一
捡漏型是否没有被拆成家庭、频次、价格态度后缀
```

第四层：边界场景是否处理。

```text
没有正式等级门店
没有有效会员消费
画像关联不完整
只有一种消费者类型
全部贡献得分相同
同一会员跨门店、跨等级消费
同一张小票包含多个目标品类 SKU
关联维表一对多导致金额膨胀
```

## 19. 现在还需要确认什么

算法 03 的业务主逻辑完整。

当前只保留会影响开发交付验收的评审事项；数据合同已经明确的表名、粒度、主键和小票键不再重复询问：

| 确认项 | 需要谁确认 | 为什么重要 |
|---|---|---|
| 算法 01 正式 `dim_customer_profile` 是否按冻结字段、版本和唯一性稳定产出 | 数据开发 | 影响画像关联成功率和 `PROFILE_LINK_INCOMPLETE` 阻断 |
| 算法 02 正式 `mart_store_category_level` 是否同时提供 `SUCCESS` / `NOT_CALCULABLE` 行并按冻结主键唯一 | 数据开发 | 影响门店群、未评级门店数和覆盖率是否可复算 |
| Bootstrap 是否能按固定种子、会员级抽样和 1,000～10,000 轮规则执行并落审计 | 数据开发 | 影响稳定性指标复现和运行成本 |

## 20. 不要做什么

```text
不要把非会员销售放进主力人群贡献得分分母
不要先算单门店占比再平均成门店群
不要把各门店等级结果相加生成 ALL_RATED
不要平均下一级品类结果生成上一级结果
不要用固定销售占比阈值或人工权重判定主力
不要因为样本较小直接删除真实消费者类型
不要用客单价、小票占比或门店覆盖率改变正式主力标签
不要在算法 03 中重新生成会员画像或门店等级
不要在上游异常时自动扩大区域或合并门店等级
不要只输出主力名称而不保留会员数、销售额、占比、参数和版本血缘
```

## 21. 一句话总结

门店群消费者画像贡献算法的本质是：

```text
先用算法 02 找到某个品类下的一组门店，
再用算法 01 找到这些门店消费会员的画像，
然后判断哪些消费者类型既覆盖更多购买会员，又贡献更多销售额，
为后续 SKU 表现和新品机会分析确定目标人群。
```
