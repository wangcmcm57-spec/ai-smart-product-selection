## 一、这张表在 AI 选品里做什么

会员画像算法的作用，是把会员过去一段时间的小票消费行为，转换成一个稳定的消费者画像标签。

后续 AI 选品不会直接看“所有人买了什么”，而是会先看：

```text
哪些消费者画像是主力人群
这些人在哪些品类、门店群里贡献高
这些人偏好什么商品方向
```

所以会员画像是后面“门店群消费者画像贡献”“目标画像 SKU 表现”“新品机会推荐”的基础。

## 二、当前业务规则摘要

会员画像算法当前使用以下规则：

| 项目 | 当前口径 |
|---|---|
| 画像粒度 | `algorithm_batch_version + customer_id`，每个统一算法批次下每个会员只有一条正式画像 |
| V1 数据范围 | 当前输入数据为华东全部业务数据；全国扩展需先完成新增城市的算法区域归属和参数验证，再从下一统一算法批次纳入 |
| 区域归属 | 跨区域会员使用华东范围内全部有效交易计算个人指标；再确定唯一主归属区域，并使用该区域模型参数贴标 |
| 渠道范围 | POS、扫码购、自提、配送等所有正常渠道的有效交易均参与画像；时间行为使用订单发生时间，不等同于到店时间 |
| 捡漏型 | 捡漏型是终止标签，最终画像只输出 `捡漏型` |
| 时间行为冲突 | 同时命中捡漏和晚高峰时，先比较相对强度，再按天数、月数、捡漏优先兜底 |
| 家庭与频次 | 家庭规模、消费频次、价格态度只对非捡漏型会员继续计算 |

## 三、最终会输出什么画像

当前规则下，画像分成两条路径。

### 路径一：命中捡漏型

只要会员最终时间行为被判定为捡漏型，就停止继续拆分后续维度。

```text
time_behavior = 捡漏型
final_profile = 捡漏型
family_level = NOT_APPLICABLE
frequency_level = NOT_APPLICABLE
price_attitude = NOT_APPLICABLE
profile_terminal_flag = 1
```

人话解释：

```text
这个会员最强的消费身份就是捡漏型。
不再判断他是大家庭还是小家庭。
不再判断他是高频、中频还是低频。
不再判断他是否价格敏感。
```

最终画像示例：

```text
捡漏型
```

### 路径二：非捡漏型

如果会员不是捡漏型，才继续计算家庭规模、消费频次和价格态度。

```text
final_profile =
time_behavior-family_level-frequency_level-price_attitude
```

最终画像示例：

```text
上班族晚高峰型-小家庭-中频-价格非敏感
常规时段型-大家庭-高频-价格敏感
```

## 四、算法整体运行流程

算法 01 是月度离线批量计算。开发先读取最近 6 个完整自然月的小票、商品和门店数据，并读取本统一算法批次已经锁定的城市、算法区域和参数回退范围快照，产出正式画像结果、解释记录、区域参数和画像汇总；月中新会员只使用当前平台成功批次的正式参数做增量贴标，不重新训练整套模型。

后续算法和前端查询只读取平台已标记成功的正式画像结果。采购或产品筛选区域、品类或消费者画像时，不触发算法 01 重新计算，也不能在查询时临时改会员标签。

```text
最近6个完整自然月小票数据
-> 过滤无效会员和异常交易
-> 读取本批次锁定的城市、算法区域和参数回退范围
-> 汇总会员在华东范围内全部有效交易
-> 判断会员主归属区域
-> 分别按算法区域和参数回退范围计算模型参数
-> 先判断时间行为
-> 如果是捡漏型，直接输出捡漏型
-> 如果不是捡漏型，继续计算家庭规模、消费频次、价格态度
-> 输出会员画像结果表、解释表、参数表和汇总表
```

## 五、数据范围

正式模型使用最近 6 个数据完整的自然月。

V1 当前输入本身就是华东全部业务数据，不是先读取全国数据再筛选华东。会员个人行为指标使用当前华东范围内的全部有效交易。

以后扩展南京或全国其他城市时，必须先完成：

```text
新增城市 -> 配置算法区域归属 -> 训练或验证区域参数 -> 从下一统一算法批次开始纳入
```

新城市数据已经进入、但算法区域和参数尚未准备完成时，不得临时套用上海或其他区域参数，也不得混入已发布的历史统一算法批次。

### 区域映射和品类编码怎么固定

一个统一算法批次使用一套固定的城市算法区域映射。默认采用该批次计算结束日有效的映射快照，六个月窗口内的历史交易统一按这套快照映射。这样同一个批次不会因为中途调整城市归属而把同一城市拆到两个算法区域。

这份快照还必须保存每个算法区域所属的“参数回退范围”。程序通过以下两个字段识别，不能靠开发人员记忆，也不能把当前数据库里的全部数据自动当成华东整体：

```text
parameter_fallback_scope_code：参数回退范围编码
parameter_fallback_scope_name：参数回退范围名称
```

华东一期的明确映射是：

```text
上海 -> SH -> EAST_CHINA_ALL / 华东整体
杭州、宁波、绍兴 -> HZ_NB_SX -> EAST_CHINA_ALL / 华东整体
苏州、常州、无锡 -> SZ_CZ_WX -> EAST_CHINA_ALL / 华东整体
```

以后全国数据进入时，新城市必须先配置“城市 → 算法区域 → 参数回退范围”，再从新统一算法批次纳入。华北、华南等范围的具体城市归属由届时业务确认，当前不提前写死。

商品基础表已有大类、中类、小类编码，V1 不需要再建一张完整的品类映射表。开发先一次性核对“蔬菜、肉禽蛋、猪肉、水产”是否都是独立且稳定的商品大类，通过后直接使用 `category_level1_code` 判断：

```text
蔬菜 = 蔬菜对应的大类编码
家庭食材 = 蔬菜、肉禽蛋、猪肉、水产对应的大类编码集合
```

`category_level2_code` 保留用于数据追溯；`category_level3_code` 用于 `x5` 家庭食材小分类去重和价格比较的商品小分类场景。程序运行时不按中文名称模糊匹配；首次核对确定的大类编码值保存在现有的区域模型参数表中，不新建映射表，并随统一算法批次保留，保证同批次重跑可复现。只有发现跨大类例外商品、品类编码调整或编码被重用时，才增加新的生效记录，并从下一统一算法批次生效。

例如系统在 2026 年 7 月运行，但 2026 年 6 月 Doris 只有 6 月 1 日至 6 月 7 日的数据，那么 6 月不是完整月，不进入正式计算。

示例周期：

```text
2025-12-01 <= business_date < 2026-06-01
```

### 统一批次月份、生效日期和重跑怎么理解

统一算法批次版本跟“这批画像用到的最后一个完整自然月”走，不跟作业实际在哪一天运行走，也不维护额外的 `1、2、3` 批次序号。

```text
计算窗口：2026-03-01 ~ 2026-08-31
algorithm_batch_version（统一算法批次版本）：BATCH_202608
calculation_start_date：2026-03-01
calculation_end_date：2026-08-31
effective_start_date：2026-09-01
```

`effective_start_date` 表示这个统一算法批次归属的生效起点，固定为计算窗口最后一个完整月的次月 1 日。它不等于作业运行日。

但“到了次月 1 日”不代表新批次已经可以使用。新批次必须先在运行级暂存区完成自动质量验收，再将四张正式表按同一 `algorithm_batch_version（统一算法批次版本）`原子写入，最后由平台把算法 01 该批任务标记为成功。不需要业务人工点击审批，也不在参数表每行保存独立发布标记或实际发布时间。如果 `BATCH_202608` 到 9 月 5 日才运行成功，9 月 1 日至 4 日仍继续读取上一个平台成功批次。

四张正式输出表必须作为同一批结果一起原子生效，不能只有画像结果表、却没有同批次的解释表、参数表和汇总表。是否可以触发下游由平台任务成功状态控制，不由区域模型参数表里的行级字段控制。

当前正式批次的判断原则是：

```text
全链路调度显式传入平台已标记成功的 algorithm_batch_version
-> 四张正式表全部按该批次精确读取
-> 下游不按参数表发布标记、最后运行时间或自行取最大批次选版
```

例如平台已标记 `BATCH_202608` 和 `BATCH_202609` 两个月度批次成功，即使 10 月又重跑了 `BATCH_202608`，当前全链路仍使用 `BATCH_202609`，不能因为 8 月批次刚刚运行过就把它重新变成当前批次。

同一数据窗口重跑时，不生成任何额外后缀，也不改变批次版本。开发先把四张表的新结果完整算成功并通过主键、行数和关联检查，再一次性替换该 `algorithm_batch_version（统一算法批次版本）` 在四张正式表中的原批次数据。不能先删除旧批次再开始计算，避免计算失败后正式结果缺失。

```text
同窗口重跑：algorithm_batch_version 不变
effective_start_date：不变
effective_end_date：不变
updated_at：更新为本次实际写入时间
四张表：必须同批替换，不能只替换其中一张
下游：已经使用该统一算法批次的下游结果按现有调度机制自动重跑
```

如果重跑的是历史 8 月版，只需处理当时锁定 8 月版的历史下游结果；已经改用 9 月版的当前结果不因此回退。

月中新会员采用补充贴标，不改变当月已经完成的正式下游批次：

```text
当前平台成功的正式批次中不存在该 customer_id
AND 会员产生至少 1 张有效小票
=> 使用截至补充日已有的华东有效交易
=> 使用同一正式批次的区域参数贴标
=> 写入独立的“月中新会员补充画像”结果区，不并入月度正式四张表
=> is_incremental_new_member = 1
=> 各适用维度置信度统一为低
```

同一正式批次内，补充画像第一次生成后不因每天新增小票频繁换标；下一月的正式全量批次再统一重算。月中新会员不计入当月正式画像汇总和正式批次验收，也不改变已经完成的正式下游批次；下游明确需要时才读取补充画像。

月中新会员的价格态度只使用当前正式批次已经冻结的促销比较基准和参数，不能因为新增一个会员就在月中重新计算整套价格基准。

## 六、主归属区域

每个会员只保留一个主归属区域。

这里的主归属区域不是直接取城市，而是取城市算法区域映射后的算法区域。

华东一期默认链路：

```text
小票 store_id
-> 门店基础表
-> 城市
-> 城市算法区域映射表
-> 算法区域
```

例如：

```text
上海 -> 上海
杭州、宁波、绍兴 -> 杭州宁波绍兴
苏州、常州、无锡 -> 苏州常州无锡
```

跨区域消费会员按以下顺序判断主归属区域：

```text
1. 最近6个完整月有效消费天数最多的区域；多1天也算更多
2. 消费天数相同，选择有效小票数最多的区域；多1张也算更多
3. 小票数仍相同，选择有效销售额最高的区域；区域销售额按实付金额合计后保留2位小数比较
4. 销售额仍相同，选择最后一笔有效交易时间更晚的区域
5. 最近交易时间仍完全相同，按算法区域编码升序选择，保证每次重跑结果一致
```

这是一套逐层判断规则，不是综合打分。上一层已经分出高低时，不再比较下一层。例如上海消费 12 天、杭州宁波绍兴消费 11 天，即使杭州宁波绍兴的小票和销售额更多，主归属区域仍是上海。

主归属区域判断完成后：

```text
个人画像指标 = 会员在华东范围内全部有效交易计算
模型训练分组 = 按会员主归属区域分组
会员贴标参数 = 使用主归属区域参数
正式画像结果 = 每个统一算法批次、每个会员只有一条
```

同一天在两个区域消费时，判断主区域时两个区域各记 1 个区域消费日；计算会员全部有效消费天数时，该自然日只记 1 天。

区域样本不足或参数不可用时，统一按以下顺序回退：

```text
主归属算法区域参数
-> 华东整体参数
-> 该维度默认结果，并标记低置信度
```

V1 不建设区域层级树。上海、杭州宁波绍兴、苏州常州无锡三个算法区域互为平级；“华东整体”是预先计算并发布的统一回退参数范围，不是三个区域中的某个父级管理区域。开发通过本批次快照中的 `parameter_fallback_scope_code = EAST_CHINA_ALL` 找到这一范围，合并该范围内三个算法区域的有效样本训练回退参数。不得使用门店表中的管理区域、大区字段或当前全表数据代替这份显式映射。

程序实际执行顺序是：

```text
先读取会员主归属算法区域参数
-> 参数不可用时，从批次快照查询该算法区域的 parameter_fallback_scope_code
-> 读取同一正式批次中 EAST_CHINA_ALL 对应的参数
-> 华东整体参数仍不可用时，才输出默认低置信度结果
```

默认结果为：时间行为 `常规时段型`、家庭规模 `小家庭`、价格态度 `价格非敏感`；消费频次仍按会员真实消费天数计算。

页面按区域筛选时，只汇总已经生成好的固定标签，不在查询时重新训练或重新贴标。区域经营汇总使用会员在所选区域实际发生的交易；同一跨区域会员可以出现在多个区域视图，但华东整体会员数必须按 `customer_id` 去重。

这里的“多个区域视图”不是为同一会员保存多条区域画像，而是同一条会员画像在不同交易发生区域的经营汇总中都可以被统计到。例如会员只有一条画像，但他在上海和杭州都发生过交易，上海视图统计上海交易，杭州视图统计杭州交易。

## 七、前置过滤

### 有效会员

```text
customer_id IS NOT NULL
AND is_customer = 1
AND customer_id NOT LIKE '6%'
```

`customer_id` 以 6 开头的记录属于非真实会员。`is_customer = 1` 用来确保只给会员交易贴画像。

### 有效交易

只保留：

```text
交易日期位于模型周期内
order_id 不为空
order_status = 'os.completed'
is_return = 0
usual_amt > 0
weight > 0
article_id 不为空
```

剔除：

```text
退货
取消
冲销
测试交易（待字段或枚举确认后过滤）
非正向销售记录
```

### 异常会员日

按 `customer_id + business_date` 统计去重小票数：

```text
单日小票数 <= 5：保留
单日小票数 > 5：剔除该会员当日全部交易
```

会员其他日期的正常交易继续参与计算。

上述有效会员、有效交易和异常会员日条件由算法 01～04 共用同一份公共实现。系统不再为这套过滤条件建立独立注册表、版本字段或实现摘要；过滤条件变化时统一更新算法卡、公共实现和验收样例，并从下一个 `algorithm_batch_version（统一算法批次版本）`生效。

POS、扫码购、自提、配送等正常渠道均使用同一套有效交易过滤，不因线上或线下身份被排除。晚高峰和捡漏窗口读取的是订单发生时间；开发验收必须同时检查各时间画像的线上、线下订单占比，防止夜间线上订单异常放大某类画像。

V1 的工作日按自然星期一至星期五判断，不额外接入法定节假日和调休日历；价格比较使用的自然周统一为星期一至星期日。

`refund_type` 的具体枚举先按真实数据验收，不因为字段存在就额外删除 `order_status = 'os.completed' AND is_return = 0` 的正常交易。测试交易也必须先落实到可识别的业务字段或枚举；在规则没有落到字段前，只能作为数据质量检查项，不能假设已经被过滤。

历史交易不能因为门店当前闭店而删除。门店表只用于补充城市和区域；当前营业状态不作为历史交易过滤条件。

## 八、时间行为怎么判断

时间行为有三类：

```text
捡漏型
上班族晚高峰型
常规时段型
```

### 时间窗口

| 日期类型 | 时间 | 行为窗口 |
|---|---|---|
| 周一至周五 | 18:00 以前 | 常规时段 |
| 周一至周五 | 18:00 至 19:30:00，含 19:30:00 | 上班族晚高峰窗口 |
| 周一至周五 | 19:30:00 之后 | 捡漏窗口 |
| 周六、周日 | 19:30:00 及以前 | 常规时段 |
| 周六、周日 | 19:30:00 之后 | 捡漏窗口 |

上班族晚高峰只计算周一至周五。

捡漏行为不区分工作日和周末。

### 晚高峰指标

```text
晚高峰消费天数占比 =
工作日 18:00-19:30:00 消费天数 / 全部有效消费天数

晚高峰小票占比 =
工作日 18:00-19:30:00 小票数 / 全部有效小票数

晚高峰销售额占比 =
工作日 18:00-19:30:00 销售额 / 全部有效销售额
```

### 捡漏指标

```text
19:30:00 后消费天数占比 =
19:30:00 后消费天数 / 全部有效消费天数

19:30:00 后小票占比 =
19:30:00 后小票数 / 全部有效小票数

19:30:00 后销售额占比 =
19:30:00 后销售额 / 全部有效销售额
```

在时段折扣生鲜业态中，19:30 后消费直接视为捡漏行为，不再额外检查单品折扣字段。

## 九、时间行为冲突怎么处理

先分别计算：

```text
commute_score：上班族晚高峰得分
bargain_score：捡漏得分
```

再和各自自然断点阈值比较。

```text
只命中晚高峰 => 上班族晚高峰型
只命中捡漏 => 捡漏型
两类都未命中 => 常规时段型
```

如果两类同时命中：

```text
commute_relative_strength = commute_score / commute_jenks_threshold
bargain_relative_strength = bargain_score / bargain_jenks_threshold
```

只有断点大于 0 且有效时才计算相对强度；断点无效时，该行为不算命中，按回退规则处理。若自然断点出现多个同样好的切分，统一选择较高的断点，避免不同程序得出不同标签。

处理规则：

```text
1. 相对强度高者为最终标签
2. 两者相差不超过 0.05 时，比较目标时段消费天数
3. 天数仍相同时，比较覆盖自然月数
4. 仍相同时，捡漏型优先
```

## 十、家庭规模怎么判断

家庭规模只适用于非捡漏型会员。

```text
最终时间行为 = 上班族晚高峰型 / 常规时段型
才继续计算家庭规模
```

捡漏型会员不参与家庭规模训练、预测和标签输出。

### 第一层：直接规则

稳定行为证据：

```text
19:00 前蔬菜消费天数 >= 3
19:00 前蔬菜消费覆盖自然月数 >= 2
```

指标：

```text
商品行实际重量kg = 小票计价数量 weight * 商品单位重量 unit_weight_kg
19:00前蔬菜总重量kg = SUM(19:00前蔬菜商品行实际重量kg)
日均蔬菜重量kg = 19:00前蔬菜总重量kg / 19:00前蔬菜消费天数
日均蔬菜 SKU 数 = 每个蔬菜消费日去重 SKU 数之和 / 蔬菜消费天数
```

`unit_weight_kg` 来自商品基础表，必须已经统一为“单个销售单位对应多少公斤”。例如 250g/袋商品的 `unit_weight_kg = 0.25`，买 2 袋时实际重量为 `2 * 0.25 = 0.5kg`。不能把 1 袋、1 盒、1 份直接当成 1kg。

开发还要同时记录参与计算的商品行数、成功换算行数和无法换算行数：

```text
重量换算完整率 = 成功换算重量的商品行数 / 应参与重量计算的商品行数
无法换算行数 = unit_weight_kg 缺失或不可靠的应计算商品行数
```

只有应参与重量计算的商品行全部成功换算，重量换算状态才是“完整”。

大家庭规则：

```text
日均蔬菜重量 >= 1.5kg
OR 日均蔬菜 SKU 数 >= 4
OR (日均蔬菜重量 >= 1.2kg AND 日均蔬菜 SKU 数 >= 3)
=> 大家庭，高置信度
```

满足稳定证据但未命中大家庭条件：

```text
并且相关蔬菜商品重量均可可靠换算
=> 小家庭，高置信度
```

重量缺失不会放宽大家庭门槛：

```text
已知重量已经达到 1.5kg
=> 大家庭，高置信度

日均蔬菜去重 SKU 数已经达到 4
=> 大家庭，高置信度

已知重量已经达到 1.2kg，并且日均蔬菜去重 SKU 数已经达到 3
=> 大家庭，高置信度

已知重量未达到门槛，但存在无法换算重量的蔬菜商品
=> 不能直接判小家庭、高置信度，进入第二层购物篮补充模型
```

### 第二层：购物篮补充模型

不满足第一层稳定蔬菜证据时，仍然需要输出大或小家庭标签。

此时使用主归属区域的逻辑回归模型补充判断。

输入指标限定在 19:00 前：

```text
x1 = 平均 SKU 数 / 票
x2 = 平均购买重量 / 票
x3 = 家庭食材 SKU 数 / 票
x4 = 家庭食材重量 / 票
x5 = 家庭食材品类数 / 票
```

家庭食材包括：

```text
蔬菜、肉禽蛋、猪肉、水产
```

上述四类已核对为稳定大类时，直接按 `category_level1_code` 识别家庭食材，不需要另建完整映射表。`x5` 再对已识别的家庭食材按 `category_level3_code` 去重；不按商品名称模糊匹配。

消费频次、客单价和销售额不进入补充模型。

第二层中的购买重量同样必须统一换算为 kg。如果会员存在参与模型的家庭食材商品无法换算重量，导致 `x2` 或 `x4` 不完整，则不得把缺失重量当作 0 代入模型；统一输出 `小家庭、低置信度`，并记录“单位重量信息不足”。这是证据不足时的保守兜底，不代表放宽或修改大家庭规则。

## 十一、消费频次怎么判断

消费频次只适用于非捡漏型会员。

可观察月份：

```text
observed_months =
从会员在当期的首次有效消费月
到模型周期结束月的自然月数，含首尾月
```

行为频次：

```text
monthly_shop_days_observed = 有效消费天数 / observed_months
```

最终频次标签：

```text
monthly_shop_days_observed >= 8 => 高频
4 <= monthly_shop_days_observed < 8 => 中频
monthly_shop_days_observed < 4 => 低频
```

区域百分位和三等分只作为辅助字段，不覆盖最终频次标签。

## 十二、价格态度怎么判断

价格态度只适用于非捡漏型会员。

```text
最终时间行为 = 上班族晚高峰型 / 常规时段型
才继续计算价格态度
```

只使用 19:00 前的常规促销行为，不使用 19:30 后时段折扣。

促销标记：

```text
discount_amt > 0 => 该商品行视为常规促销商品
```

`discount_amt` 只作促销标记，不直接求和。

促销商品销售额：

```text
促销商品销售额 =
SUM(CASE WHEN discount_amt > 0 THEN usual_amt ELSE 0 END)
```

促销商品数量按场景内去重 SKU 统计，不按商品行数统计。比较基准先排除捡漏型会员，再排除正在计算的目标会员；如果排除后不满足样本门槛，就继续按门店周、算法区域周、算法区域月、算法区域六个月回退。

价格敏感得分使用同场景促销基准、促销 SKU 偏好指数、促销销售额偏好指数，再通过区域熵权合成。

“同场景”按交易实际发生的门店和区域确定：每笔会员交易先在交易发生门店、自然周和商品小分类内找基准，回退时仍沿交易发生的算法区域逐级回退；不能把上海交易拿去和会员主算法区域之外的门店基准比较。会员最终使用哪个模型参数，仍由唯一主算法区域决定。

促销 SKU 数一律按场景内去重的 `article_id` 计算，不按商品行数计算。基准先排除捡漏型会员，再排除目标会员，然后重新检查去重会员数和去重小票数是否达到门槛。

最低证据：

```text
19:00 前促销 SKU 数 >= 3
促销购买覆盖自然月数 >= 2
促销商品覆盖小分类数 >= 2
单一促销 SKU 销售额 / 全部促销商品销售额 <= 0.50
```

价格得分阈值必须大于 0 才能计算“距离阈值”的置信度；没有有效阈值时，保守输出价格非敏感、低置信度。

最终标签：

```text
四项最低证据全部通过
AND price_sensitive_score >= price_jenks_threshold
=> 价格敏感

其他
=> 价格非敏感
```

低置信度会员统一输出价格非敏感。四项证据均满足但得分接近阈值时为中置信度；单一促销 SKU 过度集中时，价格标签保守输出价格非敏感、中置信度；没有足够 SKU、月份、品类或比较基准时为低置信度。

## 十三、输出表

会员画像算法正式交付时，不是只给一张表。它会有四张正式输出表，但每张表的用途不同。

```text
结果表 = 后续 AI 选品真正读取的会员画像
解释表 = 业务和开发验收时看“为什么这么判”
参数表 = 保存本次模型用到的权重、阈值和模型参数，保证可以复现
汇总表 = 给业务看区域和画像分布是否合理
```

| 表 | 给谁用 | 解决什么问题 |
|---|---|---|
| 会员画像结果表 | 后续算法和 AI 选品服务 | 这个会员最终是什么画像 |
| 会员画像解释表 | 你、业务、数据开发 | 为什么这个会员是这个画像，证据是什么 |
| 区域模型参数表 | 数据开发、后续复盘 | 当时用的熵权、自然断点、逻辑回归参数是多少 |
| 画像汇总表 | 业务评审 | 上海/区域里各类画像有多少人、贡献多少销售 |

区域汇总中的“月均消费天数”表示这些会员在华东全部有效交易上的个人月均消费天数的平均值，不表示会员只在该区域的消费频次。区域销售额、小票数仍按交易实际发生区域统计；如果要看会员在某个区域本地的消费天数，需要另设区域经营指标，不能和画像频次混用。

### 结果表怎么用

结果表是一张“会员最终标签表”。

一行代表：

```text
一个统一算法批次 + 一个会员
```

后续“门店群消费者画像贡献”“目标画像 SKU 表现”“新品机会推荐”主要读取这张表。

核心字段：

```text
algorithm_batch_version
customer_id
primary_region
primary_region_code
time_behavior
family_level
frequency_level
price_attitude
final_profile
profile_terminal_flag
time_confidence
family_confidence
price_confidence
is_incremental_new_member
```

捡漏型字段口径：

```text
family_level = NOT_APPLICABLE
frequency_level = NOT_APPLICABLE
price_attitude = NOT_APPLICABLE
family_confidence = NOT_APPLICABLE
price_confidence = NOT_APPLICABLE
final_profile = 捡漏型
```

非捡漏型字段口径：

```text
家庭规模、消费频次、价格态度正常输出
final_profile = time_behavior-family_level-frequency_level-price_attitude
```

### 解释表怎么用

解释表是“验收和排查表”。

比如业务问：

```text
为什么这个会员是捡漏型？
为什么这个会员是大家庭？
为什么这个会员是价格敏感？
```

解释表里要能看到：

```text
晚高峰消费天数
捡漏消费天数
蔬菜购买天数
日均蔬菜重量
单位重量换算状态
成功换算重量的商品行数
无法换算重量的蔬菜商品行数
实际使用的参数区域和回退原因
促销 SKU 数
价格敏感得分
算法阈值
是否通过
失败原因
```

没有解释表，就只能看到最终标签，看不到算法证据，后续很难验收。

### 参数表怎么用

参数表保存“这次模型到底用了什么规则参数”。

例如：

```text
上海区域的晚高峰指标权重是多少
上海区域的捡漏自然断点是多少
家庭规模逻辑回归 beta 系数是多少
价格敏感阈值是多少
哪些区域使用了华东整体参数或默认低置信度结果回退
华东整体参数由哪些算法区域样本合并生成
```

这张表的核心作用是复现。如果下个月会员标签变了，可以回头看是会员行为变了，还是模型参数变了。

### 汇总表怎么用

汇总表是业务评审用的分布表。

它回答的是：

```text
上海有多少捡漏型会员
常规时段型-小家庭-高频-价格非敏感有多少人
这些画像贡献了多少销售额
各画像的客单价和消费频次是否符合业务直觉
高、中、低置信度分布是否合理
```

所以开发最终交付的不是“很多乱七八糟的过程表”，而是：

```text
1. 会员画像结果表
2. 会员画像解释表
3. 区域模型参数表
4. 画像汇总表
```

开发过程中可以有临时表，但正式对外验收就看这四张表。

## 十四、计算样例

以下样例用于说明算法判定过程，帮助开发实现和业务验收，不代表生产模型真实参数。

### 样例 A：捡漏型

输入概要：

```text
主归属区域：上海
可观察月份：6
有效消费天数：60
19:30 后消费：12 天，覆盖 4 个月
晚高峰消费：2 天
```

计算：

```text
捡漏证据通过
晚高峰天数不足
最终时间行为 = 捡漏型
命中终止规则
家庭规模、消费频次和价格态度不再计算
```

结果：

```text
捡漏型
```

### 样例 B：非捡漏型

输入概要：

```text
主归属区域：杭州宁波绍兴
可观察月份：6
有效消费天数：30
工作日晚高峰：8 天，覆盖 4 个月
19:30 后消费：1 天
19:00 前蔬菜：6 天，日均 0.85kg，日均 1.7 个 SKU
促销行为证据齐全，但促销偏好接近同场普通会员
```

计算：

```text
晚高峰证据通过 => 上班族晚高峰型
捡漏证据不足
稳定蔬菜证据齐全但未命中大家庭阈值 => 小家庭
monthly_shop_days_observed = 30 / 6 = 5 => 中频
价格敏感得分未命中阈值 => 价格非敏感
```

结果：

```text
上班族晚高峰型-小家庭-中频-价格非敏感
```

## 十五、验收重点

开发和业务验收时，重点检查：

```text
全部有效会员必须输出一条画像
最终画像不得为空
捡漏型的家庭、频次和价格态度必须为 NOT_APPLICABLE
非捡漏型的家庭、频次和价格态度不得为空或为 NOT_APPLICABLE
同一算法批次、同一会员只能有一条最终画像
被过滤的非真实会员、退货和异常会员日不得进入计算
```

业务合理性检查：

```text
捡漏型的次月 19:30 后消费延续率应高于常规会员
晚高峰型的次月工作日晚高峰延续率应高于常规会员
大家庭的整篮 SKU 数与购买重量应高于小家庭
高频会员月均消费天数应高于中频和低频
非捡漏型价格敏感会员的促销偏好指数应高于价格非敏感会员
```

还必须检查以下边界：

```text
跨区域会员：个人指标使用华东全部有效交易，但每个统一算法批次只生成一条画像
主区域并列：消费天数、小票数、销售额、最近交易时间都相同时，固定编码兜底结果可重复
重量换算：称重、按斤、按袋、按盒商品的公斤换算结果正确；无法换算商品不会被当成 0kg
家庭标签：重量不完整时不会错误产生“小家庭、高置信度”或“大家庭”
渠道分布：晚高峰型和捡漏型的线上、线下订单占比没有异常偏移
同批次重跑：四张表全部成功后一起替换，失败时原批次仍可读取
```

单位重量正式验收项：

```text
应参与重量计算的商品行数
成功换算商品行数
无法换算商品行数
重量换算完整率
受无法换算影响的会员数
因此进入家庭规模降级的会员数
```

### 次月延续率怎么理解

次月延续率是画像稳定性的验收和监控指标，不是会员画像结果表中的一个会员标签。

例如：

```text
画像计算窗口：2026-03-01 ~ 2026-08-31
统一算法批次版本：BATCH_202608
次月验证期：2026-09-01 ~ 2026-09-30
```

验证时固定使用 `BATCH_202608` 已经产生的时间行为标签，只观察这些会员在 9 月是否继续出现对应行为；不用 9 月数据重新训练模型，也不要求会员在单个 9 月内重新满足“至少 3 天且跨 2 个月”的正式贴标条件。

晚高峰型：

```text
分母 = 原批次为上班族晚高峰型，且次月仍有有效消费的会员数
分子 = 上述会员中，次月至少有 1 个工作日在 18:00~19:30（含 19:30）消费的会员数
次月晚高峰延续率 = 分子 / 分母
```

捡漏型：

```text
分母 = 原批次为捡漏型，且次月仍有有效消费的会员数
分子 = 上述会员中，次月至少有 1 天在 19:30 之后消费的会员数
次月捡漏延续率 = 分子 / 分母
```

为了区分“会员次月没来”和“会员来了，但行为没有延续”，验收时同时看三个结果：

| 指标 | 怎么算 | 用来看什么 |
|---|---|---|
| 次月活跃率 | 次月仍有有效消费会员数 / 原标签会员总数 | 会员次月是否还来消费 |
| 活跃会员行为延续率 | 次月继续出现目标行为会员数 / 次月活跃会员数 | 画像行为是否稳定；默认所说的“次月延续率” |
| 整体行为延续率 | 次月继续出现目标行为会员数 / 原标签会员总数 | 同时反映会员流失和行为变化 |

晚高峰型要与常规时段型会员的“次月晚高峰行为出现率”比较；捡漏型要与常规时段型会员的“次月 19:30 后行为出现率”比较。目标画像的延续率高于常规会员对照率，才说明该标签有稳定的行为区分力。

由于算法 01 是按会员主归属区域训练和贴标，延续率也先在同一主归属区域内将目标画像与常规会员比较，再汇总华东整体结果。这样可以避免把不同区域的消费时段差异误判为画像稳定性差异。

历史验证中的 `6.88~9.61` 和 `2.67~2.92` 个百分点是当时规则对比的结果，只作参考，不作为每个月必须达到的固定门槛。

当月新版画像进入正式表前，系统使用已经完整的历史月做留出回测；平台标记该批任务成功后，等真实次月结束再做持续监控。因此，真实次月延续率和业务人工抽样都不是当月算法运行或触发下游前的审批门槛。

## 十六、当前确认结果和开发验收

以下业务方案已经确认：

```text
1. 每个统一算法批次锁定计算结束日有效的区域映射快照。
2. 蔬菜和家庭食材优先直接按商品基础表大类编码识别，不强制新建完整品类映射表；只有跨大类例外或编码调整时才新增带生效日期的例外配置，并从下一统一算法批次生效。
3. 家庭规模继续采用重量缺失时的严格保守方案。
4. 月中新会员进入独立补充画像，不混入月度正式四张表和正式汇总。
5. Jenks 同样优的切分选择较高阈值。
6. 常规时段型和价格态度的置信度按完整真值规则输出。
7. 区域汇总的月均消费天数使用会员全华东频次均值。
8. 同一算法批次每会员只保留一条正式画像，区域视图不生成多条画像。
```

开发交付时仍必须验收：商品单位重量是否可靠换算为 kg、品类编码覆盖率、跨区域会员是否只生成一条画像、四张表是否能够同批发布和同批替换、受影响的下游批次是否按现有调度自动重跑，以及同样输入重跑能否得到一致结果。

## 十七、不要做什么

```text
不要只用主归属区域交易计算会员个人画像指标
不要为跨区域会员在同一算法批次生成多条画像
不要把件、袋、盒、份直接当成 kg，也不要把无法换算重量填成 0
不要因重量缺失放宽大家庭高置信度阈值
不要先删除正式批次再开始同批次重跑
不要让历史批次重跑后取代更新月份的当前正式批次
不要把次月延续率或发布后的业务人工抽样当成平台任务成功前必须等待的审批结果
```

一句话总结：算法 01 用华东范围内会员的全部有效交易生成唯一画像，用主归属区域选择参数，用严格的重量和置信度规则保护家庭标签，并通过统一批次发布、整批重跑和次月延续率保证结果可用、可解释、可复核。
