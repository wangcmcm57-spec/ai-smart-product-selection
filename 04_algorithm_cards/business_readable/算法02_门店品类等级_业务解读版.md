## 1. 先用一句话理解

门店品类等级算法要做的事是：

```text
在同一个城市算法区域、同一个品类里，
比较不同门店经营这个品类的能力，
最后给每个门店品类一个等级。
```

它不是门店整体评级，也不是门店订货系统。

它服务 AI 新品推荐，回答的是：

```text
这个品类如果要开发新品，哪些门店更适合先试？
哪些门店有品类经营基础？
哪些门店虽然卖得多，但毛利、订购、促销依赖或损耗有风险？
```

## 2. 最终会输出什么

正式结果表：

```text
mart_store_category_level
```

一行结果表示：

```text
一个数据周期
+ 一个城市算法区域
+ 一个门店
+ 一个品类颗粒度
+ 一个品类
+ 一个统一算法批次版本
```

示例：

```text
2026-04-01~2026-06-30
上海
上海康桥宝邸
小分类
牛肉制品
门店品类等级 = A
```

同一家门店可以在不同品类上得到不同等级：

| 门店 | 品类 | 等级 |
|---|---|---|
| 上海康桥宝邸 | 牛肉制品 | A |
| 上海康桥宝邸 | 叶菜类 | B |
| 上海康桥宝邸 | 水产类 | C |

输出结果主要包含这些内容：

| 字段组 | 业务含义 |
|---|---|
| 数据周期与统一批次 | 说明这次等级用了哪段时间的数据，以及算法 01～算法 10 和城市区域映射共同使用的 `BATCH_YYYYMM` 批次 |
| 城市算法区域 | 说明这家门店和哪些城市/门店放在同一组里比较 |
| 门店与品类 | 说明是哪个门店、哪个大类/中类/小类 |
| 七个维度得分 | 经营规模、货盘宽度、商品效率、盈利能力、订购健康、促销健康、损耗健康 |
| 权重与综合分 | 说明七个维度分别占多少权重，以及最终综合分 |
| 暂定等级与最终等级 | 先按综合分分层，再经过经营底线修正后的等级 |
| 风险解释 | 连续亏损、损耗健康、数据缺失、促销依赖、订购异常等原因 |
| 置信度 | 说明这个等级的数据是否足够稳定 |

另外会保存参数候选和自动入选参数。任务状态、输入血缘和失败原因复用平台现有调度审计，不为算法 02 建独立运行发布表或参数发布审计表。业务不需要在页面上点击“批准”才能运行；直接连接数据库即可查看候选、入选依据和正式结果，平台任务记录用于查看运行状态。

不再单独建立“运行参数表”或“配置快照”。固定业务规则直接以算法卡和对应程序实现为准；各区域、品类、计量类型实际入选的售罄参数保存在售罄正式参数表。当前 V1 不计算严重损耗风险线，也不建立对应字段或参数表。历史批次重跑读取原城市区域映射快照和原正式售罄参数，不需要人工重新选参。

促销字段口径也会跟随本批次留痕：当前 V1 由系统自动写入 `promotion_discount_scope（促销折扣口径） = TOTAL_DISCOUNT_INCL_TIME（总折扣已包含时段折扣）`，意思是 `discount_amt（总折扣金额）`已经包含 `time_period_discount_amt（时段折扣金额）`。这不是运行前需要人工登记、选择或审批的事项。

算法 02 先把本次结果算到临时计算区，再自行检查源数据是否交齐、门店/区域/品类是否唯一关联、结果主键是否唯一、正式参数是否唯一、公式能否复算，以及应评级清单与临时结果是否双向一致。检查计数和失败明细写平台现有审计，不复制证据 JSON。不能用同一份已收到的可售记录自证没有漏店。

同区域同品类门店相互比较，漏一家也可能改变其他门店的等级。因此只要源交付、映射或结果完整性有一项不能证明，本次算法 02 整批都不发布，算法 03 也不启动；不能只拿剩余成功行继续算。

所有检查通过后，首次运行一次性把本批正式参数和正式结果提交到正式表；同批重跑继续使用原正式参数，只一次性替换正式结果。任一检查失败时，首次运行不产生正式结果；同批重跑不覆盖上一份成功结果。如果发布后发现旧结果不可靠，平台任务状态和依赖调度立即停止下游继续消费，补数后按 01→02→03 顺序重跑，不新增证据表。

开发可以在计算过程中建临时表或过程表，但后续 AI 新品机会算法稳定读取的只有 `mart_store_category_level（门店品类等级正式结果表）`。调度必须明确传入 `algorithm_batch_version（统一算法批次版本）`，并且只在同批算法 02 任务成功后启动算法 03，不能靠最新时间猜批次，也不要求算法 03 再做一遍算法 02 的全量验收。

## 3. 它在 AI 选品链路中的位置

整体链路是：

```text
基础数据表
-> 门店品类等级算法
-> mart_store_category_level
-> 门店群消费者画像贡献算法
-> 新品候选标准化与合并
-> 新品机会证据合成与风险门禁
-> 新品推荐优先级与开发需求编排
-> AI 新品推荐结果
```

这一步是离线定时计算，不需要大模型参与。

大模型后面只负责理解采购问题、查询结果、解释原因，不负责现场重新计算门店等级。

## 5. 数据周期怎么理解

正式等级每月更新一次。

每次正式计算只用最近 3 个数据完整自然月生成等级。

例如 2026 年 7 月运行：

```text
正式评估周期 = 2026-04-01 到 2026-06-30
统一算法批次版本 algorithm_batch_version = BATCH_202606
```

版本号只看数据结束月份，不看实际运行日期：

```text
algorithm_batch_version（统一算法批次版本）
= 'BATCH_' + calculation_end_date（计算结束日期）的 yyyyMM
```

因此算法 01～算法 10、城市算法区域映射快照和本批次正式参数都使用 `BATCH_202606`。如果到 8 月发现 4—6 月数据需要修正并重跑，版本仍是 `BATCH_202606`；只更新运行时间、运行ID和重跑原因。进入 7 月结束的新窗口时，才使用 `BATCH_202607`。

最近 6 个完整自然月不是再算一版等级。

6 个月数据只用来辅助：

```text
权重不稳定时回退
标准化参数不稳定时参考
订购健康区间训练
等级稳定性检查
```

最简单的理解：

```text
3 个月 = 本次正式打分用的数据
6 个月 = 帮算法判断参数稳不稳的历史参考
```

## 6. 比较范围怎么来

门店不能随便互相比。

算法只允许门店在同一个正式比较范围里比较：

```text
同一个城市算法区域
+ 同一个品类颗粒度
+ 同一个品类
```

城市算法区域的业务事实来自 `dim_city_algorithm_region（城市算法区域映射表）`，但每个新批次首次运行时，系统都会生成 `dim_algorithm_batch_city_region_snapshot（统一算法批次城市区域映射快照表）`。这份快照不是每个算法各建一张临时表，而是算法 01～算法 10 在同一 `algorithm_batch_version（统一算法批次版本）`下共同使用的范围事实。

当前已确定使用：

```text
dim_city_algorithm_region
```

表粒度：

```text
一行 = 一个城市 + 一个算法区域映射生效周期
```

关键字段：

| 字段名 | 示例 | 用途 |
|---|---|---|
| 城市 | 上海 / 杭州 / 宁波 / 苏州 | 和门店基础表的城市对齐 |
| 算法区域编码 | SH / HZ_NB_SX / SZ_CZ_WX | 算法比较范围编码 |
| 算法区域名称 | 上海 / 杭州宁波绍兴 / 苏州常州无锡 | 算法比较范围名称 |
| 生效开始日期 | 2026-07-01 | 判断某个数据周期使用哪版映射 |
| 生效结束日期 | 空 / 2026-12-31 | 支持历史追溯；结束日包含当天 |
| 是否当前有效 | 1 / 0 | 只说明现在是否有效，历史批次不用该字段回算 |
| 映射确认人 | 张三 | 追溯业务确认人 |
| 映射确认日期 | 2026-07-20 | 追溯业务确认时间 |
| 数据更新时间 | 2026-07-20 10:00:00 | 数据维护时间 |
| 备注 | 业务已确认 / 特殊说明 | 记录边界城市说明 |

运行时规则：

```text
新批次首次运行：按 calculation_end_date（计算结束日期）命中唯一有效映射，写入该 algorithm_batch_version 的完整快照。
同批次重跑：继续读取原 algorithm_batch_version 快照，即使源表后来删除或调整了区域。
区域口径变化：默认从下一个完整自然月的 algorithm_batch_version 生效，不重写历史批次。
```

`algorithm_batch_version（统一算法批次版本）`由数据结束月份生成，不由城市列表哈希生成。一个批次可以有多条城市映射明细，所以快照主键是 `algorithm_batch_version + city（城市）`；这里的 `city（城市）`用于区分同一批次里的多条明细，不代表每个城市有自己的版本。单城市区域标记为 `CITY（单城市范围）`，同一 `algorithm_region_code（算法区域编码）`包含两个及以上城市时标记为 `CITY_CLUSTER（城市群范围）`，`scope_id（范围编码）`始终取 `algorithm_region_code`，不直接取城市名称。

例如：

```text
SH -> 上海 -> CITY -> scope_id=SH
HZ_NB_SX -> 杭州、宁波、绍兴 -> CITY_CLUSTER -> scope_id=HZ_NB_SX
```

区域映射历史记录不能物理删除，只能结束旧生效周期并新增后续记录。业务不需要审批快照；系统完成唯一性和城市数量校验后自动发布，业务只查看快照和审计。

## 7. 品类颗粒度怎么处理

算法支持三个层级：

```text
大分类
中分类
小分类
```

每个层级都必须从底层数据重新聚合、重新评分、重新分层。

不能这样算：

```text
小分类等级平均 = 中分类等级
中分类等级平均 = 大分类等级
```

原因是不同品类层级的经营逻辑不同，门店排序可能完全不一样。

商品分类不增加单独快照、读取绑定或源数据版本字段。同一次全链路运行由调度系统锁定同一份 `dim_sku（商品基础表）`输入，平台现有任务血缘记录实际读取的表和分区。同批补数或商品数据修正时，01→02→03 按顺序全部重跑。历史批次无法从平台留存分区重新取得当时分类时，暂停历史重跑，不能拿今天的分类冒充历史结果。

## 8. 先过滤什么数据

正式计算前，要先过滤异常交易。

有效交易保留：

```text
门店编码不为空
商品编码不为空
业务日期不为空
正常完成交易
`order_status = os.completed`、`is_return = 0`、销售金额和销售标准量为正的有效交易
销售金额、销售数量或销售重量符合正向销售口径
商品能关联到正式品类
```

`refund_type（退款类型）`非空不能直接当成“这笔交易要删除”。V1 仍以“订单正常完成、非退货、金额和销售标准量为正”为准，退款类型只做质量检查。以后如果真实数据核实出必须剔除的退款枚举，要同时修改算法 01、02、03，并从下一个完整自然月批次开始使用；历史批次继续按当时锁定规则重跑。

会员相关指标只统计有效会员：

```text
会员编码不为空
会员编码不以 6 开头
会员小票按算法 01/02 共用的固定公共实现过滤：同一会员单日有效小票数超过 5 张时，剔除当天全部会员交易。测试、取消、冲销只有在数据合同明确对应状态字段和枚举后才能加入新规则，不能由开发自行猜测。
```

算法 02 不读取 `dim_customer_profile（会员画像结果表）`。算法 01、02 直接调用同一份会员过滤公共实现，并通过固定样例验证结果一致，不再建立独立注册表，也不把规则版本或实现摘要写入结果表。

如果会员过滤条件变化，必须同步修改算法 01、02 的算法卡、公共实现和固定验收样例，并从下一个完整自然月的 `algorithm_batch_version（统一算法批次版本）`生效。历史批次不因新规则自动改写，也不为同一个数据结束月份生成第二个结果版本。

有效营业日正式口径：

```text
门店当天处于营业状态
AND 该门店该品类至少有 1 个 SKU 可售
AND 当天交易、货盘、到货数据完整
```

因此，门店正常营业、该品类可售但当天销售为 0，也要计入有效营业日。否则只保留有销售的日期，会把日均销售、日均小票和动销率算得偏高。

营业状态直接使用已有历史数据，按门店和那一天关联，不用当前状态回填三个月，也不另建营业日表。

这里要区分“确实 0 销售”和“数据没到”：源交付和门店日期范围已经核对完整，但当天没有交易，才是 0 销售日。运行中发现缺数据日期时，相关日均指标的销售额、小票数和营业日数必须使用同一日期集，不能只减少分母；同时本批自行验收失败，不能把排除缺失日期后的过程结果正式发布。

正式结果会同时保留：潜在营业日数、数据不完整营业日数和有效营业日数，业务可以直接核对：

```text
可确定营业及可售日期全集时：有效营业日数 = 潜在营业日数 - 数据不完整营业日数
营业状态或可售记录自身缺失、全集未知时：三个计数为空，不伪装成 0
```

算法还会先生成“这次本来应该评级的门店品类清单”：先锁定本批城市范围，再从门店可售记录找出正式经营过的商品，最后按本批锁定的商品分类展开成大类、中类、小类。主键清楚但因为数据不足算不出等级的对象，也要输出一行 `NOT_CALCULABLE（不可计算）`；连门店、范围或品类主键都无法确定的源记录，进入质量问题记录，不能在关联时悄悄丢掉。

相似经营日使用既有接口名 `dim_date_calendar（日期日历表）`。它由调度用 SQL 日期序列和平台已有日历配置生成或装载，可以是 CTE、临时数据集或现有同名接口，不要求新增算法专用永久物理表；至少包含星期类型、月份、是否节假日和是否异常日期，也不是采购或业务手工输入。日历日期缺失时，系统不猜节假日，不生成相似经营日配对，只把窗口标记为不稳定。

有效在售 SKU 日一期口径：

```text
当天门店商品可订可售表显示可售
+ 当天门店有实际进货数量或进货重量
```

如果某个 SKU 日进货量小于等于 0：

```text
不计算该 SKU 日售罄率
不计入有效在售 SKU 日
不把它当作 0 销售
```

如果 19 点前销售量明显超过进货量：

```text
19点前销售量 / 实际进货量 > 110%
```

这个 SKU 日标记为异常，不进入订购健康训练，但原始销售仍可进入经营规模。

## 9. 七个维度分别看什么

门店品类等级由七个一级维度组成：

| 维度 | 看什么 | 直觉理解 |
|---|---|---|
| 经营规模 | 19 点前销售额、小票数、会员数 | 这个门店这个品类有没有基础消费盘 |
| 货盘宽度 | 有效在售 SKU、动销 SKU、SKU 动销率 | 这个门店能不能承接更多商品 |
| 商品效率 | 单 SKU 日均销售、单 SKU 日均毛利 | 每个 SKU 的产出高不高 |
| 盈利能力 | 全链路毛利额、门店毛利率 | 这个品类是不是真的赚钱 |
| 订购健康 | 19 点前售罄率是否在健康区间 | 到货量和销售消化是否匹配 |
| 促销健康 | 常规优惠依赖、时段折扣依赖、优惠后毛利 | 是否主要靠优惠或晚间折扣卖动 |
| 损耗健康 | 损耗成本率 | 损耗是否拖累经营 |

## 10. 经营规模怎么算

经营规模全部使用 19 点前数据，因为 19 点前更能代表自然消费能力。

核心指标：

```text
日均 19点前销售额 = 19点前销售额 / 有效营业日数
日均 19点前小票数 = 19点前小票数 / 有效营业日数
周期有效会员数 = 19点前去重有效会员数
```

销售额和小票数包含会员与非会员。

会员数只统计有效会员。

为了让业务和开发能看清“门店销售里会员贡献了多少”，结果表还会保留 5 个解释字段：

```text
valid_member_ticket_cnt（19点前有效会员小票数）
daily_valid_member_ticket_cnt（日均19点前有效会员小票数）
valid_member_sales_amt（19点前有效会员销售额）
valid_member_sales_ratio（19点前会员销售额占比）
valid_member_ticket_ratio（19点前会员小票占比）
```

其中：

```text
日均19点前有效会员小票数
= 19点前有效会员小票数 / 有效营业日数

19点前会员销售额占比
= 19点前有效会员销售额 / 19点前销售额

19点前会员小票占比
= 19点前有效会员小票数 / 19点前全部小票数
```

这 5 个字段只用于解释和验收，不会再次进入经营规模得分，因此不会把会员贡献重复计算。输入完整但没有有效会员交易时，小票数和销售额记为 0；对应总销售额或总小票数为 0 时，占比写空，不能除以 0；会员必要字段缺失时也写空并记录降级原因，不能把数据缺失解释成“没有会员”。如果会员小票数或会员销售额反而大于同范围全部小票数或销售额，说明分子、分母范围没有对齐，占比写空并报质量问题，不能强行截断成 100%。

这三个指标先各自转成 0-100 分，再用 CRITIC 算出经营规模内部权重，得到：

```text
scale_score
```

## 11. 货盘宽度怎么算

货盘宽度看门店是否有承接更多 SKU 的能力。

核心指标：

```text
有效在售 SKU 天数
19点前动销 SKU 天数
日均在售 SKU 数
日均19点前动销 SKU 数
19点前 SKU 动销率
```

计算方式：

```text
日均在售 SKU 数 = 有效在售 SKU 天数 / 有效营业日数
日均19点前动销 SKU 数 = 19点前动销 SKU 天数 / 有效营业日数
19点前 SKU 动销率 = 19点前动销 SKU 天数 / 有效在售 SKU 天数
```

这些指标转成 0-100 分后，用 CRITIC 得到：

```text
assortment_width_score
```

## 12. 商品效率怎么算

商品效率看的是每个有效 SKU 日的产出。

核心指标：

```text
单 SKU 日均销售产出 = 19点前有效销售额 / 有效在售 SKU 天数
单 SKU 日均毛利产出 = 全日全链路毛利额 / 有效在售 SKU 天数
```

销售品效越高越好。

毛利品效也越高越好，但它可能为负。负毛利不能填 0，因为负数本身就是经营风险。

最终得分：

```text
sku_efficiency_score =
SQRT(销售品效得分 * 毛利品效得分)
```

## 13. 盈利能力怎么算

盈利能力看这个门店这个品类是否真正赚钱。

核心指标：

```text
日均全链路毛利额 = 全日全链路毛利额 / 有效营业日数
门店毛利率 = 全日门店毛利额 / 毛利损耗表全日销售额
```

两个指标转成 0-100 分后：

```text
profitability_score =
SQRT(全链路毛利额得分 * 门店毛利率得分)
```

净经营贡献用于订购健康、连续亏损和损耗风险：

```text
净经营贡献 = 全链路毛利额 - 损耗金额
```

根据数据指标平台口径，全链路毛利额本质是：

```text
全链路收入项 - 全链路成本项
```

其中成本项里已经包含：

```text
供应链损耗额（不含税）
```

但当前公式里没有看到“门店损耗金额”被扣除。

所以一期先按以下口径配置：

```text
全链路毛利额已经扣供应链损耗
净经营贡献 = 全链路毛利额 - 门店损耗金额
```

正式结果字段 `gross_profit_includes_store_loss_flag（全链路毛利是否含门店损耗）`随 `algorithm_batch_version（统一算法批次版本）`保存当前固定口径。V1 为 `0（未包含）`，所以扣一次门店损耗；不再为这个固定值单建参数表。未来正式字段口径改变时，从新的完整自然月批次切换公式，不能由开发在同一批次临时判断或覆盖。

## 14. 订购健康怎么算

订购健康看的是：

```text
门店进了多少货，19 点前能消化多少。
```

第一步，分计量类型计算售罄率。

计件商品：

```text
19点前售罄率 = 19点前销售数量 / 门店进货数量
```

称重商品：

```text
19点前售罄率 = 19点前销售重量 / 进货重量
```

如果需要从 Doris 小票明细补算 19 点前销售数量或销售重量，统一按有效交易、`inc_time < 19:00:00` 汇总 `weight`。`weight` 是商品行计价数量，算法里映射为销售标准量：称重商品表示计价重量，计件商品表示件数/份数/袋数/只数。Doris 本身没有单位字段，具体单位由商品基础表决定。

公斤和件数不能直接相加，也不能用到货金额去加权原始售罄率。

第二步，训练健康区间。

健康区间不是业务手工写死的 80%-100%，而是用历史 SKU 日样本训练出来。

训练范围：

```text
城市算法区域 + 品类颗粒度 + 品类 + 计量类型
```

算法会看历史上不同售罄率区间下的经营结果：

```text
净经营贡献是否较好
损耗是否健康
继续增加到货后，净经营贡献是否还明显增加
```

业务文档给出的核心判断是：

```text
如果售罄率很高，而且增加到货仍能带来正向净贡献，说明可能订购不足。
如果售罄率很低，而且增加到货导致损耗升高、净贡献下降，说明可能订购偏多。
中间那段更稳定、更赚钱的区间，就是健康区间。
```

当前 V1 的损耗成本率统一使用毛利损耗表已经交付的 `sale_cost_amt（销售成本金额）`计算，不读取缺失的含税到店金额。已确认 `sale_cost_amt（销售成本金额） = receipt_amt（门店进货金额） - loss_amt（门店损耗金额）`；有库存时进货成本会被平均。

业务原文没有给出“较优”“明显增加”的单一数值，因此 V1 把候选生成、排序和并列决胜写成固定系统规则：系统生成所有连续候选区间和 P90/P95/P99 容忍距离，先过滤样本不足、有效配对少于 30、边际净贡献变异系数大于 1.00 或跨期稳定性低于 0.75 的候选，再按验证期净经营贡献、损耗成本率、等级稳定性、阈值稳定性和样本数排序；完全相同按区间下限、区间上限、P90/P95/P99 顺序决胜。没有下一月验证数据时使用训练期指标并标记 `TRAINING_ONLY（仅用训练期数据）`。这些是算法卡的固定执行规则，不是业务页面临时选择，也不重复写入配置快照。

`cross_period_stability（跨期稳定性）`不是去找前四个已经发布的历史批次，而是在本批最近六个完整自然月内部切出四个三个月窗口。例如 `BATCH_202608（2026 年 8 月统一算法批次）`使用 2026 年 3 月至 8 月数据时，四个窗口分别是“3—5 月、4—6 月、5—7 月、6—8 月”。每条候选都在四个窗口内重新评级；四次中出现最多的等级数量次数除以 4，就是跨期稳定性。若等级数量依次为 `3、3、3、2`，跨期稳定性就是 `3/4=0.75`，刚好通过门槛。

因此首个正式批次只要具备六个完整自然月，就可以正常计算，不需要等待四个历史批次。如果当前不足六个完整自然月，该候选按 `UNSTABLE（不稳定）`处理，不发布正式参数；源数据漏交则直接阻断整批，不能伪装成普通不稳定。

相似经营日窗口也必须按“先候选、后入选”执行：系统在每个“城市算法区域 + 品类 + 计量类型”组内，先用 `season_match_window_days（候选季节匹配窗口天数） = 30 / 60 / 90` 分别训练和回测，候选表保留每个窗口的样本数、稳定性和经营结果；完成质量门和排序后，再把该组唯一入选候选标记为 `AUTO_PUBLISHED（系统自动发布）`。入选窗口直接保存在该组选中的售罄参数记录里，不写成全批次唯一窗口，因为不同区域、品类、计件和称重可能入选不同窗口。不得先确定窗口，再只训练一个候选。

配对前，系统会在“日期 + 门店 + 商品”粒度，用毛利损耗表当天的 `discount_amt（总折扣金额）`和 `time_period_discount_amt（时段折扣金额）`把经营日分成三类：

```text
时段折扣金额 > 0：时段折扣日
否则总折扣金额 > 0：常规优惠日
两者都等于 0：无优惠日
```

如果一天既有时段折扣又有其他优惠，按时段折扣优先归为“时段折扣日”。金额为空、为负或时段折扣大于总折扣时，当天状态无法判断，不参与相似经营日配对。系统只比较促销状态相同的两天；排除异常日后没有合格窗口，订购健康得分留空并使用其他可用维度重算。

这项日级判断不读取 Doris 商品行的 `is_hour_promotion（是否命中时段促销）`，也不新增日级促销状态表。商品行标记仍只用于后面的促销健康分析，两个场景互不替代。

系统自动把唯一入选行写成 `AUTO_PUBLISHED`，业务不需要点击批准。所有候选、入选依据和状态变化都写入数据库，业务直接查询即可。没有合格候选时，订购健康得分留空并用其他可用维度重算；不能由开发临时挑选。

如果同一品类同时包含计件和称重商品，系统会分别读取两条入选参数，并在结果中分别保存计件参数记录 ID 和称重参数记录 ID。两种计量类型都适用时，缺少任意一套正式参数，订购健康得分都写空，不能拿计件参数替代称重参数，也不能反过来替代。

为了让开发和业务可以复算，正式结果还会保留计件、称重各自的销售量、进货量、售罄率、有效到货 SKU 天数、分类型健康度，以及健康 SKU 日数和总有效到货 SKU 日数。这样 `order_health_score（订购健康得分）`不是一个无法解释的黑盒分数。

第三步，计算订购健康分。

```text
售罄率落在健康区间内：健康度高
售罄率低于健康区间：可能进货偏多或动销不足
售罄率高于健康区间：可能进货偏少，有缺货风险
```

最终：

```text
order_health_score =
SQRT(综合售罄健康度 * 健康区间命中率得分)
```

## 15. 促销健康怎么算

促销健康仍然是算法里的一个正式维度。

但一期它的含义是：

```text
门店这个品类是否依赖常规优惠或时段折扣。
```

它不是在判断：

```text
某一次促销活动到底有没有带来真实增量。
```

### 15.1 一期用哪些字段

一期优先使用毛利损耗表里的日门店商品汇总字段。

| 计算内容 | 来源表 | 字段或公式 |
|---|---|---|
| 实际销售额 | 毛利损耗表 | 销售额 |
| 全日标准销售额 | 毛利损耗表 | 原价销售额 |
| 总优惠金额 | 毛利损耗表 | `mart_sku_margin_loss.discount_amt`；当前 V1 已包含时段折扣 |
| 时段折扣金额 | 毛利损耗表 | `mart_sku_margin_loss.time_period_discount_amt`；不使用 Doris `hour_discount_amt` 代替 |
| 常规优惠金额 | 毛利损耗表 | 当前 V1 为 `MAX(discount_amt - time_period_discount_amt, 0)` |
| 相似经营日促销状态 | 毛利损耗表 | 日级过程判断：时段折扣金额大于 0 为时段折扣日；否则总折扣金额大于 0 为常规优惠日；两者为 0 为无优惠日；异常值不参与配对 |
| 19点前标准销售额 | 毛利损耗表或 Doris 小票商品明细表 | 当前 V1 在 `TOTAL_DISCOUNT_INCL_TIME` 下按 `SUM(usual_amt + discount_amt)` 代理；条件为 `inc_time < 19:00:00` |
| 19点前常规优惠金额 | Doris 小票商品明细表 | 代理为 `SUM(discount_amt)`，条件为 `inc_time < 19:00:00 AND is_hour_promotion = 0`；不能把日粒度时段折扣额下推到商品行相减 |
| 19点前常规优惠商品标准销售额 | Doris 小票商品明细表 | 代理为 `SUM(usual_amt + discount_amt)`，条件为 `inc_time < 19:00:00 AND discount_amt > 0 AND is_hour_promotion = 0` |

Doris 小票字段中文含义：

| Doris 字段 | 中文含义 | 本算法怎么用 |
|---|---|---|
| `usual_amt` | 商品行实付金额 | 补算 19 点前实际销售额、19 点前标准销售额 |
| `discount_amt` | 商品行总优惠金额，当前 V1 已包含时段折扣 | 补算 19 点前标准销售额和优惠代理 |
| `is_hour_promotion` | 是否命中时段促销配置/ETL 规则，1 是、0 否 | 只识别促销健康计算中的商品行时段促销交易；不等于简单判断 19 点后，也不聚合为相似经营日状态 |
| `hour_discount_amt` | 会员当天同小时累计优惠金额 | 不直接按商品行求和 |
| `inc_time` | 交易发生时间 | 判断是否 19 点前 |

为什么不直接用 Doris 的 `hour_discount_amt` 求和：

```text
它是会员当天同小时累计优惠金额，
不是这一个商品行自己的时段折扣金额。
直接按商品行 SUM，可能重复累计。
```

所以一期时段折扣金额以毛利损耗表的“时段折扣额”为准。

当前 V1 的字段关系固定为：

```text
先在“日期 + 门店 + 商品”唯一粒度计算：
discount_amt = 总折扣金额（包含时段折扣）
time_period_discount_amt = 总折扣中满足时段促销的部分
常规优惠金额 = MAX(discount_amt - time_period_discount_amt, 0)

再把各日门店商品的金额汇总到门店品类结果，不能先汇总总折扣和时段折扣后再相减。
```

`hour_discount_amt` 是会员、日期、同小时累计优惠，不是单个商品行的时段折扣，不能按商品行相加。`is_hour_promotion = 1` 是商品行时段促销规则标记，只用于促销健康代理，不能替代日粒度时段折扣金额，也不能聚合成相似经营日的日级促销状态。

还要注意：上面的 `常规优惠金额 = 总折扣 - 时段折扣`只适用于毛利损耗表的全日日粒度金额。当前没有商品行级 `time_period_discount_amt（时段折扣金额）`，所以不能把这个全日金额拿到每张小票商品行上相减。19 点前常规优惠固定使用 `is_hour_promotion=0（未命中时段促销）`的商品行作为代理；命中时段促销的商品行整体不进入常规优惠代理，避免同一折扣重复计算。这是一期代理口径，不代表精确促销活动归因。

以下组合只用于数据质量对账，不能用来猜字段含义；对账前要先把来源汇总到同一个比较粒度，不能把 Doris 商品行和毛利损耗表日行逐条比较：

```text
discount_amt = 0
discount_amt = hour_discount_amt
discount_amt > 0 且 hour_discount_amt = 0
discount_amt > 0 且 hour_discount_amt > 0
```

毛利损耗表的“日期 + 门店 + 商品”主键重复时，本批结果不能正式发布，不能只把促销健康写空后继续。如果主键唯一，但总折扣、时段折扣或 `is_hour_promotion（是否命中时段促销）`缺失，折扣金额为负，或时段折扣大于总折扣，促销健康分写空并标记 `promotion_confidence=DATA_INSUFFICIENT（促销健康数据不足）`。

相似经营日与促销健康分别执行自己的异常处理：在相似经营日链路中，日级总折扣或时段折扣无法判断时，排除该门店商品日的配对；如果有效配对因此不足，订购健康维度按窗口不稳定处理。在促销健康链路中，日级折扣金额或 Doris 商品行 `is_hour_promotion（是否命中时段促销）`缺失、异常时，仍按上面的既有规则把促销健康分写空。如果只是商品行标记缺失，其他六个维度可以继续，且不会改变日级促销状态；如果日级折扣金额本身缺失或异常，则订购健康也必须执行相似日配对的降级，不能笼统声称其他六个维度全部不受影响。

### 15.2 一期计算哪些指标

常规优惠依赖：

```text
19点前常规优惠金额率 =
19点前常规优惠金额 / 19点前标准销售额
```

```text
19点前常规优惠销售占比 =
19点前有常规优惠的标准销售额 / 19点前标准销售额
```

时段折扣依赖：

```text
全日时段折扣金额率 =
时段折扣金额 / 全日标准销售额
```

```text
全日时段折扣销售占比 =
发生时段折扣的标准销售额 / 全日标准销售额
```

优惠后毛利质量：

```text
优惠商品毛利率 =
有优惠或时段折扣商品的全链路毛利额
/ 有优惠或时段折扣商品的实际销售额
```

如果没有任何优惠发生：

```text
优惠商品毛利率字段写 NULL，另用 promotion_margin_status = NOT_APPLICABLE 表示不适用
优惠依赖类指标按 0 依赖参与评分
```

如果有优惠商品但优惠商品实际销售额为 0 或毛利字段缺失：

```text
优惠商品毛利率字段写 NULL
promotion_margin_status = NOT_CALCULABLE
```

### 15.3 促销健康分怎么合成

常规优惠依赖和时段折扣依赖越低越好。

优惠商品毛利率越高越好。

```text
常规优惠非依赖得分 =
SQRT(常规优惠金额率得分 * 常规优惠销售占比得分)
```

```text
时段折扣非依赖得分 =
SQRT(时段折扣金额率得分 * 时段折扣销售占比得分)
```

```text
promotion_health_score =
GEOMEAN_AVAILABLE(
  常规优惠非依赖得分,
  时段折扣非依赖得分,
  优惠后毛利质量得分
)
```

`GEOMEAN_AVAILABLE` 的意思是：

```text
只用能算出来的分项合成。
不能算的分项不填 0。
```

## 16. 损耗健康怎么算

损耗健康看的是：

```text
损耗是否拖累这个门店品类的经营贡献。
```

正式评分使用：

```text
损耗成本率
= 全日损耗成本金额
  /（全日销售成本金额 + 全日损耗成本金额）
```

其中 `sale_cost_amt（销售成本金额）`直接来自毛利损耗表，是 `receipt_amt（门店进货金额）`减去 `loss_amt（门店损耗金额）`后的金额；有库存时进货成本会被平均。系统不会在算法 02 中按销售额、数量或门店日总成本自行分摊，也不在算法内重新反推该字段。

```text
销售成本为空、销售成本金额为负、损耗金额为负，
或销售成本金额 + 损耗金额 <= 0：
损耗成本率和损耗健康得分留空，不补 0。
```

合法的 `loss_cost_rate（损耗成本率）`只能在 0～1 之间。系统先汇总销售成本金额和损耗金额并完成上述校验，再使用不会触发 Doris `DECIMAL（定点小数）`中间精度溢出的安全除法，结果四舍五入到 6 位后仍写入 `DECIMAL(10,6)`。如果结果越界，就留空并标记损耗成本异常；不能取绝对值、不能强行截断成 0 或 1，也不能为了让任务通过而放宽正式字段类型。

这项修复只让既有公式能够稳定实现，不改变“损耗金额 /（销售成本金额 + 损耗金额）”的业务含义。如果安全计算路径仍发生聚合溢出或最终类型转换失败，本批次验收失败，修复实现或源数据后重跑，不能带错发布。

当前 V1 不读取含税到店字段，正式损耗健康只使用已经交付的销售成本金额和损耗金额。`outbound_arrival_amt_tax_included（出库到店金额含税）`只与未来可能恢复的严重损耗风险线有关，不属于当前 V1 的输入或输出，也不会被补造。

损耗金额已确认不是零售价口径，而是成本口径，可以用于损耗健康计算。

损耗成本率越低，损耗健康分越高。

```text
loss_health_score = 100 * [1 - Phi(robust_z)]
```

## 17. 标准化是什么意思

七个维度里的指标单位不一样，不能直接相加。

例如：

```text
销售额是元
小票数是笔
会员数是人
损耗率是百分比
```

所以算法要先把每个指标转成 0-100 分。

正向指标：

```text
越高越好
例如销售额、会员数、SKU 数、毛利额
```

负向指标：

```text
越低越好
例如损耗成本率、常规优惠依赖率、时段折扣依赖率
```

业务文档使用的是稳健标准化：

```text
对数或带符号对数
+ 中位数 / MAD
+ 转成 0-100 分
```

它的作用是降低极端门店对整体评分的影响。

## 18. CRITIC 动态权重是什么意思

CRITIC 是一种自动算权重的方法。

它不是大模型，也不是训练一个神经网络。

它会看两个问题：

```text
这个维度在门店之间差异大不大？
这个维度和其他维度是不是重复？
```

差异越大、和其他维度重复越少，权重越高。

差异很小、或者和其他维度高度重复，权重越低。

七个一级维度会得到七个权重：

```text
W1 经营规模权重
W2 货盘宽度权重
W3 商品效率权重
W4 盈利能力权重
W5 订购健康权重
W6 促销健康权重
W7 损耗健康权重
```

综合分：

```text
category_score =
经营规模得分 * W1
+ 货盘宽度得分 * W2
+ 商品效率得分 * W3
+ 盈利能力得分 * W4
+ 订购健康得分 * W5
+ 促销健康得分 * W6
+ 损耗健康得分 * W7
```

如果某个维度不能计算：

```text
不填 0
只用剩余可用维度重新分配权重
```

当前组门店太少、相关性不稳定时，系统依次使用同范围同品类最近 6 个历史批次的正式等级结果重新估计，再尝试读取上一历史批次正式结果中已经保存的权重；仍不可用才改为等权并降低置信度。历史结果直接读 `mart_store_category_level（门店品类等级正式结果表）`，不再为 CRITIC 新建权重表或矩阵表。

## 19. 等级怎么生成

先得到每个门店品类的综合分。

然后在同一个比较组内做分层：

```text
同一个城市算法区域
+ 同一个品类颗粒度
+ 同一个品类
```

业务文档使用：

```text
Jenks 自然断点 + BIC
```

它的意思是：

```text
先看这些门店的分数天然分成几段最合理；
再判断分 1 档、2 档、3 档还是 4 档更稳定。
```

所以结果不一定永远是 A/B/C/D 四档。

可能是：

| 分层数量 | 输出等级 |
|---|---|
| 1 档 | 全部 B |
| 2 档 | A / B |
| 3 档 | A / B / C |
| 4 档 | A / B / C / D |

如果分层不稳定，就自动降档。

稳定性检查包括：

```text
重复抽样 500 次
每次抽取 80% 有效门店
同一等级数量出现比例 >= 80%
单门店等级一致率 >= 75%
最近 4 个滚动窗口中至少 3 次等级数量一致
```

这里有两个不同的稳定性指标，不能写成同一个值：

- `cross_period_stability（跨期稳定性）`看四个时间窗口是否经常选择相同的等级数量；
- `threshold_stability_score（阈值稳定性得分）`看重复抽取 80% 门店并重新分层后，等级断点的位置是否仍接近完整样本断点。

阈值稳定性固定重复抽样 500 次；抽样后等级数量不同，该次阈值相似度记 0；等级数量相同时，按断点平均偏差占完整样本分数区间的比例换算为 0—1 分，再取 500 次平均。只有一个等级时没有断点，阈值稳定性固定为 1。完整公式以开发版算法卡第 12 节为准，开发不能直接把跨期稳定性复制给阈值稳定性。

计件和称重候选分开自动选参时，每条候选先只用自己的计量类型试算稳定性，避免尚未入选的另一类参数反过来影响本候选排序。两类参数都入选后，正式等级再按混合计量规则统一计算，并重新得到评分组唯一的正式阈值稳定性；不能随便拿计件或称重其中一条候选得分写入正式结果。

## 20. 经营底线怎么处理

综合分高，不代表一定能保留高等级。

算法还有经营底线。

### 20.1 连续亏损

如果最近 3 个完整自然月，每个月净经营贡献都小于 0：

```text
最终等级最高只能到 B
```

系统还会输出 `profitability_evaluable_month_cnt（盈利上限可评价月份数）`。只有营业、品类可售、毛利和损耗数据都完整，并且月度净经营贡献能够唯一计算的月份才计数。

如果因为新店、新品类、整月停业或整月不可售等正常业务原因，最近三个月不足三个可评价月份：

```text
continuous_loss_3m_flag（连续3个月亏损标记）= NULL
cumulative_loss_3m_flag（3个月累计亏损标记）= NULL
不应用盈利等级上限
degraded_reason（降级原因）增加 INSUFFICIENT_PROFITABILITY_HISTORY（盈利判断历史不足）
```

这里的空值表示“证据不足、无法判断”，不能写成 0。若少月份是因为源数据漏交、关联冲突或主键重复，则不是正常降级，算法02整批不得发布。

### 20.2 严重损耗

当前 V1 只计算损耗健康，不计算严重损耗风险线。销售成本金额只能用于当前损耗健康，不能冒充 `outbound_arrival_amt_tax_included（出库到店金额含税）`训练未来风险线。

因此当前 V1：

```text
不生成严重损耗风险线候选
不建立严重损耗结果字段或参数表
不应用严重损耗等级上限
继续输出损耗健康分
```

连续亏损最高 B、数据质量上限和其他正式规则继续生效。未来只有在含税到店金额按正式合同交付并通过真实数据验收后，才能先修改算法卡、程序和验收样例，再从下一个完整自然月批次恢复该能力；不能改写历史结果，也不能在同一批次切换口径。

### 20.3 数据质量

如果核心维度缺失过多：

```text
不生成正式等级
进入数据修复清单
```

如果只是个别维度缺失：

```text
继续计算
降低置信度
限制最高等级
```

## 21. 开发实际要怎么做

数据开发拿到开发版算法卡后，实际工作不是只写一条 SQL。

开发过程可以拆成：

```text
1. 建立输入表字段映射，锁定统一批次、城市范围和本批商品分类
2. 从门店可售记录生成应评级门店品类清单，并记录无法形成正式主键的源记录
3. 过滤有效交易和异常数据；退款类型非空不直接删单
4. 按历史日期关联营业状态，核对源交付、门店/区域/品类映射；缺数据不补 0，日均分子分母使用同一组日期
5. 读取毛利损耗表已有的商品日销售成本，校验没有把门店日总成本重复关联到多个商品
6. 聚合到 日期 + 门店 + 商品，再聚合到 数据周期 + 算法区域 + 门店 + 品类
7. 先生成全部季节窗口和订购健康候选及评估指标，再由系统自动排序并发布唯一售罄参数；当前 V1 不生成严重损耗候选
8. 按区域 + 品类 + 计量类型读取各自唯一 `AUTO_PUBLISHED（系统自动发布）`售罄参数；入选窗口保存在对应参数记录中，不写全批次唯一窗口；没有合格参数时按缺失状态降级
9. 做标准化并计算 CRITIC 权重
10. 计算综合分并做 Jenks/BIC 动态分层
11. 应用连续亏损、数据质量等当前有效等级上限；当前 V1 不应用严重损耗上限
12. 先把参数候选和结果写到临时计算区，自行检查源交付、映射、唯一键、参数、状态和公式复算
13. 对应评级清单和临时结果做双向核对，同时核查无法映射品类的可售/交易源记录
14. 全部检查通过后，首次运行按统一算法批次一次性提交正式参数和 `mart_store_category_level（门店品类等级正式结果表）`；同批重跑复用原参数，只替换正式结果；任一检查失败时不改正式表
15. 平台将算法 02 任务标记成功后才启动同批算法 03
```

采购前端和下游算法只读取调度指定 `algorithm_batch_version（统一算法批次版本）`下的已发布结果，不在查询时重新训练参数或计算等级。业务查看数据库即可，不存在“确认后才能跑”的页面闸门。

## 22. 业务验收看什么

验收时不要只看 A/B/C/D。

要分三层看。

第一层：数据是否对。

```text
门店数是否正确
品类映射是否正确
应评级门店品类清单是否与 SUCCESS / NOT_CALCULABLE 结果逐一对应
无法映射品类的可售和交易源记录是否全部进入质量问题记录，而不是静默丢失
日期全集已知时，潜在日数 = 不完整日数 + 有效日数；全集未知时三个计数为空；检查缺数据未补 0，日均分子分母同日期
19 点前口径是否正确
19 点前有效会员小票数、销售额及两个占比是否可由正式结果字段复算
这 5 个会员解释字段是否确认未重复进入经营规模得分
有效在售 SKU 天是否正确
计件和称重售罄率能否分别由销售量 / 进货量复算，且各自关联正确的参数记录
混合品类是否同时具备计件、称重两套适用参数，订购健康得分是否可逐级复算
门店毛利率及促销依赖比率的分子、分母是否都能从正式结果复算
进货、毛利、折扣、时段折扣、损耗是否能对上经营报表
```

第二层：指标是否合理。

```text
A 级门店是否通常销售、动销、毛利、订购和损耗更健康
高销售但低毛利、高损耗门店是否被过度高估
售罄过高是否能被解释为订购不足风险
高优惠依赖门店是否被识别出来
```

第三层：等级是否稳定。

```text
同一品类的等级数量是否合理
门店等级是否频繁跳动
业务熟悉的强门店是否大体在高等级
业务熟悉的问题门店是否被识别出风险
等级变化是否能由经营变化、统一算法批次锁定的区域映射和正式参数解释
```

## 23. 现在还需要验收什么

这里只保留开发交付时必须验收的事实，不再把业务点击批准作为算法运行条件。

| 验收项 | 验收对象 | 为什么重要 |
|---|---|---|
| 自动参数候选是否按固定排序和并列规则落表 | 数据开发 | 验收候选、唯一 `AUTO_PUBLISHED（系统自动发布）`行和选择原因是否完整；业务只查看不点击 |
| 首批次四窗口跨期稳定性 | 数据开发 | 验收当前六个月是否切成四个三个月滚动窗口；首批次不得因为没有历史已发布批次而把稳定性写成 0/0，也不得跳过 0.75 门槛 |
| 阈值稳定性独立计算 | 数据开发 | 验收 500 次重复抽样的断点波动是否单独计算；`threshold_stability_score（阈值稳定性得分）`不得复制 `cross_period_stability（跨期稳定性）` |
| 盈利上限可评价月份 | 数据开发 | 验收不足三个可评价月份时两个亏损标记写空并记录 `INSUFFICIENT_PROFITABILITY_HISTORY（盈利判断历史不足）`；源漏交必须阻断，不能降级放行 |
| 统一批次与城市映射是否锁定 | 数据开发 | 验收算法 01～算法 10、城市映射快照和正式参数是否使用同一个 `algorithm_batch_version（统一算法批次版本）`；同批次重跑是否复用原快照 |
| 会员过滤是否与算法 01 对齐 | 数据开发 | 验收同一 `algorithm_batch_version（统一算法批次版本）`内算法 01、02 是否调用同一公共实现、固定样例结果是否一致、过滤条件调整是否只从下一批次生效，且算法 02 不读取画像表 |
| 有效交易是否与算法 01、03 对齐 | 数据开发 | 验收 `refund_type（退款类型）`非空没有被直接删单；未来新增已核实枚举时必须三张算法卡同步、下一完整月批次生效，历史批次规则不变 |
| 自行验收与原子发布 | 数据开发 | 验收源交付、门店/区域/品类关联、唯一键、参数、公式和清单结果双向核对；任一检查失败时整批不发布且算法 03 不启动，全部通过后才一次性提交正式参数和结果 |
| 有效营业日数据完整性 | 数据开发 | 验收已有历史营业状态按日关联，以及交易/货盘/到货交付完整性；日均分子分母同时排除缺失日，完整的零销售日仍计入 |
| 经营规模会员解释字段 | 数据开发 | 验收 5 个字段是否按 19 点前有效会员口径落入正式结果、分子分母是否可复算、空分母是否写空，并确认这些字段不进入 `scale_score（经营规模得分）` |
| 季节窗口选参时序 | 数据开发 | 验收每个区域 + 品类 + 计量类型是否先生成 30/60/90 天全部候选，再自动发布该组唯一参数；计件、称重不得共用全批次唯一窗口 |
| 相似经营日促销状态 | 数据开发 | 验收日级状态是否只使用毛利损耗表的总折扣和时段折扣；0/0、常规优惠、时段折扣、混合优惠和异常金额是否得到唯一结果；异常日排除后各窗口有效配对数是否正确 |
| 正式指标可复算性 | 数据开发 | 验收售罄率、门店毛利率、促销依赖比率和订购健康得分的分子、分母、分类型参数记录及中间得分是否完整落表 |
| 销售成本损耗口径 | 数据开发 | 验收 `sale_cost_amt（销售成本金额）`按日期 + 门店 + 销售商品唯一交付，满足 `sale_cost_amt = receipt_amt - loss_amt`，没有把门店日总成本重复关联到多个商品；销售成本和损耗均非负，损耗成本率可复算且在 0～1 |
| 损耗成本率数值安全 | 数据开发 | 验收先聚合和校验、再用安全中间类型除法、最后写入 `DECIMAL(10,6)`；负值、非正分母和越界结果不得补 0、截断或放宽字段类型，安全路径仍溢出时整批不发布 |
| 严重损耗能力边界 | 数据开发 | 验收当前 V1 只输出损耗健康，没有用销售成本冒充含税到店金额，也没有生成严重损耗结果字段、参数表或对应等级上限 |
| 促销折扣固定口径 | 数据开发 | 验收 V1 是否由系统自动写入 `promotion_discount_scope（促销折扣口径） = TOTAL_DISCOUNT_INCL_TIME（总折扣已包含时段折扣）`，且没有人工登记或审批环节 |
| 全链路毛利口径交付验收 | 数据开发 / 财务口径负责人 | 当前批次参数按“未扣门店损耗”执行；验收正式字段与指标平台公式一致，防止重复扣减 |
| 优惠商品毛利率 V1 是否按日门店商品近似口径验收 | 数据开发 | 毛利损耗表已定义到营业日期 + 门店 + 销售商品编码；如果没有商品行级毛利，V1 按日门店商品近似，并在结果中标记口径 |

## 24. 不要做什么

```text
不要把门店品类等级理解成门店整体等级
不要跨未配置的城市算法区域比较
不要平均下一级品类等级得到上一级等级
不要把缺失值填 0
不要把公斤和件数直接合并成一个原始售罄率
不要把售罄率静默截断为 100%
不要把商品行 `is_hour_promotion（是否命中时段促销）`聚合成相似经营日状态，也不要为此新增日级状态表
不要固定强行切成 A/B/C/D
不要让高销售完全抵消连续亏损或已经计算出的损耗健康异常
不要把促销健康解释成促销效果归因
不要用门店日销售成本重复填充每个商品，也不要在算法 02 中按销售额或数量自行分摊销售成本
不要用销售成本金额冒充含税到店金额训练严重损耗风险线
不要为算法 02 单独生成模型版本、范围版本、参数版本或重跑版本
不要先填写最终季节匹配窗口，再只训练该一个候选；也不要把不同区域、品类、计量类型的入选窗口压成全批次一个值
不要把 V1 促销折扣口径写成多选项、人工登记项或审批项
```

## 25. 一句话总结

门店品类等级算法的本质是：

```text
用同一城市算法区域、同一品类下的经营数据，
判断每个门店对这个品类的真实承载能力，
并把销售、货盘、品效、盈利、订购、优惠依赖和损耗综合成可追溯的等级。
```
