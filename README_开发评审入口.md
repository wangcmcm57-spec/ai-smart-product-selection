# AI 选品 V1 开发评审入口

本文是数据开发、后端开发、Agent 开发和产品侧进入 AI 选品 V1 开发评审的唯一入口。

评审不逐页朗读算法卡，而是确认：

```text
谁要建什么表
谁要写什么任务
谁要提供什么 API
哪些口径会阻塞 V1
哪些内容只是预审，不进入本次开发
```

## 0. 先看这 5 句话

1. AI 选品 V1 是给采购做新品开发推荐，不是给门店做订货，也不是做毛利分析或购物篮提升产品。
2. 系统先用 Doris 内部交易经营数据和外部竞品数据，离线计算出稳定、可追溯的新品机会证据。
3. 数据开发本次真正要开工的是基础数据表、公共有效交易过滤逻辑、算法 01～03 结果表。
4. 后端 API 后续读取推荐结果表和证据表，不在采购提问时实时重算算法。
5. Agent Harness 负责把采购问题转成结构化参数、选择工具、轻量重排；大模型只解释结构化结果。

一句话描述：

```text
AI 选品 V1 = 离线把新品机会算成表，在线让采购通过页面或 Agent 查询“哪些新品方向值得做、为什么、价格和风险是什么”。
```

## 1. 本次评审到底评什么

本次评审的目标不是评完整 AI Agent 产品，也不是评完所有算法。

本次要让开发可以启动第一批数据和算法建设：

| 类型 | 范围 | 本次结论要回答什么 |
|---|---|---|
| P0 | 基础数据表 | Doris 小票、门店、商品、城市算法区域、毛利损耗、日价格、可订可售、外部竞品是否能按合同产出 |
| P0 | 公共过滤逻辑 | 有效交易、退款退货、负金额、负重量、字段关联和版本血缘怎么统一 |
| P0 | 算法 01 会员画像 | 是否能产出 `dim_customer_profile` 及解释、参数、汇总表 |
| P0 | 算法 02 门店品类等级 | 是否能产出 `mart_store_category_level` 及参数、解释表 |
| P0 | 算法 03 门店群消费者画像贡献 | 是否能基于 01、02 产出 `mart_store_group_consumer_contribution` |
| P1 | 算法 04～06 | 先读链路和依赖，下一轮再评实现细节 |
| 后续评审 | 算法 07～09 | 已整理为开发版算法卡，后续评审，不进入本次第一批开发细节评审 |
| 待确认 | 算法 10 | 当前待确认，只保留为算法 09 下游链路说明，不作为本次开发交付物 |
| 预审 | 后端 API / Agent Harness | 先确认边界和疑问，不要求本次进入完整开发 |

## 2. 各角色本次要准备什么

| 角色 | 本次要做 | 本次不用做 |
|---|---|---|
| 数据开发 | 确认基础表字段、主键、粒度、关联字段、调度周期；评估算法 01～03 是否能按卡落地 | 不需要实现算法 07～09 后续链路；算法 10 当前待确认；不需要设计前端交互 |
| 后端开发 | 预审后续 API 边界：推荐查询、证据查询、反馈写入、请求日志 | 不需要在本次实时实现机会推荐 API |
| Agent / Harness 开发 | 预审意图识别、参数抽取、工具路由、轻量重排、大模型禁止边界 | 不需要让大模型直接读 Doris 或实时算算法 |
| 前端开发 | 先理解后续页面或 Agent 入口会读什么结果 | 不进入本次页面开发评审 |
| 产品 / 项目侧 | 确认评审范围、字段缺口、业务口径和会后行动项 | 不在会上临时新增算法规则 |

## 5. 会前准备清单

数据开发会前需要准备：

1. 基础数据表是否能按 `02_data_contracts/` 产出。
2. 每张基础表的实际来源表、字段映射、主键粒度和调度周期。
3. 小票有效交易过滤口径是否可落地。
4. 算法 01～03 结果表是否能按开发版算法卡建表。
5. 当前阻塞字段、口径、样本周期和数据质量问题。

后端 / Agent 开发会前需要准备：

1. 后续推荐查询 API、证据查询 API、反馈写入 API 的疑问。
2. `mart_opportunity_recommendation` 作为主查询入口是否合理。
3. Agent Harness 参数抽取、工具路由、轻量重排的边界疑问。
4. 大模型解释层的禁止规则和日志记录疑问。

产品 / 项目侧会前需要准备：

1. 本次评审只让基础数据和算法 01～03 开工的边界。
2. 业务口径确认人，例如毛利、损耗、区域、城市算法区域、会员画像规则。
3. 会后任务拆分、负责人和验收节奏。

## 6. 90 分钟评审方式

| 时间 | 内容 | 目标 |
|---|---|---|
| 0～10 分钟 | V1 目标和本次边界 | 确认第一批先做基础数据和算法 01～03 |
| 10～20 分钟 | Agent 运行边界预审 | 确认离线计算、后端 API、Harness、大模型解释和反馈边界 |
| 20～35 分钟 | 基础数据表 | 确认基础表粒度、主键、字段来源、调度周期和公共过滤口径 |
| 35～55 分钟 | 算法 01 | 确认会员画像输入、输出、版本和验收 |
| 55～72 分钟 | 算法 02 | 确认门店品类等级输入、输出、权重、分层和验收 |
| 72～85 分钟 | 算法 03 | 确认 01/02 依赖、贡献口径、输出表和验收 |
| 85～90 分钟 | 会后行动项 | 明确谁建表、谁写调度、谁对字段、谁补口径 |

评审会上不要做：

```text
不逐页朗读业务解读版。
不让开发从业务原始文档自己猜实现口径。
不把算法 07～09 后续评审内容或待确认的算法 10 当成本次可开发范围。
不在评审会上临时新增算法规则。
不讨论完整前端产品形态。
```

## 7. 会后输出物

| 输出物 | 负责人 | 用途 |
|---|---|---|

| 公共有效交易过滤方案 | 数据开发 | 统一后续算法输入口径 |
| 算法 01～03 开发任务清单 | 数据开发 | 排期、建表、调度和试跑拆解 |
| 字段口径确认清单 | 数据开发 / 业务 / 财务口径负责人 | 解决阻塞字段 |
| 结果表建表计划 | 数据开发 | 确认表名、主键、分区、版本字段 |
| 后端 API / Agent Harness 预审问题 | 后端 / Agent 开发 | 标注接口、工具调用、轻量重排、日志反馈的待确认点 |

| 后续 04～06 评审计划 | 产品 / 数据开发 | 进入下一轮开发评审 |

## 9. 后续维护规则

本文只维护“开发评审怎么进入、当前评审范围是什么、各角色要准备什么”。不要把算法公式、字段明细、业务原文或接口细节继续堆进本文。

后续每次算法卡或项目状态变化时，只更新下面几类内容：

| 变化场景 | 本文需要更新什么 | 细节应该放哪里 |
|---|---|---|
| 算法 07～09 整理完成，或算法 10 状态变化 | 第 1 节评审范围、第 3 节阅读顺序、第 4 节算法链路、第 8 节 Prompt | `03_algorithm_cards/developer_version/`、`00_project_management/development_review/` |
| `mart_opportunity_recommendation` 推荐表定稿 | 第 1 节本次评审范围、第 2 节后端 / Agent 准备项、第 7 节会后输出物 | 后续推荐表合同文档 |
| 后端 API 清单定稿 | 第 2 节角色边界、第 5 节会前准备、第 8.2 节 Prompt | 后续 API / 工具合同文档 |
| Agent Harness 规则定稿 | 第 0 节核心描述、第 2 节角色边界、第 8.2 节 Prompt | 后续 Agent 运行规则文档 |
| 评审阶段变化 | 第 1 节 P0/P1/更新中状态、第 6 节会议安排、第 7 节会后输出物 | `00_project_management/development_review/AI选品V1_当前开发链路.md` |

算法卡全部整理完成后，本文应从“第一批 01～03 开发评审入口”升级为“完整 V1 开发评审入口”。建议改成：

```text
算法 01～10 已整理为开发版算法卡。
第一阶段：基础数据、公共过滤、算法 01～03。
第二阶段：算法 04～06。
第三阶段：算法 07～09。
第四阶段：算法 10 待确认通过后进入推荐结果编排评审。
第五阶段：后端 API、Agent Harness、反馈表和产品入口。
```

维护边界：

```text

02_data_contracts/：只放基础表和外部表字段合同。
```
